## 리뷰 라운드 1

### 종합 판정: **조건부 통과 — Critical 2건 해소 후 저술 가능**

이 계획은 이 하네스에서 본 계획 중 상위권이다. 레퍼런스 대조 밀도가 높고(장마다 "레퍼런스 한계" 차단선을 직접 붙였다), 오프닝 변주 규율을 표로 자체 검증했으며, 설계 근거의 기각 대안 3건이 모두 실질적이다. **아래 Critical 2건은 계획을 뒤엎는 종류가 아니라 빠진 블록을 채우는 종류다** — 항목 목록의 길이를 전면 재작업 요구로 오해하지 말 것.

Critical 2건(러닝 예제 명세 부재 / SDK 축 노후 방치)은 **저술 착수 전 반드시** 해소해야 한다. 둘 다 Phase 4 이후의 어떤 루프로도 복구되지 않는 종류의 결함이다.

## Critical

### C-1. 세 언어가 "같은 서버"를 만든다고 약속하는데, 그 서버의 명세가 계획에 없다

**근거(계획 내부 모순):**
- 3장: "tool·resource·prompt를 각각 하나씩 갖춘 최소 서버 완성", 오프닝은 "사내 위키를 클로드가 직접 읽게 해달라"
- 5장: "**3장의 TypeScript 서버와 같은 기능을** Python으로 이식하며 두 SDK의 설계 차이를 대조"
- 6장: "**3장·5장 서버와 같은 기능을** Spring Boot로 완성"

그런데 계획 어디에도 그 서버가 **무엇인지**가 없다. 도구 이름도, 파라미터도, 리소스 URI도, 패키지 이름도 정해져 있지 않다.

**왜 Critical인가:** Phase 4에서 챕터 저술가가 **병렬로** 돌아간다. 3·5·6장 저술가는 각자 "사내 위키 서버"를 상상해서 만든다 — 도구 이름이 `search_wiki` / `wiki_search` / `searchDocument`로 갈리고, 파라미터 스키마가 다르고, 리소스 URI 형태가 다른 세 개의 "같은 서버"가 나온다. 이건 style-guardian도 fact-checker도 잡지 못한다(문체 문제도 사실 오류도 아니다). 편집자가 Phase 4에서 세 장의 코드를 직접 다시 쓰는 것 말고 복구 경로가 없다. 그리고 이 계획이 5·6장에 부여한 유일한 존재 이유("같은 것을 다른 언어로 만들며 SDK 설계 차이를 대조")가 통째로 무너진다.

**파급 범위가 언어 3장보다 넓다** — 다음 장들도 같은 식별자를 쓴다:
- 4장: `claude mcp add`·`codex mcp add` 실행 예시에 서버 이름과 실행 커맨드가 들어간다
- 7장: 도구 개수·네임스페이스·description 규칙의 before/after 예시 (→ M-1 참조)
- 9장: `package.json`의 `bin` 키, npm 패키지 이름, `mcpName` 역DNS 값

**수정 제안:** `02_plan.md`에 **"러닝 예제 명세"** 섹션을 신설하고(챕터 목록 앞), 3·4·5·6·7·9장의 "주요 내용"에 "러닝 예제 명세 §를 따른다" 한 줄을 박는다. 최소한 아래를 확정할 것:

| 항목 | 확정 필요 값(예시 — 계획이 정하면 됨) |
|---|---|
| 서버 이름 / npm 패키지 | `team-wiki` / `@example/mcp-team-wiki` |
| `bin` 키 (= npx 커맨드) | `team-wiki` |
| 도구 1 | `wiki_search(query: string, limit?: number)` — 문서 검색 |
| 도구 2 | `wiki_get(path: string)` — 문서 본문 반환 |
| 리소스 | `wiki://{path}` 템플릿 1개 |
| 프롬프트 | `summarize_page(path)` 1개 |
| 오류 케이스 | 존재하지 않는 `path` → **Tool Execution Error**(3장의 SEP-1303 논지가 이 케이스로 시연된다) |

특히 **오류 케이스를 명세에 넣는 것**이 중요하다. 3장이 SEP-1303("입력 검증 오류는 Protocol Error가 아니라 Tool Execution Error")을 설명하는데, 시연할 구체 케이스가 고정돼 있지 않으면 세 언어 장에서 서로 다른 방식으로 얼버무린다.

또한 6장의 Spring AI `@McpTool` 예제는 레퍼런스 §3-4의 `add(a, b)` 계산기 코드를 그대로 인용할 수 있는데, **그건 러닝 예제가 아니다** — 인용은 인용대로 쓰되 6장의 완성 서버는 러닝 예제여야 한다는 걸 계획에 명시할 것.

### C-2. "노후는 11장에 갇힌다"는 설계 근거가 SDK 축에서는 성립하지 않는다 — 3·5장이 이틀 뒤 낡는다

**근거(계획 내부 모순):** 설계 근거 #2는 *"RC 재료를 흩뿌리면 정식화되는 순간 네 개 장이 동시에 낡는다. 11장에 몰아두면 노후는 한 장에 갇힌다"*라고 주장한다. 이 주장은 **스펙 리비전 축에만** 참이다.

계획 자신이 저술 제약 #1에서 선언한 네 축 중 **축 2(SDK semver)는 11장 격리로 전혀 보호되지 않는다.** 그리고 레퍼런스 §7-D는 이렇게 경고한다:

> "TS SDK 2.0.0 정식·Python `mcp` 2.0.0 정식도 **며칠 내** 나올 수 있다 (TS README: *stable release alongside the full release of the 2026-07-28 spec on July 28, 2026*)"

즉 **2026-07-28 — 오늘로부터 이틀 뒤**다. 그런데:
- **3장**은 *"`1.29.0`이 **프로덕션 권장**이다"*를 장의 첫 결정으로 세우고, v2를 *"beta"*로 서술한다
- **5장**은 *"현재 안정판 `1.28.1`"* / *"`2.0.0b2` 프리릴리스"*를 전제로 서 있고, 오프닝 자체가 2.0b2 wheel 실측이다
- **9장**은 `validateHostHeader`(v2 실측 API)를 권한다

TS 2.0.0이 GA되는 순간 3장의 핵심 권고 문장이 틀린 책이 되고, 5장은 "프리릴리스"라는 프레이밍 전체가 어긋난다. **저술 제약 #2는 스펙 축에만 상비 규칙을 줬고, SDK 축에는 아무 규칙이 없다.**

**수정 제안 (2단):**

**(a) 상비 표현 규칙을 저술 제약에 6번으로 추가:**
> **SDK 상태 서술은 "권고"가 아니라 "시점 관측"으로 쓴다.** ❌ "1.29.0을 써라" → ✅ "2026-07-26 시점에 TS SDK의 dist-tag는 `latest: 1.29.0` 하나뿐이었고, README는 v1.x를 프로덕션 지원 라인으로 명시했다. v2 정식이 나왔다면 6개월 지원 약속이 여기서부터 계산된다." 이렇게 쓰면 GA가 나도 **문장이 틀리지 않는다.**

**(b) 재확인 체크리스트를 3·5·9·11장 네 곳에 바인딩** (현재는 11장에만 있다):

| 확인 대상 | 확인 방법 | 구속 장 |
|---|---|---|
| `@modelcontextprotocol/sdk` dist-tags | `npm view … dist-tags` | 3, 9 |
| PyPI `mcp` `info.version` | PyPI JSON API | 5, 9 |
| `schema/` 디렉토리에 `2026-07-28/` 유무 | GitHub 저장소 열거 | 2, 11 |
| Releases의 `prerelease` 플래그 | GitHub Releases API | 1, 11 |

fact-checker가 이 표를 판정 기준으로 쓸 수 있게 계획에 표로 넣을 것.

**(c) 부수 정정:** 위 규칙이 서면 1장의 *"2026년 상반기 생태계 **전체**가 메이저 2.0으로 넘어갔다"*도 손봐야 한다. 이 문장은 3장의 "v1이 프로덕션 권장"과 **정면으로 충돌한다** — 독자가 1장을 읽고 3장에서 "그런데 2.0 쓰지 말라고?"가 된다. "Java·Spring AI는 GA로, TS·Python은 베타로 넘어갔다 — 같은 2.0인데 성숙도가 다르다"로 분리할 것. (레퍼런스가 이 표현을 쓰긴 하지만, 레퍼런스는 바로 아래 표에서 성숙도를 쪼갠다.) 부수적으로 **1장의 "레퍼런스 한계: 없음"도 정확하지 않다** — 이 문장은 검증된 사실이 아니라 요약 표현이다.

## Major

### M-1. 7장이 문헌 리뷰로 읽힐 위험이 가장 크다 — 규칙으로 착지시킬 예시가 없다

**근거(독자 적합성):** 7장의 "주요 내용" 7개 불릿이 **전부 수치·논문 인용으로 시작**한다(19% / 93.1% vs 87.1% / 7,500토큰 / 3% 미만 / 8종 중 3종). "독자가 얻는 것"은 *"근거 있는 설계 규칙"*이라고 적혀 있는데, 그 규칙이 독자의 코드에 어떻게 닿는지 보여주는 자리가 계획에 없다. 대상 독자는 "직접 만들어 쓰려는" 개발자이고, 이 장은 세 언어 구현을 다 본 직후에 온다 — 지금 형태면 "여기까지 코드를 따라왔는데 갑자기 논문 요약"이 된다.

**수정 제안:** 러닝 예제(C-1)를 재료로 한 **before/after 절 하나를 7장에 명시적으로 배정**한다. 예: "위키 API의 오퍼레이션 12개를 그대로 노출한 버전 → 의미 단위로 묶어 4개로 줄인 버전"을 도구 목록으로 나란히 놓고, 이름 네임스페이스(`wiki_*`)와 description 길이 규율을 그 목록 위에서 적용한다. 수치는 그 결정의 **근거로 뒤에 붙인다**(순서 반전). 분량은 기존 5,000자 안에서 흡수 가능하다 — 불릿 7개를 5개로 줄이고 남은 자리를 예시에 쓰면 된다.

### M-2. 8장과 9장이 예산 안에 물리적으로 안 들어간다 — 재배치 목표 하나를 정해야 한다

두 장의 문제는 성질이 다르지만 **해법이 서로를 침범**하므로 하나로 묶어 판단해야 한다.

**(가) 8장 — 밀도 초과, 그리고 사용자 필수 토픽의 단독 담당**
8장 6개 소절의 개별 사실을 세면 — 침묵 카탈로그 5건, `✓ Connected` 1건, stdout 함정(증상 3 + 원인 4 + 해결 + stderr 64MB 누수) 약 5건, 도구함·노브(Inspector + 구조적 한계 + JSONL 로그 + `--debug` 3줄 + `--safe-mode` + `--strict-mcp-config` + 타임아웃 노브 5행) 약 12건, 관찰성 6건, CVE·툴체인 보안 4건. **합계 약 25~30개 사실을 6,000자에 넣어야 한다 — 사실당 200~240자다.** 프로필이 요구하는 수사적 질문 2~3회·공감 표현 2~3회·상황 서술 오버헤드를 빼면 사실당 실질 150자 남짓이고, 이 밀도는 산문이 아니라 불릿 나열로 귀결된다.

여기에 커버리지 문제가 겹친다. 계획의 커버리지 대조표는 사용자 요구 토픽 4(구현·디버깅·모니터링/관찰성)를 **"7, 8"**로 매핑했는데 **7장에는 디버깅도 모니터링도 없다** — 도구 설계와 보안이다. 즉 **가장 과적재된 장이 사용자 필수 토픽의 단독 담당**이고, 압축분이 곧 사용자 요구 미충족이 된다.

**(나) 9장 — 예산이 "보강 실패 상태"에 맞춰져 있다**
9장 5,500자가 담을 클러스터는 7개다 — ① `package.json` 해부 4항목 + shebang 통념 정정 ② `npm publish` + `--access public` ③ PyPI/uvx ④ Docker ⑤ 원격 Streamable HTTP(세션·Origin 403·DNS rebinding) ⑥ OAuth 진화 3항목 + 실제 실패 4건 ⑦ 레지스트리 6항목. **클러스터당 780자**이고, 사용자가 "npx 배포 **상세**"를 명시 요구한 토픽에 800자가 배정된다.

**그리고 반박하기 어려운 지점:** 지금 병렬로 도는 보강 리서치 3건(uvx 커맨드 · Dockerfile 패턴 · `mcp-publisher` 시퀀스)이 성공하면 9장은 **더 커진다.** 현재 5,500자는 9장의 의도된 상태가 아니라 **격하된 상태의 예산**이다 — 보강이 성공할수록 계획이 틀리는 구조다.

**두 장의 차이가 해법을 가른다.** 8장의 과적재는 **고정돼 있고 압축 가능하다**(사실 목록이 확정됐고 표로 흡수된다). 9장의 과적재는 **증가 중이고 압축하면 사용자 약속을 깬다**. 따라서:

**권고 구조 — 9장을 둘로 쪼개 12장 구성. 8장은 6,000자 유지하되 감량 항목을 계획이 지명한다.**

| 장 | 내용 | 분량 |
|---|---|---|
| 8 | **침묵과 진단** — 침묵 카탈로그 · `✓ Connected` 거짓말 · stdout 함정 · 도구함과 노브 · 관찰성(OTel) | 5,500 |
| 9 | **남에게 주기 — 패키징과 배포** — npm/npx 상세 · PyPI/uvx · Docker · 레지스트리 | 5,500 |
| 10 | **원격으로 열기, 그리고 도구를 의심하기** — Streamable HTTP 세션 · Origin/DNS rebinding · OAuth 진화와 실패 4건 · 툴체인 보안(CVE-2025-49596 · 시크릿 유출 · `.mcp.json` 자기승인 · 셸 인젝션) | 5,000 |
| 11 | 방향을 뒤집다 (기존 10장) | 4,500 |
| 12 | 2026-07-28과 그 이후 (기존 11장) | 5,000 |

총 본문 약 61,500자. 이 배치의 이점 세 가지: ① 8장에서 툴체인 보안 소절(4건)이 빠져 소절 6→5개, 밀도가 실측 가능한 범위로 내려온다 ② 새 10장이 "서버를 밖에 열면 무엇이 공격면이 되는가"로 한 논지에 선다 — 기각 대안 3이 보안을 7/8/9 세 갈래로 쪼갠 것이 **7/10 두 갈래**(설계 보안 / 운영·툴체인 보안)로 정리돼 오히려 깔끔해진다 ③ 9장이 보강 리서치 결과를 받을 여유를 갖는다.

**기각 권고 — 8장을 쪼개고 9장을 유지하는 안:** 관찰성을 독립 장으로 세우면 8장 밀도는 풀리지만, 9장의 **증가하는** 과적재는 그대로 남고 사용자 요구 토픽 6이 계속 눌린다. 압축 가능한 쪽을 쪼개고 압축 불가능한 쪽을 놔두는 선택이라 방향이 반대다.

**구조를 바꾸지 않겠다면** — 저자 재량으로 11장을 유지하는 것도 존중한다. 다만 그 경우 **계획이 8·9장에서 무엇을 빼는지 직접 지명**해야 한다(감량 후보: 타임아웃 노브 5행을 표로만, `/usage` 비용 분해와 tool-pool 7배를 각 1문장, OAuth 실패 4건을 2건으로). **"저술가가 알아서 압축"은 선택지가 아니다** — 그러면 무엇이 빠질지 계획이 통제하지 못한다.

### M-3. 9장이 v2 베타 전용 API를 권하는데 3장은 v1을 쓰라고 한다

**근거(레퍼런스 대조 + 내부 모순):** 9장 원격 배포 항목: *"SDK 2.0의 `validateHostHeader`/`validateOriginHeader`로 DNS rebinding 방어"*. 레퍼런스 §3-1에서 이 두 심볼은 **v2 패키지 실측 목록에만** 등장한다 — 1.29.0에 존재한다는 근거가 레퍼런스에 없다. 그런데 3장은 같은 책에서 *"v1.x가 프로덕션 권장"*이라고 결정한다. 독자가 3장 결정대로 v1으로 만들고 9장(권고 구조에서는 10장)에 오면 **존재하지 않는 API를 찾게 된다.**

**수정 제안:** 해당 장에 한 줄 못 박기 — "이 두 헬퍼는 2.0 계열에서 확인된 API다(2.0.0-beta.5/2026-07-21 기준). 1.x로 만들었다면 Host·Origin 검증은 트랜스포트 앞단에서 직접 해야 한다." 1.x에 동등 API가 있는지는 레퍼런스가 답하지 못하므로 **단정 금지 항목으로 "레퍼런스 한계"에 추가**할 것.

### M-4. 8장 논지에 가장 정확히 맞는 사례 두 개가 어느 장에도 배정되지 않았다

**(가) claude-code #80996 — 레퍼런스 §3-7 함정 6번**
> *"our agents' **only inbound-message path is an MCP server**, so a session that resumes with the MCP down is **functionally deaf while looking alive from the outside**."* `/mcp`가 **대화형 전용**이라 자동 복구 경로가 없다. 우회책의 대가는 *"~15 min penalty per event"*.

계획 10장의 "문서화된 함정 6가지"를 레퍼런스와 대조하면 ①=#1 ②=#2 ③=#3 ④=#4 ⑤=#5 ⑥=**#7(함대 행)**이다. **#6이 통째로 빠졌다.** 8장의 침묵 카탈로그에도 없다. 이건 단순 누락이 아니라 **8장의 주제문("고통은 에러가 아니라 침묵")을 가장 정확히 예시하는 인용을 놓친 것**이다 — "밖에서 보면 살아 있는데 기능적으로 귀머거리"는 8장 오프닝으로도 쓸 만한 문장이다.

**(나) 레퍼런스 §5-3 함정 9번 — 토큰이 맞는데 401**
설정값 앞뒤의 **보이지 않는 공백** 때문에 인증이 실패한다(v2.1.219가 경고를 추가한 이유). 어느 장에도 없다. 원인이 문자 그대로 눈에 보이지 않는 실패이므로 8장 논지의 정중앙이다.

**수정 제안:** 둘 다 8장 소절 2(`✓ Connected`는 거짓말을 한다) 또는 소절 1(침묵의 카탈로그)에 배정한다. #80996은 10장 함정 ⑤(헤드리스 무신호)와 이어지므로 10장에서는 8장 참조로 처리하고 경계 표에 한 행 추가할 것.

### m-1. 오프닝은 11장 전부 배정했는데 클로징은 한 장도 배정하지 않았다

### m-2. `### 이 장의 핵심` 박스 사용 여부가 미결
프로필상 선택이지만 **"쓰기로 했다면 책 전체에서 형식을 통일"**이 조건이다. 계획이 정하지 않으면 저술가마다 갈린다. 권고: 개념 밀도가 높은 **1·2·7·8장에만** 두고 나머지는 두지 않는다 — 계획에 명시.

### m-4. 컨텍스트 비용 논쟁이 1장과 7장 양쪽에서 나올 위험 — 경계 표에 없다

### m-5. 보안이 여러 장에 흩어지는데 독자를 위한 실 꿰기가 없다
기각 대안 3의 논리(보안을 떼면 "나중에 읽을 장"이 된다)에는 동의한다. 다만 그 대가로 독자는 보안을 조각으로 만난다. 최소 조치: **7장 클로징에서 나머지 조각의 위치를 명시**하고, 마지막 장의 닫는 매듭 또는 후미 부속물에 **보안 체크리스트 한 장**을 모은다. 편집자(Phase 4)가 알 수 있게 계획에 적을 것. (M-2 권고 구조를 채택하면 보안이 7/10 두 갈래로 줄어 이 문제도 완화된다.)

### m-6. 버전 귀속 하나가 섞여 있다 (팩트체크 선제 정리)

### m-7. 10장의 3,600초를 일반 규범처럼 쓰면 자기모순이다
계획: *"기본 타임아웃 3,600초 vs 일반 도구 60초~5분 — 두 자릿수 배 차이"*. 레퍼런스 §3-7 함정 2는 `CLAUDE_CLI_TIMEOUT_SECONDS` 기본 3600초를 **출처 리포를 특정하지 않고** 기술한다(같은 절의 함정 1은 steipete와 agent-intern을 명시 인용하지만 함정 2는 어느 쪽도 인용하지 않는다). 10장은 "대표 구현이 아카이브됐다"를 논지로 삼는 장이므로, **이 값이 어느 구현의 기본값인지 확인되지 않은 채 업계 규범처럼 쓰이면 장의 논지와 충돌한다.** 저술 전 출처 리포를 특정하고, 특정되지 않으면 "일부 래퍼 구현의 기본값이 3,600초였다" 수준으로 낮출 것.

### m-8. 7장의 반대 증거를 반만 인용하고 있다
계획: *"도구 3,251개 환경에선 고정 목록이 총 커버리지에서 앞선다"*. 레퍼런스 §4-2는 여기에 단서를 붙인다 — 고정 5개가 총 커버리지는 높지만(64.7% vs 61.9%) **어려운 질의에서는 아무것도 못 찾는다.** 반대 증거를 소개하는 대목에서 그 반대 증거의 한계를 자르면 균형이 오히려 깨진다. 단서까지 함께 배정할 것.

## Nice-to-have

- **N-1. 쪽수 추정의 근거 확인.** "본문 57,000자 + 부속물 62,000자 = **200쪽 안팎**"이 무엇을 포함한 계산인지 계획에 드러나지 않는다. 산문 밀도만으로 환산하면(쪽당 600~900자) 70~105쪽이지만, 이 책은 코드 블록·표·mermaid 그림이 많고 그것들은 글자수 대비 쪽수를 크게 늘린다. **코드·표·그림을 추정에 포함했다면 200쪽이 성립할 수 있다.** 근거를 계획에 한 줄 남기거나, 불확실하면 쪽수를 빼는 편이 낫다 — 이 숫자는 `book_manifest.json`과 책 소개 markdown으로 전파된다.
- **N-2. 머리말 독자 경로 안내를 "빠른 경로"까지 확장.** 계획은 머리말에 Java 독자용 경로(3장은 읽어야 한다)를 안내한다고 적었다. 코드를 만나기까지 1·2장 10,500자를 지나야 하는 구조이므로, **"당장 만들어보고 싶으면 3장 → 4장 → 1장 순서로 읽어라"**는 대안 경로를 같은 자리에 넣으면 진입 마찰이 크게 준다. (1·2장을 앞에 두는 결정 자체는 설계 근거 #3이 잘 방어했으므로 배치는 유지 권고.)
- **N-3. 인용 상한 규율을 8·10장에도.** 1장에만 "인용 4명 상한"을 걸었는데, 8·10장도 원문 인용이 밀집한다(README 경고문·이슈 원문·CHANGELOG). 장당 원문 인용 상한을 두면 "인용 모음집" 인상을 막을 수 있다.

## 오케스트레이터 질의에 대한 답 — 조건부 처리(보강 실패 시 개념 서술로 격하)는 적절한가

**판정: 방향은 옳다. 다만 세 가지가 미규정이라 지금 상태로는 저술가에게 위임할 수 없다.**

계획이 "명령어를 지어내지 않는다"를 차단선으로 세운 것 자체는 정확한 판단이다(이 책의 브랜드가 정직성이므로 더욱). 보완할 점:

1. **"개념 서술"의 허용 범위가 정의되지 않았다.** 저술가에게 "개념으로 써라"만 주면 검증 안 된 내용을 산문으로 채울 유인이 생긴다 — 코드 블록만 없을 뿐 사실 주장은 그대로다. 규정 필요: **(가)** 레퍼런스에 `[검증]`/`[웹]`으로 있는 사실만 쓴다, **(나)** 커맨드·플래그·파일 경로는 일절 쓰지 않는다, **(다)** 공식 문서 URL로 독자를 넘긴다, **(라)** *"이 책은 X를 1차 소스로 확인하지 못했다"*를 본문에 명시한다. (라)를 넣는 것이 이 책에서는 오히려 신뢰 자산이다.
2. **격하 시 분량 재배분 계획이 없다.** 9장은 클러스터 3개가 개념으로 줄면 1,000~1,500자가 빈다. 대체 재료를 미리 지정할 것 — 예: npm/npx 심화(스코프 패키지·`files` 함정·설치 검증 절차)로 흡수. 5장도 마찬가지(2.0 예제 미확보 시 → 1.x→2.0 마이그레이션 전략과 `<2` 상한 실무로 대체).
3. **격하 결정의 파급 지점 목록이 없다.** Desktop 케이스만 "제목에서 뺀다"를 적었다. 실제 파급은 최소 네 곳이다 — **장 제목 / 사용자 요구 토픽 커버리지 표 / 머리말의 약속 / 최종 책 소개 markdown**. 격하가 확정되면 이 네 곳을 함께 고치도록 계획에 적어둘 것.

**추가로, 보강 5건의 우선순위가 평평하게 제시돼 있다.** 오케스트레이터가 예산을 배분할 수 있게 등급을 붙일 것:
- **필수(실패 = 사용자 약속 위반):** ①uvx/uv run ②Dockerfile ③`mcp-publisher`/`server.json` — 사용자가 토픽 6에서 명시 요구
- **선택(없어도 장이 성립):** ④Python 2.0 `MCPServer` 예제 — 5장은 "구조는 실측됐다 + 1.x 코드가 안 돈다 + `<2` 상한"만으로도 논지가 완결된다

**Desktop(보강 5번)에 대해서는 계획의 처리안을 바꿀 것을 권한다.** 보강 실패 시 "제목에서 Desktop을 뺀다"는 처리는 **반대 방향의 불일치**를 만든다 — 4장 본문에는 이미 레퍼런스로 검증된 Desktop 고유 동작 3건(DCR `client_name` 403 / 심링크 설정 파일 덮어쓰기 / `.mcpb` 도구 편측 노출)이 배정돼 있고, `add-from-claude-desktop`이라는 검증된 진입점도 있다. **내용은 있는데 제목에서 빼면 독자가 찾지 못한다.** 대신 제목을 정직하게 조정할 것: *"클라이언트에 붙이기 — Claude Code·Agent SDK·Codex, 그리고 Desktop이 다른 점"*. 그리고 커버리지 표의 토픽 3 항목에 "Desktop은 **등록 절차가 아니라 동작 차이** 중심으로 다룬다"를 명기해 약속 범위를 좁힌다.

**리뷰어가 요구한 3건은 모두 무의미해졌다 — 보강 리서치가 5건 전부를 해소했기 때문이다.** 그에 따라:

### 반영판 자체 점검에서 추가 보정한 3건 (리뷰 항목 외)

9장도 보강으로 크게 불어났다 — Docker 패턴(공식 서버 7개 전수, 하위 항목 5+4개)·레지스트리 게시 6단계(+소유권 마커의 패키지별 차이 + 인증 4종 + `server.json` 필수 필드)·`uvx`/`uv run` 구분·`.mcpb` 빌드(4장에서 **유입**)가 모두 새로 들어왔다. 그런데 예산은 5,500 → **6,000자, +500자뿐**이고 6,000은 프로필 상한이라 더 올릴 수도 없다. 감량 목록도 없다.

라운드 1에서 지적한 "9장 예산이 격하 상태 기준"이 **보강 성공 후 재발**한 형태다. 다만 이번엔 계획 수정 없이 Phase 4 지시로 처리 가능하므로 **비차단**으로 분류한다. 권고 감량 목록:

1. **Docker Python 템플릿은 Dockerfile 1개 + 주석 5줄로 갈음**(멀티스테이지·`UV_COMPILE_BYTECODE`·레이어 캐싱·`--locked`·`ENTRYPOINT`를 산문으로 다시 풀지 않는다)

3. **레지스트리 인증 4종은 한 줄 열거**, 본문 서술은 `github` device flow 하나만
4. **Docker 카탈로그 245개·서명은 한 문장**
5. **`.mcpb` 빌드는 커맨드 4단계 + "2차 배포 경로" 한 문장** — 4장이 이미 예고했으므로 배경 재설명 금지

### 5. 계획의 자체 점검 3건에 대한 평가
