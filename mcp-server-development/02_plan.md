## 제목 후보

1. **MCP 서버 개발 실전 — TypeScript·Python·Java로 만들고 Claude Code에 붙이기**
   - **톤:** 실무 매뉴얼. 담백하고 구체적이다.
   - **포지셔닝:** 대상 독자("직접 만들어 쓰려는 개발자")가 서점·검색에서 자기 책이라고 즉시 알아본다. 세 언어와 대표 클라이언트를 제목에 박아 기대치를 정확히 설정한다. 국내에 없는 조합(3언어 + 연결 + 디버깅 + 배포)을 제목이 그대로 광고한다.

2. **"MCP 2.0"은 없다 — 스펙 혼동부터 배포까지, MCP 서버 만들기**
   - **톤:** 도발적 정정. 1장의 문제의식을 그대로 표지에 올린다.
   - **포지셔닝:** 기억에 남고 차별화가 가장 강하다. **다만 위험이 있다** — Java SDK 2.0.0과 Spring AI 2.0.0은 GA이자 프로덕션 권장 선택지다. 독자가 "SDK 2.0을 쓰지 말라는 책"으로 오독할 여지가 실재한다. 부제·마케팅 문구로는 훌륭하지만 정식 제목으로는 부담이 있다.

3. **침묵하는 프로토콜 — 에러가 아니라 침묵으로 실패하는 MCP를 다루는 법**
   - **톤:** 에세이형 기술서. 문제의식이 앞선다.
   - **포지셔닝:** 이 책에서 가장 독자적인 통찰(§5-1 "고통은 에러가 아니라 침묵")을 전면에 세운다. 이미 MCP를 써본 독자에게는 강력하지만, "만드는 법"을 찾는 입문 독자에게는 무슨 책인지 전달되지 않는다.

**추천: 1번.** 이 책의 성패는 "직접 만들어 쓰려는 개발자"에게 정확히 도달하는가에 달렸다. 2번의 도발과 3번의 통찰은 각각 1장과 8장이 본문에서 충분히 수행한다 — 제목까지 그 역할을 맡을 필요는 없다. 2번은 홍보 문구·부제 후보로 살려둔다.

### 저술 제약 (전 챕터 구속)

이 책은 빠르게 움직이는 주제를 다룬다. 아래는 스타일이 아니라 **사실 규율**이며 fact-checker가 이 기준으로 판정한다.

1. **네 개의 버전 축을 절대 합치지 않는다** — ① 스펙 리비전(`2025-11-25` 정식 / `2026-07-28` RC) ② SDK semver(TS 1.29.0·2.0.0-beta.5 / Python 1.28.1·2.0.0b2 / Java 2.0.0 / Spring AI 2.0.0) ③ 클라이언트 CLI(Claude Code 2.1.220 / Codex 0.145.0 / Agent SDK 0.3.220·0.2.128) ④ 레지스트리 `server.json` 스키마(`2025-12-11`).
2. **주 서술 대상은 `2025-11-25`(정식)이다.** `2026-07-28`은 12장에 격리하고, 다른 장에서는 "RC 기준, 확정 시 변동 가능"으로만 스친다. 예제 코드가 `server/discover`를 전제하면 출간일에 틀린 책이 된다.
3. **"2.0"의 의미가 언어마다 다르다.** Java·Spring AI 2.0.0은 **GA이면서 `2025-11-25`를 구현**한다. Python 2.0.0b2는 `2026-07-28`을 **실제로 협상**한다. TS 2.0.0-beta.5는 신형 타입을 export하지만 `SUPPORTED_PROTOCOL_VERSIONS`에 `2026-07-28`이 **없다**(README는 지향 선언). **세 문장을 하나로 묶지 않는다.**
4. **구체 주장에는 "{버전}/{시점} 기준"을 붙인다.** 버전·수치·API 시그니처가 대상이다.
5. **`01_reference.md` §7-B와 §8-H는 차단선이다.** 각 장의 "레퍼런스 한계"가 그 장의 금지 목록이다. **§8이 해소한 항목은 차단선에서 내려왔다**(8-A 참조) — 반대로 §8-H가 새로 세운 차단선은 해당 장에 반영돼 있다.
6. **🆕 SDK 상태는 "권고"가 아니라 "시점 관측"으로 쓴다** (리뷰 C-2a).
   - ❌ "1.29.0을 써라" / "2.0은 아직 베타다"
   - ✅ "2026-07-26 시점에 TS SDK의 dist-tag는 `latest: 1.29.0` 하나뿐이었고, README는 v1.x를 프로덕션 지원 라인으로 명시하며 v2 출시 후 최소 6개월 수정을 약속했다."
   - **이렇게 쓰면 정식 GA가 나와도 문장이 틀리지 않는다.** 스펙 축(제약 2)에는 격리라는 방어가 있지만 **SDK 축에는 이 표현 규율이 유일한 방어**다. TS·Python 2.0 정식은 이 계획 작성 시점 기준 **이틀 안에** 나올 수 있다.

## 🆕 러닝 예제 명세 (리뷰 C-1)

**3·4·5·6·7·9·10장이 같은 서버 하나를 만든다.** 병렬 저술에서 세 언어가 각자 다른 서버를 상상하는 것을 막기 위해 아래를 **확정 명세**로 고정한다. 해당 장들의 "주요 내용"에 `러닝 예제 명세를 따른다`가 박혀 있다.

| 항목 | 확정 값 |
|---|---|
| **서버 이름** (클라이언트 등록명) | `team-wiki` |
| **npm 패키지** | `mcp-server-team-wiki` (스코프 없음) |
| **npm `bin` 키** | `mcp-server-team-wiki` — 패키지명과 **일치시킨다** |
| **PyPI 패키지** | `mcp-server-team-wiki` |
| **`[project.scripts]` 키** | `mcp-server-team-wiki = "mcp_server_team_wiki:main"` |
| **Docker 이미지 / ENTRYPOINT** | `mcp-server-team-wiki` / `ENTRYPOINT ["mcp-server-team-wiki"]` |
| **레지스트리 `name`** | `io.github.example-org/team-wiki` (역DNS. npm은 `package.json`의 `mcpName`, PyPI는 README의 `mcp-name:` 줄로 소유권 증명) |
| **도구 1** | `wiki_search(query: string, limit?: number = 10)` — 문서 제목·본문 검색. 반환은 `{path, title}` 객체 배열 (content=요약 텍스트, structured_content=이 배열 — 5장의 이원 반환 논의가 이 구조에 의존한다) |
| **도구 2** | `wiki_get(path: string)` — 문서 본문 반환 |
| **리소스** | 템플릿 `wiki://{path}` 1개 |
| **프롬프트** | `summarize_page(path)` 1개 |
| **오류 케이스** | 존재하지 않는 `path` → **Tool Execution Error**(`isError`)로 반환. **Protocol Error로 던지지 않는다** — 3장의 SEP-1303 논지를 이 케이스 하나로 시연하고, 5·6장이 같은 케이스를 각 언어로 재현한다 |

**부수 규약**

- **이름 규칙이 세 배포 경로를 동시에 결정한다** — `[project.scripts]` 키 하나가 `uvx <이름>`·Docker `ENTRYPOINT`·`pip` 설치 커맨드를 전부 정한다(§8-C의 📌). npm의 `bin` 키도 같은 역할을 한다. **9장은 이 대칭을 논지로 삼는다.**
- **도구 이름의 `wiki_` 접두사는 우연이 아니다** — 7장의 네임스페이스 규칙이 이 명세를 사후 정당화한다.
- **6장의 Spring AI `@McpTool` 계산기 예제(`add(a, b)`)는 레퍼런스 §3-4 원문 인용이다** — 인용은 인용대로 쓰되, **6장이 완성하는 서버는 `team-wiki`여야 한다.**
- **7장 before/after의 재료** — "위키 API의 오퍼레이션 12개를 그대로 노출한 버전" vs "의미 단위로 묶어 4개(`wiki_search`·`wiki_get`·`wiki_list_spaces`·`wiki_recent`)로 줄인 버전". 최종 명세는 위의 2개 도구이고, 나머지 2개는 before/after 논증용 중간 산물이다.
- **⚠️ 러닝 예제는 스코프 없는 패키지다 — `--access public` 함정은 별도 곁가지로 다룬다.** `mcp-server-team-wiki`는 unscoped라 `npm publish`에 `--access public`이 필요 없다. 9장은 스코프 패키지 함정을 **이름을 붙인 곁가지**(가정 패키지 `@example/mcp-server-team-wiki`)로 분리해 서술하고, **러닝 예제의 실제 publish 커맨드에 `--access public`을 붙이지 않는다.** 러닝 예제 이름을 스코프형으로 바꾸는 것도 금지한다 — `bin`·`[project.scripts]`·`ENTRYPOINT`·`mcpName` 대칭이 9장의 척추이기 때문이다.

## 내러티브 아크

이 책은 **"혼동을 걷어내고 → 하나를 끝까지 만들어 붙이고 → 내 언어로 옮기고 → 잘 만들고 → 안 보이는 실패를 보이게 하고 → 포장해 남에게 주고 → 밖에 열고 지키고 → 경계 너머를 내다보는"** 순서로 흐른다.

**1~2장(왜·무엇)**은 손을 대기 전에 지형을 정리한다. 1장이 "MCP 2.0 스펙은 없다"로 시작하는 건 도발이 아니라 필요다 — 독자가 검색으로 이미 오염된 채 책을 펴기 때문이다. 네 개의 버전 축을 분리해 세운 뒤, 곧바로 더 큰 질문("2026년 내내 '죽었다'는 소리를 듣는 프로토콜을 왜 배우나")을 정면으로 받는다. 이 논쟁을 마지막 장으로 미루면 독자는 열한 장 내내 의심을 안고 읽는다. 2장은 그 위에 프로토콜의 뼈대(JSON-RPC, 세 primitive, 트랜스포트, 버전 협상)를 얹는다.

**3~4장(첫 왕복)**에서 **피드백 루프를 최대한 빨리 닫는다.** 3장에서 TypeScript로 `team-wiki` 서버를 만들고, 4장에서 그것을 Claude Code·Claude Desktop·Agent SDK·Codex에 실제로 붙인다. 4장 끝에서 독자는 **동작하는 물건**을 손에 쥔다 — 이게 이 배치의 유일한 목적이다.

**5~6장(내 언어로)**은 같은 서버를 Python과 Java·Spring AI로 다시 만든다. 3장이 정본 워크스루이고 5·6장은 이식이다 — 그래서 Java만 쓸 독자도 3장은 읽어야 한다(머리말에서 이 경로를 안내한다). 두 장 모두 "2.0"이라는 같은 숫자가 언어마다 전혀 다른 뜻이라는 걸 각자의 방식으로 증명한다.

**7~8장(잘 만들기)**이 이 책을 튜토리얼과 가르는 지점이다. 7장은 "도구를 몇 개, 어떻게 이름 붙이고, 얼마나 신뢰할 것인가"를 러닝 예제의 before/after로 착지시키고 생태계 실측·보안 연구를 그 결정의 근거로 뒤에 붙인다. 8장은 이 책의 심장이다. MCP의 고통은 에러가 아니라 **침묵**이고(2048자 절단, 스키마 소실, 거짓 `✓ Connected`, "밖에서 보면 살아 있는데 기능적으로 귀머거리"), 그래서 디버깅과 관찰성은 같은 장에서 하나의 주제로 다뤄야 한다 — 둘 다 "보이지 않는 것을 보이게 만드는 일"이다.

**9~10장(밖으로)**은 서버를 세상에 내보낸다. 9장은 **포장**이다 — npm/npx·PyPI/uvx·Docker·레지스트리를 다루며, 이름 하나(`bin` 키 = `[project.scripts]` 키 = `ENTRYPOINT`)가 세 배포 경로를 동시에 결정한다는 통찰로 묶는다. 10장은 **개방과 방어**다 — 원격 Streamable HTTP로 열 때 세션·Origin·OAuth가 무엇을 요구하는지, 그리고 툴체인 자체가 공격면이 된 사례(디버깅 도구의 RCE, 시크릿 출력, 설정 파일 자기승인)를 한 논지로 묶는다.

**11장(뒤집기)**은 반대 방향 — 서버가 코딩 에이전트를 호출하는 패턴 — 을 **실험적 영역으로 정직하게** 소개한다. 대표 구현이 아카이브됐다는 사실을 숨기지 않는 것이 이 장의 가치다.

**12장(그 다음)**은 이틀 뒤 정식화될 `2026-07-28` 리비전을 한곳에 격리해 다룬다. 스펙이 `initialize`를 없애고 stateless로 재설계된다는 사실은 앞 열한 장을 부정하지 않는다 — 왜 부정하지 않는지(SDK 채택 속도, 최소 12개월 deprecation 창)를 밝히는 것이 이 장의 임무이고, 동시에 책 전체를 닫는 매듭이 된다.

**머리말의 독자 경로 안내(2종)** — ① **언어별:** Python·Java 독자도 3장은 읽어야 한다(정본 워크스루). ② **빠른 경로:** 당장 만들어보고 싶으면 **3장 → 4장 → 1장** 순서로 읽어도 된다. 1·2장을 앞에 두는 배치는 유지하되(설계 근거 #3), 코드까지 10,500자를 지나야 하는 진입 마찰은 안내로 푼다.

## 설계 근거

### 채택한 구조의 이유

1. **12장은 압축 불가능한 하한이다.** 사용자 요구 토픽 6개 중 하나(언어별 구현)가 이미 3개 장을 요구하고, 나머지 5개 토픽이 각 1장 이상을 요구한다. 여기에 Why 장, 설계·보안 장, 미래 격리 장이 붙는다. 하네스 기본값(5~10장)을 넘기지만 이는 주제 폭에서 온 것이다.
2. **`2026-07-28` RC를 한 장에 격리했다.** 오늘은 2026-07-26이고 RC는 **이틀 뒤 정식화 예정**이다(§7-D). RC 재료를 여러 장에 흩뿌리면 정식화되는 순간 여러 장이 동시에 낡는다. **단, 이 격리는 스펙 축만 보호한다** — SDK 축은 저술 제약 6(시점 관측 표현)과 재확인 체크리스트가 담당한다(리뷰 C-2).
3. **CLI-vs-MCP 논쟁(§4-1)을 마지막이 아니라 1장에 놓았다.** 2026년 2~5월에 400점대 HN 스레드가 네 달 연속 올라온 논쟁이다. 뒤로 미루면 독자는 열한 장 내내 "이거 배워도 되나"라는 의심을 품고 읽는다.
4. **연결(4장)을 언어 챕터 사이에 끼웠다.** 3→4장에서 "만들고 붙여서 동작을 확인"하는 왕복을 완결시킨다.
5. **🆕 배포를 "포장(9장)"과 "개방·방어(10장)"로 쪼갰다** (리뷰 M-2 권고 채택). 보강 리서치(§8-B~D)가 uvx/uv run 구분·Dockerfile 패턴·mcp-publisher 6단계를 **전부 확보**해 9장 재료가 크게 늘었다. 동시에 8장에서 툴체인 보안 소절(4건)을 10장으로 옮겨 8장 밀도를 낮췄다. 부수 효과로 **보안이 7장(설계)/10장(운영·툴체인) 두 갈래로 정리**돼 기각 대안 3의 3갈래 분산보다 깔끔해졌다.

### 기각한 대안 1 — 토픽 6(서버→에이전트 오케스트레이션)을 종합 장의 한 절로 흡수해 장 수를 줄인다

**기각 사유:** 사용자가 명시적으로 요구한 6개 토픽 중 하나를 부록 취급하게 된다. 게다가 이 토픽은 국내 한국어 자료가 사실상 없는 영역(§7-C)이라 오히려 이 책의 차별점이다. 생태계가 미성숙하다는 사실은 **분량을 줄일 이유이지 장을 없앨 이유가 아니다** — 그래서 11장은 전체에서 가장 짧은 4,500자로 배정하고, "떠오르는 베스트 프랙티스"가 아니라 "실험적이며 대표 구현이 유지보수를 멈춘 영역"으로 프레이밍한다.

### 기각한 대안 2 — 언어별로 책을 3부로 나누고 각 부에 구현·연결·배포를 반복 배치한다 (TS편 / Python편 / Java편)

**기각 사유:** 독자가 한 언어만 읽고 덮을 수 있어 언뜻 친절해 보이지만, 세 가지를 잃는다. ① 연결·디버깅·배포·보안의 **80%는 언어 무관**이라 세 번 반복하면 분량이 1.5배로 부풀고 중복 검수 비용이 든다. ② "2.0의 의미가 언어마다 다르다"는 이 책의 핵심 통찰은 **세 언어를 나란히 놓아야만** 드러난다 — 부를 나누면 대조가 사라진다. ③ 도구 설계 규칙(19% 노출, 네임스페이스, 개수 억제)은 언어를 초월한 원리인데, 3부 구조에서는 놓을 자리가 없다.

### 기각한 대안 3 — 보안을 독립 장으로 세운다

**기각 사유:** 재료는 충분하다(논문 A-1~A-9, CVE-2025-49596, 시크릿 유출·셸 인젝션 이력). 그러나 보안을 따로 떼면 독자가 "나중에 읽을 장"으로 미루고, MCP 보안의 실제 성질 — **설계 결정 자체가 보안 결정**(도구 개수·description·권한 범위) — 이 흐려진다. 대신 두 갈래로 배치한다: 설계·tool poisoning·ETDI → **7장**, 원격 노출·OAuth·툴체인 → **10장**. 흩어진 조각을 독자가 다시 꿰도록 **7장 클로징에서 나머지 조각의 위치를 지시**하고, **후미 부속물에 "보안 체크리스트" 한 장**을 모은다(리뷰 m-5).

### 🆕 기각한 대안 4 — 8장(침묵)을 쪼개 관찰성을 독립 장으로 세우고 배포는 한 장으로 유지한다

**기각 사유:** 리뷰 M-2가 이 안을 명시적으로 반대했고 동의한다. 8장의 과적재는 **고정돼 있고 표로 압축 가능**한 반면, 9장의 과적재는 **증가 중이고 압축하면 사용자 약속을 깬다**(사용자가 "npx 배포 **상세**"를 명시 요구했다). 압축 가능한 쪽을 쪼개고 압축 불가능한 쪽을 놔두는 건 방향이 반대다. 게다가 보강 리서치가 성공해 9장 재료가 실제로 늘었으므로, 채택했다면 계획이 즉시 틀렸을 안이다.

### 1장. "MCP 2.0"은 없다 — 그리고 왜 아직도 MCP인가

- **핵심 질문:** 검색하면 나오는 "MCP 2.0"과 "MCP는 죽었다"는 각각 무엇을 가리키는 말인가? 나는 어떤 기준으로 시작해야 하나?
- **주요 내용:**
  - "MCP 2.0 스펙"은 존재하지 않는다 — 스펙은 `2024-10-07`부터 날짜 리비전만 써왔고 릴리스 태그 전수에 `2.0`이 없다. 유일한 `"2.0"`은 `JSONRPC_VERSION`(JSON-RPC 2.0)
  - **네 개의 독립 버전 축** 분리: 스펙 리비전 / SDK semver / 클라이언트 CLI / 레지스트리 `server.json` 스키마. 이 표가 책 전체의 좌표계다
  - **그런데 "2.0"은 실재한다 — SDK 세대로서. 단 성숙도가 갈린다** (리뷰 C-2c): **Java SDK 2.0.0·Spring AI 2.0.0은 GA**로 넘어갔고, **TypeScript·Python 2.0은 2026-07-26 관측 시점에 프리릴리스**였다. **"생태계 전체가 2.0으로 넘어갔다"고 뭉뚱그리지 않는다** — 그렇게 쓰면 3장의 "v1이 프로덕션 지원 라인"과 정면충돌해 독자가 "그래서 2.0을 쓰라는 거야 말라는 거야"가 된다. 게다가 같은 2.0이 언어마다 다른 스펙을 구현한다
  - "MCP는 죽었다, CLI 만세" 논쟁 정면 돌파: HN 400점대 스레드가 2026년 2~5월 **4개월 연속**. 관점 A(CLI로 충분·조합 가능·샌드박스 탈출면) vs 관점 B(웹·모바일엔 CLI가 없다·키를 에이전트에게서 격리·조직 단위 표준 배포)
  - **⚠️ 인용 상한: 4명까지만 쓴다.** 레퍼런스에는 13명 이상의 목소리가 있지만 전부 옮기면 장이 무너진다. 배정 — ① **bb88의 프레임 전복**(*"MCP exists to take capability away from agents"*) ② **CLI가 존재할 수 없는 환경**(0x696C6961 또는 p_ing 중 하나) ③ **ejholmes** — "죽었다" 글의 저자 본인이 제목은 의도적 도발이었다고 인정 ④ **국내 실무자의 단계별 분기**(kaydash 또는 sonnet 중 하나)
  - 이 책의 서술 기준 선언: 주 대상은 `2025-11-25`, `2026-07-28`은 12장에 격리
- **독자가 얻는 것:** 버전 혼동이 걷힌 좌표계. 그리고 "언제 MCP를 쓰고 언제 쓰지 않을지"의 1차 판단 기준
- **오프닝 기법:** 정의 뒤집기 — "'MCP 2.0'을 검색하면 수백 건이 나온다. 그런데 그런 스펙은 존재하지 않는다."
- **클로징:** 질문 남기기 — "그래서 만들 만한가? 그건 만들어봐야 안다"로 3장을 당긴다 (다음 장 예고형 금지)
- **`### 이 장의 핵심` 박스:** 있음
- **다이어그램:** 그림 1 — 네 개의 버전 축 타임라인
- **예상 분량:** 5,500자
- **레퍼런스 한계:** ① 재확인 체크리스트의 `prerelease` 플래그를 저술 직전 조회한다. ② **"생태계 전체가 2.0으로" 같은 요약 표현은 검증된 사실이 아니다** — 성숙도를 쪼갠 문장으로만 쓴다. ③ **컨텍스트 비용 수치는 7장 소관이다** — 이 장은 논쟁의 존재만 언급하고 토큰 수치·deferred loading 시점을 인용하지 않는다(리뷰 m-4)

### 2장. 프로토콜 해부 — JSON-RPC 위에 무엇이 얹혀 있나

- **핵심 질문:** MCP는 정확히 무엇을 표준화했고, 내 서버가 클라이언트와 주고받는 건 실제로 어떤 메시지인가?
- **주요 내용:**
  - Host / Client / Server 3자 구조와 JSON-RPC 2.0 기반. 학술적 한 줄 규정("secure tool invocation and typed data exchange")이 마케팅 문구("USB-C port")보다 정확한 이유
  - **세 primitive** — `tools` / `resources` / `prompts`와 각 메서드. 서버→클라이언트 방향(`roots`·`sampling`·`elicitation`·`logging`)
  - lifecycle: `initialize` → `notifications/initialized` → capability negotiation
  - **트랜스포트 3종의 현재 지위** — stdio(로컬 기본), Streamable HTTP(권장), HTTP+SSE(deprecated). stdio의 구조적 약점 4가지(stdout 오염·trace context 전파 불가·프로세스 생명주기·재연결 불일치)
  - **버전 협상의 함정** — 협상 실패 fallback이 최신이 아니라 `2025-03-26`이다. "왜 내 서버가 구버전으로 붙지?"의 답
  - **버전 문자열을 부등호로 비교하지 마라** — SDK 주석 원문 인용(`"zzz" > "2025-11-25"`). 리비전은 순서 있는 스칼라가 아니라 **열거된 집합**이다
  - `2025-11-25`가 가져온 것들(icons·URL elicitation·sampling 도구 호출·tasks 실험적·OIDC Discovery·JSON Schema 2020-12 기본 dialect)
- **독자가 얻는 것:** 로그에 찍힌 JSON-RPC 메시지를 읽고 어느 단계에서 어긋났는지 짚어낼 수 있는 눈
- **오프닝 기법:** 수사적 질문 — "최신 스펙을 지원하는 SDK를 썼는데, 왜 내 서버는 2025-03-26으로 붙을까?"
- **클로징:** 한 문장 여운 — 협상은 끝났고 이제 무엇을 노출할지가 남았다
- **`### 이 장의 핵심` 박스:** 있음
- **다이어그램:** 그림 1 — Host/Client/Server 메시지 흐름 / 그림 2 — `initialize` 버전 협상 시퀀스(성공·실패 fallback 분기 포함)
- **예상 분량:** 5,000자
- **레퍼런스 한계:** `schema/2026-07-28/` 유무를 저술 직전 재확인한다(체크리스트). RC 내용은 존재와 지위까지만, 상세는 12장

### 3장. 첫 서버 — TypeScript로 `team-wiki` 만들기

- **핵심 질문:** 동작하는 MCP 서버 하나를 처음부터 끝까지 만들려면 정확히 무엇을 쓰고 무엇을 조심해야 하나?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — `wiki_search`·`wiki_get` 두 도구, `wiki://{path}` 리소스 템플릿, `summarize_page` 프롬프트
  - **버전 선택을 시점 관측으로 서술한다**(저술 제약 6) — 2026-07-26 시점에 `@modelcontextprotocol/sdk`의 dist-tag는 `latest: 1.29.0` 하나뿐이었고, README는 v1.x를 프로덕션 지원 라인으로 명시하며 v2 출시 후 최소 6개월 수정을 약속했다. **저술 직전 dist-tags를 재조회한다**
  - 프로젝트 골격: `type: "module"`, **`bin` 키를 패키지명과 일치시킨다**(9장에서 이 결정이 회수된다 — 여기서는 한 줄 언급만 하고 이유는 9장으로 넘긴다)
  - `McpServer` / `registerTool` / `registerResource` / `registerPrompt`, `StdioServerTransport`로 최소 서버 완성
  - **오류 처리 — SEP-1303 시연.** 존재하지 않는 `path`로 `wiki_get`을 부르면 **Protocol Error가 아니라 Tool Execution Error**로 돌려준다. 그래야 모델이 스스로 고친다. 이 케이스가 5·6장에서 그대로 재현된다
  - **별도 절: SDK 2.0 계열은 무엇이 다른가**(2.0.0-beta.5 / 2026-07-21 관측 기준) — 모노레포 패키지 분할(`server`/`client`/`core`/`node`/`express`·`hono`·`fastify`/`codemod`), Zod 3→4 메이저 점프, Standard Schema 채택, `serveStdio`, `WebStandardStreamableHTTPServerTransport`. **그리고 관측된 사실** — 신형 타입과 세대 분기 유틸(`ProtocolEra` 등)은 export되지만 `SUPPORTED_PROTOCOL_VERSIONS`에 `2026-07-28`이 없어 **그 시점엔 협상하지 않았다**
  - 장 끝: `claude mcp add`로 한 줄 연결해 동작만 확인
- **독자가 얻는 것:** 손에 쥔 첫 서버, 그리고 v1/v2 중 무엇으로 시작할지에 대한 근거 있는 결정
- **오프닝 기법:** 상황 가정 — "사내 위키를 클로드가 직접 읽게 해달라는 요청이 왔다고 해보자."
- **클로징:** 적용 과제 — 도구를 하나 더 붙여보게 하고 4장으로 넘긴다
- **다이어그램:** 없음 (코드 밀도가 높다)
- **예상 분량:** 5,500자
- **경계 명시:** `createSdkMcpServer`(인프로세스 서버)는 **4장 소관**. `chmod 755`·`files`·배포 절차는 **9장 소관** — 이 장은 `bin` 키를 정한다는 사실만 한 줄 언급한다(리뷰 N-4)
- **레퍼런스 한계:** dist-tags 재확인(체크리스트). v2 전용 심볼을 v1 사용자에게 권하지 않는다(→ 10장 M-3 처리와 동일 규율)

### 4장. 클라이언트에 붙이기 — Claude Code·Desktop·Agent SDK·Codex

- **핵심 질문:** 만든 서버를 실제로 쓰는 도구에 어떻게 등록하고, 왜 같은 서버가 클라이언트마다 다르게 동작하나?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — 등록명은 `team-wiki`, 실행 커맨드는 3장 빌드 산출물
  - **Claude Code** — `claude mcp add [options] <name> -- <command> [args...]`. 실측 옵션 전수: `--scope`(기본 `local`), `--transport`(`stdio`|`sse`|`http`), `-e`/`-H`, OAuth 계열. `--` 뒤는 "passed to the server untouched"
  - **🆕 스코프는 3단계가 아니라 5단계다**(§8-G, 이제 `[검증]`이라 **단정 가능**) — ① local ② project ③ user ④ 플러그인 제공 서버 ⑤ claude.ai 커넥터. 앞의 셋은 **이름**으로 중복을 판정하고, 플러그인·커넥터는 **엔드포인트**로 판정한다
  - **🆕 가장 중요한데 2차 자료에 거의 없는 사실** — *"The entire server entry from that source is used; **fields are not merged across scopes**."* 스코프 간 필드 병합은 일어나지 않는다. 이 책의 차별점 중 하나

### 5장. Python 서버 — FastMCP, 그리고 `MCPServer`로 가는 길

- **핵심 질문:** Python으로 서버를 만들 때 지금 무엇을 쓰고, 2.0이 오면 내 코드는 어떻게 되나?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — 같은 `team-wiki`를 Python으로. 오류 케이스(존재하지 않는 `path`)도 동일하게 재현
  - **현재 안정 라인의 FastMCP API**(1.28.1 / 2026-06-26 관측 기준) — `from mcp.server.fastmcp import FastMCP`, `@mcp.tool()`·`@mcp.resource()`·`@mcp.prompt()`, `mcp.run(transport="streamable-http")`. 설치 `uv add "mcp[cli]"`
  - **🆕 로컬 실행은 `uvx`가 아니라 `uv run`이다**(§8-B) — 공식 Python 퀵스타트 경로: `uv init` → `uv venv` → `uv add "mcp[cli]" httpx` → `uv run server.py`. 클라이언트 등록은 `command: "uv"`, `args: ["--directory", "<절대경로>", "run", "server.py"]`. **`uvx`는 배포 후 경로다** — 9장에서 다룬다
  - 3장의 TypeScript 서버와 대조하며 두 SDK의 설계 차이 짚기
  - **최대 파괴적 변경** — `FastMCP` → **`MCPServer`** 개명. 두 독립 경로가 일치한다: wheel 전체 문자열 검색 0건 + **`docs/migration.md` 원문 *"The `FastMCP` class has been renamed to `MCPServer`"***. **강하게 단정해도 되는 사실**
  - **🆕 2.0 공식 예제가 존재한다**(§8-E — §7-B-6 반증). `docs_src/index/tutorial001.py` 원문을 인용: `from mcp.server import MCPServer` → `mcp = MCPServer("Demo")` → `@mcp.tool()` / `@mcp.resource("greeting://{name}")`. `first_steps/tutorial001.py`는 `@mcp.prompt()`까지 세 프리미티브를 모두 보여준다
  - **🆕 도구 등록 철학** — 공식 문서 원문: *"You declare one by putting `@mcp.tool()` on a plain Python function. **That's the whole API.**"* SDK가 함수에서 읽는 것: 이름=함수명, 설명=docstring, 인자=타입 힌트. *"Type hints aren't documentation here. They are **the contract**."* 기본값을 주면 `required`에서 빠진다. 반환은 `result.content`(모델용)와 `result.structured_content`(클라이언트용)로 갈린다 — **이 분리가 `wiki_search`의 반환 설계와 직결된다**
  - 그 밖의 breaking change: camelCase→snake_case, `mcp.types`→`mcp-types` 분리, `McpError`→`MCPError`, 리소스 URI `AnyUrl`→`str`, `streamablehttp_client` 제거, 트랜스포트 파라미터가 생성자→`run/app`, 동기 핸들러의 워커 스레드 실행, Roots·Sampling·Logging deprecated. 의존성: `httpx`→`httpx2`, **`opentelemetry-api` 필수 승격**(관찰성이 기본이 됐다 — 8장 복선)
  - **Python이 세대 다리를 실제로 건너고 있다** — `mcp_types/version.py`의 `KNOWN`/`HANDSHAKE`/`MODERN_PROTOCOL_VERSIONS` 상수. TS 2.0 beta와 결정적으로 다른 지점(3장 콜백)
  - **🕒 반드시 인용할 프로덕션 경고** — README 원문: *"**Do not use v2 in production.** … **v1.x is the only stable release line**"*, 그리고 *"add a `<2` upper bound … (for example `mcp>=1.27,<2`)"*
  - 혼동 주의: PyPI의 `fastmcp`(jlowin, 3.4.4)는 이름만 같은 **별개 패키지**다
  - **스키마 함정 예고** — `Optional[str]`을 쓰면 `anyOf [X, null]` 스키마가 모델에 도달하기 전에 제거될 수 있다(8장에서 전면 분석)
- **독자가 얻는 것:** 동작하는 Python 서버 + 2.0 전환기에 의존성을 어떻게 잠글지에 대한 결정
- **오프닝 기법:** 충격적 수치·사실 — "`mcp` 2.0 휠 전체를 뒤져도 'fastmcp'라는 문자열은 한 건도 나오지 않는다."
- **클로징:** 질문 남기기 — 같은 서버를 JVM에서 만들면 무엇이 달라질까
- **다이어그램:** 없음
- **예상 분량:** 5,000자
- **레퍼런스 한계:** ① **`mcp.server` vs `mcp.server.mcpserver` 동치 미확인** — **`from mcp.server import MCPServer`를 쓰고 "둘은 같다"고 단정하지 않는다**(§8-H). ② **v2 정식 목표일(README 2026-07-27)과 스펙 정식일(2026-07-28)의 하루 차이는 근거 불명 — 뭉뚱그리지 않는다.** ③ PyPI `info.version`을 저술 직전 재확인(체크리스트). ④ ~~2.0 예제 미확보~~ **해제됨**(§8-E)

### 6장. Java와 Spring AI — `@McpTool`, 그리고 GA인 2.0의 진짜 의미

- **핵심 질문:** JVM 진영에서 MCP 서버를 만들 때 무엇을 쓰고, Java SDK 2.0이 "최신 스펙"을 뜻하지 않는 이유는 무엇인가?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — 이 장이 완성하는 서버도 `team-wiki`다. **레퍼런스 §3-4의 `add(a, b)` 계산기는 `@McpTool` 문법을 보여주는 원문 인용으로만 쓴다**
  - **공식 Java SDK 2.0.0 GA**(2026-06-11 기준) — 좌표 `io.modelcontextprotocol.sdk:mcp`. 릴리스 노트가 명시하는 구현 스펙은 **`2025-11-25`**다. **숫자가 2.0이라고 `2026-07-28`을 구현한다고 착각하면 안 된다** — 이 장이 1장의 "네 개 축"을 가장 선명하게 증명한다
  - 2.0의 breaking change와 마이그레이션: `McpSchema` 필수 필드 강제, 도구 입력·JSON Schema 2020-12 종단 검증, `JsonSchema` 제거 후 `inputSchema`가 `Map`으로. `MIGRATION-2.0.md`
  - **"Streamable HTTP first: SSE transports are now deprecated"** — 릴리스 하이라이트 원문
  - **Spring AI 2.0.0**(2026-06-12 기준) — Java SDK GA **바로 다음 날** 나왔다. MCP 관련 스타터는 **5개가 전부**(서버 3 + 클라이언트 2)
  - **가장 흔한 오해 정정: 서버 아티팩트는 3개인데 프로토콜은 프로퍼티로 고른다.** `-server-webmvc` 하나가 SSE·STREAMABLE·STATELESS를 다 커버한다 — "WebMVC용 Streamable 스타터"를 따로 찾으면 안 된다. 매트릭스 표 제시. STATELESS는 공식 문서상 *"microservices architectures and cloud-native deployments"*에 적합
  - **두 번째 오해 정정: `@Tool`/`ToolCallbackProvider`가 아니라 `@McpTool` 체계다.** `@McpTool`·`@McpToolParam`으로 JSON 스키마 자동 생성, 속성(`name`·`description`·`title` 우선순위·`generateOutputSchema`·`annotations`), `@McpResource`
  - 오류 케이스(존재하지 않는 `path`)를 Spring AI에서 Tool Execution Error로 돌려주는 방법
- **독자가 얻는 것:** 동작하는 Spring AI `team-wiki` + 아티팩트/프로퍼티 매트릭스를 헤매지 않고 고르는 능력
- **오프닝 기법:** 인용·일화 — 릴리스 노트 한 줄에서 출발: *"It tracks the latest 2025-11-25 MCP specification."* 2.0인데 최신이 아닌 스펙을 따른다는 문장에서 시작한다
- **클로징:** 한 문장 여운 — 세 언어로 같은 것을 만들었으니 이제 "무엇을 만들 것인가"가 남았다
- **다이어그램:** 없음 (매트릭스 표가 그 역할을 한다)
- **예상 분량:** 4,500자
- **레퍼런스 한계:** **Java/JVM MCP는 논문 근거도 커뮤니티 논의도 없다**(§7-A-11) — 이 장은 **SDK·Spring AI 공식 문서 1차 소스에만 근거해 선다.** "실무자들이 이렇게 한다"류 서술을 쓰지 않는다. Spring AI 2.0.0이 pin하는 java-sdk 버전과 `@McpTool`의 소속 아티팩트는 미확인(§7-B-7) — 단정 금지

### 7장. 도구를 몇 개나 만들 것인가 — 설계가 곧 보안이다

- **핵심 질문:** 내 API를 도구로 노출할 때 몇 개로, 어떤 이름으로, 얼마나 신뢰하게 만들어야 하나?
- **주요 내용:** (**리뷰 M-1 반영 — 예시가 앞, 수치는 근거로 뒤**)
  1. **🆕 before/after 절 — 러닝 예제로 착지시킨다.** 위키 API의 오퍼레이션 12개를 그대로 노출한 `team-wiki` v0(도구 목록 전체를 지면에 깐다) → 의미 단위로 묶어 4개로 줄인 v1 → 최종 2개(`wiki_search`·`wiki_get`). **줄이는 과정에서 무엇을 버렸고 무엇을 합쳤는지**를 도구 목록 위에서 보여준다. 이름의 `wiki_` 접두사와 description 길이 규율도 이 목록 위에서 적용한다
  2. **그 결정의 근거 ①** — 공식 서버 116개 실측: 88.6%가 REST 백엔드, 92%가 API 껍데기, 그런데 노출하는 오퍼레이션은 **중앙값 19%**뿐이다. 그 선택은 무작위가 아니라 예측 가능한 패턴을 따른다. **REST API 전체를 1:1로 노출하지 마라**
  3. **그 결정의 근거 ②** — 도구를 줄이는 건 손해가 아니라 정확도를 올리는 일이다. 짧은 적응형 목록이 선택 정확도를 93.1% vs 87.1%로 개선했고, 중난도 질의에선 76.8% vs 60.9%로 격차가 벌어진다. **반대 증거도 단서까지 온전히**(리뷰 m-8): 도구 3,251개 환경에선 고정 5개가 총 커버리지에서 앞서지만(64.7% vs 61.9%) **어려운 질의에서는 아무것도 찾지 못한다**

### 8장. 침묵과 진단 — 에러 없이 실패하는 MCP를 보이게 만들기

- **핵심 질문:** 아무 에러도 안 나는데 도구가 동작하지 않을 때, 나는 어디를 봐야 하나?
- **주요 내용:** (**소절 5개** — 툴체인 보안은 10장으로 이관)
  1. **침묵의 카탈로그** — 2,048자 `description` **말없는 절단**(실측 502건, 최악 10,780→2,048자 81% 손실. 서버는 그 사실을 끝내 통보받지 못하고, `/mcp`는 잘리지 않은 원문을 보여줘 눈으로 확인조차 안 된다), `tools/list` 2페이지 이후 도구 드롭, `Optional[X]`/`anyOf [X, null]` 스키마 소실(5장 예고 회수), 16KB 초과 `inputSchema` 드롭, 헤드리스 연결 실패의 무신호. **🆕 그리고 토큰이 맞는데 401**(리뷰 M-4나) — 설정값 앞뒤의 **보이지 않는 공백**이 원인이다(v2.1.219가 경고를 추가한 이유). 원인이 문자 그대로 눈에 보이지 않는, 이 장 논지의 정중앙에 있는 사례
  2. **`✓ Connected`는 거짓말을 한다** — 핸드셰이크 성공 ≠ 도구 사용 가능. 표시가 `! Connected · tools fetch failed`로 바뀐 이유. "왜 안 붙나" 사례의 상당수가 실은 "붙었는데 도구가 없다". **🆕 가장 정확한 예시**(리뷰 M-4가, #80996): *"our agents' **only inbound-message path is an MCP server**, so a session that resumes with the MCP down is **functionally deaf while looking alive from the outside**."* `/mcp`가 대화형 전용이라 자동 복구 경로가 없고, 우회책의 대가는 *"~15 min penalty per event"*
  3. **stdout 함정 — 한 번은 다 당하는 실수 1위** — 증상(`Parse error: Unexpected token '[2m2026-0'`, `Method not found: notifications/initialized`, 즉시 `Connection closed`) → 원인(배너·ANSI 컬러·`print()`·의존 라이브러리 로그, **래퍼 스크립트와 `.zshrc` 출력까지**) → 해결(stdout엔 JSON-RPC만, 로깅은 stderr). 단 stderr도 공짜가 아니다(서버당 64MB 누적 누수 이력)
  4. **도구함과 노브** — MCP Inspector 1.0.0(2026-07-18 기준. 직전이 0.22.0이었다)과 **그 구조적 한계**: Inspector는 당신의 서버와 **직접** 말하므로 스코프·환경변수·PATH·승인 상태를 재현하지 않는다 → "Inspector에선 되는데 Claude Code에선 안 된다"의 정체. Claude Code JSONL 로그를 `jq`로 파기, **🆕 Claude Desktop 로그**(`~/Library/Logs/Claude`의 `mcp.log`=연결 일반 / `mcp-server-{이름}.log`=해당 서버 stderr, `tail -n 20 -f`)와 **Desktop 트러블슈팅 5단계**(완전 재시작 → JSON 문법 → **절대경로 확인** → 로그 → 커맨드 직접 실행. 4장에서 이관), `--debug` 실제 출력 읽는 법(`MCP error -32000: Connection closed`가 가장 자주 만날 문자열), `--safe-mode`로 이분 탐색, `--strict-mcp-config`로 격리. **타임아웃 노브는 표 하나로 압축** — 기본 60초, 2분 초과 시 자동 백그라운드(`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`), 원격 5분 무응답(`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`), sub-1000ms 값 무시, `MCP_SERVER_CONNECTION_BATCH_SIZE`(커뮤니티에 돌던 틀린 이름을 실측으로 반증한 사례)
  5. **관찰성 — 디버깅의 프로덕션 판** — 권장 span 계층(`session → task → turn → tool.call`), stdio는 헤더가 없어 trace context를 파라미터·환경변수로 명시 전달해야 한다, `OTEL_LOG_TOOL_DETAILS`, `/usage`의 MCP 서버별 비용 분해, 도구가 많으면 CPU 비용도 든다(tool-pool 캐싱 최적화 이력). 그리고 **관찰성은 운영 편의가 아니라 공격의 사후 탐지 수단이다** — 무엇을 실행했는지만으론 부족하고 어떤 컨텍스트가 그 호출을 유발했는지까지 남겨야 tool poisoning을 사후 판별할 수 있다
- **독자가 얻는 것:** 침묵을 의심하는 습관과 이분 탐색 절차. 이 책에서 가장 오래 남을 장
- **오프닝 기법:** 실패 장면 — "10,780자짜리 도구 설명이 2,048자에서 잘렸다. 서버는 그 사실을 끝내 듣지 못했다."
- **클로징:** 적용 과제 — 자기 서버로 이분 탐색을 한 번 돌려보게 한다
- **`### 이 장의 핵심` 박스:** 있음
- **다이어그램:** 그림 1 — **침묵 판정 이분 탐색 절차 플로차트**(이 책에서 가장 값진 그림이 될 자리)
- **원문 인용 상한:** 5개 이내(리뷰 N-3). 이슈·CHANGELOG 원문이 밀집하는 장이라 "인용 모음집" 인상을 막는다

### 9장. 포장해서 남에게 주기 — npm·PyPI·Docker·레지스트리

- **핵심 질문:** 내 서버를 남이 한 줄로 설치해 쓰게 하려면 무엇을 준비해야 하나?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — `mcp-server-team-wiki`라는 하나의 이름이 이 장 전체를 관통한다
  - **🆕 이 장을 묶는 통찰**(§8-C 📌) — **이름 하나가 세 배포 경로를 동시에 결정한다.** Python의 `[project.scripts]` 키 = `uvx <이름>` = Docker `ENTRYPOINT` = `pip` 설치 커맨드. npm의 `bin` 키도 같은 자리다. 3장에서 "`bin` 키를 패키지명과 일치시킨다"고 한 결정이 여기서 회수된다
  - **npm → `npx`** — 공식 quickstart의 실물 `package.json` 해부: `"type": "module"`, **`bin`(키가 곧 커맨드 이름)**, `"files": ["build"]`, 그리고 build 스크립트가 `chmod` 대신 **Node 인라인 스크립트로 755를 거는 이유**(Windows에서도 되게). **⚠️ 통념 정정** — 그 공식 예제의 `bin` 타깃에는 **shebang이 없다.** 통념(`#!/usr/bin/env node` 필수)과 어긋나므로 베끼기 전에 실제 `npx` 실행을 검증해야 한다. 배포 절차. **곁가지(러닝 예제와 분리) — 스코프 패키지 함정:** `@example/...` 같은 스코프 패키지는 기본 private이라 **`--access public` 없이는 배포가 실패한다.** 러닝 예제 `mcp-server-team-wiki`는 unscoped이므로 **이 플래그가 필요 없다** — 예제의 publish 커맨드에 붙이지 않는다
  - **🆕 Python — `uv run`(로컬)과 `uvx`(배포 후)를 갈라 쓴다**(§8-B). `uvx`는 `uv tool run`의 별칭이다(*"exactly equivalent to: `uv tool run ruff`"*). **패키지명과 커맨드명이 다르면 `--from`이 필요하다** — 그래서 `[project.scripts]` 키를 배포명과 똑같이 둔다. 공식 서버 실물 2건(`src/fetch`·`src/git`)이 이 규약으로 일치하고, 빌드 백엔드는 둘 다 `hatchling`, `requires-python = ">=3.10"`
  - **🆕 Docker**(§8-C) — 공식 레퍼런스 서버 **7개** 전수의 Dockerfile에서 추출한 패턴. **Python 3건은 사실상 동일 템플릿**: ① 멀티스테이지(빌드 `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` → 런타임 순정 `python:3.12-slim-bookworm`, **uv는 최종 이미지에 없다**) ② `UV_COMPILE_BYTECODE=1`(콜드 스타트)·`UV_LINK_MODE=copy` ③ 의존성/소스 분리 설치(원문 주석: *"Installing separately from its dependencies allows optimal layer caching"*) ④ `uv sync --locked --no-dev --no-editable` ⑤ `ENTRYPOINT ["mcp-server-…"]`. Node 4건은 alpine 멀티스테이지 + `NODE_ENV=production` + **`npm ci --ignore-scripts --omit-dev`**(공급망 관점에서 `--ignore-scripts`가 핵심) + `dist/`만 복사. **종료 지시자는 `ENTRYPOINT` 6 / `CMD` 1** — ⚠️ **"공식이 권장한다"가 아니라 "공식 서버 7개 중 6개가 쓴다"는 측정치로 서술한다**(명문 규정이 없다). stdio 컨테이너 실행: `"command": "docker", "args": ["run", "-i", "--rm", "mcp/fetch"]` — `-i`는 stdin 유지에 필수, `-t`는 쓰지 않는다(TTY가 JSON-RPC 프레이밍을 깨뜨린다 ※ 이 해설은 저술가 서술이고 커맨드만 `[검증]`). Docker MCP 카탈로그: `mcp/` 네임스페이스 공개 리포 245개(2026-07-26 실측), *"Docker builds and signs all local servers in the catalog"*
  - **🆕 MCP Registry — 게시 6단계**(§8-D). **반직관 포인트가 핵심이다: 패키지를 먼저 npm/PyPI에 올리고 그 다음 레지스트리에 등록한다**(*"The MCP Registry only hosts metadata, not artifacts"*). ① 소유권 마커 추가 → ② 패키지 게시 → ③ `brew install mcp-publisher` → ④ `mcp-publisher init` → ⑤ `mcp-publisher login github` → ⑥ `mcp-publisher publish`. **서브커맨드는 `--help`가 보여주는 것보다 많다**(`validate`·`status`는 문서에만). **소유권 마커가 패키지 타입마다 다르다** — npm은 `package.json`의 `mcpName`, **PyPI·NuGet은 README의 `mcp-name: <server-name>` 줄**(실물: `src/fetch/README.md` 3행). 인증 4종(`github` device flow / `github-oidc` CI / `dns`·`http` 키쌍 / `none`). `server.json` 필수 필드와 `$schema = 2025-12-11` — **축 4와 정확히 일치**(레지스트리 API와 게시 문서라는 독립 두 경로가 같은 값을 준다). **레지스트리는 여전히 preview**다
  - **`.mcpb` 빌드**(4장에서 넘어옴) — `npm install -g @anthropic-ai/mcpb` → stdio 서버 → `mcpb init` → `mcpb pack`. `manifest.json`이 **유일한 필수 파일**. MCPB v0.4+는 `server.type = "uv"`로 `pyproject.toml`만 넣으면 호스트가 Python·의존성을 관리한다(uv 논의가 여기서 닫힌다). 다만 **MCPB는 2차 배포 경로**이고 언어 권장은 Node.js다
- **독자가 얻는 것:** 설치 한 줄로 끝나는 네 갈래 배포 경로(npx·uvx·docker·레지스트리)와 그것을 하나로 묶는 이름 규약
- **오프닝 기법:** 상황 가정 — "서버가 내 노트북에서 잘 돈다. 이제 팀에게 줄 차례라고 해보자."
- **클로징:** 질문 남기기 — 남에게 주는 것과 인터넷에 여는 것은 전혀 다른 문제다
- **다이어그램:** 그림 1 — 하나의 이름이 npx·uvx·docker·registry 네 경로로 갈라지는 구조도
- **예상 분량:** 6,000자
- **레퍼런스 한계:** ① **Claude Code 공식 문서에 `uvx` 리터럴 예시가 없다**(2페이지 전문 검색 0건) — **`uvx`를 대입한 `claude mcp add` 문장을 쓰되 "공식 문서의 예시"로 귀속하지 않는다.** ② **`docker mcp` CLI 전체 서브커맨드 미확인** — 확인된 건 `docker mcp catalog pull <oci-reference>` 하나. **`docker mcp run` 같은 커맨드를 창작하지 않는다.** ③ **uv의 `[project.scripts]` 해석 메커니즘 명문 규정 없음** — 공식 서버 `pyproject.toml` 실물 2건을 근거로만 서술. ④ **`ENTRYPOINT` 권장의 명문 규정 없음** — 6/7 측정치로만. ⑤ **MCPB `MANIFEST.md` 전체 필드 미취득 — 필드를 열거하지 않는다.** ⑥ 계획 초안이 지목했던 `publish-server.md`는 **존재하지 않는다**(트리 전수 확인) — 인용하지 않는다. ⑦ ~~uvx/Docker/mcp-publisher 개념 수준 격하~~ **전면 해제됨**(§8-A)

### 10장. 원격으로 열기, 그리고 도구를 의심하기

- **핵심 질문:** 서버를 인터넷에 열면 무엇이 공격면이 되고, 내가 쓰는 도구 자체는 얼마나 믿을 수 있나?
- **주요 내용:**
  - **러닝 예제 명세를 따른다** — 로컬 stdio `team-wiki`를 Streamable HTTP로 여는 시나리오
  - **세션과 상태** — `Mcp-Session-Id` 기반 세션(`2025-11-25`까지). `2026-07-28` RC에서 제거되고 "서버가 발급한 핸들을 일반 도구 인자로" 방식으로 바뀐다는 사실은 **여기서 한 줄만 예고하고 상세는 12장**
  - **Origin·Host 검증과 DNS rebinding 방어** — 잘못된 Origin에 **HTTP 403**. **⚠️ 버전 계열을 못 박는다**(리뷰 M-3): `validateHostHeader`·`validateOriginHeader`는 **2.0 계열에서 확인된 API**다(2.0.0-beta.5 / 2026-07-21 관측 기준). **1.x로 만들었다면 Host·Origin 검증은 트랜스포트 앞단에서 직접 해야 한다** — 3장의 결정(v1 라인)을 따라온 독자가 존재하지 않는 API를 찾지 않게 한다
  - **OAuth 진화와 그 대가** — OIDC Discovery·incremental scope consent·Client ID Metadata Documents. 그리고 실제로 터진 실패들: OAuth 요구 서버가 CLI 전체를 얼림, 빈 User-Agent로 WAF 403, 스코프 미지정 시 전체 카탈로그 요청으로 자체 호스팅 IdP에서 `invalid_scope`(**자체 호스팅 IdP를 쓰는 국내 기업 환경에 특히 관련**). **실패 사례는 4건 중 2~3건만 본문에 풀고 나머지는 표로 압축한다**
  - **🆕 그리고 당신의 도구 자체가 공격 경로였다**(8장에서 이관) — MCP Inspector **CVE-2025-49596**(CVSS 9.4): 클라이언트-프록시 간 인증 부재 + 브라우저 취약점 체이닝으로 **악성 사이트 방문만으로 개발자 워크스테이션 RCE**. "로컬 개발 도구니까 안전하다"는 가정이 깨진 사례. 함께: `claude mcp list`가 시크릿을 터미널에 출력하던 시절(**v2.1.161**에서 수정 — 출력을 이슈·슬랙에 붙여넣으면 토큰이 샜다), 커밋된 `.mcp.json` 자기승인 차단(**v2.1.196**), `headersHelper` 셸 인젝션 수정(**v2.1.207**). **각 항목의 버전 귀속을 분리해 쓴다**
  - 이 장의 논지: **7장이 "내가 만드는 도구를 남이 믿을 수 있게"였다면, 이 장은 "내가 쓰는 도구를 내가 얼마나 믿을 것인가"다**
- **독자가 얻는 것:** 원격 노출 전 점검 목록, 그리고 툴체인을 신뢰 경계 안에 두지 않는 습관
- **오프닝 기법:** 충격적 수치·사실 — "CVSS 9.4. 취약했던 건 당신이 만든 서버가 아니라, 당신이 디버깅에 쓰던 도구였다."
- **클로징:** 한 문장 여운 — 여기까지가 "서버를 만들고 지키는" 이야기다
- **다이어그램:** 없음 (배정 표 기준 — 이 장에는 그림을 두지 않는다. OAuth 흐름은 산문+표로 처리)

### 11장. 방향을 뒤집다 — MCP 서버가 코딩 에이전트를 부를 때

- **핵심 질문:** 서버가 거꾸로 Claude Code나 Codex를 호출하게 만들 수 있나? 만들 수 있다면, 만들어도 되나?
- **주요 내용:**
  - **먼저 두 패턴을 분리한다** — 패턴 A: 에이전트를 MCP 서버로 *노출*(`claude mcp serve`, `codex mcp-server`) / 패턴 B: MCP 서버가 에이전트를 *호출*(`claude -p`, `codex exec`). 이 장의 주제는 B다
  - **정직한 포지셔닝이 이 장의 핵심이다** — 이건 떠오르는 베스트 프랙티스가 **아니다.** 확인된 구현체는 3개뿐이고, 1,313⭐를 받은 대표 리포는 **아카이브**됐으며, 2위는 14개월 방치됐다. 활발한 건 16⭐ 신생 프로젝트 하나다. 여러 검색 쿼리가 모두 빈 결과를 냈다 — **이건 실패가 아니라 결과다**
  - **문서화된 함정** (번호는 `01_reference.md` §3-7의 함정 번호를 그대로 따른다 — 자체 번호를 새로 매기지 않는다)**:** **#1** 샌드박스가 상속되지 않는다(진입 조건이 `--dangerously-skip-permissions`를 요구하고, `workspace` 인자는 시작 컨텍스트일 뿐 보안 경계가 아니다. 예외적으로 `codex exec`의 `sandbox` 플래그는 실제 강제되는 경계다) **#2** **시간 스케일이 다르다** — ⚠️ **귀속을 낮춘다**(리뷰 m-7): `CLAUDE_CLI_TIMEOUT_SECONDS` 3,600초는 **출처 리포가 특정되지 않았다.** 저술 전 특정되지 않으면 **"일부 래퍼 구현의 기본값이 3,600초였다"** 수준으로 쓰고 업계 규범처럼 서술하지 않는다 **#3** **에이전트마다 답을 돌려주는 방식이 다르다** — 서버가 에이전트의 출력 규약에 인질로 잡힌다(stdout / `transcript.jsonl` 스크래핑 / `--output-last-message` 파일) **#4** 병렬 실행 시 `HOME` 상태 경합 **#5** 헤드리스에서 MCP 실패가 무신호 — *"zero signal in stderr or the stream-json output"*, 오케스트레이터는 도구 개수를 세는 것 말고 탐지 방법이 없다 **#7** 함대가 커지면 헤드리스 호출이 행(전체 11개 서버 → 68초 초과, `--strict-mcp-config`로 1개만 → 약 5초). **§3-7의 #6(재개 후 MCP가 죽은 채 "살아 있는 척")은 8장에서 이미 다뤘으므로 여기서는 한 문장 참조로 처리한다 — 번호를 재사용하지 않는다**
  - **반직관적 발견** — 비용 폭발·무한 재귀 사고 보고는 하나도 없다. 오히려 이 패턴의 명시적 동기가 **비용 절감(쿼터 차익거래)**이다. 먼저 터지는 건 비용이 아니라 **권한과 상태**다
  - 그럼에도 시도한다면: 타임아웃 분리, 출력 규약 어댑터, `HOME` 격리, 실패 탐지를 도구 개수로 하는 방어적 설계
- **독자가 얻는 것:** 이 패턴을 시도할지 말지에 대한 판단, 그리고 시도할 경우의 알려진 지뢰 지도. 한국어로는 사실상 처음 정리되는 내용
- **오프닝 기법:** 인용·일화 — README의 경고문에서 출발: *"This runs unsandboxed code with your privileges … with no usable approval gate."*
- **클로징:** 질문 남기기 — 생태계가 이렇게 흔들리는데 지금 배운 것은 얼마나 갈까
- **원문 인용 상한:** 5개 이내(리뷰 N-3)
- **다이어그램:** 그림 1 — 패턴 A/B 방향 대조도
- **예상 분량:** 4,500자
- **레퍼런스 한계:** 커뮤니티 근거가 리포지토리 3개와 GitHub 이슈에 한정된다. **"실무에서는 이렇게 한다"는 일반화를 쓰지 않는다.** 3,600초 귀속은 위 ② 규율을 따른다

### 12장. 2026-07-28과 그 이후 — 이 지식은 언제 낡는가

- **핵심 질문:** `initialize`를 없애는 리비전이 코앞이다. 앞의 열한 장에서 배운 것은 얼마나 오래 유효한가?
- **주요 내용:**
  - **`2026-07-28` RC가 바꾸는 것** — 프로토콜 레벨 세션 제거(`Mcp-Session-Id` 삭제, 교차 호출 상태는 서버가 발급한 핸들을 **일반 도구 인자**로), **`initialize`/`notifications/initialized` 제거**하고 모든 요청이 `_meta`에 프로토콜 버전·capability를 싣는 무상태 설계, **`server/discover`**(서버 MUST·클라이언트 MAY), `subscriptions/listen`, `ping`·`logging/setLevel` 제거, tasks를 코어 밖 공식 확장으로 이관, **MRTR**로 서버 개시 요청 대체(`InputRequiredResult` → 클라이언트가 원 요청을 재시도), 모든 결과에 `resultType` 필수, SSE 재개·재전달 제거
  - **무엇을 배우지 말아야 하는가** — **Roots·Sampling·Logging 기능 자체가 deprecated**되고 공식 대체가 제시됐다(Roots → 도구 파라미터·리소스 URI, Sampling → **LLM 공급자 API 직접 연동**, Logging → stderr 또는 OpenTelemetry). OAuth DCR도 deprecated → Client ID Metadata Documents
  - **스펙이 스스로를 부정한 사건** — `2025-11-25`가 sampling에 도구 호출을 *추가*했는데, 한 리비전 뒤 RC가 sampling 자체를 폐기했다. 관점 A(구현 클라이언트가 적고 보안·비용 귀속이 모호했으니 정리가 맞다) vs 관점 B(한 리비전 만의 진동이 채택을 늦춘다)
  - 앞 장들과 이어지는 조각들: 분산 추적이 프로토콜에 들어왔다(`_meta`의 `traceparent`·`tracestate`·`baggage` — 8장 회수), `CacheableResult`의 `ttlMs`·`cacheScope`, 결정적 `tools/list` 순서, 새 에러코드 대역(`-32020~-32099` 스펙 예약)
  - **왜 앞의 열한 장이 낡지 않는가** — RC 릴리스 노트 원문: *"SDKs will adopt this version at their own pace, and the prior version of the spec may remain in use for an undetermined amount of time."* 그리고 **최소 12개월 deprecation 창**을 정책화한 feature lifecycle(Active/Deprecated/Removed 3상태). Java SDK 2.0·Spring AI 2.0이 GA면서 `2025-11-25`를 따르는 것이 그 증거다
  - **학습 타이밍 딜레마에 대한 답** — v1으로 배워라 vs v2로 배워라. 결론은 "둘 중 하나"가 아니라 **네 개의 축을 분리해 읽는 습관**이다. 이 책이 처음부터 끝까지 요구한 그것
  - **닫는 매듭** — 우리는 "MCP 2.0은 없다"로 시작해 열두 장을 지나왔다. 독자가 가져갈 것: 만들 줄 아는 손, 침묵을 의심하는 눈, 그리고 언제 쓰지 말아야 할지 아는 판단. MCP는 에이전트 프로토콜 스택의 **첫 단계**이지 전부가 아니다 — "MCP냐 A2A냐"는 애초에 잘못된 질문이다. (여기서 §3-5의 SDK 티어링(SEP-1730)을 한 문단으로 붙여 "내 언어 SDK의 공식 지원 등급을 어떻게 확인하나"에 답하고 다음 걸음으로 넘긴다)
- **독자가 얻는 것:** 다음 리비전이 정식화돼도 자기 지식의 유효 범위를 스스로 계산할 수 있는 능력. 그리고 책 전체의 회고
- **오프닝 기법:** 앞 장 콜백 — "1장에서 우리는 'MCP 2.0 스펙은 없다'로 출발했다. 그런데 스펙 자체를 갈아엎는 리비전은 실재한다."
- **클로징:** **회고형(닫는 매듭)** — 이 책에서 유일하게 회고형 클로징을 쓰는 장
- **다이어그램:** 그림 1 — `initialize` 있는 흐름 vs `_meta` 무상태 흐름 대조
- **예상 분량:** 5,000자
- **레퍼런스 한계:** **`server/discover` RPC 상세 시그니처와 `_meta` 봉투 전체 필드 목록은 미확인이다**(§7-B-5) — changelog 수준까지만 서술하고 **예제 코드를 지어내지 않는다.** 저술·팩트체크 시점에 `schema/2026-07-28/` 유무와 릴리스 `prerelease` 플래그를 **반드시 재확인**한다(체크리스트). 정식화됐다면 "RC" 서술을 전면 갱신한다
