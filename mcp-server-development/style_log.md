# 라운드 1 — 12개 초안 전수 검수 (2026-07-26)

## 총평

**판정 요약: 통과 5 / 수정 필요 7**

- **통과(5):** 1·7·9·10·12장 — Major 없음, Minor만
- **수정 필요(7):** 2·3·4·5·6·8·11장 — Major 1건 이상

먼저 분명히 해둘 것이 있다. **계획의 배정 표는 12장 전부가 지켰다.** 오프닝 기법 12/12, 클로징 형태 12/12, `### 이 장의 핵심` 박스 배정(1·2·7·8장에만) 4/4, 다이어그램 배정 8개 그림 전부가 계획과 일치한다. 그림 번호도 챕터마다 1부터 다시 매겨져 있고, 계획이 "그림 없음"으로 지정한 3·5·6·7·10장에는 실제로 mermaid 블록이 하나도 없다. **배정 위반은 0건이다.** 병렬 저술에서 이 정도로 배정이 지켜지는 경우는 드물다.

문체 자체도 안정적이다. 청유형은 과포화 없이 자연스럽고(장당 5~18회, 리듬에 맞게 분포), 공감 표현은 총 19회로 장당 1~2회 밴드 안에 정확히 들어와 있으며, "기억해두자"는 책 전체 6회로 오히려 절제됐다. `그렇다면`(3회)·`물론`(4회) 같은 논리 전환구도 과다 반복이 없다. 불릿 남용도 없다 — 장당 0~8줄로, 산문이 리스트에 잡아먹힌 구간이 없다. 강압 표현("반드시 ~해야 한다")은 10건 검출됐으나 전부 SDK 제약이나 스펙 사실을 기술하는 문장이고 독자를 향한 명령이 아니다. 통과 처리했다.

그래서 이번 라운드의 지적은 **문장 단위가 아니라 형태 단위**에 몰려 있다. 세 가지다 — ① 굵게가 소제목 노릇을 하는 문단 연쇄, ② 계획이 4장에만 배정한 "질문으로 닫기"가 8장으로 번진 것, ③ 수평선(`---`) 표기가 5장에만 있는 표기 흔들림. ①과 ②는 개별 장을 아무리 들여다봐도 안 보이고 12장을 나란히 놓아야 보이는 종류다.

## 01장. "MCP 2.0"은 없다

**판정: 통과**

계획 배정(정의 뒤집기 / 질문 남기기 / 핵심 박스 있음 / 그림 1) 전부 준수. 인용 상한 4명(bb88·0x696C6961·ejholmes·kaydash)도 정확히 지켰다. "숫자가 크다고 최신이 아니다"라는 좌표계 선언이 책 전체의 축으로 잘 서 있다.

### Minor

1. **클로징이 배정된 "질문 남기기"보다 한 발 물러서 있다.**
   > [원문 123~125] "…결국 '그래서 내 경우엔 만들 만한가'로 돌아오게 된다. // 그건 읽어서 알 수 있는 게 아니다. 만들어봐야 안다. 하나 만들어보고 나서 다시 이 질문으로 돌아오자."

   질문이 **인용부호 안에 갇혀** 있고 마지막 문장은 청유형 서술이다. 계획의 의도는 독자에게 질문을 남긴 채 끝내는 것이었다.
   > [제안] "…결국 하나로 돌아오게 된다. **그래서, 내 경우엔 만들 만한가?** // 그건 읽어서 알 수 있는 게 아니다. 만들어봐야 안다."

   **이유:** 마지막 문장을 질문 뒤로 빼면 "돌아오자"는 지시 없이도 독자가 스스로 다음 장으로 넘어간다. 통권 변주 점검 ②와도 연결된다 — 이 장은 배정상 질문으로 닫아도 되는 4장 중 하나이므로, 여기서만큼은 질문을 선명하게 남기는 편이 낫다.

2. **긴 문장 12개(120자 초과).** 특히 69행 "2026-07-26 관측 시점에 TS `2.0.0-beta.5` 패키지의 런타임 번들을 풀어 상수를 읽어보면 `SUPPORTED_PROTOCOL_VERSIONS` 목록에 `2026-07-28`이 들어 있지 않았다." 는 관측 절차와 결과가 한 문장에 묶여 있다.
   > [제안] "…런타임 번들을 풀어 상수를 읽어봤다. `SUPPORTED_PROTOCOL_VERSIONS` 목록에 `2026-07-28`은 **없었다.**"

   **이유:** 관측 행위와 관측 결과를 끊으면 결과가 강조된다. 굵게를 하나 줄이는 효과도 있다.

3. **오프닝 반전이 접속사에 기대고 있다.** "…나온다. **그런데** 그런 스펙은 존재하지 않는다." 통권 변주 점검 ④ 참조 — 이 장은 첫 장이라 우선순위가 낮지만, 아래 8·10장 모델을 참고할 자리다.

## 02장. 프로토콜 해부

**판정: 수정 필요**

배정(수사적 질문 / 한 문장 여운 / 핵심 박스 / 그림 2개) 전부 준수. 버전 협상 시퀀스 다이어그램에 fallback 분기가 계획대로 들어가 있고, 프리미티브 표와 트랜스포트 표가 산문을 대신하는 자리도 정확하다.

### Major

1. **같은 사실이 한 문단에서 여러 번 강조되고, 138행은 다섯 항목을 동시에 굵게 처리해 바로 뒤 문장을 배신한다.** 굵게 자체가 많은 게 문제는 아니다 — `**Host**`·`**Client**`·`**Server**`·`**프리미티브**` 같은 **용어 도입 굵게는 정당하니 그대로 두자.** 문제는 그 위에 얹힌 문장 전체 강조이고, 그게 이 장에서 강조를 무력화한다. (참고 수치: 1,154어절에 38개로 12장 중 최고밀도. 다만 판정 근거는 아래 두 구절의 구조다.)
   > [원문 13] "**전송 형식은 JSON-RPC 2.0이고, 표준화한 것은 도구 호출과 타입 있는 데이터 교환이다.**"
   > [원문 138] "**stdio 서버의 stderr 로깅 허용**, **JSON Schema 2020-12를 기본 dialect로 채택**, **잘못된 `Origin` 헤더에 HTTP 403 응답**, **SDK 티어링 시스템** 도입, 그리고 **입력 검증 오류의 처리 방식 변경**이다."

   > [제안] 13행은 굵게를 해제한다(바로 앞 인용문이 이미 그 내용을 실어 나른다). 138행은 다섯 개 굵게를 전부 풀고 마지막 하나만 남긴다 — "…stdio 서버의 stderr 로깅 허용, JSON Schema 2020-12 기본 dialect 채택, 잘못된 `Origin` 헤더에 HTTP 403 응답, SDK 티어링 시스템 도입, 그리고 **입력 검증 오류의 처리 방식 변경**이다."

   **이유:** 138행은 다섯 항목을 나란히 굵게 처리해 셋째 문단("마지막 하나가 특히 중요하다")의 강조가 죽었다. 다섯이 다 굵으면 그중 하나만 중요하다는 다음 문장이 배신당한다. 이 장에서 6~8개를 해제하면 남은 굵게가 살아난다.

### Minor

2. **수사적 질문 9회 — 12장 중 최다이고 일부는 장식적이다.**
   > [원문 47] "서버 개발자가 하는 일은 결국 이 몇 개의 요청에 응답 핸들러를 붙이는 것이다. 생각보다 단출하지 않은가?"

   > [제안] "…응답 핸들러를 붙이는 것이다. 생각보다 단출하다."

   **이유:** 이 질문은 논리를 전환하지 않고 방금 한 말에 동의를 구할 뿐이다. 같은 장의 104행 "아찔하지 않은가?"는 `"zzz" > "2025-11-25"`라는 구체적 위험 뒤에 붙어 제 역할을 하므로 **그건 살리자.** 하나를 지워야 다른 하나가 산다.

3. **오프닝이 배정(수사적 질문)보다 '실패 장면'에 가깝다.** 3~5행은 "띄웠다 → 로그를 봤다 → 버그일까?"라는 장면 서술이고, 4장·8장의 실패 장면 오프닝과 형태가 겹친다. 질문을 앞으로 당기면 배정에 더 맞는다.
   > [제안] 첫 문장을 "**왜 내 서버는 최신 SDK를 쓰는데 `2025-03-26`으로 붙을까?**"로 열고, 로그 정황을 그 뒤에 붙인다.

4. **`---` 수평선(150행)이 클로징 앞에 있다.** 통권 점검 ③ 참조 — 12장 중 5장에만 있다.

## 03장. 첫 서버 — TypeScript

**판정: 수정 필요**

배정(상황 가정 / 적용 과제 / 박스 없음 / 그림 없음) 준수. 계획의 경계 명시도 잘 지켰다 — `bin` 키는 "맞춰둔다"만 언급하고 이유는 9장으로 넘겼고, `createSdkMcpServer`는 건드리지 않았다. 코드 밀도가 높은 장인데 산문이 코드 사이에서 끊기지 않는다.

### Major

1. **굵게 리드인 문단이 8개 — 코드 설명 구간이 사실상 불릿 목록이다.**
   > [원문 43~45] "**`\"type\": \"module\"`** — SDK가 ESM 전제로 만들어졌다. …
   > **`bin` 키를 패키지 이름과 똑같이 맞췄다.** 지금은 그냥 실행 파일 등록으로 보이겠지만…"
   > [원문 204~210] "**패키지가 쪼개졌다.** … **스키마 라이브러리 정책이 바뀌었다.** … **새 진입점과 트랜스포트가 생겼다.** … **그리고 관측된 사실 하나.**"

   204~210행은 **네 문단이 연속으로 굵은 문장으로 시작한다.** 형태만 산문이지 읽는 눈에는 불릿 네 개다.
   > [제안] 첫 항목만 굵게로 남기고 나머지 셋은 평문 도입으로 바꾼다 — "패키지가 쪼개졌다. …" / "스키마 라이브러리 정책도 달라졌다. …" / "새 진입점과 트랜스포트가 생겼다. …" / "마지막으로 관측된 사실 하나를 덧붙인다. …" 첫 항목의 굵게가 절 전체의 신호 역할을 하고, 뒤 셋은 그 리듬을 타고 흐른다.

   **이유:** 같은 형태가 네 번 반복되면 독자는 문단을 읽지 않고 굵은 부분만 훑는다. 이 절은 v1 사용자가 v2를 판단하는 근거를 주는 자리라 정작 읽혀야 할 곳이다. 43~45행도 같은 처리를 권한다(둘 중 하나만 굵게).

### Minor

2. **클로징이 배정된 "적용 과제"인데 질문으로 한 번 더 닫힌다.**
   > [원문 229~231] "**`wiki_list_spaces`라는 도구를 하나 더 붙여보자.** … // 붙여봤다면 하나 더 생각해보자. 이렇게 계속 도구를 늘려도 괜찮을까? 이 질문은 7장에서 다시 만나게 된다."

   > [제안] 마지막 문단을 "붙여봤다면 도구가 셋이 된다. 넷, 다섯으로 늘리면 어떻게 될지는 7장에서 다시 만난다."로 바꾼다.

   **이유:** 적용 과제로 배정된 장이 질문으로 착지하면서 클로징 형태가 흐려졌다. 통권 점검 ②의 핵심 사례다 — 계획이 질문 클로징을 4장에만 배정한 이유가 여기 있다. 과제는 과제로 끝내는 편이 낫다.

3. **"반드시"가 독자 대상 명령으로 읽힐 여지.**
   > [원문 101] "`outputSchema`를 선언하면 **`structuredContent`를 반드시 함께 돌려줘야 한다.**"
   > [제안] "`outputSchema`를 선언했다면 `structuredContent`도 함께 돌려줘야 한다. 빠뜨리면 SDK가 검증 단계에서 오류를 던진다."

   **이유:** SDK 제약이라 사실 자체는 맞다. 다만 뒷문장이 이미 근거를 대주므로 "반드시"는 잉여이고, voice.md §5가 피하라고 한 어형이다.

4. **`---` 수평선(225행)** — 통권 점검 ③.

## 04장. 클라이언트에 붙이기

**판정: 수정 필요**

배정(실패 장면 / 다음 장 예고형 허용 / 박스 없음 / 그림 1) 준수. 계획이 지명한 감량 5건도 전부 이행됐다 — Desktop 트러블슈팅은 8장으로 넘겼고("붙지 않을 때는 8장으로 가면 된다"), 스코프 저장 위치와 읽지 않는 경로는 표 하나로 통합했고, 파편화 사례는 2건+1문장으로 줄였고, `.mcpb` 예고는 3문장, Agent SDK는 트레이드오프까지만 썼다. 밀도 통제가 계획대로 됐다.

### Major

1. **굵게 43개 — 12장 중 절대 개수 최다(어절 32개당 1개).** 특히 49행 한 문단에 굵게가 셋이다.
   > [원문 49] "**필드는 스코프를 넘어 병합되지 않는다.** … 이때 user 쪽 환경변수가 함께 적용될까? 안 된다. **local 엔트리가 통째로 이기고**, user 쪽에 적어둔 환경변수는 통째로 사라진다."

   > [제안] "**필드는 스코프를 넘어 병합되지 않는다.** … 이때 user 쪽 환경변수가 함께 적용될까? 안 된다. local 엔트리가 통째로 이기고, user 쪽에 적어둔 환경변수는 통째로 사라진다."

   **이유:** 바로 위 인용문(*"fields are not merged across scopes"*)과 첫 굵게가 이미 같은 말을 두 번 했다. 셋째 굵게까지 붙으면 한 문단에서 같은 사실이 네 번 강조된다. 이 장 전체에서 10개쯤 해제하면 "**읽지 않는다**"(58행 표)나 "**stdio는 자동으로 재연결하지 않는다**"(101행) 같은 진짜 함정이 도드라진다.

2. **굵게 리드인 문단 7개 — Desktop 절과 Agent SDK 절이 특히 심하다.**
   > [원문 143~147] "**외부 프로세스 셋** — stdio·SSE·HTTP. 지금까지 본 것과 같은 방식이다. // **그리고 인프로세스 하나.** `createSdkMcpServer`(…)로 도구를 정의하면 **별도 프로세스를 띄우지 않고 같은 프로세스 안에서** MCP 서버가 동작한다."

   > [제안] "받을 수 있는 형태는 넷이다. 셋은 지금까지 본 것과 같다 — stdio·SSE·HTTP. 나머지 하나가 다르다. `createSdkMcpServer`(Python은 `create_sdk_mcp_server`)로 도구를 정의하면 **별도 프로세스 없이 같은 프로세스 안에서** MCP 서버가 동작한다."

### Minor

## ① 굵은 리드인 문단 — 불릿을 산문으로 위장한 형태 (Major)

`**굵은 문장.** 설명…` 형태로 시작하는 문단이 8장 10개, 3장 8개, 4장 7개, 11장 6개, 12장 5개다. 반면 5·6·9장은 0개다. **같은 책 안에서 같은 정보를 어떤 장은 산문으로, 어떤 장은 위장 불릿으로 처리하고 있다.**

특히 **연속 3회 이상**은 독자가 문단을 읽지 않고 굵은 부분만 훑게 만든다 — 이 책이 명시적으로 피하려 한 AI-slop 패턴이다.

각 장은 자기 행을 통과한다. 그런데 **책을 이어 읽으면 여덟 번 연속으로 질문을 받는다.** 계획이 클로징 배정 표를 만든 목적이 정확히 이것을 막는 것이었다("프로필이 경고하는 실패 모드 — 모든 장이 같은 공식으로 닫히는 것 — 를 병렬 저술에서 막기 위해 미리 배정한다").

**재작성 타깃 — 두 장만 고치면 배정대로 돌아온다:**

## ③ 수평선(`---`) 표기 흔들림 (Minor, 그러나 전권 일괄 결정 사항)

클로징 앞에 `---`를 넣은 장이 **1·2·3·4·11장 다섯**, 넣지 않은 장이 **5·6·7·8·9·10·12장 일곱**이다. EPUB에서는 이게 실제 가로선으로 렌더되므로, 어떤 장은 마무리 앞에 선이 그이고 어떤 장은 안 그인다. 독자가 규칙을 찾다 실패하는 종류의 불일치다.

연동된 사항 하나 — `### 이 장의 핵심` 박스는 **헤딩 표기가 네 장 모두 정확히 통일됐다(✅).** 다만 1·2장은 박스와 클로징 사이에 `---`가 있고 7·8장은 없다. 같은 장치가 장마다 다르게 보인다.

**제안: 전권에서 `---`를 빼거나, 전권에서 넣거나 하나로 통일한다.** 편집자 판단이 필요하면 빼는 쪽을 권한다 — 7·8·9·10·12장이 수평선 없이도 클로징 전환이 자연스럽고, 5·6장처럼 소절 흐름 그대로 마무리로 미끄러지는 형태가 이 책 산문의 기본 리듬이기 때문이다.

부수 관찰: **핵심 박스 넷이 모두 정확히 5불릿이다.** 3~5 밴드의 상한이고 네 장이 기계적으로 같다. 규정 위반은 아니지만, 1장이나 2장을 4불릿으로 줄이면 "정해진 개수를 채웠다"는 인상이 옅어진다. 강제하지 않는다.

#### S-5. 책의 마지막 30행에 "셋" 열거가 세 번 — 에필로그 것만 조정한다

[제안]
> 이어서 할 만한 것을 남긴다.
