## 책 특성

- **장르:** tech-book (Toby 문체, 신선도·사실 규율 강하게 작동)
- **분량:** 본문 14장 합계 약 89,000자(순수 산문 기준), 부록 산문 약 3,000자(템플릿 코드 블록은 제외), 머리말·맺음말은 편집 단계에서 별도. 전체 약 92,000자
- **난이도:** 중급~중상급. 에이전틱 코딩 입문은 다루지 않는다. 도메인 모델링·API 설계·CI를 실무에서 다뤄 본 독자를 전제로 한다
- **대상 독자:** Claude Code·Codex로 매일 코딩하고, Hermes Agent·OpenAI dots 같은 상시 자동화 에이전트를 쓰거나 검토 중인 한국 개발자
- **독자 여정:**
  - **진입 상태:** 에이전트로 빠르게 만들고 있다. 그런데 "테스트 다 통과"라는 보고를 믿어도 되는지, CLAUDE.md·AGENTS.md에 무엇을 얼마나 써야 하는지, Spec Kit 같은 도구는 왜 이렇게 무거운지 찜찜하다. 문서를 쓰긴 하지만 "작업 방식" 문서(커밋 규칙·코딩 규칙)에 머물러 있다 (레퍼런스 §05 한국 커뮤니티 관찰).
  - **출구 상태:** 기능 하나를 brief → 도메인 규칙 → 계약 → 수용 기준 → 수직 기능 → 테스트 → 검증 증거까지 추적 ID로 잇는 최소 문서 세트를 직접 만들 수 있다. 위험에 따라 Design Ready를 판정하고, 문서 규칙을 훅·CI·PR에 연결하고, 에이전트에게 역할과 결정 한계를 담은 입력 꾸러미를 건넬 수 있다. 상시 에이전트에게 맡길 일(드리프트 점검·증거 수집)과 맡기면 안 될 일(정책 결정·위험 수용)을 가를 수 있다.
- **관통 예제:** 원전의 가상 기능 **"예약 셀프 취소"(CAN)**. 4장부터 9장까지 한 단계씩 쌓고, 10~13장은 같은 산출물을 통제·역할·결정·자동화 관점에서 다시 쓴다. 14장에서 전체 사슬을 회수한다.

## 내러티브 아크

책은 네 개의 움직임으로 흐른다.

**1부 "왜 지금, 어떤 문서인가"(1~3장)**는 각성 구간이다. 1장은 개발자가 2026년에 실제로 AI로 어떻게 일하는지(설문·생산성 연구의 충돌)에서 출발해, 에이전트가 "가진 것을 증폭"한다면 증폭될 대상, 즉 합의·검증·변경 제어를 하는 문서가 더 중요해진다는 논지를 세운다. 독자는 이미 스펙 주도 개발(SDD) 도구를 써 봤거나 그 비판을 들었을 것이다. 그래서 2장에서 "마크다운 속의 워터폴" 논쟁을 양쪽 모두 공정하게 펼치고, 이 책의 입장(위험 크기에 맞춘 문서, 의식이 아니라 결정과 증거의 연결)을 일찍 못 박는다. 3장은 원전의 "원본 하나" 원칙을 Claude Code·Codex·Hermes가 지시 파일을 실제로 읽는 규칙 위에 올린다. 문서가 "설명"이 아니라 에이전트에게는 "지시"라는 사실이 여기서 드러난다.

**2부 "기능 하나를 약속으로 바꾼다"(4~7장)**는 배움 구간이다. 4장에서 CAN 요청이 도착하고, 원전의 여섯 번의 합의를 지도로 펼친 뒤 첫 합의인 짧은 제품 합의서(brief)와 관찰 가능한 비기능 요구를 쓴다. 5장은 화면보다 먼저 상태·불변식·권한·경합을 도메인 원본에 쓴다. 6장은 API·이벤트·UX 계약을 "실패의 의미"까지 쓰고 추적 ID를 연결한다. 7장은 "테스트 다 통과"의 허점에서 출발해 수용 기준을 정상 하나와 실패 넷으로 쓴다.

**3부 "착수하고, 끝까지 잇고, 통제한다"(8~10장)**는 적용 구간이다. 8장은 Design Ready를 위험으로 판정하고, AI 리뷰가 왜 독립 검증이 아닌지를 연구로 설명한다. 9장은 CAN을 수직 기능 하나로 잘라 에이전트에게 넘기고, 테스트와 검증 기록(VAL)까지 8단계 추적 사슬을 완성한다. 10장은 그 사슬을 PR·CI·출시 통제 지점에 묶고, "강조를 더해도 안 지켜지는 규칙은 훅으로"라는 결정적 통제의 원리를 다룬다.

**4부 "사람의 결정, 기계의 일"(11~14장)**은 종합 구간이다. 11장은 AI 역할을 에이전트 수가 아니라 결정 한계로 나누고, 사람이 소유할 결정을 공학적 필요로 설명한다. 12장은 결정의 계보(ADR)와 문서의 유통기한(메타데이터·드리프트)을 다룬다. 13장은 12장이 남긴 질문, 즉 "이 점검을 누가 매주 하나"에 답하는 장으로, Hermes·dots를 상시 점검자로 쓰는 패턴을 **저자 제안으로 명시해** 내놓는다. 14장은 작은 프로젝트와 중간 규모 프로젝트의 도입 경로, 30분 빠른 시작, 흔한 실패를 정리하고 CAN의 전체 사슬을 회수하며 닫는다.

이 순서인 이유: 원전의 권장 읽는 순서(처음 시작 01→04, 설계 리뷰 05→07, 개발 운영 08→10, 바로 적용 11→14)를 큰 틀에서 유지하면서, 독자가 이미 매일 쓰는 도구의 언어(1~3장)로 먼저 문을 연다. CAN이 4장부터 단계마다 한 산출물씩 늘어나므로, 독자는 "기능 하나가 끝까지 가는 모습"을 장을 넘기며 본다.

## 설계 근거

**채택한 구조:** 원전 14절의 흐름을 척추로 두고, 그 위에 관통 예제 CAN과 독자 도구 스택을 얹은 4부 14장 구성.

1. **관통 예제가 원전의 핵심을 증명한다.** 원전의 고유한 주장은 "문서 유형"이 아니라 "연결"(REQ → POL → API → UX → AC → SLICE → TC → VAL)이다. 연결은 한 기능이 끝까지 가는 모습을 보여 줄 때만 설득된다. 원전의 CAN은 금전·권한·동시성·외부 연동·결과 불명확(타임아웃)을 모두 품고 있어 위험 기반 판단을 보여 주기에도 알맞다. (운영자 지정 결정 — 레퍼런스가 반대할 근거 없음. 커뮤니티 리서처도 "수직 기능은 커뮤니티 담론에 거의 없는 책의 차별점"으로 관찰했다, 레퍼런스 §03 긴장.)
2. **원전의 순서를 존중하되 독자의 진입점에서 시작한다.** 독자는 SDD 도구와 지시 파일 문제를 이미 겪고 있다. 1~3장에서 그 경험을 먼저 다루고, 2장에서 SDD 논쟁에 대한 이 책의 입장을 세워야 이후 장들이 "또 하나의 의식(ceremony)"으로 읽히지 않는다.
3. **증거는 규칙을 설명할 때만 쓴다.** 연구(컨텍스트 파일·SWE-bench 테스트 약점·자기 교정 한계·상관된 오류·자동화 편향)는 원전의 특정 규칙을 설명하는 장에 배치한다. 연구를 모은 장은 두지 않는다. 다수가 프리프린트라서, 규칙 옆에 놓아야 hedge가 자연스럽고 독자가 "연구가 규칙을 대신한다"고 오해하지 않는다.

**운영자 지정 결정의 반영:** CAN 관통 예제 유지(채택), 12~14장 + 부록(14장 채택), 개발자의 실제 AI 사용 방식으로 시작(1장), SDD 논쟁 공정 제시 후 위험 크기 포지셔닝(2장), 연구 증거는 규칙 설명용·프리프린트 hedge(전 장 + 아래 저술 규율). 레퍼런스가 이 결정들에 강하게 반대하는 지점은 없었다.

**기각한 대안 1: 원전 14절을 1:1로 14장에 옮기기.** 가장 단순하고 원전과의 대응도 명확하다. 기각 사유: 원전 §06은 CAN 전체를 한 절에 몰아넣은 예제여서, 1:1로 옮기면 한 장이 비대해지고 나머지 장은 CAN 없이 추상적으로 흐른다(운영자가 원한 "단계별로 쌓이는 관통 예제"와 정면 충돌). 또 §12(메타데이터)·§13(체크리스트)은 성격상 장보다 부록에 가깝다. 장 분량이 2,000~10,000자로 크게 출렁인다.

**기각한 대안 2: 도구별 구성(Claude Code 편 / Codex 편 / Hermes·dots 편).** 독자 스택에 가장 직접 맞닿고 목차만 봐도 실용적이다. 기각 사유: (a) 2026-10 기준 Claude Code 2.1.312, Codex CLI 0.165.0처럼 버전이 몇 주 단위로 바뀌어 책의 수명이 짧아진다(레퍼런스 §0 주의). (b) 독자는 Claude Code와 Codex를 같은 저장소에서 함께 쓰므로, 도구별 장은 같은 원칙을 두 번 쓰게 된다. (c) 원전의 원칙은 도구 중립이다. 도구는 "이 문서를 어디에 두면 에이전트가 읽는가"라는 질문에 답하는 층으로 각 장에 녹이는 편이 낫다.

**기각한 대안 3: 문서 유형별 카탈로그(brief 장, spec 장, domain 장, ADR 장, plan 장, validation 장).** 템플릿 책으로는 찾아보기 쉽다. 기각 사유: 원전이 가장 강조하는 "원본 하나 + ID·링크로 연결"이 장 경계에서 끊긴다. 2장에서 다룰 SDD 비판("문서가 많고 서로 반복된다", Böckeler)을 이 책 스스로 재현하게 된다. 템플릿은 부록으로 충분하다.

**기각한 대안 4: 연구 증거를 앞에 모으는 구성(1~4장 실증 연구·논쟁, 5장부터 실천).** 근거의 무게를 보여 주기에는 좋다. 기각 사유: 독자는 실천가다. 레퍼런스 §9가 경고하듯 2026년 컨텍스트 파일·SDD 연구 다수가 프리프린트이고 여러 편이 단독 저자다. 연구를 앞세우면 책의 권위가 가장 약한 근거에 기대게 된다. 연구는 규칙의 "왜"를 설명하는 자리에 둔다.

**세부 결정 두 가지:**
- **Hermes·dots는 전용 장(13장) 하나에 모으고, 3장(컨텍스트 로드 규칙)과 11장(dots Custom Rules 대조표)에 사실 범위만 짧게 둔다.** 이 두 도구를 설계 문서와 잇는 공개 실천은 아직 없다(레퍼런스 3.D ⚠). 제안을 한 장에 격리해야, 증거로 뒷받침되는 다른 장에 제안이 섞여 사실처럼 읽히는 사고를 막을 수 있다.
- **SDD 논쟁을 책 끝(종합)이 아니라 2장에 둔다.** 끝에 두면 독자가 3~12장을 "결국 또 하나의 SDD 의식"으로 의심하며 읽는다.

| product brief | **제품 합의서** (첫 등장 "제품 합의서(product brief)") | 파일명 `product-brief.md`. 본문에서 "brief" 단독 표기도 허용 |

## 공통 저술 규율 (이 책 전용)

이전 책(같은 장르)의 교훈과 레퍼런스 §7 "단정 금지 목록"(53항목)을 장 단위 작업 규칙으로 옮겼다. 저술가와 fact-checker 모두 이 절을 기준으로 삼는다.

1. **연구 결과의 방향을 뒤집지 않는다.** METR(P-1)은 완료 시간 기준으로 쓴다: "완료 시간이 19% 늘었다. 개발자는 20% 빨라졌다고 믿었다." "AI를 쓰면 19% 느려진다"로 일반화하지 않고 "2025년 초, 숙련 OSS 개발자 16명, 자기 저장소" 조건을 붙인다. 후속(2026-02 블로그)은 신뢰구간이 0을 포함하고 METR 스스로 "only very weak evidence"라고 했다는 점까지 쓴다.
2. **hedge는 해당 논문에 붙어 있어야 한다.** 레퍼런스의 `P-22`·`P-52`·`P-10`은 **여러 논문을 묶은 번호**다(P-22 = Yan·ContextCov(Sharma)·McMillan·Chakrabarti, 모두 프리프린트·단독 저자 / P-52 = Grounded Copilot·Vasconcelos·Lee·Prather·Kosmyna 등 / P-10 = Sakib·Duma·Kraishan·Haque·Sawada 등). 본문에서는 **저자명으로** 인용하고, 각 논문의 플래그(프리프린트·2차·단독 저자)를 그 논문 문장에 붙인다. 묶음 번호의 플래그를 다른 논문으로 옮기지 않는다.
3. **커뮤니티 장면을 원문 이상으로 꾸미지 않는다.** 시각·감정·대사·인물 소속을 덧붙이지 않는다. 쓸 수 있는 것은 레퍼런스(→ `research/community.md`)에 있는 문장과 사실뿐이다. 소속 주장(예: "I work on Claude Code")은 "자신을 Claude Code 개발자라고 소개한 사용자"처럼 주장으로 쓴다. 모든 커뮤니티 항목은 "의견·경험담"이지 증거가 아니다.
4. **CAN 장면은 가상임을 밝힌다.** CAN 관련 장면(요청 도착, 타임아웃, 새벽 점검 등)은 원전이 "가상 예시"로 제시한 기능이다. 실제 사건처럼 쓰지 않는다. 원전의 예시 수치(p95 ≤ 500ms, 5xx ≤ 0.5%, 10만 건, 초당 20건, 15분, 10분 경보, 첫 주 5일 일정)와 HTTP 상태 코드(404·409 등)를 **권장 기본값이나 표준으로 쓰지 않는다**(레퍼런스 §7 #51·#52).
5. **앞 장 참조는 앞 장이 실제로 쓴 범위까지만.** 아래 "장간 참조 원장"이 각 근거의 주 담당 장을 정한다. 다른 장은 그 근거를 "앞서 살펴본 ~"으로 가리킬 때 원장에 적힌 범위를 넘는 내용(수치·결론)을 덧붙이지 않는다. 더 필요하면 그 장에서 새로 인용하고 출처를 단다.
6. **저자 실측은 시점을 단다.** 저자가 직접 실행했다고 쓰는 명령·설정·관찰에는 "저자 실측(2026-10 기준)" 태그를 붙인다. 레퍼런스에 실측 기록이 없는 실행 결과는 지어내지 않는다. 설정·명령 예시는 "예시(미실행)"로 표시하거나 공식 문서 인용으로 쓴다.
7. **도구 사실은 "{버전}/2026-10 기준"으로 못 박고, 레퍼런스에 없는 경로·플래그·옵션은 만들지 않는다.** 레퍼런스에서 확인되는 것: Claude Code `CLAUDE.md`(200줄 이하 권장), `.claude/rules/` + `paths:`, `.claude/skills/`, `@path` 임포트, 자동 기억 `MEMORY.md`(첫 200줄 또는 25KB), AGENTS.md 직접 읽기 규칙, 훅(PreToolUse)·deny 규칙·관리 설정, 플랜 모드(`/plan`, `--permission-mode plan`, `defaultMode: plan` — W-B12, 검색 요약 경유라 hedge) / Codex `AGENTS.override.md` → `AGENTS.md`, 디렉터리당 1개, `project_doc_max_bytes` 기본 32 KiB, Goal·Context·Constraints·Done when, 플랜 모드, `.agents/skills/`(2차)·`.codex/hooks.json`(2차) / Hermes `.hermes.md` → `AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules` first-match, `MEMORY.md` 2,200자·`USER.md` 1,375자, 번들 스킬 `claude-code`·`codex`, cron / dots Custom Rules 4행동, Codex 클라우드 태스크 생성. 서브에이전트 정의 파일 경로처럼 레퍼런스에 없는 것은 `(사실 확인 필요)`로 남긴다.
8. **Hermes·dots 운용 패턴은 저자 제안이다.** "업계에서는 이렇게 한다"로 쓰지 않는다. 13장 본문과 3·11장 언급 모두 "공개된 실천 사례는 아직 없다(2026-10 기준). 아래는 저자의 제안이다"를 분명히 한다. dots는 출시 한 달 된 제품이고 1차 문서가 403이었다 — 교차 확인 범위(레퍼런스 3.D)를 넘지 않는다.
9. **영어 인용은 대부분 요약 모델 경유(`[요약 경유]`)다.** 직접 인용 부호로 넣을 문장은 원 URL에서 재대조할 대상으로 표시하고, 가능하면 한국어로 풀어 쓴다.
10. **AI 자기 검토를 증거로 쓰지 않는 원전의 원칙을 책 스스로도 지킨다.** "~가 확인됐다"는 표현은 실행 증거·1차 출처가 있을 때만.

### 3장. 원본은 하나, 에이전트는 링크를 따라온다

- **핵심 질문:** 같은 규칙이 여러 문서에 있을 때, 그리고 문서와 코드가 어긋날 때, 에이전트는 무엇을 따르는가?

- **주요 내용:**

  - CAN 계약: `API-CAN-01`(202 접수, 상태 조회, 재전송·키 충돌·진행 중·종료 상태·조건 위반), `EVT-CAN-01`(발행 조건, eventId·aggregateVersion·correlationId, 적어도 한 번 전달, outbox 검증, 오래된 상태 덮어쓰기 금지). "HTTP 상태 코드는 이 예제의 선택입니다"
  - 사례로 보는 멱등성: Stripe의 키 정리(24시간 이후 정리 가능, 정리 후 재사용 시 새 요청) → 원전 "키 기록 정리 후에도 이력과 업무 제약이 중복 환불을 방어"; outbox는 "정확히 한 번"을 보장하지 않는다("The Message relay might publish a message more than once"). 멱등 충돌 응답 대조표(원전 409 / IETF 초안 -07 422(-08 변경 여부 미확인) / Stripe) — 표준이 정해지지 않은 지점은 ADR 대상
  - UX 계약 `UX-CAN-01`: 접수 직후 "취소 처리 중", 성공 확정 후 "취소 완료", 재방문 시 조회. 중복 클릭 방지는 편의일 뿐 서버가 방어한다
  - 추적 ID: `REQ-CAN-01` → `POL-CAN-01` → `API-CAN-01` → `AC-CAN-01`. "모든 문장에 번호를 붙일 필요는 없지만, 변경 시 찾아야 하는 약속에는 안정적인 ID". 추적성의 정량 근거(Mäder & Egyed, 2차·AI 이전 연구 — 에이전트 적용은 책의 추론). 우아한형제들의 Swagger 기반 생성 = 스키마가 계약의 원본
- **독자가 얻는 것:** 실패·중복·지연의 의미가 담긴 계약을 쓰는 법, 그리고 표준이 갈리는 지점을 결정 기록 대상으로 식별하는 눈.
- **오프닝 기법:** 실패 장면 — (가상) 결제사 환불 응답이 오지 않고, 사용자는 취소 버튼을 다시 누른다
- **클로징 기법:** 남은 미결정 목록으로 닫기 — 이 장에서 결정하지 않은 것(멱등키 보존 기간, 충돌 응답 코드, 이벤트 재처리 기간)을 담당자·기한 칸과 함께 남긴다
- **스캐폴드 유형:** 사례 분석형
- **이 장의 핵심 박스:** 둔다
- **권장 그림:** 요청 → 타임아웃 → 늦은 콜백 → 조회·재조정 시퀀스 다이어그램
- **경계:** 각 실패를 수용 기준으로 쓰는 일은 7장. 멱등 충돌 코드의 ADR 작성은 12장.
- **예상 분량:** 7,000자

### 7장. 수용 기준은 실패 넷과 정상 하나로 쓴다

- **핵심 질문:** 에이전트가 "테스트 다 통과"라고 보고했을 때, 그 테스트는 무엇을 약속하고 있었는가?
- **주요 내용:**
  - 테스트 통과의 허점: SWE-bench Verified의 "그럴듯한" 패치 중 일부가 정답과 다르게 동작했고 해결률이 부풀려졌다(Wang 외, ICSE 2026), 테스트를 늘리면 pass@k가 떨어진다(EvalPlus). 원전 "테스트가 통과한다고 문서와 다른 동작을 자동 승인하지 않는다"
  - CAN 수용 기준 `AC-CAN-01`~`05`(원전 그대로): 정상 처리 / 확정된 실패 / 중복 요청과 동시 클릭 / 타임아웃과 늦은 콜백 / 권한과 상태 경합. 각 AC의 UX와 검증 방법. 화면 테스트로 권한 검증을 대체하지 않는다
  - 표기 비교: Given-When-Then(BDD), EARS(Kiro), OpenSpec SHALL + WHEN/THEN. 어느 표기든 "관찰 가능한 결과"와 "예외"가 핵심. 원전 수용 기준 템플릿(연결 요구사항·원본 규칙·검증 테스트 ID·승인)
  - 테스트 먼저: "명세가 테스트 목록을 결정하고, 테스트 목록이 구현 범위를 결정합니다"(jaemin_ve, 커뮤니티 의견). 상호작용으로 의도를 테스트로 확정하는 효과(TiCoder)
  - 테스트도 공격 대상이다: 테스트를 지우거나 우회해 초록불을 만드는 패턴(Kent Beck의 경고 신호 "disabling or deleting tests" — 블로그 요약 경유, 에피소드 인용은 hedge), 그래서 검증 권한을 에이전트 밖에 둔다(9·10장으로 연결)
- **독자가 얻는 것:** 기능 하나에 대해 실패 시나리오가 먼저 보이는 수용 기준 세트를 쓰고, 그것을 테스트 ID와 원본 규칙에 잇는 방법.
- **오프닝 기법:** 인용·일화 — "“Done, all tests pass.” Except they don't."(LambdaLogic, HN, 원문 그대로)
- **클로징 기법:** 반론 남기기 — "이렇게 테스트를 늘리면 느려지지 않는가?"라는 반문을 세우고 짧게 답한다
- **스캐폴드 유형:** 문제-해결형
- **권장 그림:** AC 5개 ↔ 원본 규칙(POL·INV) ↔ 계약 매핑 표(그림 대신 표)
- **경계:** 테스트 실행과 증거 기록은 9장. AI 리뷰의 한계는 8장.
- **예상 분량:** 5,500자

### 3부. 착수하고, 끝까지 잇고, 통제한다

### 8장. Design Ready는 위험이 정한다

- **핵심 질문:** 문서가 이만큼 쌓였으면 이제 구현을 시작해도 되는가? 그 판단을 AI 리뷰에 맡겨도 되는가?
- **주요 내용:**
  - Design Ready의 정의: "모든 의문이 사라지는 시점이 아니라, 지정한 구현 범위를 안전하게 시작할 근거가 있는 시점". BLOCK / CONDITIONAL / LATER와 각각의 처리. 게이트 다섯 가지(명확성·정합성·실현 가능성·추적성·책임성)
  - CAN 판정표(책이 추가한 가상 예): 결제사 요청별 멱등성 지원 여부(원전의 큰 가정) → 스파이크 전 BLOCK, 취소 가능 시점 정책 미승인 → 해당 규칙 구현 보류, 멱등키 보존 기간 → CONDITIONAL(담당자·기한), 부분 취소·양도 → LATER(비범위)
  - 스파이크: 질문 하나("응답 유실 후 동일 환불 키 재요청이 추가 환불을 만들지 않는가?"), 입력·환경·기대 결과·실패 판단·시간 제한을 먼저. 실험 코드는 운영 코드가 아니다. 멈추는 것도 정상 결과다(Spec Kit assess-decide "Stopping with a documented reason …")
  - AI 리뷰를 과신하지 않는 법: 외부 피드백 없는 자기 교정의 한계(Huang 외, Kamoi 외 — "외부 신호가 있을 때만 스스로 고친다"), 상관된 오류(Kim 외: 둘 다 틀릴 때 60% 같은 답 — 특정 데이터셋 조건), 비슷한 모델 편애(Goel 외), 자기 선호(Panickssery 외). Claude Code로 쓰고 Codex로 리뷰하는 교차 리뷰 경험담(커뮤니티 의견) — 누락 탐지에는 유용, 승인은 아니다. 리뷰어는 늘 "뭔가"를 찾는다(W-B1). 근거 없는 교차 리뷰 수치(71.6%→89.7% 등)는 쓰지 않는다
  - "정책은 책임자가, 사용성은 사용자 관찰이, 연동·성능은 실행 실험이 확인한다" — 위험에 맞는 증거 종류 고르기. 착수 전 18항목 체크리스트(§13)는 판정 보조 도구이며 체크 표시가 증거는 아니다(전문은 부록 C)
- **독자가 얻는 것:** 위험 등급으로 착수를 판정하는 기준표와, AI 리뷰를 누락 탐지 도구로 제자리에 두는 감각.
- **오프닝 기법:** 앞 장 콜백 — "앞 장에서 수용 기준 다섯 개를 썼다. 이제 구현을 시작해도 될까?"
- **클로징 기법:** 판정표로 닫기 — CAN 미결정 항목의 최종 판정과 "첫 수직 기능 범위"를 표 하나로 확정하며 닫는다
- **스캐폴드 유형:** 개념 도입형
- **이 장의 핵심 박스:** 둔다
- **권장 그림:** BLOCK / CONDITIONAL / LATER 분류 흐름도
- **경계:** AI 역할 설계 전반은 11장. 여기서는 "리뷰는 독립 검증이 아니다"까지.
- **예상 분량:** 6,500자

### 9장. 수직 기능 하나를 끝까지

- **핵심 질문:** 승인된 설계를 에이전트에게 어떤 단위로 넘겨야, "끝났다"를 증거로 말할 수 있는가?
- **주요 내용:**
  - 가로로 자르기 vs 세로로 자르기: 커뮤니티의 "작게"는 대부분 태스크를 가로로 자른다(커뮤니티 리서처 관찰). 원전은 UI부터 저장·실패·관측까지 한 번에 관통하는 수직 기능으로 자른다. `SLICE-CAN-01` 구현 순서(계약·실패 가짜 서버 → 상태·권한·원자성 테스트 → 접수 API·조회 → outbox·환불 어댑터·콜백 → 최소 UI → 종단 테스트·관측), 샌드박스·기능 플래그로 첫 시연 제한
  - 계획은 대화가 아니라 파일로: `plan/` 위치, Codex ExecPlan("living document", Progress·Surprises & Discoveries·Decision Log·Outcomes — archived 페이지라 구버전일 수 있음), Claude Code 플랜 모드(조작법은 hedge). 플랜 모드 논쟁(커뮤니티 의견, "플랜 모드는 그냥 프롬프트"를 사실로 쓰지 않음) → 도구 기능과 설계 산출물을 구분한다. spec.md·STATUS.md로 compaction·세션 전환을 넘긴다(simonw·ozgung), 단계마다 새 세션, worktree 병행. plan 파일이 현장에서는 드물다는 조사(Abubakar 외)
  - 테스트와 증거: `TC-CAN-01`~`05`가 AC와 1:1로 이어지는 방식, "the command it ran and its output"을 요구한다(W-B1). `VAL-CAN-01`에 남길 것(커밋·문서 기준선·환경·명령·결과 링크·실패 로그·미검증 조건·검토자). "'AI가 검토 완료' 한 문장은 증거를 대체하지 않는다"
  - 8단계 추적 사슬 완성: REQUIREMENT → DOMAIN → CONTRACT → EXPERIENCE → ACCEPTANCE → PLAN → TEST → EVIDENCE. 검증 기록 템플릿이 사람의 검증 비용을 낮춰 과의존을 줄인다(Vasconcelos 외의 결과를 이 책 논리로 연결 — 책의 해석임을 표시)
  - 구현 중 새 규칙이 필요해지면: 임의 확정 금지, 영향 분석과 승인 경로로 되돌린다(10장 예고)
- **독자가 얻는 것:** 수직 기능 계획 파일, 테스트 ID, 검증 기록까지 갖춘 "끝났다"의 모양.
- **오프닝 기법:** 상황 가정 — Design Ready 판정을 받은 CAN을 Codex와 Claude Code에 넘기는 날이라고 해보자(가상)
- **클로징 기법:** 증거 기록 한 장 — 채워진 `VAL-CAN-01`(가상 값, 실행 결과 날조 금지 — "예시" 표시)을 보여 주며 "이것이 끝났다의 모양"으로 닫는다
- **스캐폴드 유형:** 사례 분석형
- **권장 그림:** 8단계 추적 사슬(REQ → … → VAL) 흐름도
- **경계:** PR·CI·출시 통제는 10장. 역할별 프롬프트는 11장.
- **예상 분량:** 7,000자

### 10장. 문서를 PR·CI·출시에 묶는다

- **핵심 질문:** 지시 파일에 "절대 하지 마라"고 써 둔 규칙이 지켜지지 않을 때, 무엇이 그 규칙을 실제로 집행하는가?
- **주요 내용:**
  - 통제 흐름(원전 §09): 영향 분석 → 설계 승인 → 코드 PR → 검증·리뷰 → 출시·관측. 영향 매트릭스를 CAN에 적용("취소 가능 시점 변경" → domain + spec, 경계 시각·경합·업무 승인). 설계 PR에서 승인할 것 vs 코드 PR에서 확인할 것. 내부 리팩터링에 무의미한 문서 수정 강제 금지
  - 결정적 통제 vs 비결정적 지시: "If something has to happen every time, make it a hook, a deny rule, or a managed setting", "강조를 계속 더해도 놓치면 그 줄은 훅으로 가야 한다"(W-B1, 요약 경유). "types → lint rules → tests → md"(mkw5053, 커뮤니티 의견). 토스의 플러그인 훅(main 커밋 감지 → feature 브랜치 유도). 반대편: "Hooks' hell"(Milofax). 자연어 지시를 실행 가능한 검사로 바꾸는 시도(ContextCov — 프리프린트·단독 저자), 공개 CLAUDE.md의 보안 규칙 중 내장 통제와 대응하는 것은 일부뿐(Yan — 프리프린트·단독 저자)
  - 자동 검사와 사람 리뷰의 분담표: 문서 CI(링크·ID 누락·스키마)·코드 CI·사람 리뷰·출시 게이트·출시 후 확인과 각각 "증명하지 못하는 것". "CI 초록색의 정확한 의미" = 마지막 수정 이후 정확한 PR head 커밋에서 필요한 검사가 실행되었는가. CI 통과는 배포 완료가 아니다
  - 왜 통제 지점이 필요한가: 에이전트 PR의 보안 스멜(Sakib 외 — 유출 비밀의 다수는 사람이 넣었고 기존 리뷰가 대부분 놓쳤다, "에이전트가 비밀을 유출한다"로 단순화 금지), 환각 패키지(Spracklen 외), 에이전트 PR 규모(Octoverse 2025). 1장의 품질 부채 결과를 한 문장으로만 회수
  - 출시: 커밋 → 아티팩트 → 배포 환경 연결, 롤백이 데이터 변경을 되돌리지 못할 때의 현실적 복구 계획. "비결정적 소프트웨어에 프로덕션 직접 쓰기 권한을 주지 마라"(guluarte, 커뮤니티 의견)
- **독자가 얻는 것:** 어떤 규칙을 md에 두고 어떤 규칙을 훅·CI·브랜치 보호로 옮길지 가르는 기준, 그리고 PR마다 확인할 증거 목록.
- **오프닝 기법:** 실패 장면 — "An AI agent deleted our production database"(HN 47911524): 에이전트가 받은 안전 규칙을 스스로 나열하며 모두 어겼다고 인정했다는 원 글의 문장(인용 범위 그대로, 장면 각색 금지)
- **클로징 기법:** 대비로 닫기 — "md에 남길 것 / 훅·CI로 옮길 것" 두 열 정리 후 경계를 한 문장으로
- **스캐폴드 유형:** 문제-해결형
- **이 장의 핵심 박스:** 둔다
- **권장 그림:** 영향 분석 → 설계 PR → 코드 PR → CI(head 커밋) → 출시 게이트 → 출시 후 확인 파이프라인
- **경계:** 역할별 금지·결정 한계는 11장. 상시 자동화로 점검을 돌리는 것은 13장.

### 4부. 사람의 결정, 기계의 일

### 11장. AI에게는 역할과 결정 한계를 함께 준다

- **핵심 질문:** 에이전트에게 "기획부터 구현까지 알아서"를 맡기면, 어떤 결정이 조용히 넘어가는가?
- **주요 내용:**
  - 역할 분리의 목적은 에이전트 수가 아니라 결정 한계와 검증 지점이다: MetaGPT 역할 제거 실험은 단조 증가가 아니다, 다중 에이전트 실패의 상당수가 명세 불이행·명확화 실패·검증 없음(Why Do MAS Fail?), 강한 프롬프트의 단일 에이전트가 토론과 비슷하다(P-58) — 이 착지는 논문 리서처가 제안한 책의 결론임을 표시
  - 원전 네 역할과 금지: PLANNER(근거 없이 수요·목표를 사실로 만들기 금지), DESIGNER(미결정 정책을 확정처럼), REVIEWER("문제 없음"을 실행 증거로 — 8장 상관된 오류 범위만 참조), IMPLEMENTER(정책·보안 임의 변경, 범위 밖 리팩터링, 테스트 삭제, 미실행 검증 주장)
  - 공통 입력 꾸러미 vs 도구 권고 대조표(책의 해석): 원전 꾸러미 / Codex 4요소(Goal·Context·Constraints·Done when) / GitHub 3단 경계(always·ask first·never) / dots Custom Rules 4행동. 금지형 규칙이 이롭다는 보고와 무작위 규칙도 효과가 있었다는 단서를 함께(Guardrails Beat Guidance, 프리프린트)
  - 독자 스택에 배치하기: 역할을 Claude Code 스킬·서브에이전트, Codex 스킬·서브에이전트로 옮기는 방식(레퍼런스에 있는 경로만 — 없는 것은 `(사실 확인 필요)`), CAN 입력 꾸러미로 채운 프롬프트 4 발췌(전문은 부록 B). 국내 사례: 컬리("신입 개발자의 제안처럼 검증", TPM AI 1 + MSA AI 11 — 구버전 기준 명시), LY(계획·구현·PR·초기 리뷰는 AI, 테스트·리뷰·릴리스 최종 책임은 사람). LLM이 쓴 설계 근거는 대안 목록에 좋고 결론으로는 위험(Zhou 외)
  - 사람이 소유할 결정(제품 가치·업무 정책·법·보안·위험 수용·출시 승인)은 윤리가 아니라 공학적 필요: 자동화 편향은 전문가에게도(Parasuraman & Manzey, 2차), AI 도우미 사용자가 덜 안전한 코드를 쓰고 더 안전하다고 믿었다(Perry 외), AI 위임은 개념 이해를 떨어뜨렸지만 "생성 후 이해·개념 질문" 패턴은 달랐다(Shen & Tamkin, 52명·프리프린트 — 일반화 금지). 설계 문서를 직접 쓰는 행위가 이해를 지키는 장치
- **독자가 얻는 것:** 역할마다 입력·출력·금지·중단 조건을 갖춘 에이전트 설정, 그리고 사람이 내려놓으면 안 되는 결정 목록.
- **오프닝 기법:** 정의 뒤집기 — "역할 분리"를 에이전트를 여러 개 띄우는 일로 여기는 통념을 "결정 한계를 나누는 일"로 뒤집는다
- **클로징 기법:** 인용으로 닫기 — 원전 "AI 역할을 나누더라도 이 책임이 자동으로 이전되지는 않습니다"를 마지막 문장으로
- **스캐폴드 유형:** 비교 대조형
- **권장 그림:** 네 역할의 입력 → 출력 → 사람 결정 지점 흐름도
- **경계:** ADR·결정 기록은 12장. 상시 에이전트의 권한 설계는 13장.
- **예상 분량:** 7,000자

### 12장. 결정의 계보와 문서의 유통기한

- **핵심 질문:** 지시 파일과 설계 문서의 어느 줄이 이미 낡았는지, 우리는 어떻게 아는가?
- **주요 내용:**
  - 근거가 사라진 지시는 지워지지 않고 쌓인다: 지시 파일이 생애 동안 커지고 오래된 지시일수록 삭제되지 않으며, 원인은 근거 상실이라는 보고(Chakrabarti — 프리프린트·단독 저자). 그래서 "왜"를 남기는 ADR이 에이전트 시대에 다시 필요해진다. "설계 지식의 증발"은 흔히 그렇게 부르는 표현으로(원문 인용 형식 금지)
  - ADR의 생애(원전 §08): Draft → Accepted → Superseded, 결론을 조용히 덮어쓰지 않는다, 오탈자 수정과 결정 변경 구분. Nygard 형식, MADR 4.0.0의 "Confirmation". 현장에서는 처음부터 accepted로 만드는 경향(2차·저자 미확인 — hedge). LLM에게는 대안 목록을 시키고 결정은 사람이(11장 Zhou 외 범위만 참조)
  - CAN 예: `brainstorming/async-cancel.md`(Exploring) → 검증 → 채택 이유는 `ADR-001-async-cancellation`, 상태 규칙은 domain, 사용자 약속은 spec으로 승격. 6장에서 남긴 멱등 충돌 코드 문제를 Draft ADR로(책이 추가한 가상 예). 커뮤니티의 상반된 경험(ADR이 낡아 맹목적으로 따름 vs "append-only log"와 유지 규율, "에이전트 전용 문서는 만들지 마라") — 원전의 답은 유지 규율
  - 공통 머리말(§12): id·status·owner·reviewers·updated·scope·canonical_for·references·decisions·validation — 지시 파일에도 owner·updated를. "Accepted 명세는 승인된 약속이지 이미 구현됨이 아니다", 낡음은 수정 날짜가 아니라 실제 변경과의 불일치로 판단
  - 모델이 바뀌면 지시를 다시 본다: "instructions written for a model that no longer exists"(HN 49376287, 커뮤니티 의견). 결정의 "왜"는 세션 로그가 아니라 정제된 커밋·문서로(rfw300), PR 옆에(esafak)
- **독자가 얻는 것:** ADR과 아이디어 승격을 운용하는 규칙, 그리고 문서와 지시 파일이 낡았는지 판단하는 기준.
- **오프닝 기법:** 인용·일화 — "a meaningful percentage of my system prompt is now actively making things worse … But I can't tell which lines those are"(HN 49376287 원 글, 원문 범위 그대로)
- **클로징 기법:** 다음 장으로 넘기는 문제 제기 — "이 점검을 사람이 매주 할 수 있을까?"로 13장의 질문을 세운다(책 전체에서 다음 장을 직접 가리키는 클로징은 이 장 하나)
- **스캐폴드 유형:** 개념 도입형
- **권장 그림:** brainstorming → 검증 → 결정 → 승격(ADR·domain·spec으로 갈라지는 화살표)
- **경계:** 자동 점검 운용은 13장.
- **예상 분량:** 5,500자

### 13장. 상시 에이전트에게 문서의 정원을 맡긴다 — Hermes와 dots (저자 제안)

- **핵심 질문:** 코딩 에이전트가 쉬는 동안, 문서와 코드의 어긋남은 누가 지켜보는가? 상시 에이전트에게 무엇을 맡기고 무엇을 맡기지 말아야 하는가?
- **주요 내용:**
  - 먼저 선을 긋는다: 2026-10 기준 Hermes·dots를 설계 문서와 잇는 공개 실천은 찾지 못했다. 이 장의 패턴은 **저자의 제안**이며, 공식 문서로 확인된 사실과 구분해 쓴다
  - 확인된 사실(2026-10 기준): Hermes v0.22.5 — 범용 상시 에이전트, cron("Daily reports, nightly backups, weekly audits"), 메신저 게이트웨이, 번들 스킬 `claude-code`·`codex`로 코딩을 위임하는 오케스트레이션 층, 컨텍스트 파일 first-match 규칙, 기억 상한, "두 에이전트 프로세스가 같은 Hermes home을 쓰지 말라"는 공식 경고. dots — ChatGPT 안의 상시 개인 에이전트(DevDay 2026-09-29), Custom Rules 4행동(묻지 않고 실행 / 사전 승인 시 실행 / 먼저 묻기 / 넘기기), Codex 클라우드 태스크 생성. 교차 확인 범위를 넘는 기능(앱 수·가격·기억 삭제 불가 등)은 쓰지 않는다
  - 제안 패턴 1 — 야간 드리프트 점검: CAN 추적 ID(REQ ↔ AC ↔ TC ↔ VAL)의 링크·ID 누락, 지시 파일과 코드의 불일치 후보, 머리말 `updated`와 실제 변경의 괴리를 찾아 **보고만** 한다(3장 낡은 지시 파일, 12장 낡음 기준 회수)
  - 제안 패턴 2 — 증거 수집: PR head 커밋의 검사 실행 여부, VAL 기록의 빈칸(명령·결과 링크·미검증 조건)을 모아 리뷰어에게 건넨다. 판정은 하지 않는다. 제안 패턴 3 — 주간 미결정 점검: 기한이 지난 미결정·CONDITIONAL 항목을 담당자에게 알린다
  - 권한과 결정 한계: 읽기 전용 자격 증명, MR까지만 열기(OliverGuy), 승인 대기(mike_hearn — 둘 다 Hermes·dots가 아닌 인접 사례, 커뮤니티 의견), dots 규칙에서 "먼저 묻기 / 넘기기"를 원전의 중단 조건·결정 요청과 대응(웹 리서처의 해석). handoff에서 의도가 사라진다는 지적(slurpyb, 커뮤니티 의견) → handoff에는 11장의 입력 꾸러미(원본 경로·ID·중단 조건)를 실어 보낸다. 어디에 둘 것인가 비교: CI 스케줄 작업 vs Hermes cron vs dot — 결정적이어야 하는 검사는 CI로(10장), 해석이 필요한 점검과 사람 알림은 상시 에이전트로
- **독자가 얻는 것:** 상시 에이전트를 문서 정원사로 시험해 볼 구체적 패턴 세 가지와, 그것을 안전하게 묶는 권한·중단 조건. 무엇이 사실이고 무엇이 제안인지의 명확한 구분.
- **오프닝 기법:** 상황 가정 — (저자 제안 장면) 새벽, 당신이 자는 동안 Hermes가 저장소를 한 바퀴 돌며 CAN의 추적 링크를 점검한다고 해보자
- **클로징 기법:** 시험 운영 제안 — 패턴 하나만 골라 정해진 기간 돌려 보고, 유지·폐기를 판단할 중단 기준을 미리 적어 두자고 제안하며 닫는다
- **스캐폴드 유형:** 비교 대조형
- **권장 그림:** 코딩 에이전트(Claude Code·Codex) — 상시 에이전트(Hermes·dots) — CI — 사람 사이의 역할·권한 배치도
- **경계:** 설정 파일·명령 예시는 "예시(미실행)" 또는 저자 실측(2026-10 기준) 태그. 실행 결과를 지어내지 않는다.
- **예상 분량:** 6,500자

### 14장. 가장 작은 유효한 기준선부터

- **핵심 질문:** 이 모든 것을 내일 아침 다 시작해야 하는가? 작은 팀과 커지는 팀은 무엇부터 해야 하는가?
- **주요 내용:**
  - 문서의 양은 팀 규모가 아니라 위험에 맞춘다(원전 §11): SMALL 구성(`spec/overview.md`·`domain/rules.md`·`plan/first-slice.md`, 파일을 합쳐도 절의 원본 책임은 유지), MEDIUM 구성(공통 brief·용어집, 경계별 분리, 계약 소유자, architecture, validation). 나눌 신호는 길이가 아니라 동시 변경·다른 승인자·독립 계약. 금전·민감정보·외부 연동이 있으면 작은 팀도 안전 검증은 생략하지 않는다. CAN을 SMALL 구성으로 접어 보기
  - 시작 방법: 30분 빠른 시작(5·10·5·5·5분) — 결과는 구현 승인이 아니라 다음 결정과 검증이 보이는 초안. 첫 주 실행 예시는 조정 가능한 예시(날짜보다 종료 조건). "필요할 때 더한다"(GitHub "Start simple … Add detail when your agent makes mistakes", simonw의 "프로젝트가 좋은 상태면 에이전트에게 말할 게 많지 않다")
  - 흔한 실패 8가지와 대신 할 일(원전 §14)을 1~13장의 내용과 짝지어 회고
  - 전체 여정 회수: 한 문장 — "제품의 의도는 spec에, 업무의 진실은 domain에, 상호작용은 계약과 UX에, 결정의 이유는 ADR에, 실행 순서는 plan에", 그리고 그 모두를 요구사항에서 운영 증거까지 잇는 연결. CAN 사슬 전체를 한 번에 되짚는다. 1장의 질문("무엇이 증폭되는가")에 답하며 닫는다
- **독자가 얻는 것:** 자기 팀 규모·위험에 맞는 첫걸음과, 책 전체를 하나의 판단 절차로 묶은 관점.
- **오프닝 기법:** 수사적 질문 — "이 모든 걸 내일 아침 당장 다 해야 할까?"
- **클로징 기법:** 닫는 매듭 — 여정 회고 + 원전 "기억할 한 문장" 회수 + 1장 질문에 대한 답
- **스캐폴드 유형:** 종합 정리형
- **권장 그림:** SMALL → MEDIUM 전환 신호 흐름도
- **경계:** 템플릿 전문은 부록.
- **예상 분량:** 5,000자
