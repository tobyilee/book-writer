## 제목 후보

1. **쌓이는 지식, 답하는 에이전트** — 부제: LLM 위키 패턴으로 짓는 사내 지식 베이스와 Claude 에이전트. 톤: 독자의 서비스 두 반쪽(계속 자라는 지식 베이스 + 거기서 답하는 에이전트)을 제목에 그대로 담은 서사형. 포지셔닝: "RAG는 매번 처음부터, 위키는 쌓인다"는 패턴의 핵심 한 줄을 제목으로.
2. **LLM 위키로 짓는 사내 지식 베이스** — 부제: Karpathy 패턴을 Claude 에이전트 서비스로 옮기는 설계 결정 12가지. 톤: 실무 결정 가이드. 포지셔닝: 검색 키워드("LLM 위키", "사내 지식 베이스")를 정면에 두어 찾기 쉬움.
3. **위키는 LLM이 쓴다** — 부제: Karpathy LLM Wiki 패턴 실전 — 구축·호스팅·시스템 프롬프트·에이전트 연결. 톤: 도발적 선언형. 포지셔닝: "사람은 한 글자도 안 쓰는 위키"라는 역할 전도를 앞세움.

**추천:** 1번 **쌓이는 지식, 답하는 에이전트**. 독자가 만들 서비스의 두 구성 요소를 그대로 호명하고, 책이 끝까지 붙드는 핵심 논점(accumulation)을 담는다. 부제에 "LLM 위키"와 "사내 지식 베이스"를 넣어 2번의 검색성도 챙긴다. 3번은 입문서 느낌이 강해 "결정 가이드 + 구축 계획"이라는 포지셔닝과 어긋난다.

## 책 특성

- 장르: tech-book
- 분량: 약 90,000자 (12장, 장당 6,000~9,000자 — 아래 챕터별 명시). 기본값(3,000~6,000자)을 넘는 장은 스캐폴드 스케일 규칙대로 **소절(`###`) 수를 5~8개로 늘리고 소절당 순수 산문 3,000자 상한**을 지킨다. 표·코드·mermaid·인용 블록은 자수에서 제외.
- 난이도: 중급 (Claude Code를 써 봤고 Python 또는 TypeScript로 서비스를 짓는 개발자. RAG·임베딩 개념은 알지만 직접 운영해 본 적은 없어도 됨)
- 독자 여정: **진입** — Karpathy의 gist를 읽었고 "우리 회사 지식 베이스에 이걸 쓰고 싶다"까지는 왔지만, 어디서 시작해 무엇을 결정해야 하는지 모른다. 블로그마다 "그냥 RAG다", "이것이 미래다"로 갈려 더 혼란스럽다. → **출구** — 자기 회사의 규모·소스·질문 유형에 맞춰 (1) 위키/RAG/긴 컨텍스트의 포지셔닝, (2) 저장·호스팅 방식, (3) 스키마와 시스템 프롬프트, (4) Agent SDK와 직접 API 중 연결 경로, (5) 린트·승격·평가 운영 주기를 **스스로 결정하고 근거를 댈 수 있으며**, 첫 4주 구축 계획을 손에 들고 책을 덮는다.
- 각성 지점: 2장(컨텍스트 윈도우는 용량이지 성능이 아니다), 10장(LLM 위키는 방치돼도 방치된 것처럼 보이지 않는다 — 조용한 부패).

## 내러티브 아크

책은 "판단 → 설계 → 구축 → 운영 → 종합"의 네 부와 종합 장으로 흐르고, 가상의 회사 **페이지원**(아래 "러닝 예시 정전")이 1장부터 12장까지 관통한다.

**1부 판단(1~3장)**은 "왜 위키인가"를 세 겹으로 쌓는다. 1장은 패턴 원전(3계층·3연산·2특수 파일)을 사내 지식 베이스의 눈으로 읽고, 업무 지식은 연구 지식과 달리 계속 뒤집힌다는 반론을 미리 꺼낸다. 2장은 "그냥 컨텍스트에 다 넣으면 되지 않나"에 연구로 답한다 — 컨텍스트 로트, Lost in the Middle, NoLiMa, 그리고 Generative Agents → MemGPT → A-MEM으로 이어지는 메모리 계보에서 raw/wiki 분리가 어디서 왔는지. 3장은 커뮤니티의 세 논쟁(그냥 RAG다 / 쓰기 루프가 다르다 / 상호보완)을 결정 기준으로 바꾸고, 페이지원의 규모·소스·질문 유형을 재어 "위키는 지도, 근거 문장은 원문" 하이브리드로 포지셔닝한다. 여기서 독자는 자기 회사의 결정표를 처음 쓴다.

**2부 설계(4~6장)**는 파일 하나하나를 정한다. 4장은 디렉터리·페이지 규약·프런트매터 — 사내 지식 다섯 유형(브랜드·전략·도구 사용법·시나리오·결정)마다 페이지 템플릿과 토큰 예산 계층을 준다. 5장은 Notion·Slack·PDF가 raw/가 되고 다시 위키 페이지가 되는 수집 파이프라인 — 소스 분류, 작은 단위 투입, 기록 트리거, 결정 vs 논의 구분. 6장은 가장 중요한 파일인 스키마(CLAUDE.md)와 답변용 시스템 프롬프트를 실제 실패 사례에서 역산해 완성한다.

**3부 구축(7~9장)**은 에이전트가 위키를 읽게 만든다. 7장은 검색 계층 로드맵(index.md → grep → BM25 → 하이브리드 → 벡터)을 규모 수치와 함께 비교하고, 8장은 통째로 프롬프트에 넣는 찜찜한 첫 구현에서 출발해 Agent SDK 경로와 직접 API 경로를 각각 설계한다(훅·서브에이전트·세션 / 인용 API·캐싱·메모리 도구). 9장은 혼자 쓰던 위키를 팀에 공개하는 순간 터지는 것들 — 어디에 두고(마크다운+git vs DB), 누가 읽고(Obsidian·Quartz·SSO), 무인 에이전트에게 무엇을 금지할지. 호스팅을 에이전트 뒤에 둔 이유는 "로컬에서 돌아가는 것을 먼저, 공유는 그다음"이 커뮤니티 증거와 맞기 때문이다(설계 근거 참조).

**4부 운영(10~11장)**은 책의 가장 무거운 경고를 담는다. 10장은 조용한 부패 — 린트 두 층, 모순을 뭉개지 않기, 검토 주기와 소스 해시, 캡처와 승격의 분리, 자율 vs 사람 검토 논쟁. 11장은 "데스크를 믿어도 되는가"에 숫자로 답하는 평가 — 골든셋, 거부 항목, 회귀 평가, 인용 품질.

**12장 종합**은 열한 장에서 내린 결정을 한 장의 결정 목록과 4주 구축 계획으로 접고, 페이지원 전체 아키텍처를 한 그림으로 보여 준 뒤, 독자가 자기 회사로 돌아갈 때 들고 갈 관점 하나로 닫는다.

사용자의 다섯 질문은 이렇게 매핑된다: (1) 어떻게 짓나 → 4·5·6장, (2) 어디에 저장·호스팅 → 9장(+4장 저장 규약), (3) 시스템 프롬프트 → 6장, (4) 에이전트가 위키를 참조하는 법 → 7·8장, (5) 최근 연구·구현·전략 → 2·3장에 집중 + 10·11장에 운영 증거로 분산.

## 설계 근거

- **채택한 구조: 판단→설계→구축→운영→종합 4부+1, 러닝 예시 관통.** 이유 셋. (1) 사용자의 말이 "어떻게 접근해야 할지 알고 싶어"다 — 서베이가 아니라 결정 가이드이므로 각 장이 하나의 설계 결정으로 끝나고, 12장이 그 결정들을 계획으로 접는 구조가 맞다. (2) 레퍼런스의 증거가 "통제 실험 없는 자기 보고"와 "인접 연구"뿐이라(16.2절), 연구 근거(2장)를 앞에 두고 각 설계 결정이 어느 근거에 기대는지 장마다 밝히는 편이 정직하다. (3) 병렬 저술가 4명이 연속 묶음(1~3, 4~6, 7~9, 10~12)을 쓰기 좋게 부 경계와 묶음 경계를 일치시켰다.
- **기각한 대안 1: 사용자 질문 다섯 개를 그대로 5부로(구축 → 호스팅 → 시스템 프롬프트 → 에이전트 참조 → 연구).** — 기각 사유: 연구가 맨 뒤에 가면 앞의 설계 결정(페이지를 짧게, 모순을 병기, 인덱스를 계산)이 근거 없이 나오고, 호스팅이 구축보다 먼저 오면 아직 없는 것을 호스팅하는 순서가 된다. 또 "시스템 프롬프트"는 스키마(CLAUDE.md)와 답변 프롬프트로 갈라지는데 질문 순서대로면 이 둘이 에이전트 장과 분리돼 중복이 생긴다.
- **기각한 대안 2: 28일 따라하기 튜토리얼(Day 1 디렉터리 만들기 … Day 28 평가).** — 기각 사유: 레퍼런스의 모든 구현 수치가 자기 보고라 "정답 코스"로 제시하면 과장이 되고, SDK 버전(2026년 10월 기준 0.2.x/0.3.x)·모델명·캐시 배수에 책 전체가 묶여 신선도 위험이 최대가 된다. 튜토리얼의 장점(손에 잡히는 계획)은 12장의 4주 계획으로 압축해 살린다.
- **기각한 대안 3: 사례 중심 구성(Taktile·Platformer·Jim Liu·Ghelbur·vellumkasane… 사례 한 건 = 한 장).** — 기각 사유: 회사 규모 사례가 희소하고(Taktile·psanchez·Stigmergy 정도), 국내 사내 도입 후기는 사실상 없으며, 사례마다 스택이 달라 독자가 자기 결정으로 환원하기 어렵다. 사례는 각 장의 증거로 분산 배치하고(특히 6·10장), 11절 표는 12장 부록 성격의 "사례 대조표"로만 쓴다.

### 1장. 사람은 한 글자도 쓰지 않는 위키
- **핵심 질문:** Karpathy가 제안한 것은 정확히 무엇이고, 사내 지식 베이스에 옮기면 무엇이 그대로이고 무엇이 달라지는가?
- **주요 내용:**
  - 사람 위키가 죽는 이유("유지보수 부담이 가치보다 빨리 자란다")와 LLM 위키가 사는 이유(부기 비용 ≈ 0). 원문 인용 중심
  - 3계층(`raw/`·`wiki/`·스키마) · 3연산(수집·질의·린트) · 2특수 파일(`index.md`·`log.md`) — 원문 정의 그대로 + mermaid 그림
  - 역할 분담: "You're in charge of sourcing... The LLM's job is everything else" — 페이지원에서 김보라·박태오·"나"의 역할
  - RAG와의 차이 한 줄: "There's no accumulation." (논쟁은 3장으로 미룸)
  - 업무 지식은 다르다는 반론(@_avichawla: 연구 지식은 안정, 업무는 마감·결정이 계속 뒤집힘) — 페이지원 소스 다섯 유형 소개와 함께. 이 책이 "개인 연구 위키"가 아니라 "조직의 기억"을 짓는다는 선언
  - 패턴 반응 규모(gist 2026년 4월 초, 별·포크, HN·GeekNews)는 짧게
- **독자가 얻는 것:** 패턴의 정확한 어휘(이후 장의 공통 언어)와, 자기 회사 소스를 다섯 유형으로 보는 눈
- **레퍼런스 출처 절:** 1.1, 1.2, 1.3, 2.4(업무 지식 반론·생각 외주화), 11.1(당근 "이유와 근거"), 14(#19 #11 #8)
- **오프닝 기법:** 정의 뒤집기 — "흔히 위키는 사람이 쓰는 문서 모음이다. Karpathy의 제안은 사람이 한 글자도 쓰지 않는 위키다."
- **클로징 기법:** 질문 남기기 — "그런데 정말 다 컨텍스트에 넣으면 안 되는 걸까?" (2장으로)
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 6,000자 (소절 4~6)

### 3장. 위키, RAG, 긴 컨텍스트 — 페이지원은 어디에 서는가
- **핵심 질문:** "이건 그냥 RAG 아닌가?"에 어떻게 답하고, 우리 회사 지식 베이스를 어떤 조합으로 포지셔닝할 것인가?
- **주요 내용:**
  - 논쟁 A 세 관점: "그냥 RAG다"(grep도 RAG) / "쓰기 루프가 다르다"(코퍼스가 정적이지 않다) / "상호보완"(위키=지도·캐시, 내용 검색은 BM25/하이브리드). VentureBeat "bypasses RAG" 프레임이 양자택일을 키웠다는 지적
  - 논쟁 B 위키(컴파일) vs 원문(raw): 손실 압축·인용 정확도 vs compile once, keep current → 절충 "위키는 지도, 근거 문장은 원문에서"
  - 증거의 무게 재기: GraphRAG(전역 질문에서 RAG 실패, 루트 요약 9~43배 적은 토큰, LLM-as-judge·directness는 벡터 우세), RAPTOR(검색된 노드 18.5~57%가 비단말 = "README 있는 폴더가 검색이 잘 된다"), Mem0(그래프 자체는 약 2% — 벤더 자체 평가), HippoRAG, "Retrieval as Reasoning"(2차 요약만 — 조심스럽게), Taktile 실측(위키 답변 86% 빠르고 61% 저렴 — 자기 보고), 클리앙 500+ 메모 "둘 다 비슷하지만 위키가 느림"
  - 회의론을 정면으로: "2차 정보 재탕"(Imanari), "모델 붕괴"(devnullbrain와 반론), "위키 누락이 너무 많다"(PyTorchKR) — 이 책의 답은 하이브리드와 10장의 운영
  - 결정 기준 네 축: 소스 규모(수십/수백/수천), 지식의 변화 속도, 질문 유형(국소 사실 vs 전역 종합), 인용 정확도 요구(규제·법무면 원문 필수)
  - 페이지원 결정: 소스 60→300건, 전략·가격은 fast-changing, 질문은 국소 사실 위주 + 가끔 전역("우리 마케팅 방향이 뭐야") → **위키 계층 + 근거는 원문 + BM25 준비** (7장에서 구체화). 독자용 빈 결정표 제공
- **독자가 얻는 것:** 네 축 결정표와 자기 회사의 첫 결정. "그냥 RAG 아니냐"는 동료의 질문에 대한 2분짜리 답
- **레퍼런스 출처 절:** 2.2, 2.4, 12 논쟁 A·B(·E 일부), 13 T12·T13·T19, 11(Taktile·클리앙·clue.oz4e 행)
- **오프닝 기법:** 수사적 질문 — "이건 그냥 RAG 아닌가?"
- **클로징 기법:** 결정표 작성 과제 — 독자가 자기 회사 네 축을 채우도록 빈 표로 닫는다
- **스캐폴드 유형:** 비교 대조형
- **예상 분량:** 7,000자 (소절 5~6)
- **사실 확인 민감:** Retrieval as Reasoning 수치(F5 — 원문 대조 전 보수적으로), "21배 토큰"(F6 — 2차), PwC grep 논문(F7 — 7장과 중복 피함), Mem0·Zep 자체 평가(F28), 커뮤니티 수치 전부 자기 보고 명시(F33), LC vs RAG 실패 유형은 4범주(F25), Search-R1은 "20~41%"(F24)

### 4장. 저장소 설계 — 디렉터리, 페이지, 프런트매터
- **핵심 질문:** `pageone-wiki`의 첫 커밋에 무엇이 들어가야 하고, 사내 지식 다섯 유형은 각각 어떤 페이지가 되는가?
- **주요 내용:**
  - 디렉터리: 파생 구현들의 공통형(`raw/`, `wiki/{topic}/`, `index.md`, `log.md`) + 토스 하네스의 3계층(Global/Domain/Local — 가설임을 명시)을 빌려 페이지원 구조 확정. 사내용 하위 디렉터리: `wiki/brand/`, `wiki/strategy/`, `wiki/howto/`, `wiki/scenarios/`, `wiki/decisions/`, `wiki/people/`
  - 업무 지식의 타입 엔티티: 사람·결정·약속·마감(@_avichawla) — `decisions/` 페이지 템플릿(결정일·결정자·근거·뒤집힌 이전 결정·유효 기간)
  - 페이지 규약: 모든 페이지 상단 TL;DR(50자 이하), 토큰 예산 계층 L0~L3(자기 보고 수치임을 밝히되 실용 기본값으로), 한 줄 = 자족적 원자 명제(Dense X Retrieval: 11.2단어 vs 58.5단어, Recall@20 +10.1), 청킹을 똑똑하게 하느니 LLM이 쓴 의미 단위 페이지(Qu 2024)
  - 프런트매터 필드 세트: 출처 유형(human / LLM / LLM-reviewed), `confidence`, `last_verified`, `review_after`, `superseded_by`, `contradicts`, `valid_from/valid_to`(Zep의 만료 처리: 삭제가 아니라 무효화 — 벤더 자체 평가 명시). 토스 Topic의 신뢰 상태(`trusted`…`insufficient_evidence`) 비교. 반대 의견(YAML 대신 굵은 글씨)도 한 줄
  - `index.md`는 카탈로그, `log.md`는 append-only 원장 — 일관 prefix(`## [2026-08-20] ingest | …`)로 grep 가능하게. 로그 쓰기 실패가 본작업을 깨지 않게
  - 다섯 유형별 페이지 예시 (가격 페이지 v1 — 29,000원, `valid_from: 2026-01-01` — 10장에서 낡게 되는 바로 그 페이지)
  - 이미지·PDF 인라인 처리(텍스트 먼저, 이미지 별도)
- **독자가 얻는 것:** 복사해 쓸 수 있는 디렉터리 트리, 다섯 유형 페이지 템플릿, 프런트매터 스펙

- **오프닝 기법:** 상황 가정 — "첫 커밋을 만든다고 해보자. 빈 저장소에 폴더 세 개를 만드는 데 10초가 걸린다. 그 폴더 이름을 정하는 데는 이 장이 통째로 필요하다."
- **클로징 기법:** `### 이 장의 핵심` 박스(이 장은 규약 밀도가 높음) + 적용 과제 한 줄(자기 소스 다섯 유형을 템플릿에 대보기)
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 8,000자 (소절 6~8; 템플릿·표는 자수 제외)

### 10장. 조용한 부패 — 린트, 신선도, 승격
- **핵심 질문:** 여섯 달 뒤 데스크가 자신 있게 틀린 답을 할 때, 무엇이 그것을 잡아 주는가?

- **국내 사내 도입 후기 부재** — 토스·우아한형제들·LY는 LLM 위키 패턴 그 자체가 아니라 "사내 지식 에이전트"의 참조점이다. 본문에서 혼동시키지 않는다(9·11·12장).
- **2026년 논문 3편 미대조** — Retrieval as Reasoning(2605.25480), Is Grep All You Need(2605.15184), 자동 생성 AGENTS.md(2602.11988)는 2차 요약만 있다. 3·6·7장은 요지만 쓰고 수치는 `(사실 확인 필요)`를 남긴다. fact-checker가 원문 대조 후 해소.
- **모든 커뮤니티 수치는 자기 보고** — 본문에서 "자기 보고", "통제군 없음"을 그 자리에서 밝힌다(별도 각주로 미루지 않음).
- **모델명·가격·캐시 배수·SDK 버전**(8장)은 "2026년 10월 기준" 명기 + "공식 문서를 함께 확인하자" 안전 문구. 레퍼런스에 없는 시그니처·옵션명은 지어내지 않는다.
- **Reddit·X 본문 미접근** — Reddit 발언은 인용하지 않는다. Karpathy 트윗은 요지만.
- **참고문헌**은 editor가 15절 원장 그대로 옮긴다. 본문의 `[W{n}]`·`[P{s}-{n}]` 표기는 저술가가 그대로 써도 되고, editor가 통일한다.

## 사용자 판단이 필요한 것

1. 러닝 예시 회사(페이지원/원북/데스크)와 가격 인상 예시 — 이대로 가도 되는지, 혹은 실제 회사 상황에 가깝게 소스 유형·규모를 바꿀지.
2. 8장의 주 경로를 **Agent SDK**로 두고 직접 API를 부 경로로 둔 배치 — 독자가 Claude Code 사용자라는 전제에서 정했다. 반대(직접 API 주 경로)를 원하면 8장만 뒤집으면 된다.
3. 총 분량 약 90,000자(장당 6,000~9,000자) — 기본값(장당 3,000~6,000자)보다 크다. "결정 가이드 + 구축 계획"에 코드·템플릿·표가 많이 들어가서 잡은 값이다. 줄이려면 2·7·8·10장을 7,000자로.
4. 2장(연구 근거)의 비중 — 사용자가 "최근 연구를 깊이"라고 했으므로 8,000자 한 장을 통째로 썼다. 가볍게 가려면 2장을 5,000자로 줄이고 논문 상세는 3·10장에 분산.
