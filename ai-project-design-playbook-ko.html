01

문서는 세 가지 일을 해야 합니다

설명의 양이 아니라, 결정의 명확성과 검증 가능성으로 문서의 가치를 판단합니다.

A

합의의 기준선

문제, 범위, 용어, 업무 규칙을 공유합니다. 서로 다른 화면이나 구현이 동일한 규칙을 다르게 해석하지 않도록 합니다.

질문 무엇이 맞는 동작이고, 무엇은 이번에 하지 않는가?

B

검증의 대상

요구사항을 관찰 가능한 조건으로 바꿉니다. 프로토타입, 계약 테스트, 부하 실험, 사용자 확인으로 가정과 결정을 구분합니다.

질문 무엇을 보면 이 설계가 충분하다고 말할 수 있는가?

C

변경의 제어 장치

코드가 바뀔 때 영향받는 규칙과 테스트를 찾고, 의도된 변경인지 확인합니다. 구현 계획은 승인된 기준선을 실행 가능한 단위로 나눕니다.

질문 누가 왜 바꿨고, 어떤 증거로 출시하는가?

핵심 원칙　하나의 결정에는 하나의 권위 있는 원본을 둡니다. 다른 문서는 그 내용을 복사하지 않고 식별자와 링크로 참조합니다. 요약이 필요하면 “요약이며 원본은 여기”라고 표시합니다.
문제관찰과 가설
규칙업무와 계약
증거실험과 검토
수직 기능끝까지 동작
학습문서와 구현 갱신

이 흐름은 한 번만 통과하는 폭포수 절차가 아닙니다. 불확실성이 큰 부분은 앞 단계로 돌아가며, 작은 변경은 필요한 문서와 검증만 사용합니다. “문서 완성률 100%” 대신 “다음 구현을 시작해도 되는가”를 판단합니다.

02

폴더보다 중요한 것은 원본의 책임입니다

기존의 spec · plan · domain · adr · ux · guides · brainstorming을 유지하면서, 문서가 답할 질문을 분리합니다.

권장 책임 분리 · 폴더 이름은 팀에 맞게 바꿔도 됩니다
위치답해야 하는 질문권위 있는 내용언제 바꾸는가
spec/사용자에게 무엇을 약속하는가?기능 범위, 요구사항 ID, 수용 기준, 외부 동작사용자에게 보이는 동작이나 수용 조건 변경
domain/업무적으로 무엇이 참이어야 하는가?용어, 엔터티, 불변식, 상태 전이, 권한 정책업무 규칙·상태·소유권·허용 행위 변경
ux/사용자는 상태와 선택을 어떻게 이해하는가?사용자 여정, 화면 흐름, 로딩·빈 상태·오류·접근성화면 순서·피드백·입력 방식 변경
adr/왜 이 기술적 선택을 했는가?대안, 근거, 비용, 수용한 위험, 결정 상태되돌리기 비싼 선택 또는 기존 결정의 교체
plan/누가 어떤 순서로 구현하고 검증하는가?수직 기능, 작업 분해, 의존성, 검증·출시 순서순서·범위·담당·진행 상황 변경
guides/같은 일을 어떻게 일관되게 수행하는가?개발 환경, 실행·테스트 명령, 코딩·운영 절차공통 작업 방식과 실제 실행 절차 변경
brainstorming/어떤 가능성과 미해결 가설이 있는가?아이디어, 질문, 실험 후보, 기각 사유아이디어의 생성·검증·보류·승격
product-brief.md왜 만들며 무엇으로 성공을 판단하는가?대상, 문제, 가치, 범위·비범위, 성공 지표제품 가설·대상·성공 정의 변경
architecture/경계와 통합 방식은 어떻게 구성되는가?컴포넌트 경계, 데이터 흐름, API·이벤트 계약의 위치경계·연동·배포·운영 책임 변경
validation/무엇을 어떤 조건에서 확인했는가?위험 목록, 실험 설계, 결과, 한계, 증거 링크실험·리뷰·검증 결과 추가 또는 무효화

마지막 세 위치는 필요할 때 추가하는 선택지입니다. 작게 시작한다면 product brief는 spec의 첫 페이지, architecture는 설계 문서의 한 절, validation은 검증 로그 한 파일로 충분합니다. 폴더를 만드는 것 자체가 설계는 아닙니다.

원본 하나를 정하는 예

domain/cancellation.md#POL-CAN-01이 취소 가능 상태의 원본이라면, spec은 그 규칙을 참조하여 사용자 약속을 설명하고 UX는 그 규칙에 따른 버튼과 안내를 정의합니다.

API 스키마를 OpenAPI 등 별도 파일로 관리한다면 그 스키마를 계약의 원본으로 정하고 architecture에는 위치와 설명만 둡니다.

피해야 할 중복

spec에는 “확정 전 취소”, UX에는 “결제 후 취소”, plan에는 “언제든 취소”가 각각 적혀 있다면 코드보다 먼저 충돌을 해결해야 합니다.

테스트는 규칙을 검증하는 실행 가능한 표현입니다. 테스트가 통과한다고 문서와 다른 동작을 자동 승인하지 않습니다.

03

아이디어를 여섯 번의 작은 합의로 바꿉니다

각 단계는 입력, 활동, 산출물, 검토자, 종료 조건을 갖습니다. 위험이 작은 항목은 합치고, 큰 항목은 반복합니다.

1

문제와 성공 조건을 좁힙니다

입력
아이디어, 관찰, 사용자 불편, 제약, 기존 대안
활동
사용자와 상황을 특정하고 문제·가설·사실을 분리합니다. 비범위와 가장 위험한 가정을 적습니다.
산출물
짧은 product brief, 가정 목록, 성공 지표 초안
검토자
제품·업무 결정권자와 실제 사용자 또는 업무 담당자
종료 조건　누구의 어떤 문제인지, 이번에 하지 않을 일, 성공을 관찰할 방법을 설명할 수 있습니다.
2

핵심 시나리오와 경계를 그립니다

입력
brief, 사용자 역할, 주변 시스템, 주요 제약
활동
대표 여정 하나를 정상·실패·복구까지 작성합니다. 용어를 맞추고 책임 경계를 나눕니다.
산출물
spec 초안, domain 용어·상태 초안, UX 흐름, 시스템 문맥도
검토자
업무 담당자, 설계자, 개발자, UX 담당자
종료 조건　같은 용어를 같은 뜻으로 사용하며, 시스템 안팎의 책임과 핵심 실패 지점을 식별했습니다.
3

규칙과 계약을 구체화합니다

입력
시나리오, 상태·권한 초안, 외부 연동 조건
활동
불변식, 전이 조건, 동시성, 멱등성, API·이벤트, 관측 지표를 정합니다. 품질 목표를 측정식으로 바꿉니다.
산출물
domain/spec/ux 정합성 있는 초안, 계약 스키마, 필요한 ADR 초안
검토자
업무 책임자, 구현 담당자, 연동 상대, 보안·운영 담당자 중 필요한 사람
종료 조건　입력과 상태가 주어졌을 때 허용·거절·대기 동작을 예측할 수 있고, 미결정은 담당자와 기한이 있습니다.
4

가장 위험한 가정을 검증합니다

입력
위험 목록, 계약 초안, 품질 목표, 미결정 사항
활동
작은 기술 실험, 계약 테스트, 사용자 프로토타입 검토, 장애·경합 시뮬레이션을 수행합니다.
산출물
조건·결과·한계를 포함한 증거, 수정된 설계, 결정 기록
검토자
해당 위험의 책임자와 결과를 재현하거나 반박할 수 있는 검토자
종료 조건　구현을 막는 위험은 해소되었고, 남은 위험은 수용 권한자가 범위·완화책·재검토 시점을 승인했습니다.
5

작은 구현 범위를 승인합니다

입력
검증된 설계 초안, 승인된 결정, 잔여 위험
활동
Design Ready를 검토하고 요구사항 ID와 테스트를 연결합니다. UI부터 저장·관측까지 한 번에 관통하는 기능을 나눕니다.
산출물
승인된 설계 기준선, 수직 기능 계획, 코드 PR의 완료 조건
검토자
업무 승인자와 기술 승인자. 작은 팀에서는 겸임하되 역할을 구분합니다.
종료 조건　첫 구현 범위, 수용 기준, 검증 명령, 변경 경로와 출시 제한이 명확합니다.
6

수직 기능으로 설계를 다시 확인합니다

입력
승인된 문서 버전·커밋, 구현 계획, 테스트 조건
활동
최소 경로를 구현하고 정상·실패 테스트, 관측, 제한된 환경의 시연을 수행합니다. 새 사실은 변경 절차로 반영합니다.
산출물
검증된 코드 PR, 실행 증거, 갱신된 문서, 다음 기능의 위험·우선순위
검토자
코드 리뷰어, 업무 담당자, 출시·운영 책임자
종료 조건　약속한 동작을 종단에서 확인했고, 미지원 동작은 명확히 제한했습니다. 출시한다면 별도 출시 게이트를 통과합니다.
04

처음 쓰는 문서는 짧은 제품 합의서입니다

무엇을 만들지보다 왜 만들고 어디까지 할지를 먼저 고정합니다. 다음 예시는 실제 제품 규칙이 아닙니다.

product-brief.md가상 예시 · 예약 서비스의 셀프 취소
사용자와 상황
확정된 예약을 가진 사용자가 이용 전에 일정을 바꿔야 합니다.
문제
취소하려면 운영자에게 연락해야 하고, 처리 상태를 알기 어렵습니다. 실제 빈도와 불편 정도는 인터뷰·문의 기록으로 확인합니다.
가치 가설
가능한 예약을 직접 취소하고 상태를 확인할 수 있으면, 취소 관련 문의와 불확실성이 줄어듭니다.
이번 범위
로그인한 예약 소유자의 전액 취소, 처리 상태 조회, 환불 연동 결과 반영, 실패 시 운영 인계
비범위
부분 취소, 양도, 다중 결제수단, 운영자 예외 승인 UI. 실제 요구가 있으면 별도 결정합니다.
성공 판단
셀프 취소 완료율, 취소 관련 문의율, 처리 지연 분포를 비교합니다. 분모·측정 기간·기준선·목표치는 데이터 확보 후 승인합니다.
제약
결제사 계약, 개인정보 보존 정책, 예약 확정 과정과 취소의 동시성, 사용자에게 보이는 정합성
큰 가정
결제사가 요청별 멱등성과 결과 조회를 지원하는가? 사용자가 “요청 접수”와 “취소 완료”를 구분할 수 있는가?
결정과 미결정
범위 승인자: 업무 책임자 역할. 취소 가능 시점·환불 기한·예외 처리 권한은 미결정이며, 승인 전 실제 정책처럼 구현하지 않습니다.

비기능 요구사항도 관찰 가능한 문장으로 씁니다

“빠르게”, “안전하게”, “확장 가능하게” 대신 부하, 환경, 측정 구간, 허용 기준을 적습니다. 아래 숫자는 형식을 보여 주기 위한 예시이며 권장 기본값이 아닙니다.

ID와 목표측정 조건과 기준의 예검증 증거와 주의점
NFR-P01
접수 응답 지연		명시한 스테이징 사양에서 대표 데이터 10만 건, 초당 20건의 취소 요청, 워밍업 후 15분 측정. 유효 요청의 서버 응답 p95 ≤ 500ms, 5xx 비율 ≤ 0.5%.외부 환불 완료 시간은 별도 측정. 부하 도구·데이터·설정·커밋·원시 결과를 저장하고, 스테이징 결과를 운영 SLA로 주장하지 않습니다.

NFR-O01

05

화면보다 먼저 상태와 경계를 맞춥니다

화면은 업무 상태를 표현합니다. 도메인 규칙과 통합 계약을 먼저 맞춰야 오류와 재시도에도 같은 의미를 유지합니다.

도메인에 꼭 적을 것

  • 용어와 소유권 예약, 취소 요청, 환불은 서로 다른 개념인지 정의합니다.
  • 불변식 예: 취소 완료는 확인된 환불 성공 이후에만 선언합니다.
  • 상태 전이 시작 상태, 트리거, 조건, 결과, 금지 전이를 씁니다.
  • 권한 주체 × 자원 × 행위 × 조건을 정의하고 서버에서 검증합니다.
  • 경합과 시간 동시에 들어온 요청, 마감 시각, 지연 결과의 승자를 정합니다.

아키텍처에 꼭 적을 것

  • 책임 경계 무엇이 결정을 내리고 무엇이 실행·전달하는가?
  • 데이터 흐름 신뢰 경계, 저장 위치, 민감 데이터, 추적 ID를 표시합니다.
  • 일관성 하나의 트랜잭션과 비동기 경계를 구분합니다.
  • 실패 복구 타임아웃, 재시도, 중복, 보상·정합성 회복을 정의합니다.
  • 운영 경계 관측, 경보, 운영 인계, 배포·복구 책임을 정합니다.

06

하나의 취소 기능을 끝까지 연결해 봅니다

아래는 결제된 예약의 전액 취소를 설명하는 가상 설계입니다. 실제 서비스의 취소·환불 정책은 별도 승인이 필요합니다.

가상 기능 CAN예약 소유자만 요청환불 확인 전 완료 금지

예시 요구사항 REQ-CAN-01　예약 소유자는 취소 가능한 확정 예약의 취소를 요청하고 진행 상태를 확인할 수 있습니다. 요청 접수와 완료를 구분하며, 중복 요청이 추가 환불을 만들지 않아야 합니다.

CONFIRMED확정 예약
→
CANCEL_PENDING취소 요청 접수
환불 결과 확인 중
→
CANCELLED환불 성공 확인
취소 완료

확정된 실패
환불 거절이 최종 확정되면 예약은 CONFIRMED로 복귀하고 취소 시도는 FAILED로 기록합니다.

결과 불명확
타임아웃은 실패 확정이 아닙니다. CANCEL_PENDING을 유지하고 조회·재조정으로 확인합니다.

도메인 규칙의 원본

domain/cancellation.md

  • POL-CAN-01 소유자이고 CONFIRMED이며 정책상 취소 가능할 때만 신규 시도를 시작합니다. 예시에서는 아직 이용이 시작되지 않은 예약으로 제한합니다.
  • INV-CAN-01 예약당 활성 취소 시도는 최대 하나입니다. 상태 검사와 활성 시도 생성은 원자적으로 처리합니다.
  • INV-CAN-02 검증된 환불 성공 전에는 CANCELLED로 전이하지 않습니다.
  • INV-CAN-03 동일 취소 시도의 외부 환불 키는 재시도에도 유지합니다. 성공한 환불을 다시 실행하지 않습니다.

전이와 권한의 부가 조건

  • 예약과 취소 시도의 상태는 분리합니다. 시도는 PENDING → SUCCEEDED 또는 FAILED이며 감사 이력은 남깁니다.
  • 취소 요청과 이용 시작이 경합하면, 동일한 상태·버전 조건을 가진 원자적 갱신으로 하나만 성공하도록 설계합니다.
  • 타인의 예약은 예시상 404로 처리해 존재 여부를 노출하지 않습니다. 내부 감사에는 거절 사유를 구분합니다.
  • FAILED 후 재시도는 새 시도로 생성하되, 이전 환불 실패가 최종 확정된 경우에만 허용합니다.

API와 이벤트의 계약 예시

API-CAN-01  POST /reservations/{id}/cancellation-requests
인증       로그인 사용자 + 서버의 예약 소유권 검증
헤더       Idempotency-Key: 요청자가 생성한 키
입력       { "reasonCode": "CHANGE_OF_PLANS" }
접수       202 { requestId, reservationId, status: "PENDING", statusUrl }
조회       GET /cancellation-requests/{requestId}  → 소유자만 조회
재전송     동일 사용자·예약·키 + 동일 입력 → 기존 requestId 반환
키 충돌    동일 키 + 다른 입력 → 409 IDEMPOTENCY_CONFLICT
다른 키    활성 시도가 있으면 409 CANCELLATION_IN_PROGRESS + 상태 조회 위치
종료 상태  이미 CANCELLED인 예약 → 409 ALREADY_CANCELLED, 신규 환불 없음
조건 위반  409 CANCELLATION_NOT_ALLOWED / 인증 없음 401 / 비소유자 404

EVT-CAN-01  ReservationCancellationCompleted.v1
발행 조건  검증된 환불 성공 + 예약 CANCELLED 갱신 후
필드       eventId, occurredAt, reservationId, cancellationRequestId,
           aggregateVersion, correlationId, schemaVersion
전달 가정  적어도 한 번 전달될 수 있음. 수신자는 eventId로 중복 제거
일관성     상태 변경과 outbox 기록을 같은 DB 트랜잭션으로 묶는 안을 검증
순서       aggregateVersion을 확인하고 오래된 상태 덮어쓰기를 금지

HTTP 상태 코드는 이 예제의 선택입니다. 멱등키 보존 기간, 환불사 키 정책, 이벤트 보존·재처리 기간은 위험에 맞춰 반드시 결정해야 합니다. 키 기록 정리 후에도 예약·시도 이력과 업무 제약이 중복 환불을 방어해야 합니다. outbox는 “정확히 한 번”을 보장하지 않으므로 수신자 중복 처리도 필요합니다.

AC-CAN-01 / TC-CAN-01　정상 처리

Given 소유자의 취소 가능한 CONFIRMED 예약이 있고, When 요청이 접수된 뒤 검증된 환불 성공이 오면, Then 활성 시도 하나와 환불 부작용 하나만 생성되고 예약은 CANCELLED가 됩니다.

UX 접수 직후 “취소 처리 중”, 성공 확정 후 “취소 완료”를 표시합니다. 확인 화면을 떠나도 재방문 시 상태를 조회할 수 있습니다. 검증 도메인 단위 테스트 + 계약 테스트 + UI에서 저장·이벤트까지 종단 테스트.

AC-CAN-02 / TC-CAN-02　확정된 실패

Given CANCEL_PENDING인 시도가 있고, When 환불사가 최종 거절을 확정하면, Then 시도는 FAILED, 예약은 CONFIRMED로 돌아갑니다. 완료 이벤트는 발행하지 않습니다.

UX “취소되지 않았습니다”와 실패 사유에 맞는 다음 행동을 표시합니다. 재시도 가능 여부는 정책으로 결정합니다. 검증 외부 거절 응답 주입, 전이·이벤트 부재·감사 로그 확인.

AC-CAN-03 / TC-CAN-03　중복 요청과 동시 클릭

Given 같은 멱등키 또는 서로 다른 키의 요청이 동시에 들어오면, Then 동일 키는 기존 시도를 재사용하고 다른 키는 진행 중 충돌로 안내합니다. 활성 시도와 환불 부작용은 하나입니다.

UX 버튼 비활성화는 편의 기능일 뿐이며 서버가 중복을 방어합니다. 검증 병렬 요청, 응답 유실 후 재전송, 키·입력 불일치, outbox 재발행과 소비자 중복 수신을 각각 테스트합니다.

AC-CAN-04 / TC-CAN-04　타임아웃과 늦은 콜백

Given 외부 요청이 타임아웃되어 결과를 모르면 CANCEL_PENDING을 유지합니다. When 늦게 도착한 서명 검증된 성공 콜백이 현재 시도와 결제 거래에 정확히 대응하면, Then 성공을 한 번만 반영합니다.

이미 처리한 콜백은 무해하게 종료합니다. 이전 시도에 대한 콜백이나 확정 실패와 모순되는 결과는 현재 상태를 덮어쓰지 않고 정합성 확인 대상으로 격리합니다. 조회 API로 확인한 결과와 운영 인계를 통해 해결합니다.

UX “결과 확인 중”과 조회·문의 경로를 제공합니다. 검증 지연·중복·역순 콜백, 잘못된 서명, 잘못된 거래 ID, 확인 작업 재시작을 주입합니다.

AC-CAN-05 / TC-CAN-05　권한과 상태 경합

Given 비소유자의 요청 또는 이용 시작과 동시에 발생한 취소가 있으면, Then 권한 없는 행위는 차단되고 경합에서는 승인된 상태 전이 하나만 성공합니다. 모순된 상태나 신규 환불이 생기지 않습니다.

검증 API 직접 호출, 다른 사용자의 상태 조회, 낡은 버전의 상태 변경, 경합 재현. 화면 테스트만으로 권한 검증을 대체하지 않습니다.

SLICE-CAN-01 구현 계획 예　계약·실패 가짜 서버 작성 → 상태·권한·원자성 테스트 → 접수 API와 상태 조회 → outbox·환불 어댑터·콜백 → 최소 UI → 종단 테스트와 운영 관측. 첫 시연은 샌드박스와 기능 플래그로 제한할 수 있지만, 실서비스 출시 전에는 중복·권한·지연 결과의 안전 장치를 생략하지 않습니다.

VAL-CAN-01에 남길 증거 테스트한 코드 커밋, 문서 기준선, 환경·외부 샌드박스 조건, 실행 명령, 결과 링크, 실패 로그, 미검증 조건, 검토자. “AI가 검토 완료” 한 문장은 증거를 대체하지 않습니다.

07

Design Ready는 위험에 따라 판단합니다

모든 의문이 사라지는 시점이 아니라, 지정한 구현 범위를 안전하게 시작할 근거가 있는 시점입니다.

BLOCK

착수를 막는 위험

핵심 업무 규칙 미승인, 금전·권한·개인정보 불변식 충돌, 불가능할 수 있는 외부 계약, 데이터 손실 복구 미정처럼 이후 작업을 무효화하거나 큰 피해를 만드는 항목입니다.

처리 결정·실험·책임자 승인 전 관련 구현을 보류합니다. 탐색용 스파이크는 별도 허용할 수 있습니다.

CONDITIONAL

조건부 진행

영향이 제한되고 되돌리기 쉬우며 완화책이 있는 불확실성입니다. 미검증 기능의 비활성화, 사용자 제한, 추가 관측 등을 적용합니다.

처리 위험 ID, 책임자, 허용 범위, 종료 기한, 재검토 조건을 기록합니다.

LATER

나중에 결정

다음 수직 기능에 필요하지 않은 미래 확장과 낮은 위험의 표현 세부입니다. 보류가 현재 계약을 모호하게 만들지 않아야 합니다.

처리 비범위 또는 후속 항목으로 표시하고, 결정이 필요해지는 트리거를 남깁니다.

게이트에서 확인할 다섯 가지

  1. 명확성 범위·비범위, 역할, 용어, 수용 기준을 이해할 수 있는가?
  2. 정합성 spec·domain·계약·UX에 서로 모순되는 약속이 없는가?
  3. 실현 가능성 외부 연동·성능·보안·운영의 핵심 위험에 실제 증거가 있는가?
  4. 추적성 첫 구현 작업과 테스트가 요구사항으로 연결되는가?
  5. 책임성 결정권자, 남은 위험의 소유자, 변경 승인 경로가 정해졌는가?

스파이크를 잘 쓰는 법

질문 하나를 정하고, 최소 코드나 실험으로 답합니다. 예: “응답 유실 후 동일 환불 키 재요청이 추가 환불을 만들지 않는가?”

입력·환경·기대 결과·실패 판단·시간 제한을 먼저 적고, 결과와 한계를 남깁니다. 실험 코드는 곧바로 운영 코드로 간주하지 않습니다.

AI 검토를 과신하지 않는 법

다른 AI 역할의 반박은 누락 탐지에 유용하지만 독립적인 현실 검증은 아닙니다. 같은 잘못된 가정을 공유할 수 있습니다.

정책은 책임자가, 사용성은 사용자 관찰이, 연동·성능은 실행 실험이 확인합니다. 위험에 맞는 증거 종류를 선택하세요.

08

현재의 규칙과 과거의 판단 근거를 구분하면, 왜 바뀌었는지 되짚을 수 있습니다.

ADR을 만들 기준

데이터 소유권, 동기·비동기 경계, 인증 모델, 데이터베이스 선택, 외부 의존성처럼 영향이 크거나 되돌리기 비싼 선택에 사용합니다.

  • 맥락과 제약을 먼저 적습니다.
  • 실제로 고려한 대안과 비용을 비교합니다.
  • 결정, 근거, 부작용, 검증 증거를 남깁니다.
  • 승인자·날짜와 재검토 조건을 기록합니다.

결정이 바뀌면 새 기록을 씁니다

Accepted ADR의 결론을 조용히 덮어쓰지 않습니다. 새 ADR에 변경 근거를 쓰고 이전 ADR을 Superseded로 표시하며 서로 링크합니다.

오탈자 수정과 결정 변경을 구분합니다. 검토 후 채택하지 않은 초안은 Rejected 또는 Withdrawn으로 남길 수 있습니다.

brainstorming은 구현 명세가 아닙니다

아이디어문제·가설·대안
검증실험·비교·반박
결정채택·보류·기각
승격공식 원본에 반영

승격의 예　brainstorming/async-cancel.md에서 비동기 취소를 탐색했다면, 채택 이유는 ADR로, 상태 규칙은 domain으로, 사용자 약속은 spec으로 보냅니다. 아이디어 메모에는 “채택됨”과 대상 문서 링크를 남깁니다. 공식 문서에도 출처 메모와 ADR을 연결하되 규칙 본문을 여러 곳에 복제하지 않습니다.

간단한 상태 표시만으로도 충분합니다　Exploring / Validated / Promoted / Parked / Rejected. 고정된 보드 수나 컨텍스트 수는 필요하지 않습니다. 프로젝트가 사용하는 용어로 일관되게 관리하세요.

설계 PR에서 승인할 것

  • 변경 이유와 바뀌는 약속
  • 원본 문서와 연결된 요구사항 ID
  • 수용 기준·위험·호환성·데이터 영향

큰 변경은 설계 PR을 먼저 합의합니다. 작은 변경은 문서와 코드를 같은 PR에 넣어도 되지만, 의미 변경이 리뷰에서 명확히 드러나야 합니다.

코드 PR에서 확인할 것

  • 승인된 문서 버전과 작업·테스트 링크
  • 구현 결과와 계획의 차이, 문서 갱신 여부
  • 정상·실패·권한·경합 테스트 증거
  • 출시 제한, 운영 관측, 복구·중단 방법

구현 중 새로운 규칙이 필요해지면 AI나 개발자가 임의로 확정하지 않습니다. 영향 분석과 승인 경로로 되돌립니다.

CI 초록색의 정확한 의미　마지막 수정 이후의 정확한 PR head 커밋에 필요한 검사가 실행되었는지 확인합니다. 병합 큐가 있다면 최종 병합 후보도 검증합니다. 이전 커밋의 통과, 부분 재실행, 생략된 검사는 별도로 구분해야 합니다. CI 통과는 배포 완료나 운영 검증의 증거가 아닙니다.

출시 시에는 코드 커밋 → 빌드 아티팩트 → 배포 환경을 연결하고 실제 배포된 버전을 확인합니다. 롤백이 데이터 변경을 되돌리지 못한다면 롤포워드, 백업 복원, 기능 중단 등 현실적인 복구 계획을 검토합니다.

한 번에 “기획부터 구현까지 알아서”보다, 입력과 출력이 분명한 역할로 나누고 사람이 업무 결정을 소유합니다.

공통 입력 꾸러미　이번 작업의 목표, 범위·비범위, 권위 있는 원본의 경로와 버전, 관련 ID, 미결정 목록, 허용된 변경 범위, 검증 명령, 중단 조건을 제공합니다. 모든 문서를 무조건 넣기보다 필요한 원본과 관련 연결만 포함합니다.

프롬프트 1　아이디어를 설계 질문으로 바꾸기

역할: 신규 프로젝트 기획 보조.
입력: [아이디어와 관찰], [제약], [알려진 사용자], [기존 문서].
출력: product brief 초안, 사실/가설/미결정 구분, 비범위,
      성공 지표의 측정 정의, 위험도 순으로 정렬한 질문.
규칙: 확인되지 않은 수요·숫자·정책은 추정이라고 표시하라.
      기술 선택을 먼저 확정하지 말고, 질문별 결정권자 역할을 제안하라.
완료 기준: 첫 사용자 시나리오와 먼저 확인할 가정 하나가 보일 것.

프롬프트 2　규칙과 계약을 설계하기

역할: 도메인 및 계약 설계 보조.
기준선: [문서 경로/버전], 대상 요구사항: [REQ ID].
작업: 용어, 상태 전이, 권한, 불변식, API/이벤트 계약,
      실패·중복·타임아웃·늦은 결과를 포함한 설계 초안을 작성하라.
원본 책임: 업무 규칙은 domain, 사용자 약속은 spec,
           화면 표현은 ux, 큰 기술 결정의 이유는 ADR에 둔다.
규칙: 미결정은 선택지·장단점·검증 방법으로 제시하고 확정하지 마라.
출력: 문서별 변경안 + 교차 참조 + 충돌 목록 + 필요한 스파이크.

프롬프트 3　설계를 반박하고 검증 계획 만들기

역할: 독립적인 관점의 설계 리뷰어. 승인자가 아니다.
입력: [문서 기준선], [위험 목록], [검증 결과].
점검: 요구사항↔규칙↔계약↔UX의 모순, 권한 우회, 경합,
      중복 부작용, 결과 불명확성, 운영·복구 누락을 찾는다.
출력 형식: 심각도 | 근거 문서/위치 | 재현 시나리오 |
          영향 | 수정 선택지 | 확인할 실험 | 차단 여부 제안.
규칙: 추측과 확인 사실을 분리하고, 실행하지 않은 테스트를 통과로 쓰지 마라.
      문제를 찾지 못했더라도 검토 범위와 미확인 조건을 명시하라.

프롬프트 4　승인된 수직 기능만 구현하기

역할: 승인된 설계에 따라 구현하는 개발 보조.
기준선: [승인 문서 버전/커밋], 작업: [SLICE ID], 범위: [파일/기능].
절차: 관련 원본과 기존 코드를 읽고 계획·변경 목록을 먼저 제시한다.
      최소 구현 → 지정 테스트 → 회귀 검사 → 결과·차이 보고를 수행한다.
중단 조건: 문서 충돌, 업무 정책 미결정, 권한 확대, 계약 파괴,
          데이터 손실 위험 발견 시 임의 해결하지 말고 결정 요청을 남긴다.
금지: 범위 밖 리팩터링, 테스트 삭제로 통과 만들기, 미실행 검증 주장.
보고: 변경 파일, 연결 ID, 실행 명령과 결과, 미검증 항목, 잔여 위험.

사람이 최종 소유할 결정: 제품 가치와 범위, 가격·환불 등 업무 정책, 법·보안·개인정보 의무, 위험 수용, 출시 승인. AI 역할을 나누더라도 이 책임이 자동으로 이전되지는 않습니다.

11

문서의 양은 팀 규모보다 위험에 맞춥니다

작은 프로젝트는 합치고, 여러 경계와 팀이 생기면 나눕니다. 문서·컨텍스트·보드의 개수를 미리 고정하지 않습니다.

SMALL / LOW COMPLEXITY

작게 시작하는 구성

  • spec/overview.md에 brief, 범위, 수용 기준
  • domain/rules.md에 용어·상태·권한
  • plan/first-slice.md에 순서와 검증
  • UX와 검증 결과는 위 문서의 별도 절로 시작
  • 중요한 결정이 생기면 ADR 추가

파일을 합쳐도 각 절의 원본 책임은 유지합니다. 금전·민감정보·외부 연동이 있으면 작은 팀이라도 필요한 안전 검증은 생략하지 않습니다.

MEDIUM / MULTIPLE BOUNDARIES

경계가 늘어날 때의 구성

  • 공통 brief와 용어집을 진입점으로 유지
  • 업무 능력·책임 경계별 domain/spec 분리
  • API·이벤트 계약과 소유자 명시
  • architecture에서 경계·통합·운영 연결
  • validation에서 위험별 증거와 잔여 위험 관리

문서를 나눌 신호는 길이보다 동시 변경, 다른 승인자, 독립된 계약과 생명주기입니다. 같은 규칙이 여러 곳에서 수정되면 책임 분리를 다시 검토합니다.

이 체크리스트는 검토를 돕는 개인용 도구입니다. 체크 표시 자체가 승인이나 실행 증거를 대신하지 않습니다.

0 / 18 항목 확인

체크 상태는 이 브라우저의 로컬 저장소에만 저장됩니다. 파일 위치나 브라우저가 바뀌면 유지되지 않을 수 있으며, 서버로 전송하지 않습니다.

18개를 전부 체크해야 항상 착수 가능한 것은 아닙니다　해당하지 않는 항목은 검토 기록에 이유를 남기고, 위험 수준에 맞춰 게이트를 조정합니다. 반대로 체크가 끝났더라도 핵심 위험이 해결되지 않았다면 관련 구현·출시는 보류합니다.

가장 작은 유효한 기준선부터 시작하세요

완벽한 문서 체계를 먼저 만드는 대신, 한 기능의 약속을 명확히 하고 끝까지 검증합니다.

흔한 실패대신 할 일
문서 양과 폴더 개수를 진척으로 판단결정된 질문, 해결된 위험, 실행된 검증으로 진척을 판단합니다.
같은 규칙을 spec·domain·UX에 복사규칙의 원본 하나를 정하고 나머지는 ID와 링크로 참조합니다.
화면 정상 경로만 상세히 설계권한·중복·경합·시간초과·복구를 같은 기능의 일부로 다룹니다.
AI가 그럴듯하게 채운 빈칸을 확정가정·제안·미결정을 표시하고 결정권자와 증거를 붙입니다.
설계 승인 후 문서를 동결구현에서 발견한 사실을 변경 절차로 반영하고 기준선을 갱신합니다.
Accepted ADR을 새 결론으로 덮어쓰기새 ADR과 상호 링크로 결정의 계보를 보존합니다.
테스트 통과나 CI 초록을 출시 완료로 해석정확한 코드 버전, 배포된 아티팩트, 운영 상태를 각각 확인합니다.
첫 주에 미래 기능 전체를 설계다음 수직 기능을 막는 결정과 가장 큰 위험부터 다룹니다.

30분 빠른 시작

  1. 5분　사용자, 문제, 기대 가치, 이번 비범위를 각각 한 문장으로 씁니다.
  2. 10분　대표 기능 하나의 정상·실패·중복·지연 시나리오를 적습니다.
  3. 5분　업무 규칙과 계약의 원본 위치, 결정권자 역할을 정합니다.
  4. 5분　가장 위험한 가정 하나와 그것을 확인할 실험을 고릅니다.
  5. 5분　다음 작은 구현 범위와 “끝났다고 말할 조건”을 적습니다.

30분의 결과는 구현 승인이 아니라, 다음 결정과 검증이 보이는 초안입니다. 이후에는 “더 많이 쓰기”보다 모호함을 없애고 증거를 연결하기에 시간을 쓰세요.

기억할 한 문장　제품의 의도는 spec에, 업무의 진실은 domain에, 상호작용은 계약과 UX에, 결정의 이유는 ADR에, 실행 순서는 plan에 둡니다. 그리고 이 모든 것을 하나의 요구사항에서 테스트와 운영 증거까지 이어지는 연결로 만듭니다.
