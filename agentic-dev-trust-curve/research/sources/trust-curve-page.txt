    "에이전트를 믿지 못하면, 당신은 영원히 마이크로매니저다."

    에이전트의 결과를 믿을 수 있어야 → 병렬화 가능 → 자동 머지 가능. 신뢰는 '느낌'이 아니라 3개의 시스템으로 만든다.

      1VERIFICATION — 에이전트가 스스로 앱을 실행·측정·확인한다

      2SKILLS + EVALS — 실패 패턴을 스킬로 만들고, 스킬을 테스트한다

      3ARCHITECTURE — "가장 짧은 길 = 가장 좋은 길"이 되게 코드베이스를 설계한다

    결과: 아침에 일어나면 PR 20개가 이미 main에 머지되어 있다.

  The Trust Curve
  신뢰 곡선 — 지름길은 없다

  Lauren이 직접 그린 "비과학적" 차트. 신뢰가 쌓일수록 자율성과 병렬 규모가 커진다. 단계를 건너뛸 수는 없다.

    1
모든 출력을 지켜봄1~3개 로컬 에이전트. in-the-loop. 병렬화 불가.

    2
에이전트가 스스로 검증검증 스킬로 "맞는 코드"를 확인. 사람은 PR만 리뷰.

    3
클라우드 에이전트버그 리포트 같은 신호를 스스로 집어 PR 생성.

    4
자동 머지main에서 사후 리뷰. PM·디자이너도 기여.

  ⚠️①에서 바로 "클라우드 에이전트 1,000개"로 점프하면 토큰만 태우고 결과는 쓰레기. 반드시 단계를 밟을 것.

  "에이전트 1개의 출력도 못 믿는데 100개를 띄울 수는 없다."

  Chapter by chapter
  타임라인

    00:00오프닝 — AI는 페어 프로그래머다"생각을 외주화"하면 안 된다. 코드 작성 시간은 줄지만 리뷰·수정 시간이 늘어나는 경험.

    01:22큰 주제: 신뢰에이전트가 "smoking gun을 찾았다"고 100번째 자신 있게 틀릴 때 신뢰를 잃는다 → 매니저의 마이크로매니지먼트와 같은 상태.

    02:35신뢰 곡선1년 전엔 모두 in-the-loop. 5개월간 곡선을 올라 지금은 에이전트가 PR을 자동 머지.

    04:49기여 그래프입사 후 기여도가 급증. 월 1,000 PR.

    05:29가장 중요한 스킬 = Verification에이전트가 직접 실행·트레이스·힙 스냅샷·시뮬레이터로 확인. "좋은 코드"는 보장 못 해도 "맞는 코드"는 보장.

    07:17사례: Agents Window (코드명 Glass)입사 첫 주, 출시 1주 전. Chrome DevTools 플레임 그래프를 본인도, 에이전트도 못 읽음 → 스크린샷 붙이고 추측하는 느린 루프.

    09:08control-glass 스킬에이전트에게 Chrome DevTools Protocol(CDP)로 앱을 조작·측정하는 법을 가르침. "사람이 검증자이면 사람이 병목."

    10:39Feature Map스킬이 있어도 에이전트가 "사이드바가 뭔지" 모름 → 모든 기능의 위치·진입 경로·단축키·DOM 셀렉터를 적은 지도. "??? + 스크린샷" 수준의 리포트도 처리 가능.

    13:33pstack 소개Y Combinator CEO Garry Tan의 gstack을 패러디한 "potato stack". 플러그인을 만들 생각은 없었고, 스킬이 하나씩 쌓인 결과.

    14:35how 스킬툴 콜을 열어보니 에이전트가 영향받을 코드를 읽지도 않고 단정 → "추측 금지, 서브에이전트로 실제 검색" 스킬로 캡슐화.

    15:49매니저 비유"코딩은 잘하지만 비즈니스 맥락이 0인, 5초 전에 입사한 엔지니어"를 가르치는 방법 = 스킬(마크다운). 고품질 토큰이 모델을 "더 똑똑한 latent space"로 끌어올림.

    17:40Eval = 에이전트용 단위 테스트코디네이터가 루브릭 작성 → 서브에이전트 다수 생성 → 평가 중임을 숨긴 디렉터리명(에이전트가 알면 행동이 바뀜) → 여러 모델에 걸쳐 매트릭스 평가.

    19:49스킬 유지보수스킬을 바꿀 때마다 eval 실행. 유지보수는 "taste와 관찰"이 필요. 백시트 드라이버가 되어 툴 콜·thinking 블록을 모두 읽어라.

    21:02Hill-climbing다른 모델을 judge로 써서 편향 교차검증. /loop로 "모두 10/10이 될 때까지" 반복.

    22:23헤드 셰프 비유당신은 더 이상 요리하지 않는다. 주방(환경)을 설계하고 스테이션에 일을 배정한다.

    23:41어디서 시작?로컬에서. 에이전트가 앱을 띄우고 API를 호출하는 모습을 관찰할 수 있어야 한다.

    24:15클라우드 에이전트환경 세팅에 시간을 들이면 개인→팀→회사 전체가 이득.

    25:36Benny 에이전트버그 리포트를 받아 클라우드 데스크톱에서 Cursor를 띄우고 같은 control 스킬로 재현 → "이미 main에서 고쳐짐"까지 자동 확인.

    26:50경고신뢰 없이 수천 개의 클라우드 에이전트로 점프 = 토큰 낭비.

    27:20호스트 중간 정리① 검증 스킬 → ② 로컬 신뢰 → ③ 클라우드 스케일 → ④ 자동 머지 + main 사후 리뷰.

    28:24"나를 믿지 말라"pstack은 지름길이지만 포크해서 자기 것으로 만들어라. 각자의 엔지니어링 기준을 스킬에 인코딩.

    29:043번째 축: 리라이트업계 최대 논쟁. Lauren은 조건부 찬성.

    30:18Brownfield vs Greenfield빅테크 인프라(가드레일, 권한 제한)는 "가장 못하는 엔지니어"를 위해 설계됨 → 에이전트에게도 잘 맞음. "AI slop 전에 human slop이 있었다."

    32:13Greenfield = 최대 리스크 & 기회Grockbot(전날 출시, 에이전트 오케스트레이션 앱)은 바이브코딩으로 탄생. 가드레일 0 → "organic architecture"로 통제 불능.

    33:34600+ PR 리팩터링강한 제약을 넣어 Dune 아키텍처로 전환. 이제 코드를 거의 안 본다. 디자이너·PM·GTM도 기능 추가 가능.

    35:35PR 크기하드 캡 없음. git history가 풍부한 컨텍스트이므로 원자적 PR 선호 → 리버트·원인 추적 용이. (가상화 라이브러리 Pretext 언급)

    37:29Dune 아키텍처 & CI"Electron용 Next.js, 에이전트가 쓰도록 설계". useEffect 금지, 코드 주석 금지, main/renderer 임포트 경계 검사, Bugbot.

    40:08왜 그렇게 엄격한가Agents Window는 아직 이 아키텍처가 없어 성능 회귀가 끝없이 발생. 렌더러 스레드 오염 → 16ms 초과 → jank.

    42:06집행 레이어아키텍처(최강) > CI/린트/컴파일러(하드) > 룰/스킬/Bugbot/스타일가이드(소프트). 소프트만 있으면 "코드베이스가 쓰레기가 되는 건 시간 문제".

    43:20설계 원칙"The shortest path is the best path." 에이전트는 지름길을 좋아하니, 지름길을 정답으로 만들어라. 기능 = 한 디렉터리에 colocated.

    45:24언어 선택Rust 인기 재점화는 컴파일러의 엄격함 때문. unsafe만 막으면 "컴파일 = 대체로 동작".

    46:42코드 리뷰 = 안티패턴사람이 PR 코멘트로 불변식을 지키고 있다면 그건 code smell. 린트/CI/카테고리 제거로 바꿔라.

    47:45Q: 토큰 비용AI 랩 소속으로 토큰 무제한임을 인정. 그러나 ROI 질문: "사람 1명 더 고용 vs 가장 멍청한 에이전트도 잘하도록 코드베이스 세팅".

    50:17에이전트의 진짜 가치"혼자서는 몇 년 걸릴 제약 집행을 가능하게 한다." 토큰 절약이 아니라 이전엔 불가능했던 일.

    50:58Grok 4.6 발표4.5와 동일 토큰 단가로 더 높은 지능. 비용-지능 파레토 프런티어 최적화.

    52:16Q: 제품팀은 어떻게 따라가나Grockbot = 비개발자의 "Cursor 모먼트". iMessage 같은 UI. PM이 "버그 고쳤어요, 봐주세요" → 완벽 → stamp.

  Pillar 1
  Verification — 에이전트가 직접 확인하게 하라

  문제: 사람이 검증자면 사람이 병목이다

    ❌ Before
프롬프트→에이전트 코드 작성→사람이 dev 빌드 실행→스크린샷·콘솔 복붙↺
느림 · 병렬화 불가 · 추측 반복

    ✅ After
프롬프트→에이전트 코드 작성→에이전트가 앱 실행 (CDP)→트레이스·스냅샷 측정→PR
자동 · 병렬 가능 · 사람은 결과만 리뷰

  control-glass 스킬이 하는 일

    Electron / 웹 앱 → Chrome DevTools Protocol로 클릭·입력·트레이스·힙 스냅샷

    iOS 앱 → Apple 시뮬레이터 유틸리티로 프로그래매틱 제어

    코드 자체는 "별로 흥미롭지 않다. 에이전트가 쉽게 만들어 준다"

  🗺 Feature Map — 스킬의 숨은 핵심

    항목내용

    왜 필요한가스킬이 있어도 에이전트는 "왼쪽 사이드바가 렉 걸린다"가 어디인지 모른다. 코드만 뒤지며 허우적댐.

    무엇을 담나기능 목록, 사용자 관점 진입 경로, 서브 기능, 키보드 단축키, CDP 셀렉터용 DOM 속성

    효과"??? + 스크린샷" 수준의 저품질 리포트도 재현 가능

    유지pstack의 create-verification 스킬이 초기 맵을 생성, maintain-verification 스킬이 갱신

  ☁️ Benny — 검증 스킬이 클라우드에서 하는 일

  Slack 버그 리포트→Benny (클라우드 에이전트)→클라우드 데스크톱에서 Cursor 실행→control 스킬로 재현→"재현됨. main에서 이미 수정됨. 새 빌드만 릴리스하면 됨."

  💡한 사람이 1시간 붙잡고 "고쳐졌나? 안 고쳐졌나?" 할 일을 자동으로 처리. 팀 전체, 회사 전체가 이득.

  Pillar 2
  Skills + Evals — 관찰하고, 스킬로 만들고, 테스트하라

    스킬이란? 마크다운 파일 = "5초 전 입사한, 코딩은 잘하지만 맥락은 0인 엔지니어"에게 주는 온보딩 문서 = 고품질 토큰을 먼저 넣어 모델을 "더 똑똑한 latent space"로 끌어올리는 장치.

  pstack이 만들어진 과정 (의도된 설계 ✗, 점진적 축적 ✓)

    관찰된 실패→ 만든 스킬

    "코드를 안 읽고 단정한다"how 스킬: 추측 금지, 서브에이전트로 검색

    "앱을 못 다룬다"control-glass 스킬

    "기능이 어디 있는지 모른다"Feature Map

    "스킬이 잘 작동하는지 모른다"Eval Playbook

  Eval = 에이전트용 단위 테스트

    파이프라인
코디네이터가 루브릭 작성

다른 모델의 Judge가 점수 + 편향 교차검증
/loop "전부 10/10까지 반복" → hill-climbing

    포인트
특별한 프레임워크 불필요. 엄격함은 본인 선택
Cursor는 여러 모델 지원 → 모델 매트릭스로 스킬 평가
스킬을 수정할 때마다 eval 실행
검증 스킬 자체도 같은 방법으로 검증 (verify the verifier)

  스킬 유지보수의 현실

  "꽤 어렵다. taste와 관찰이 필요하다. 좋은 백시트 드라이버가 되어야 한다."

    초기 단계에선 수동적 관찰자가 아닌 운전석에 앉아라

    모든 툴 콜, 읽은 코드, thinking 블록을 열어 보라 → 실패 지점이 보인다 → 스킬로 만든다

  🧑‍🍳헤드 셰프 비유. 당신은 더 이상 요리하지 않는다. 주방(환경)을 설계하고 스테이션에 일을 배정한다.

  Pillar 3
  Architecture — 가장 짧은 길이 가장 좋은 길이 되게 하라

  리라이트 논쟁: Brownfield vs Greenfield

    🏢 Brownfield (빅테크형)🌱 Greenfield (바이브코딩 프로토타입)

    상태프레임워크, 컨벤션, 가드레일, 권한 제한 이미 존재가드레일 0, 사람은 코드를 읽지 않음

  AI Agentic Coding
  교훈 12가지

    L1신뢰는 감정이 아니라 시스템이다
못 믿는 건 당신 탓도 모델 탓도 아니다. 검증·스킬·제약이 없기 때문이다. 시스템을 만들면 신뢰는 따라온다.

    L2당신이 검증자면 당신이 병목이다
스크린샷 복붙 루프에 있다면 병렬화는 불가능하다. 에이전트가 스스로 실행하고 측정하게 하는 것이 첫 번째 투자다.

    L3"맞는 코드"와 "좋은 코드"는 다르다
검증은 correctness를 준다. quality는 아키텍처와 집행 레이어가 준다. 둘을 혼동하지 말라.

    L4매니저처럼 생각하라
"5초 전 입사한, 코딩만 잘하는 신입"에게 무엇을 줄 것인가? 온보딩 문서(스킬), 환경(아키텍처), 피드백 루프(eval).

    L5헤드 셰프처럼 일하라
당신은 더 이상 요리하지 않는다. 주방을 설계하고 스테이션에 일을 배정한다. 환경 설계가 곧 당신의 코드다.

    L6지름길을 정답으로 만들라
"The shortest path is the best path." 금지하는 것보다 올바른 길이 가장 쉬운 길이 되게 설계하라.

    L7코드 리뷰 코멘트는 code smell이다
사람이 반복적으로 "이거 하지 마세요"라고 말한다면, 그건 린트·CI·아키텍처로 승격해야 할 신호다.

    L8소프트 규칙만으로는 코드베이스가 썩는다
AGENTS.md, 스킬, Bugbot은 유용하지만 에이전트는 잊는다. 하드 집행(CI 빨간불) 없이는 "시간 문제".

    L9단계를 건너뛰지 말라
1~3개 로컬 에이전트 → 검증 → 클라우드 → 자동 머지. 신뢰 없이 규모를 키우면 토큰 소각이다.

    L10남의 플러그인을 믿지 말고 포크하라
pstack조차 "맹목적으로 믿지 말라". 당신 팀의 엔지니어링 기준을 당신의 스킬에 인코딩하라.

    L11그린필드가 가장 위험하다
바이브코딩 프로토타입은 가드레일이 0이다. 초기에 강한 제약을 넣지 않으면 organic architecture로 통제를 잃는다.

    L12에이전트의 가치는 "불가능했던 일"이다
토큰 절약이 아니다. 혼자서는 수년이 걸릴 제약 집행, 리팩터링, 검증을 가능하게 하는 것이 진짜 ROI다.

  Actionable
  실전 팁 체크리스트

  체크 상태는 이 브라우저에만 저장됩니다.

    🔍 관찰 & 디버깅

      에이전트가 "범인을 찾았다"고 할 때 툴 콜을 열어 실제로 관련 코드를 읽었는지 확인하라
      thinking 블록과 읽은 파일 목록을 보라. 실패 패턴이 반복되면 → 스킬 후보
      초기엔 운전석에 앉아 백시트 드라이버처럼 질문하라 ("왜 그걸 안 읽었어?")

    ✅ 검증 스킬 만들기

      로컬에서 시작. 에이전트가 앱을 띄우고 조작하는 걸 눈으로 보라
      앱 종류별 제어 수단: 웹/Electron → CDP, iOS → 시뮬레이터, CLI → 직접 실행
      Feature Map 작성: 기능명 / 진입 경로 / 단축키 / DOM 셀렉터. 에이전트에게 초안 생성시키기
      검증 스킬 자체도 eval로 검증하라 (verify the verifier)

    🧪 스킬 & Eval

      스킬은 한 번에 하나, 실제로 관찰한 실패 패턴에서만
      eval 구조: 코디네이터(루브릭) → 서브에이전트 N개(격리 디렉터리) → 다른 모델의 judge → 점수
      디렉터리명에 "eval", "test" 같은 단어를 넣지 말라. 눈치채면 행동이 바뀐다
      스킬 수정 시마다 eval 실행. /loop로 "10/10까지" hill-climb
      자주 쓰는 모델들로 매트릭스 평가

    🏗 아키텍처 & 집행

      기능 = 디렉터리 하나. 관련 코드를 colocate해서 grep 탐색을 없애라
      "에이전트가 못하는 것" 발견 → 린트 룰 / CI 체크 / 임포트 경계로 하드 집행
      의존성 그래프 검사를 CI에 넣어 레이어 간 교차 임포트 차단
      코드 주석 금지를 검토하라. 에이전트 주석은 대개 무관한 역사 기록
      소프트 레이어(rules/skills/Bugbot)는 보조로 쌓되 유일한 집행 수단으로 삼지 말라
      엄격한 컴파일러 언어(예: Rust)를 고려하라. 컴파일 = 신뢰
      PR을 원자적으로 쪼개라. git history를 컨텍스트 자산으로 관리

    ☁️ 스케일링

      로컬 신뢰 → 클라우드 에이전트 순서를 지켜라
      반복 업무(버그 재현, 회귀 확인)를 자동 트리거 에이전트(Benny 패턴)로
      자동 머지는 마지막 단계. 그 전에 CI가 모든 불변식을 지키는지 확인
      비개발자(PM/디자이너)가 안전하게 기여할 수 있는지 = 제약이 충분한지의 리트머스 테스트

    💸 비용 관리

      리팩터링·세팅 비용은 선불. "고용 vs 토큰"으로 ROI 계산
      제약이 강한 코드베이스에선 더 작은/저렴한 모델도 잘함 → 장기 비용 절감
      신뢰 없이 규모 확장 = 가장 비싼 실수

  Self-check
  나의 로드맵 — 지금 어디에 있는가?

Stage 0 · "기능 만들어달라고 하고 결과를 복붙 검증"→ 할 일: 툴 콜 열어보기. 실패 패턴 기록 시작.

Stage 1 · "로컬 에이전트 2~3개, 모든 출력을 지켜봄"호스트 & 대부분의 청중→ 할 일: 검증 스킬 1개 + Feature Map. 사람이 병목인 지점을 제거.

Stage 3 · "클라우드 에이전트가 신호를 집어 PR 생성"→ 할 일: 아키텍처 제약 하드 집행. CI 금지 목록. 임포트 경계.

  Remember
  기억할 문장들

    AI의 최선의 용도는 페어 프로그래머다. 코드 작성을 대체하거나, 더 나쁘게는 생각을 외주화하는 도구가 아니다.

    에이전트 1개의 출력도 못 믿으면서 100개를 띄울 수는 없다.

    검증은 좋은 코드를 보장하지 않는다. 하지만 맞는 코드를 쓰게 한다. 그게 신뢰의 큰 한 걸음이다.

    AI slop 이전에 human slop이 있었다.

    The shortest path is the best path. 에이전트는 지름길을 택한다. 그러니 지름길을 최선의 길로 만들라.

    사람이 PR 코멘트로 규칙을 지키게 하고 있다면, 매번 그것을 code smell로 여겨라.

    룰과 스킬과 스타일가이드만 있다면, 코드베이스가 쓰레기가 되는 건 시간 문제다.

    나를 믿지 말라. pstack을 포크해서 당신의 것으로 만들라.

    에이전트의 가치는 토큰을 아끼는 게 아니다. 이전엔 할 수 없었던 일을 하게 해주는 것이다.
