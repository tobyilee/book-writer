## 편집자가 남긴 질문 세 가지 — 판정

## 조정자가 짚은 질문: "훅은 로컬 세션에서만 돈다"는 맞는가

**맞지 않다.** 6장 "둘째 겹은 CI다. 훅은 로컬 세션에서만 돈다."는 1차 출처와 어긋난다.

- `claude-code-action`은 Claude Code를 Agent SDK로 띄우면서 설정 원천을 기본으로 `["user", "project", "local"]`로 둔다(`parse-sdk-options.ts`: "otherwise use all sources … e.g., `--setting-sources user` to avoid in-repo configs"). 그러니 체크아웃한 저장소의 `.claude/settings.json` 훅은 8장의 구현 잡과 수정 잡에서도 돈다. 이 책 안에서도 5·9장이 이미 "`--bare` 없이 `-p`를 돌리면 프로젝트 훅을 실행한다"고 적었으니, 6장의 문장은 책의 다른 문장과도 부딪힌다.
- PR 이벤트에서는 액션이 `.claude/`, `CLAUDE.md` 등을 PR의 base 브랜치 판으로 되돌린 뒤 Claude를 띄운다. 다만 그 훅이 저장소 안의 스크립트나 실행 가능한 프로젝트 설정을 읽는 도구를 부르면, 그 명령은 PR이 가져온 파일로 풀린다(`docs/security.md`).

이 사실이 책에 주는 의미는 두 갈래다.

1. **걱정하던 경로는 막혀 있다.** 구현 잡이 한 실행 안에서 `check.sh`를 고치고 바로 돌리는 경로는, Claude Code 잡에서도 가드 훅이 `scripts/dev/` 편집을 막으므로 편집 도구로는 열리지 않는다. 책의 억제는 6장 문장이 말하는 것보다 오히려 튼튼하다.
2. **9장이 밝혀야 할 남는 한계가 있다.** 6장은 "에이전트가 고칠 수 있는 스크립트의 실행을 허락하면 무엇이든 실행하게 허락한 것과 다르지 않다"고 쓴다. 그런데 같은 논리가 테스트에도 적용된다. `check.sh`는 에이전트가 방금 쓴 테스트와 빌드 스크립트를 실행하고, 구현 잡에서는 에이전트가 그 파일들을 써야만 일이 된다. 그러니 `scripts/dev/`를 보호해도 허용 목록이 "실행할 수 있는 것"을 묶지는 못한다. 구현·수정 잡이 실제로 억제되는 근거는 다음 넷이다. 잡이 쥔 토큰의 범위(앱 토큰으로 자기 브랜치·draft PR·코멘트, 머지 명령 없음), 브랜치 보호, 배포·클라우드 비밀이 그 잡에 없다는 점, 그리고 사람 게이트다. 9장의 "허용한 `check.sh`도 에이전트가 고쳐 놓고 실행하면 이 목록을 뚫는 구멍이 된다 … 넣어 둔 이유다"는 그 구멍이 닫혔다고 읽힌다. 또 두 행의 "나갈 수 있는 곳"은 실행된 테스트 코드가 러너의 네트워크를 쓸 수 있다는 점(이그레스를 묶지 않은 GitHub 호스트 러너라면)을 빠뜨린다.
