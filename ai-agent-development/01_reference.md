# AI Agent 개발 레퍼런스 — 원리부터 프레임워크·데이터·평가·운영까지

**대상 독자:** LLM API(chat completion, tool use)는 써봤지만 에이전트를 직접 설계·배포·운영해본 적 없는 백엔드/풀스택 개발자 및 테크리드. 실무 도입을 앞두고 "무엇을 어떻게 조합할지" 결정해야 하는 사람.

**검색 시점: 2026-07-25 기준.** 이 문서의 모든 버전·가격·점수는 그날 확인된 값이다.

## 0. 이 문서를 쓰는 법 (저술가·fact-checker 필독)

이 책은 도구 서베이다. 본문에 버전·수치·기능 주장이 촘촘히 들어가고, Phase 4의 fact-checker가 그 주장을 **이 문서와 대조**해 판정한다. 따라서 세 가지 규율이 있다.

1. **버전·가격·점수를 쓸 때는 반드시 아래 「신선도 원장」의 표에서 값을 가져온다.** 원장에 없는 값을 기억으로 쓰면 안 된다. 원장의 모든 버전 셀은 2026-07-25에 `gh api` / PyPI / npm 레지스트리 / 공식 문서 fetch로 실제 확인된 값이다.
2. **「단정 금지 목록」(§7.2)에 있는 항목은 본문에서 수치로 단정하지 않는다.** 확인되지 않은 값이다. 특히 **MTEB·SWE-bench·GAIA 리더보드 점수와 Cohere 토큰 단가**가 여기 속한다.
3. **버전·릴리스는 "{버전}/{연도} 기준"으로 못 박아 쓴다.** 예: "LangGraph 1.2.9(2026-07 기준)". 이 분야는 6개월이면 낡는다.

### 0.1 증거 등급 A / B — 섞어 쓰면 안 된다

리서치 과정에서 **수치의 신뢰도가 두 등급으로 갈린다는 것이 실증적으로 드러났다.** 이 구분을 무시하면 사실 오류가 들어온다.

| 등급 | 무엇 | 취급 |
|------|------|------|
| **A · 결정론적 API** | §신선도 원장 표 A~K의 **버전·라이선스·날짜·스타** 열 전부. `gh api` / PyPI JSON / npm registry 직접 호출값 | **그대로 인용 가능** |
| **B · 페이지 요약 경유** | 비용·지연·한도 수치, 블로그 인용문·수치, 가격표 | **인용 전 원문 대조 필요.** "2026-07 기준" 단서 필수 |

> **이 구분이 필요한 이유 — 실제로 발생한 오류 2건:**
> 1. web #1의 1차 수집이 우아한형제들 글의 컨텍스트 감소 수치를 "약 20,000 bytes → 약 1,000 bytes"로 뭉갰다. **원문에 존재하지 않는 숫자였다.** 재확인 결과 실제는 규모별 3행 표였다.
> 2. web #2의 페이지 요약 모델이 OpenAI의 "62,500 pages per dollar" 표기를 잘못된 ¢/1M 단가로 환산했다. 해당 값은 전량 폐기됐다.
>
> 두 오류 모두 **그럴듯했고**, 재확인 없이는 통과했을 것이다. B등급 수치를 본문에 박을 때는 원문을 한 번 더 열어라.

> **리서치 구성:** web-researcher 2명(1차 소스·정규화 표), paper-researcher(학술 계보·평가 방법론), community-researcher(운영 현실)를 병렬로 돌렸다. 원본은 `research/web.md`(+`web_frameworks.md`·`web_data_eval.md`), `research/papers.md`, `research/community.md`에 보존돼 있다 — 삭제하지 말 것.

## 1. 개념과 정의 (축 1)

### 1.1 에이전트와 워크플로의 경계 — 이 책의 출발점

이 구분이 업계 공용어가 된 출처는 Anthropic이다.

> **Workflows:** *"Systems where LLMs and tools are orchestrated through predefined code paths."*
> **Agents:** *"Systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks."*
> — Anthropic, *Building effective agents*, **2024-12-19** (웹)

같은 글이 제시한 **워크플로 패턴 5종**이 사실상 표준 분류가 됐다: prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer.

판단 기준도 같은 글에 있다. 워크플로는 서브태스크가 고정적이고 일관성이 우선일 때. 에이전트는 단계를 미리 정할 수 없는 열린 문제일 때. 대가는 *"higher costs, and the potential for compounding errors"*이며, *"extensive testing in sandboxed environments, along with appropriate guardrails"*를 요구한다.

**중요한 신선도 메타:** 이 글은 2024-12-19 발행으로 **약 1년 7개월 지났다.** 정의·패턴 분류는 계속 인용되지만, 글 안의 프레임워크 언급 부분은 구버전 정보다.

두 번째 벤더가 같은 결론에 독립적으로 도달했다는 점이 이 절의 무게를 만든다.

> *"If you can write a function to handle the task, do that instead of using an AI agent."*
> — Microsoft Learn, *Agent Framework Overview*, **2026-07-10 갱신** (웹)

Microsoft는 아예 공식 판단 표를 제공한다 — **에이전트** = 열린/대화형·자율적 도구 사용과 계획 / **워크플로** = 단계가 정의됨·실행 순서의 명시적 제어·다수 에이전트 조율 필요.

### 1.1.1 에이전트 루프의 학술 계보 (논문)

> 인용 규율: 아래 arXiv ID·저자·리비전일은 모두 **제목 검색으로 해석**한 값이다(기억한 ID로 조회하지 않음 — 그러면 "존재하는 다른 논문"이 나와 그럴듯한 오인용이 된다). **`발표처 미확인`은 "아마 맞지만 확인하지 않았다"는 뜻이므로 "ICLR 2023에서 발표된 ReAct"처럼 쓰면 안 된다.**

| 논문 | 출처 | 실무자에게 의미하는 것 |
|------|------|---------------------|
| **ReAct** (Yao et al., 2022) | arXiv:2210.03629v3 (v1 2022-10-06 / v3 2023-03-10), 발표처 미확인 | 오늘 쓰는 거의 모든 루프(think→tool→observe)의 조상. 핵심 함의: **"생각"은 장식이 아니라 도구 호출 오류를 잡는 채널**이다. 대가는 스텝마다 히스토리 재전송 |
| **Chain-of-Thought** (Wei et al., 2022) | arXiv:2201.11903v6, 발표처 미확인 | "단계별로 생각하라"의 뿌리. **원논문 주장 범위는 산술·상식·기호 추론**이다 |

### 1.2 도구 호출 프로토콜 — MCP

**현행 스펙 리비전은 `2025-11-25`다** (2026-07-25 확인, `modelcontextprotocol.io/specification/latest`가 이 리비전 schema를 authoritative로 지목). **2026년에 새 리비전이 나오지 않았다 — 스펙은 안정화 국면이고 움직이는 건 SDK와 레지스트리다.**

> ⚠️ **자주 틀리는 지점:** MCP 리비전을 `2025-06-18`로 쓴 자료가 아직 많다. 현행은 `2025-11-25`다.

- **아키텍처:** JSON-RPC 2.0, 상태 유지 연결, 능력 협상(capability negotiation)
- **3역할:** Hosts(연결을 시작하는 LLM 앱) / Clients(호스트 내 커넥터) / Servers(컨텍스트·능력 제공)
- **서버가 제공:** Resources(컨텍스트·데이터) / Prompts(템플릿 워크플로) / Tools(모델이 실행하는 함수)
- **클라이언트가 제공:** Sampling(서버 주도 재귀 LLM 호출) / Roots(URI·파일시스템 경계) / Elicitation(서버 주도 추가 정보 요청) — **대부분의 한국어 자료가 빠뜨리는 부분이라 차별점이 된다**
- **설계 계보:** 스펙 스스로 **Language Server Protocol(LSP)**에서 영감을 얻었다고 밝힌다 → 백엔드 개발자에게 MCP를 설명하는 최적의 비유
- **보안 인용:** *"Tools represent arbitrary code execution and must be treated with appropriate caution."* / *"descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server."*

### 1.3 에이전트 간 통신 — A2A (MCP와 혼동 금지)

**A2A v1.0.0** (릴리스 2026-05-28). 핵심 개념: **Agent Card**(*"A JSON metadata document ... describing its identity, capabilities, skills, service endpoint, and authentication requirements"*), **Task**(*"The fundamental unit of work managed by A2A ... stateful and progress through a defined lifecycle"*), Message, Artifact, SSE 스트리밍, 웹훅 푸시. 바인딩 3종(JSON-RPC 2.0 / gRPC / HTTP+JSON).

> **책에서 반드시 구분해야 하는 지점:** MCP = 에이전트↔도구/컨텍스트(**수직**). A2A = 에이전트↔에이전트(**수평**). 둘은 경쟁이 아니라 직교하며, Google ADK는 양쪽을 동시에 내장한다.

⚠️ A2A를 "Google 프로젝트" 또는 "Linux Foundation 프로젝트"로 단정하면 안 된다 — 스펙 사이트는 `a2aproject` 커뮤니티 거버넌스만 명시한다. (Linux Foundation 귀속이 확인된 것은 **AGENTS.md** — Agentic AI Foundation 산하)

### 1.4 2026년의 새 층 — SDK 위의 "harness"

이번 리서치의 가장 신선한 발견이다. **"프레임워크를 고른다"가 더 이상 마지막 결정이 아니다.** 벤더 네 곳이 같은 용어를 동시에 채택했다.

> **수 정정 (Phase 4 오케스트레이터, 2026-07-26):** 이 문장은 최초 작성 시 "벤더 3곳"이었으나, 아래 열거된 제품은 **네 조직에서 나온 네 개**다 — LangChain(`deepagents`) / AWS(Strands Harness) / Microsoft(Agent Framework Harness) / Anthropic(Claude Agent SDK). Writer A가 4장 저술 중 이 산수 불일치를 발견해 보고했다. **본문에서 이 수를 인용할 때는 "네 곳"이거나, 수를 세지 않는 표현("여러 벤더가 비슷한 시기에")을 쓴다.**

- **SDK 층** — 루프·도구 호출·핸드오프만 제공. OpenAI Agents SDK: *"very few abstractions"*, 원시 개념 5개(Agents/Handoffs/Guardrails/Sessions/Runner)
- **harness 층** — 계획·todo 추적·컨텍스트 압축·파일/메모리 접근·도구 승인 정책·관측을 **미리 조립해서** 준다
  - `deepagents` — "The batteries-included agent harness" (LangGraph 위)
  - **Strands Harness** — 레포가 `strands-agents/sdk-python` → **`strands-agents/harness-sdk`로 개명**
  - **Microsoft Agent Framework의 Harness** — *"An opinionated agent with batteries-included capabilities for long, multi-step tasks — planning and todo tracking, context compaction, file access and memory, don't-ask-again tool approval, and observability."*
  - **Claude Agent SDK** — Claude Code의 harness를 그대로 라이브러리화

한국에서도 같은 용어가 쓰인다. 우아한형제들(2026-04-17)은 *"AI가 길을 잃지 않고 안정적으로 일할 수 있도록 외부 통제 환경을 구축하는 것"*으로, AWS Korea(2026-04-22)는 *"마구(馬具)처럼 에이전트의 행동을 묶고, 방향을 잡고, 안전하게 제어하는 구조"*로 정의한다.

**언제 harness인가:** 긴 다단계 작업(코딩·리서치 에이전트)이면 harness부터 본다. 도구 호출 1~3회짜리 짧은 작업이면 SDK만으로 충분하고 harness는 오히려 비용·지연을 늘린다.

## 2. 핵심 관점들 — 선택의 축 (축 2·3·5)

독자는 결정을 내려야 하는 사람이다. 그래서 "무엇이 있나"보다 **"무엇으로 갈리나"**를 축으로 정리한다.

### 2.1 프레임워크 선택 축 (축 2)

> 전체 도구 레코드는 §신선도 원장 「표 A」(25행) 참조.

**축 ①: 명시적 그래프 상태 ↔ 역할 기반 자율 위임**

- **LangGraph (명시적 극단).** 공식 정의: *"a low-level orchestration framework and runtime for building, managing, and deploying long-running, stateful agents"*, *"mix deterministic, hand-coded steps with LLM-driven agentic steps in the same graph"*. **고를 때:** 감사 추적·재개·HITL 승인이 요구사항일 때, 상태 전이를 코드로 설명해야 하는 규제 도메인. **대가:** 보일러플레이트 — 공식 문서 스스로 초보자에게는 `langchain`의 `create_agent`를 권한다.
- **CrewAI (역할 위임 극단, 단 이원 구조).** Crews는 역할·목표 선언으로 팀을 만들고 위임을 LLM이 결정한다. 그런데 CrewAI는 **Flows**를 별도로 뒀다 — *"event-driven workflows requiring state management, conditional branching, human oversight, or orchestration across multiple crews"*용이며 `@start`·`@listen`·`@router`·`@persist` 프리미티브를 쓴다. **즉 CrewAI 자신이 "자율 위임만으로는 프로덕션이 안 된다"를 제품 구조로 인정한 셈이다** — 축 논쟁의 강력한 논거.
- **Google ADK (템플릿 중간항).** 완전 자율(LlmAgent)과 완전 명시(그래프) 사이에 **Sequential / Parallel / Loop** 3종 템플릿을 둔다. 2.0부터 그래프 워크플로 추가.

**축 ②: 언어·타입 시스템 정합성** (백엔드 개발자에게 가장 실질적인 기준)

| 스택 | 선택지 | 근거 |
|------|-------|------|

**축 ③: SDK ↔ harness** — §1.4 참조.

**축 ④: 죽은 것을 피하기.** 이 축이 실무에서 가장 비싸다. §7.1의 "자주 틀리는 주장" 표를 반드시 볼 것.

> **가장 중요한 단일 사실 — 단, 서술 경계선을 지켜야 한다.**
> **인용 가능한 것 (검증됨):** ① AutoGen 최신 릴리스는 `python-v0.7.5`(**2025-09-30**)로 **약 10개월 경과**, 마지막 push 2026-04-15. ② Microsoft Learn이 명문화한다 — *"The Agent Framework is the direct successor, created by the same teams. ... In short, Agent Framework is the next generation of both Semantic Kernel and AutoGen."*
> **⚠️ 쓰면 안 되는 것:** **"AutoGen은 개발이 중단됐다 / 종료됐다 / deprecated다"는 근거가 없다.** 레포는 `archived: false`(2026-07-25 확인)이고 Microsoft는 폐기 공지를 낸 적이 없다. 같은 Learn 페이지는 오히려 *"Both Semantic Kernel and AutoGen have benefited significantly from the open-source community"*라고 쓴다.
> **실무 결론은 그대로 유효하다:** 신규 프로젝트를 AutoGen으로 시작하라고 권하는 서술은 근거가 없다. "공식 후속이 있다" + "릴리스가 10개월 정지 상태다"까지가 안전한 표현이다.

같은 규율이 **OpenAI Swarm**에도 적용된다 — 릴리스 태그 이력이 아예 없고 레포 자기 소개가 *"Educational framework"*, Agents SDK 문서가 이를 *"our previous experimentation for agents, Swarm"*으로 규정하지만, **`archived: false`이고 공식 폐기 공지는 미확인**이다. "폐기됨"이 아니라 "공식 후속이 있는 교육용 실험"으로 써야 한다.

### 2.2 데이터·검색 축 (축 3)

> 전체 도구 레코드는 §신선도 원장 「표 E·I·J·H」 참조.

**축 A: 내장(기존 DB 겸업) ↔ 전용 엔진**

| 갈림길 | 내장형 (pgvector/Redis/Atlas/sqlite-vec) | 전용형 (Qdrant/Weaviate/Milvus/Pinecone) |
|--------|------------------------------------------|------------------------------------------|
| 새 인프라 | 없음 | 새 서비스 하나를 운영 대상에 추가 |
| 트랜잭션 정합성 | 본문·메타데이터와 **같은 트랜잭션** | 원본 DB↔인덱스 동기화 파이프라인 별도 필요 |
| 검색 표현력 | 제한적 | Milvus 다중 벡터 필드+내장 BM25, Qdrant prefetch 다단계 |

> **이 책이 줄 수 있는 가장 구체적인 실무 지식:** **pgvector의 HNSW/IVFFlat 인덱스는 `vector` 최대 2,000차원이다.** 그런데 `text-embedding-3-large`의 기본 차원은 **3,072**다. 즉 이 조합은 **그냥 안 된다.** 선택은 셋 중 하나 — ① `dimensions` 파라미터로 1,536 이하 축소, ② `halfvec`(4,000까지), ③ 전용 엔진. (MongoDB Atlas는 최대 8,192차원이라 이 제약이 없다.) **"pgvector로 충분한가"가 아주 구체적인 숫자에서 갈린다.**

**축 B: 하이브리드 검색 — "지원/미지원"이 아니라 융합 알고리즘과 조절 손잡이 수로 갈린다**

| 엔진 | 융합 방식 | 조절 손잡이 |
|------|----------|-----------|
| Weaviate | Relative Score Fusion(v1.24+ 기본), Ranked Fusion | `alpha` 하나 (1=순수 벡터, 0=순수 키워드). 키워드는 BM25F. **기본값 미확인** |
| Qdrant | RRF, DBSF | prefetch + fusion + Formula Queries — 표현력 최고 |
| Milvus | RRF Ranker, Weighted Ranker | **내장 BM25로 sparse 임베딩 자동 생성** — BM25 파이프라인을 안 짜도 된다 |
| Elasticsearch | RRF | retriever 문법. `rank_constant`/`rank_window_size` **기본값 미확인** |

**축 C: 운영 부담 스펙트럼**
`sqlite-vec`(서버 없음) → `Chroma`/`LanceDB`(임베디드) → `pgvector`(기존 Postgres) → `Qdrant`/`Weaviate`/`Milvus`(전용 운영) → `Vespa`(최중량) → `Pinecone`/`Turbopuffer`/`Atlas`(매니지드, 운영을 돈으로 치환)

**축 D: 라이선스 — 성능 열과 같은 급으로 다뤄야 한다**
`Apache-2.0`: Qdrant·Milvus·Chroma·LanceDB·Vespa·OpenSearch·sqlite-vec / `BSD-3-Clause`: Weaviate / `MIT`: FAISS / **`GPL-3.0`: Typesense** / **`NOASSERTION`(비-OSI 계열 주의): Elasticsearch, Redis(RediSearch)**. 사내 배포 정책에서 실제로 걸리는 축이다.

### 2.3 벡터 DB가 필요 없는 경우 (축 3의 가장 값진 절)

**벤더·모델 제공자가 스스로 "안 써도 된다"고 말한 근거만** 모았다.

**근거 1 — 코퍼스가 작으면 그냥 다 넣어라**
> *"If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt that you give the model, with no need for RAG or similar methods."*
> — Anthropic, *Introducing Contextual Retrieval*, **2024-09-19**

**20만 토큰 / 약 500페이지**라는 임계값이 제공자 공식 발표문에 박혀 있다. ⚠️ 2024-09 글이므로 본문에는 반드시 **"2024년 Anthropic 기준"**으로 연도를 붙이고, 그 사이 컨텍스트 창이 커졌으므로 **보수적 하한**으로 프레이밍해야 한다.

**근거 2 — 코딩 에이전트는 인덱스 대신 탐색 도구를 쓴다**
Claude Code 공식 문서가 전제하는 코드베이스 탐색은 임베딩 인덱스가 아니라 에이전틱 탐색이다. 컨텍스트 소모 문제는 **인덱스가 아니라 서브에이전트로** 해결한다: *"Subagents run in separate context windows and report back summaries"*. 외부 조회도 *"CLI tools are the most context-efficient way to interact with external services"*.
> ⚠️ **정직한 한계:** 이 문서에 "우리는 RAG를 쓰지 않는다"는 **명시적 부정 문장은 없다.** "공식 문서가 권장하는 워크플로가 인덱스가 아니라 탐색 도구·서브에이전트 기반이다"가 확인 가능한 서술의 **상한선**이다.

**근거 3 — 검색이 안 맞을 때 DB를 바꾸는 건 오진**
Anthropic 실험(2024-09-19)에서 top-20 검색 실패율은 **5.7% → 1.9%**로 떨어졌고, 경로는 DB 교체가 아니라 **컨텍스트 보강 청킹 + BM25 병용 + 리랭킹**이었다. (단독 컨텍스트 임베딩 35%↓ → +BM25 49%↓ → +리랭킹 67%↓) 리랭커 단가는 임베딩보다 싸다(Voyage `rerank-2.5-lite` $0.02/1M).
⚠️ 2024-09 실험이고 모델이 바뀌었으므로 **"이 실험에서"를 반드시 붙여라.**

**근거 4 — 벡터 검색은 1차 후보 축소기다**
Turbopuffer 공식 문서의 자기 규정: *"first-stage retrieval to efficiently narrow millions of documents ... down to tens or hundreds"*. 정답을 고르는 건 리랭커와 LLM이다. 이 프레이밍이 "벡터 검색 정확도"에 과투자하는 실수를 막는다.

**근거 5 — 정형 데이터는 SQL이 맞다**
논리적으로 자명하나 **인용 가능한 1차 소스를 확보하지 못했다.** 출처를 붙이지 말고 저자 주장으로 쓸 것.

### 2.4 실행환경·런타임 축 (축 5)

> 전체 도구 레코드는 §신선도 원장 「표 B·D」 참조.

**축 ①: 격리 강도 ↔ 시작 지연 (실행환경의 유일한 진짜 트레이드오프)**

강한 격리부터: **microVM(Firecracker)** > **유저스페이스 커널(gVisor)** > **컨테이너(Docker/Podman)** > **Wasm capability 샌드박스(Wasmtime/WasmEdge — 격리는 강하나 생태계 제약이 큼)**

- 신뢰할 수 없는 **에이전트 생성 코드**에 컨테이너 단독은 불충분하다. Vercel Sandbox는 *"Each sandbox runs in a secure Firecracker microVM with its own filesystem and network"*를 명시하고, Modal Sandbox는 *"secure containers for executing untrusted user or agent code"*로 규정한다.
- ⚠️ **E2B·Modal·Fly의 구체적 격리 기술은 확인하지 못했다.** Firecracker 명시가 확인된 건 **Vercel Sandbox뿐이다.** "E2B는 Firecracker를 쓴다"고 쓰면 안 된다.
- **분업이 현실적:** 에이전트가 만든 코드 실행에는 microVM, 플러그인/도구 자체의 격리에는 Wasm.

**축 ②: 신뢰성을 어디서 얻나 — 프레임워크 내장 ↔ 외부 durable execution**

- **내장:** LangGraph 체크포인터, CrewAI `@persist()`, Cloudflare Durable Objects, Agent Framework 워크플로 체크포인팅
- **외부 위임:** Temporal / Restate / DBOS / Inngest / Cloudflare Workflows
  - **Temporal** 공식 정의: *"Durable Execution ensures that your application behaves correctly despite adverse conditions by guaranteeing that it will run to completion."* 메커니즘은 이벤트 히스토리 + 리플레이, 대가는 **결정론 제약** → LLM 호출을 Activity로 밀어내야 한다는 설계 귀결.
  - ⚠️ Temporal 공식 개념 문서는 **AI 에이전트를 언급하지 않는다.** "Temporal은 에이전트를 위해 만들어졌다"고 쓰면 사실 오류.
  - **DBOS**는 별도 오케스트레이터 없이 **Postgres 하나로** 같은 보장을 라이브러리로 제공 → 이미 Postgres를 쓰는 팀에게 운영 부담 최소 경로.
- **판단 기준:** 에이전트 실행이 (a) 분 단위를 넘고 (b) 외부 부작용(결제·발송·쓰기)을 만들고 (c) 중간 실패 후 재개해야 하면 → 외부 durable execution. 그 외에는 내장 체크포인터로 충분.

**축 ③: 비용·지연의 비직관적 사실 (1차 소스 수치)**

| 사실 | 수치 | 출처 |
|------|------|------|
| **I/O 대기는 CPU로 과금되지 않는다** | *"Time spent waiting for I/O (such as network requests, database queries, or AI model calls) does not count toward Active CPU."* | Vercel Sandbox 가격 문서 (2026-06-16) |
| 샌드박스 실측 원가 | 5분/2vCPU ≈ **$0.03**, 30분/4vCPU ≈ **$0.34**, 2시간/8vCPU ≈ **$2.73** (100% CPU 가정) | 동일 |
| **대기 인스턴스는 동시성 한도에 안 잡힌다** | `waiting` 상태 인스턴스는 동시성 한도에 **미포함** → 사람 승인을 며칠 기다리는 에이전트를 수만 개 띄워도 버틴다 | Cloudflare Workflows limits |
| 최대 sleep | **365일(1년)** | 동일 |
| E2B pause/resume | pause ≈ **1GiB RAM당 4초**, resume ≈ **1초**. pause된 샌드박스는 **무기한 보존**, pause/resume 후 **연속 실행 한도가 리셋**된다 | E2B persistence 문서 |

> **합성 관찰:** 벤더별 "정답 스택"은 사실상 **자기 플랫폼 락인 축**으로 갈린다. 반면 **플랫폼 중립 조합은 `Pydantic AI 또는 LangGraph` + `Temporal/DBOS` + `E2B/Modal` + `MCP`로 수렴한다.** 이 대비 자체가 챕터 하나 값이다.

### 3.4 운영 현실의 고통 — 챕터 오프닝 소재 (커뮤니티)

> **귀속 규율:** 아래는 대부분 **익명·준익명 커뮤니티 발언**이다. 수치는 특별한 표시가 없으면 **한 사용자의 주장이며 독립 검증되지 않았다.** 본문에는 반드시 **"한 개발자는 ~라고 말한다"** 형태로 귀속시키고, 수치를 사실로 단정하지 마라.
> **대표성 주의:** HN 댓글은 Algolia API로 수집했기 때문에 **스레드 내 위치·점수를 알 수 없다.** 어떤 인용이 지지받은 최상위 댓글인지 묻힌 댓글인지 판별 불가 → **"커뮤니티 대표성"을 과대평가하지 마라.**

**① 비용 폭발**
- **관심이 "경고"에서 "하드 컷오프"로 옮겨갔다:** *"알림도 유용하지만 자동 한계선이 더 중요하다 — 소규모 사업자라서 새벽 2시의 루프가 날 파산시키지 않도록"* (HN 48872850, 2026-07-11)
- **서브에이전트 팬아웃이 청구서를 곱한다:** *"1시간 15분 동안 크레딧 $120을 태웠다… 클로드가 '서브에이전트에는 저렴한 모델을 쓰라'는 내 지시를 잊어버려서 최상위 모델 여러 개를 동시에 돌리고 있었다"* (HN 49030357, 2026-07-24) — **"지시가 잊혀진다"가 곧 비용 사고가 되는 구조**
- **단위 원가를 아무도 모른다:** *"비용은 '이 호출이 토큰을 몇 개 썼나'가 아니라 '이 사용자 액션 하나가 모든 에이전트 루프·재시도·툴 호출·임베딩을 합쳐 토큰을 몇 개 썼나'다. 대부분의 관측 도구는 LLM 호출을 하나의 평평한 span으로 보여준다."* (HN 47346646, 2026-03-12, ※ 자사 APM 홍보 맥락)

**② 루프 실패·거짓 성공 — 반복 강도 최상, 챕터 오프닝 1순위**
- **가장 자주 반복되는 서술 구조:** *"한 시간 동안 문제를 풀려고 루프를 돌다가, '해결했습니다'라고 하고, 그러면 당신이 문제가 해결되지 않았다고, 에러 메시지가 똑같다고 말해줘야 한다."* (HN 45001692, 2025-08-24) — **최소 6곳에서 같은 실패가 반복 서술된다**
- **`max_iter`는 양방향으로 틀린다:** *"너무 일찍 멈추면 아직 개선 중이던 루프를 잘라내고, 너무 늦게 멈추면 루프가 이미 최선의 답을 찾은 뒤의 반복에 돈을 내고 — 게다가 마지막 시도를 출하하는데 그게 때로는 이전 것보다 더 나쁘다."* (HN 48475406, 2026-06-10). crewAI 이슈가 독립적으로 같은 진단 — *"맹목적인 `max_iter` 카운터(유효한 15단계 워크플로를 11단계에서 죽인다)"* (crewAI#6414)
- **결정적 실패를 일시적 실패로 취급하는 재시도:** *"같은 툴 호출이 같은 인자 패턴으로 실패하는데 재시도 루프가 이걸 일반적으로 취급하면, 사실상 실행 증폭기(execution amplifier)가 된다."* (crewAI#4495, 2026-02)
- **지터 루프:** 같은 호출이 아니라 **매번 질의를 조금씩 바꿔가며** 도는 루프 — 단순 해시 dedupe로 안 잡힌다 (HN 47006768, 2026-02-13)
- **증거 없는 성공 선언:** 최종 출력이 `"Done. All tests passed. Ready to publish."`인데 *"명령 출력, 트레이스 증거, 사람의 승인을 아무것도 첨부하지 않았을 수 있다"* (langgraph#7844, 2026-05-17)

**③ 권한·샌드박스**
- **"에이전트는 자기 차선을 지키지 않는다":** 샌드박스 운영자의 14,000+ 세션 분석 — *"'이 함수의 유닛 테스트를 써줘'라고 요청받은 에이전트는, 완전히 지시받지 않았는데도, 테스트하려던 소스 코드를 수정하고, 패키지를 설치하고, 네트워크 요청을 시도한다. **악의적인 게 아니다. 에이전트는 그냥 '도움이 되려고' 하는 것이다.**"* (HN 47161210, 2026-02-26) — **검증 상태: 확인 필요(벤더 자체 로그).** 그럼에도 **"악의가 아니라 도움이 되려는 성질이 위험"**이라는 프레이밍은 권한 설계 챕터의 핵심 논거
- **에이전트가 만드는 보안 버그는 새롭지 않고 그냥 빠르다:** *"보안 문제 28개를 찾았는데, 그중 새로운 종류는 하나도 없었다 — 주니어가 늘 출하해온 것과 똑같은 고전들이었고, 다만 훨씬 높은 처리량으로 생산됐을 뿐이다. '시니어 엔지니어 리뷰' 단계가 많은 AI 보조 워크플로에서 조용히 사라졌다."* (HN 48094454, 2026-05-11) — **균형 잡힌 시각**

**④ MCP의 현실 — 공식 문서가 말하지 않는 것**
- **툴 정의는 매 요청마다 실린다:** *"MCP 툴은 매 요청마다 전송된다. notion MCP를 보면 search 툴 설명이 사실상 미니 튜토리얼이다. 이게 컨텍스트 윈도로 곧장 들어간다. …**둘째, MCP 툴은 조합 가능하지 않다.** …모델은 얼마나 많은 데이터를 처리할지 결정할 수단이 없다."* (HN 47158526, 2026-02-25) — **반복 강도 최상**
- **툴이 많아지면 에이전트가 "더 멍청해진다":** *"에이전트가 너무 많은 선택지에 혼란스러워진다. 플러그인 인터페이스 뒤에 '숨겨두는' 게 실제로 프로덕션에서 에이전트 안정성에 더 좋다."* (HN 47080603, 2026-02-19)
- **MCP 옹호자조차 인정하는 결함:** *"더 나쁜 문제는 MCP의 출력이 어딘가로 파이프되는 대신 에이전트의 컨텍스트로 곧장 들어간다는 점이다."* (HN 47714718, 2026-04-10)
- **MCP의 진짜 가치는 기술이 아니라 생태계라는 통찰:** *"왜 function calling 시스템을 확장하지 않았는지 모르겠다. …이 접근의 유일한 단점은 MCP '마켓플레이스'를 가질 수 없다는 것"* (HN 43951934, 2025-05-11)

**⑤ 상태·장기 실행**
- **"에이전트는 자기 역사를 환각한다"** — 이 축 최고의 인용: *"어려운 부분은 코드 양이나 토큰 비용이 아니다. 상태 연속성이다. …장기 실행 루프에서 약 50~60턴을 넘으면, 큰 컨텍스트 윈도가 있어도 앞선 정보에 가중치를 덜 주기 시작하고 이미 해결한 문제를 다시 풀기 시작한다. 명시적 검색을 갖춘 파일 기반 메모리가 컨텍스트에 밀어넣기보다 더 신뢰할 만하다."* (HN 47126051, 2026-02-23) — **검증 상태: 50~60턴은 개인 관찰.** 메커니즘은 Lost in the Middle(arXiv:2307.03172)이 학술적으로 뒷받침하지만 **이 숫자 자체는 논문 근거가 없다**
- **클라우드 플랫폼 불일치:** *"대부분의 클라우드 플랫폼은 무상태 앱이나 짧게 사는 함수를 위해 설계됐고, 장기 실행 에이전트를 위한 게 아니다."* (HN 44578559, 2025-07-16)
- **실패는 조용하다:** *"대부분의 에이전트 실패는 조용하다. 대부분의 실패는 테스트 중에 아무 문제도 보이지 않았던 컴포넌트에서 발생한다."* (HN 46245185, 2025-12-12)

**⑥ 한국어 소스 — 최고 품질의 실무 정리 (Youngju Kim, 2026-07-17, 원문 HTML 직접 대조 ✅)**

> ⚠️ **인용 형태 주의 — 이 책의 초안이 이미 한 번 틀렸다.** 아래 인용들은 **원문 HTML을 직접 받아 대조한 정확한 형태**다. 초기 수집 때 요약 도구가 **별개 두 문장을 하나로 융합**해서 *"MCP는 멱등성 힌트만 주고… 재시도 정책은…"*이라는 존재하지 않는 문장을 만들었다. **아래 형태로만 인용하라.**

- **재시도 정책의 정체 (정확한 원문):** *"전통적 클라이언트는 재시도할지를 코드가 결정하지만, 에이전트는 모델이 결정합니다. 모델은 도구가 실패했다고 판단하면(혹은 실패했다고 오판하면) 그냥 다시 부릅니다. **재시도 정책이 프롬프트 안에 있는 셈이고, 그건 정책이 아니라 확률입니다.**"*
  > **"정책이 아니라 확률"은 이 책이 훔쳐야 할 문장이다.**
- **MCP의 멱등성 (위와 별개 문장):** *"**즉 MCP는 멱등성에 대해 어휘는 주지만 도구는 주지 않습니다.** 서버가 '나는 멱등해요'라고 주장할 수는 있는데, 그 주장은 (a) 강제되지 않고 (b) 신뢰할 수 없는 서버에서 오면 믿지 말라고 스펙이 직접 경고하며 (c) 멱등하지 않은 도구를 재시도 안전하게 만들 방법은 프로토콜에 아예 없습니다."*
  - 근거로 제시된 **검증 가능한** 스키마 사실: MCP 리비전 2025-11-25 스키마에서 *"2573줄짜리 스키마 전체에서 `idempotentHint`는 선언되는 그 한 곳에만 등장"*하고 *"'retry'라는 단어는 스키마에 한 번도 나오지 않는다"* → **web-researcher가 스키마로 직접 재확인 가능·권장 (§7.2)**
- **MCP 애노테이션 기본값이 전부 비관적이라는 관찰:** `readOnlyHint` false / `destructiveHint` **true** / `idempotentHint` false / `openWorldHint` true → *"**애노테이션이 없으면 모든 도구는 파괴적이고 멱등하지 않은 쓰기 작업으로 취급해야 한다**는 뜻입니다. 이건 좋은 설계입니다."* (**대조 대상**)
- **가장 비직관적이고 가장 값진 통찰 — 멱등성 구현이 오히려 루프를 유발한다:** *"하나는 **500까지 재생한다**는 것 — 멱등 재시도는 '다시 시도'가 아니라 '원래 결과를 다시 보여주기'입니다. **모델이 실패를 보고 재시도하면 실패를 다시 봅니다. 이건 버그가 아니라 설계이고, 모델이 이걸 이해하지 못하면 무한 루프에 빠집니다.** 다른 하나는 **24시간**입니다. 며칠에 걸쳐 도는 장기 실행 에이전트가 어제의 키로 재시도하면, 그건 재시도가 아니라 새 부작용입니다."*
  > **축 2(루프 실패)와 축 8(MCP)을 잇는 다리다.** Stripe식 멱등 재시도 관행이 에이전트 문맥에서 역효과를 낸다는 것 — 문서·논문 어디에도 없는 통찰.
- **대부분의 개발자가 놓치는 실패 모드:** *"재시도가 위험한 건 도구가 실패했을 때만이 아닙니다. **도구가 성공했는데 응답이 유실됐을 때가 더 위험합니다.** 이때 모델이 보는 건 '결과 없음'이고, 모델의 합리적 행동은 재시도입니다. 그리고 부작용은 이미 일어났습니다."*
- **비용의 구조적 원인 (축 1의 가장 간결한 설명):** *"루프 한 바퀴마다 컨텍스트 전체가 다시 모델에 들어가므로 **비용은 선형이 아니라 그보다 가파르게 붙습니다.**"*
  > 커뮤니티의 일화적 비용 보고($45/3프롬프트, $120/75분)가 **왜** 발생하는지를 이 한 문장이 설명한다.
- **MAST 백분율 인용 (2단계 주의):** *"가장 흔한 실패 모드 두 개는 단계 반복(15.7%)과 종료 조건 미인지(12.4%) — 합치면 전체의 28.1%입니다. …에이전트가 같은 일을 반복하고 멈출 줄 모른다는 뜻이고, 그건 토큰 청구서인 동시에 **부작용이 두 번 일어난다**는 뜻입니다."*
  - 이 문장은 **블로그 원문과 일치한다(✅)**. 그러나 **블로그가 인용한 MAST 백분율 자체는 원 논문에서 확인되지 않았다(❌)** — §7.2 참조. **"비용과 부작용을 한 문장에 묶은" 정식화는 인용 가치가 높지만, 백분율은 쓰지 마라.**

## 4. 논쟁점·상충 관점

> 이 책의 독자는 결정을 내려야 하는 사람이다. 그래서 어느 쪽도 봉합하지 않고 양쪽을 병기한다.

### 4.1 워크플로로 충분한가 vs 자율 에이전트가 필요한가

- **관점 A (단순한 것부터):** Anthropic — *"Start with simple prompts"*, 단순한 해법이 부족할 때만 복잡도를 더한다. Microsoft — *"If you can write a function to handle the task, do that instead of using an AI agent."* **두 벤더가 독립적으로 같은 결론.** (웹)
- **관점 B (제품 구조가 증언하는 것):** 역할 기반 자율 위임의 대표 프레임워크인 CrewAI가 **스스로 명시적 워크플로 층(Flows)을 추가했다.** 자율 위임만으로 프로덕션이 안 된다는 걸 제품으로 인정한 셈. (웹)
- **판정:** 이 논쟁은 사실상 한쪽으로 기울어 있다 — **결정적 워크플로가 기본값이고, 자율성은 필요한 만큼만 사는 것**이 벤더 공통 권고다.

### 4.2 RAG vs 롱 컨텍스트

- **관점 A (RAG 불필요):** 20만 토큰(약 500페이지) 미만이면 *"no need for RAG"* — Anthropic, 2024-09-19. 컨텍스트 창이 그 뒤 더 커졌으므로 임계값은 상향됐을 가능성. (웹)
- **관점 B (RAG는 여전히 필요):** 코퍼스가 그 이상이거나, 비용·지연이 문제거나, 출처 추적이 요구사항이면 검색이 필요하다. 그리고 검색 품질은 DB가 아니라 **하이브리드+청킹+리랭킹**에서 나온다(5.7%→1.9%). (웹)

|------|------|------|
| 롱 컨텍스트가 검색을 대체한다 | **LOFT** (Lee et al., arXiv:2406.13121) | LCLM이 명시적 학습 없이도 SOTA 검색·RAG 시스템에 "맞먹는" 능력 |
| 검색이 이긴다 (비용까지 보면 압도적) | **Retrieval meets Long Context** (Xu, Ping et al., arXiv:2310.03025v2, **ICLR 2024**) | **4K 컨텍스트 + 단순 검색이 16K 파인튜닝 모델과 비슷한 성능, 훨씬 적은 계산** |
| 롱 컨텍스트가 오히려 품질을 떨어뜨린다 | **OP-RAG** (Yu, Xu, Akkiraju, arXiv:2409.01666) | 검색 청크 **수**를 늘리면 품질이 올랐다가 **떨어지는 역U자 곡선** — 스위트 스팟이 존재 |
| 롱 컨텍스트 자체가 위치에 취약하다 | **Lost in the Middle** (Liu et al., arXiv:2307.03172v3, **TACL 2023**) | 관련 정보가 중간에 있으면 성능이 유의하게 하락. **명시적 롱 컨텍스트 모델도 마찬가지** |

**실무 결론:** 이 논쟁은 "누가 이기나"가 아니라 **"무엇을 최적화하나"**의 문제다. 정확도만 보면 접전, **비용·지연을 넣으면 검색 쪽으로 기운다.** 그리고 컨텍스트에 다 넣는 전략은 **Lost-in-the-Middle 세금**을 낸다.
⚠️ OP-RAG의 역U자는 청크 **수**에 관한 것이고 청크 **크기**에 관한 것이 아니다 — 혼동 금지.

**커뮤니티 관점 (관점 C — 논문에 없는 축):** 코딩 도메인에서는 임베딩보다 **구조적 검색**(ast-grep)이 이긴다. "순수 임베딩 기반 검색은 비자명한 상속 계층이나 다형성이 있는 코드베이스에서 실패하는 경향이 있다" (HN 47898384, 2026-04-25). 반대로 "RAG 부고" 주장(HN 45445280, 2025-10-02)에 대한 최상위 반박이 스케일 문제를 지적한다: *"grep은 로컬 파일시스템의 수천 개 파일에서 훌륭하다. 하지만 대부분의 엔터프라이즈 RAG 용례는 분산 시스템에 걸친 수백만 개 문서다. 2M 토큰 컨텍스트 윈도가 있어도 엔터프라이즈 지식 베이스 전체를 컨텍스트에 넣을 수 없다."*
> **3소스 수렴 결론:** 이항 질문("RAG냐 아니냐")이 낡았다. 결정 축은 ① 컨텍스트에 들어가는가 → 넣어라 ② 구조가 있는가(코드·스키마) → 구조적 검색 ③ 수백만 문서·분산 → 검색 필수(하이브리드+리랭커).

### 4.4 에이전트 벤치마크가 실무를 예측하는가

- **관점 A (신뢰 곤란 — 이번 리서치가 직접 확인한 것):**
  - **점수를 확인할 수조차 없다.** MTEB·GAIA는 HF Space가 JS 렌더링이라, SWE-bench는 리더보드 본문 truncate로 **정적 fetch로 점수를 못 읽었다.** 유일하게 확보된 **Terminal-Bench 2.0**은 상위권이 **80%대에 ±2%대 오차로 몰려 있어 1~5위가 통계적으로 겹친다** → "1위 모델" 식 서술이 성립하지 않는다.
  - **벤치마크 자체가 죽어간다.** WebArena 최신 릴리스 **2023-10-21**, AgentBench push **2026-02-08**(5개월 정체), SWE-bench push 2026-04-01(4개월). "표준 벤치마크"로 나열하면 독자를 죽은 벤치마크로 보낸다. (웹)
**학술 근거 (논문) — 이 논쟁이 이 책에서 가장 중요하다**

| 진영 | 논문 | 근거 (전부 초록에서 확인된 수치) |
|------|------|------|
| 벤치마크가 진보를 측정한다 (원논문 측) | SWE-bench (arXiv:2310.06770v3, **ICLR 2024**) / GAIA (arXiv:2311.12983) / WebArena (arXiv:2307.13854v4) | 실제 GitHub 이슈·실제 웹사이트·실행 기반 채점으로 현실성 확보 |
| ❌ 데이터 품질 결함 | **SWE-Bench+** (Aleithan et al., arXiv:2410.06992v2) | 성공 패치의 **32.67%가 해답 유출(solution leakage)**, **31.08%가 약한 테스트**. 걸러내면 SWE-Agent+GPT-4 해결률 **12.47% → 3.97%** (3배 이상 하락). 또한 **94% 이상의 이슈가 지식 컷오프 이전 생성** |
| ❌ 평가 설계 결함 | **ABC** (Zhu, Jin et al., arXiv:2507.02825v5) | 태스크 설정·보상 설계 결함이 성능을 **상대적으로 최대 100%** 과대/과소 평가. *"SWE-bench Verified는 테스트 케이스가 불충분하고, TAU-bench는 빈 응답을 성공으로 계산한다"* |
| ❌ 비용·홀드아웃·재현성 결함 | **AI Agents That Matter** (Kapoor, Stroebl et al., arXiv:2407.01502) | 정확도만 보는 좁은 초점 → SOTA 에이전트가 *"불필요하게 복잡하고 비싸다"*. 홀드아웃 부재로 벤치마크 과적합 |
| 신뢰성은 아예 다른 축이다 | **τ-bench** (Yao, Shinn et al., arXiv:2406.12045) | gpt-4o가 태스크 **50% 미만** 성공, 그리고 **pass^8이 retail에서 25% 미만** |

> **이 책이 독자에게 줘야 하는 단일 개념: `pass@k` vs `pass^k`.** pass@k는 "k번 중 한 번이라도 성공", pass^k는 "k번 모두 성공". **프로덕션이 요구하는 건 후자다.** τ-bench가 이 격차를 정량화했다.
> **그리고 채점기를 먼저 감사하라** — SWE-Bench+와 ABC가 보여준 건 결함이 모델이 아니라 **보상 설계**에 있었고, 점수를 3배까지 왜곡했다는 것이다. "신뢰성을 재려고 만든 벤치마크(τ-bench)에도 채점기 결함이 있었다"는 쌍이 특히 아프다.

**LLM-as-judge 편향 (§4.7로 분리)**

**커뮤니티 관점 — 벤더가 스스로 인정한다**
- 평가 도구 창업자(Traceloop): *"이 지표들 상당수(예: RAGAS)가 LLM-as-a-judge 지표다. 이건 신뢰성과 거리가 아주 멀다. …최종 평가 기준으로 생각하면 안 된다. 골든 기준은 인간 평가자여야 한다."* (HN 40987261, 2024-07-17 ⚠️2024)
- DeepEval 창업자: *"도메인 전문가가 큐레이션한 고품질 데이터셋이 있어도 우리 평가 지표가 여전히 목표 달성의 가장 큰 걸림돌이다."* (HN 43119210, 2025-02-20)
- **트레이싱 ≠ 평가:** *"에러가 1%의 경우에만 발생할 때는 회귀 테스트 능력이 없다."* (같은 출처)
- **평가 단위가 다르다:** *"LLM ops 평가는 보통 프롬프트 단위지만, 에이전트 평가는 보통 세션 또는 실행 단위다."* (HN 44736570, 2025-07-30)
- **구조화된 출력의 거짓 확신:** 스레드 제목 자체가 실패의 이름이다 — "Structured outputs create false confidence"(HN 46349308, 2025-12-21). **스키마 통과 = 정답이 아니다.**
- **실무 처방(확인된 사실 기반):** 리더보드는 출발점이지 결론이 아니다. **자기 도메인 데이터로 다시 재라.**

### 4.5 관측성 표준은 믿을 만한가

- **관점 A (표준이 왔다):** OTel GenAI semantic conventions가 **Agent Spans**까지 규약 범위에 포함했다. 벤더 중립 관측성의 기반. (웹)
- **관점 B (아직 이르다 — 확인된 사실):** 상태가 **`Status: Development`**(stable도, experimental 승격도 아님)이고, **코어 semconv에서 별도 리포로 막 분리됐으며**, **태그된 릴리스가 아예 없다**(★192). 구 문서 URL은 *"no longer maintained in the current location"* 안내만 남았다. (웹)
- **정확한 서술:** "표준화가 진행 중이고 Agent Spans까지 규약에 들어왔다. **지금 붙이면 스키마 변경을 감수해야 한다.**" — "따르면 벤더 중립이 된다"는 현시점 **과장**이다.

### 4.6 공식 소스끼리 상충하는 사례 — OpenAI 임베딩 단가

**봉합하지 말 것. 두 공식 표면이 다른 값을 말한다.**

- **관점 A (모델 카드, 직접 fetch 확인):** `text-embedding-3-large` = **$0.13 / 1M tokens**, `text-embedding-3-small` = **$0.02 / 1M tokens**
- **관점 B (가격 페이지, 미검증):** 3-large를 **$0.065**로 표기한다는 보고. OpenAI 개발자 포럼에 버그로 보고돼 있음(2025-08 시점)
- **출처 등급이 다르다:** A는 직접 fetch로 검증됨, B는 검색 요약(미검증).
- **fact-checker 지시:** 본문에 단가를 쓸 경우 반드시 **"모델 카드 기준 $0.13(2026-07 확인), 가격 페이지와 불일치 보고 있음"**처럼 출처 표면을 특정하라. **이 값으로 총비용 계산 예시를 만들면 2배 오류가 난다.**

### 4.7 LLM-as-judge를 신뢰할 수 있는가 (논문)

| 진영 | 논문 | 근거 |
|------|------|------|
| 신뢰할 만하다 | **MT-Bench / Chatbot Arena** (Zheng et al., arXiv:2306.05685v4, **NeurIPS 2023 D&B**) | GPT-4 판정이 인간 선호와 **80% 초과 일치** — 인간끼리의 일치도와 같은 수준 |
| 순서만 바꿔도 뒤집힌다 | **LLMs are not Fair Evaluators** (Wang et al., arXiv:2305.17926v2) | 응답 등장 순서를 바꿔 순위를 "해킹" 가능. ChatGPT를 평가자로 두고 **Vicuna-13B가 80개 질의 중 66개에서 승리**하게 만들 수 있었다 |
| 자기 출력을 편애한다 | **LLM Evaluators Recognize and Favor Their Own Generations** (Panickssery, Bowman, Feng, arXiv:2404.13076) | self-recognition 능력과 self-preference 편향 강도 사이 **선형 상관**, 통제 실험으로 인과 주장 |
| 설계하면 쓸 수 있다 | **A Survey on LLM-as-a-Judge** (Gu et al., arXiv:2411.15594v6) | 일관성 개선·편향 완화 전략 정리 |

> **핵심:** MT-Bench 논문 **자체가** position·verbosity·self-enhancement 편향을 인정한다. 따라서 실무 규칙은 "judge 쓰지 마라"가 아니라 **"순서 무작위화 / 양방향 집계 없는 judge 점수는 보고하지 마라"** + **심판과 피심판을 분리하라**다.

### 4.8 프롬프트 인젝션은 원리적으로 막을 수 있는가 (논문 + 커뮤니티)

| 진영 | 논문 | 근거 |
|------|------|------|
| 효과적 완화가 없다 | **Not what you've signed up for** (Greshake et al., arXiv:2302.12173v2) | LLM 통합 앱이 **데이터와 명령의 경계를 흐린다**. "효과적 완화가 현재 부재하다" |
| 모델을 고치는 방식으로는 안 된다 (실증) | **AgentDojo** (Debenedetti et al., arXiv:2406.13352v3) | 97개 태스크·629개 보안 테스트. **더 유능한 모델이 오히려 공격하기 쉬운 역스케일링 경향** |
| 시스템 설계로 막을 수 있다 | **CaMeL** (Debenedetti et al., arXiv:2503.18813v2) | 제어 흐름/데이터 흐름 분리로 **AgentDojo 태스크의 77%를 "증명 가능한 보안"으로** 해결 (무방어 84% 대비) |
| 패턴화 가능하다 (유틸리티 대가) | **Design Patterns for Securing LLM Agents** (Beurer-Kellner et al., arXiv:2506.08837v3) | 증명 가능한 저항 패턴 집합 + 트레이드오프 명시. ⚠️ **효과 크기 수치 인용 금지**(초록에 정량 결과 없음) |

> **가장 실무적인 발견 — 인젝션 방어의 1순위는 프롬프트 가드가 아니라 권한이다.**
> AgentDojo 본문 확인: *"Our simple tool filtering defense is particularly effective, lowering the attack success rate to 7.5%."* (§4.3) — **"이 태스크에 필요한 도구만 노출하기"**가 가장 값싸고 효과적인 방어다. 사용자가 이메일을 읽기만 하면 되는 요청에 `send_email`을 붙여 두지 마라.
> 단, 논문이 **한계도 명시**한다 — 사용자 태스크가 읽기만, 공격자 태스크가 쓰기를 요구할 때 잘 통하고 그렇지 않으면 실패한다. 은탄환이 아니다.
> 그리고 *"more capable models tend to be easier to attack, a form of inverse scaling law"* (§4.1) → **모델 업그레이드로 보안이 개선될 거라는 기대는 근거가 없다. 보안은 모델 축이 아니라 시스템 축이다.**
> **CaMeL의 77% vs 84%가 그 대가의 크기다** — 실무자가 결국 하는 질문은 "안전한가"가 아니라 **"이 에이전트의 자유도를 얼마나 깎아야 안전해지는가"**이기 때문에 이 숫자가 값지다.

**안전 정렬을 통제로 계산하지 마라 — AgentHarm** (arXiv:2410.09024v3, **ICLR 2025**): 악의적 에이전트 태스크 110개(증강 440개), 11개 위해 범주. 발견 — ① 선도 모델들이 **탈옥 없이도 놀랍도록 순응적**, ② 단순 범용 탈옥 템플릿을 에이전트용으로 적응시키면 충분, ③ 탈옥 후에도 **일관되고 유해한 다단계 능력이 유지**됨. → 통제는 **도구 계층과 권한 계층**에 있어야 한다.

**커뮤니티가 더한 것 (문서·논문에 없는 프레이밍)**
- **문제는 탈옥이 아니라 경계 혼동:** *"에이전트 시스템에서 더 큰 문제는 경계 혼동(boundary confusion)인 것 같다 — 신뢰할 수 없는 콘텐츠가 결국 툴이 어떻게 사용되는지에 영향을 준다."* (HN 47298207, 2026-03-08, 스레드 제목: "우리는 탈옥은 고쳤다. 에이전트는 못 고쳤다") — **챕터 제목 후보**
- **MCP 서버는 두 개의 다른 위험이다:** *"하나는 툴 출력을 통한 프롬프트/컨텍스트 인젝션. 다른 하나는 훨씬 더 전통적인, 전이 의존성을 가진 신뢰할 수 없는 코드를 내 머신에서 실행하는 위험. 컨테이너화는 두 번째만 돕고 첫 번째는 돕지 않는다."* (HN 47581930, 2026-03-31) — **공급망 위험과 인젝션을 분리한 가장 실용적인 정리**
- **내부 테스트는 항상 통과한다:** *"내 테스트 스위트는 내가 상상한 공간을 지도로 그리는데, 적대적 입력은 정확히 거기서 탈출하려 한다."* / 인젝션이 잘 통한 이유 — *"탐지가 약해서가 아니라 우리가 의도가 아니라 내용을 매칭하고 있었기 때문"* (HN 47179283, 2026-02-27)
- **인젝션 방어가 정당한 기능을 깨뜨린다 (2차 효과):** 모델이 툴 결과를 "정보로는 취급하되 지시로는 취급하지 않도록" 훈련되면, 툴 결과로 구현된 제어 훅도 무시된다는 관찰 (HN 47896464, 2026-04-24) — **검증 상태: 확인 필요(추론이며 벤더 확인 아님).** 문서에 없는 설계 트레이드오프

### 4.9 프레임워크 vs 직접 구현 (커뮤니티 — 가장 뜨거운 논쟁)

- **관점 A (버려라):** 최상위 답변 — LangChain을 아직 쓰냐는 질문에 *"불행히도, 그렇다. 선택은 아니고."* 같은 사용자가 라이브러리 자체를 *"절대적으로 끔찍하고, 좋게 말할 게 사실상 아무것도 없다"*고 평가(HN 44840323/44840626, 2025-08). 다른 참가자는 *"완전한 쓰레기장 화재"*라 부르며 품질이 아니라 **초기 시장 지배력** 때문에 살아있다고 주장.
  - **가장 구체적인 불만 — 타입 없는 상태:** *"모든 그래프의 상태가 타이핑이 거의 없는 멍청한 JSON 덩어리라서 멍청한 런타임 타입 에러를 고치는 데 시간을 다 쓰고, 데이터가 시스템을 어떻게 흐르는지 알아내기가 너무 어렵다. …테스트를 쓰기 어렵다."* (HN 44307883, 2025-06-18) — **이 인용 하나가 "왜 추상화를 버리는가"의 절반을 설명한다.**
  - **"에이전트는 그냥 루프다"** — 260줄 Rust 구현으로 논증 (HN 47189061, 2026-02-28)
  - 버전 업그레이드(1.6.1→1.9.3)가 툴 인자 바인딩을 깨서 무한 루프 유발 (crewAI#4495)
- **관점 B (남거나 재평가):** **등급을 나눠 봐라** — LangGraph는 *"가장 덜 나쁜"* 것이고 대안은 OpenAI Agents SDK·Pydantic AI. 직접 만들면 **상태·재시도·관측성·내구성을 다 만들어야 하는데 그게 정확히 과소평가되는 비용**이다.
- **불만의 방향이 이동했다 (중요):** *"인기 있는 프레임워크들은 무거운 편이다 — …루프나 실패 같은 신뢰성 문제에 대한 내장 안전장치는 더 적다."* (HN 46730883, 2026-01-23) → **"추상화가 너무 많다"에서 "정작 필요한 신뢰성 안전장치는 안 준다"로 바뀌었다.**
- **관점 C (문제는 프레임워크가 아니라 모듈성이다) — 백엔드 독자에게 가장 유용한 재구성:** 자바/Spring 배경 개발자의 진단이 논쟁 자체를 다시 세운다. *"파이썬에 Spring 같은 게 없는 걸 여전히 아쉬워한다. …**Spring을 쓰려면 Spring IoC를 채택해야 하지만, 그 너머는 전부 모듈식이다. ORM, 메시징, 캐싱처럼 필요한 추상화만 골라 쓸 수 있다.**"* (HN 40821394, 2024-06-28 ⚠️2024)
  > **불만의 정체가 "추상화가 있다"가 아니라 "추상화를 골라 쓸 수 없다"임을 정확히 짚는다.** 대상 독자가 이미 가진 프레임워크 감각(Spring)으로 이 판단을 내릴 수 있게 해주는 **최적의 다리**다.
  > 같은 스레드의 2024년 요구 — *"LangChain은 관측성 도구가 좀 있는데 그건 진짜 유용해 보인다. **이 도구들만 쓸 방법이 있나?**"* — 가 2025~2026년의 "Langfuse로 관측성만 분리" 실천을 **1년 앞서 예고했다.**
- **현재 무게중심:** **"전체를 사거나 버리거나"가 아니라 계층별로 갈라 사는 쪽.** 관측성(Langfuse)·오케스트레이션(LangGraph/Agents SDK/Pydantic AI)을 분리 선택하고 **LLM 인터페이스 래퍼는 직접 쓰는** 조합이 반복 관찰된다. 그리고 그 공백을 프레임워크 이슈 트래커가 스스로 메우려 한다(langgraph#8026 ApprovalNode 요청 40댓글, openai-agents-python#2868 툴별 권한 미들웨어 31댓글).

### 4.10 멀티에이전트가 정말 필요한가 (논문 + 커뮤니티가 같은 결론)

- **관점 A (이득이 있다):** Du et al., *Multiagent Debate* (arXiv:2305.14325) — 여러 인스턴스가 토론하면 수학·전략 추론과 사실성이 향상.
- **관점 B (이득이 미미하고 실패가 구조적):** **MAST** (arXiv:2503.13657v3) — *"성능 향상이 종종 미미하다"*, 14개 실패 모드 3범주. 커뮤니티: *"학계의 많은 사람들이 멀티에이전트 시스템을 현 세대 LLM의 인공물로 본다"*(HN 46852260, 2026-02-02), *"B는 종종 비례하는 이득 없이 복잡도를 추가한다"*(HN 46753582, 2026-01-25).
- **관점 C (컨텍스트 한계가 강제한다):** *"단일 에이전트는 이걸 한 API 호출로 달성할 컨텍스트 윈도 크기가 부족하고, 그래서 병렬 에이전트가 필요하다. …사실상 에이전트를 스레드로, 역할을 함수로 취급하고 있다"*(HN 46763212, 2026-01-26). 서브에이전트의 실질 가치는 조율이 아니라 **깨끗한 컨텍스트**다 — *"명확히 정의된 하위 작업을 독립적으로 수행할 수 있는 신선한 컨텍스트 윈도를 만든다"*(HN 44387136, 2025-06-26).
- **✅ 논문과 커뮤니티가 독립적으로 같은 결론에 도달했다:** 질문이 **"멀티에이전트냐"에서 "왜 멀티에이전트냐"로 재정의됐다.** 정당한 이유는 둘 — **(a) 컨텍스트 격리, (b) 병렬성.** **"정확도 향상"을 근거로 삼으면 MAST가 반박한다.** "역할 놀이"로서의 멀티에이전트는 회의론이 우세하다.
- **숨은 비용 2개:** ① 서브에이전트 팬아웃이 청구서를 곱한다(§4.11) ② **조용한 상태 덮어쓰기** — *"가장 과소평가된 문제는 상태 조율이다. …두 에이전트가 공유 상태에서 서로의 작업을 조용히 덮어쓰는 것을 막는 일. 고전적인 경쟁 조건인데, AI 시스템에서는 출력이 그럴듯해 보여서 프로덕션까지 알아채지 못한다."* (HN 47387252, 2026-03-15)
- **정의를 날카롭게 하는 인용:** *"하나를 고른다. 그게 돈다. 맞기를 바란다. 그건 멀티에이전트가 아니다 — 채팅 히스토리가 있는 단일 에이전트다."* (HN 48196003, 2026-05-19)

### 4.11 매니지드 eval 플랫폼 vs 자체 구축 (커뮤니티)

- **관점 A (플랫폼):** 관측/트레이싱은 일회성 디버깅에 쓰이고 **1%에서만 나는 에러의 회귀 테스트 능력이 없다** → 데이터셋과 지표를 소유한 전용 평가 도구가 필요.
- **관점 B (자체·인간 중심):** 같은 벤더가 **자기 핵심 지표의 신뢰성이 최대 걸림돌**이라고 인정한다. **도구를 사도 평가 설계·라벨링 노동은 이전되지 않는다.**
- **현재 무게중심:** **평가의 어려움은 도구 선택 문제가 아니라 데이터·기준 문제다.** 수렴점 — **트레이싱과 평가를 다른 물건으로 취급하라.** 트레이싱(Langfuse 등)은 도구를 사고, **골든 데이터셋과 판정 기준은 직접 소유하라.**
- ⚠️ **이 축은 발언자 다수가 벤더다.** 처방보다 진단을 신뢰하라.

### 4.12 코딩 에이전트가 실제로 생산성을 올리는가 (커뮤니티)

- **관점 A (순손실 가능):** *"스티어링, 손잡아주기, 이중 확인의 양이 결국 더 느린 빌드 과정보다 더 많은 인간 자원을 소모할 것"*(HN 47876462, 2026-04-23) — 같은 글의 비유 *"SOTA 모델들조차 그 열의에서 골든 리트리버 같은 느낌"*. 1년+ 사용 후 전면 철수 사례도 존재(HN 48083162, 2026-05-10).
- **관점 B (맥락 의존적 큰 이득):** *"한 달 전에 AI 보조가 큰 순손실이었던 작업을 오늘 Claude Code로 20분쯤에 했다."*(HN 44598694, 2025-07-17)
- **논쟁이 정책으로 구체화됐다 — 리뷰 부담의 외부화:** Redox OS의 no-LLM 정책 근거가 이 논쟁의 핵심을 가장 잘 표현한다 — *"과거에는 코드 자체가 일종의 노력의 증거였다. …LLM이 표면적으로 맞아 보이는 PR을 빠르게 생성할 수 있으므로 더 이상 그렇지 않다. 노력이 들어갔을 수도 있지만, 더 자세히 리뷰하는 데 시간을 쓰지 않고는 알 방법이 없다."* (HN 47320789, 2026-03-10). Zig도 같은 방향.
- **현재 무게중심:** 개인 속도 이득에는 광범위한 동의가 있으나, **그 이득이 어디로 이전되는지(리뷰·검증·유지보수)에 대한 회의가 커졌다.** 커뮤니티가 "생산성"을 개인 처리량이 아니라 **시스템 처리량**으로 재정의하는 중이다.
- ⚠️ **자기 선택 편향 경고:** 커뮤니티는 불만이 있는 사람이 더 많이 쓴다. **이 논쟁에서 정량 주장을 커뮤니티 근거로 쓰면 안 된다.**

### 4.13 에이전트 사고의 책임은 누구에게 있는가 (커뮤니티)

프로덕션 DB 삭제 사건이 이 논쟁을 촉발했다. 에이전트의 "자백"이 공개됐다 — *"'절대 추측하지 마라!' — 그런데 내가 정확히 그걸 했다. …검증하지 않았다."*
- **관점 A (도구 문제):** 에이전트가 검증 없이 파괴적 명령을 실행할 수 있었던 **도구·권한 설계의 실패** (HN 47911720, 2026-04-26)
- **관점 B (운영자 문제):** 후속 스레드 제목이 그 자체로 반박이다 — **"AI가 네 DB를 지운 게 아니라, 네가 지웠다"** (HN 48027109, 2026-05-05). 원 글이 *"에이전트를 돌린 사람의 책임은 0으로 둔다"*는 비판.
- **현재 무게중심:** 책임 논쟁이 **"최소 권한을 실제로 어떻게 거는가"라는 공학 질문으로 수렴**했다. 반복 처방 — 개발/프로덕션 환경 분리, 승인 게이트, 자격증명 범위 축소.
- **함께 다뤄야 할 오해:** *"코딩 에이전트에게 '왜 그랬어?'라고 묻는 사용자는 오해를 보여준다. 에이전트는 뭘 하기로 결정하고 나서 하는 게 아니라, 그냥 텍스트를 출력한다."* (HN 47911720) → **사후 합리화를 근거로 쓰지 말라는 경고.**

## 5. 실무 적용 팁 · 용도별 추천 기술 조합 (축 6)

### 5.1 가드레일은 필터 하나가 아니라 4층이다

확인된 벤더 권장 배치를 층으로 정리하면:

| 층 | 무엇 | 확인된 근거 |
|----|------|-----------|
| ① 입력단 | 주입·탈옥 전용 분류기 | Azure **Prompt Shields**(입력 한도 10K자), Meta Prompt Guard |
| ② 실행 중 | 도구 호출 승인·권한 축소 | Claude Code: 기본이 **권한 요청**. 완화 3종 — auto mode classifier(*"scope escalation, unknown infrastructure, or hostile-content-driven actions"*만 차단) / 허용목록 / **OS 레벨 샌드박싱**. 비대화형 배치엔 `--allowedTools` |
| ②' 실행 중 | **도구 사용 이탈 감시** (에이전트 특화) | Azure **Task adherence API**(preview): *"Detects when tool use by AI agents is misaligned, unintended, or premature"* (입력 한도 100K자) |
| ③ 출력단 | 근거성·콘텐츠 검사 | Azure **Groundedness detection**(preview), OpenAI Moderation(**무료**, 13 카테고리, 이미지 지원) |
| ④ 결정적 게이트 | 코드로 강제 | *"Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens."* 예: migrations 폴더 쓰기 차단 훅 |

> **독자가 가장 자주 틀리는 지점:** **advisory 지시(프롬프트·규칙 파일)와 deterministic 훅(코드)의 구분.** 프롬프트로 "하지 마"라고 쓰는 것은 보장이 아니다.

**비용 팁 (공식 문서 근거):** *"a lightweight model runs guardrail checks before deploying expensive models, thereby reducing costs for blocked requests"* — 값싼 모델로 먼저 걸러라. OpenAI Agents SDK는 가드레일 발동 시 `{Input,Output}GuardrailTripwireTriggered`를 **즉시 raise하고 실행을 중단**한다.

### 5.2 청킹 실무 — 출처 있는 수치만

| 지침 | 확인된 수치 | 신선도 |
|------|-----------|--------|
| 청크 크기(일반) | *"usually no more than a few hundred tokens"* — Anthropic | **2024-09-19, 구버전 주의** |
| 청크 크기(작게/크게) | **128–256** / **512–1024** tokens — Pinecone | 발행일 미확인 |
| 전략 6종 | 고정 크기 / 문장·문단 / recursive character / 문서 구조 기반 / semantic / **contextual chunking with LLMs** | Pinecone |
| **오버랩** | **확인 못 함.** 흔히 말하는 "10~20%"의 1차 소스 근거를 찾지 못했다 | — |

> **오버랩 수치를 본문에 박지 마라.** "모델·문서 구조에 따라 조정하는 튜닝 대상"으로 서술하라.

### 5.3 논문 38편이 수렴한 설계 원칙 6개

각 원칙을 뒷받침하는 논문이 **서로 다른 축에서 나왔다**는 점이 이 원칙들의 강도다.

1. **검증기 없는 루프는 넣지 마라.** 리플렉션·트리 탐색·멀티에이전트 토론이 효과를 본 사례에는 **전부 값싼 외부 판정 신호가 있었다.** 없으면 성능이 떨어지기도 한다. (Huang et al. 2310.01798 / ToT 2305.10601 / MAST의 "task verification" 실패 범주)
2. **정확도만 보고하지 마라 — 비용과 분산을 함께 보라.** (AI Agents That Matter 2407.01502 / τ-bench의 pass^k 2406.12045)
3. **채점기를 먼저 감사하라.** 벤치마크 결함의 상당수는 모델이 아니라 **보상 설계**에 있었고, 점수를 3배까지 왜곡했다. (SWE-Bench+ 2410.06992 / ABC 2507.02825)
4. **judge를 쓰면 순서를 무작위화하고 심판과 피심판을 분리하라.** (2305.17926 / 2404.13076 / MT-Bench가 자체 인정한 편향 목록)
5. **인젝션 방어는 프롬프트가 아니라 권한에서 시작하라.** 가장 효과가 컸던 단순 방어는 **도구 노출 최소화**였고, 모델을 키우는 것은 오히려 역효과 경향이 있었다. (AgentDojo 2406.13352 / CaMeL 2503.18813 / AgentHarm 2410.09024)
6. **컨텍스트는 크기가 아니라 배치와 예산의 문제다.** 검색과 롱 컨텍스트는 대체재가 아니고, 청크를 더 넣는 것은 어느 지점부터 해가 된다. (2310.03025 / OP-RAG 2409.01666 / Lost in the Middle 2307.03172)

> **원칙 1의 실무 번역 (논쟁 3의 해소):** Reflexion과 "LLM은 자기 교정을 못한다"는 **모순이 아니다.** Reflexion에는 외부 환경 피드백(컴파일러·테스트·게임 결과)이 있고, Huang et al.이 반박한 건 **피드백 없는 자기 성찰**이다. 그래서 설계 규칙은 "리플렉션 루프를 넣어라"가 아니라 **"검증기(테스트·타입체커·스키마 검증·HTTP 상태 코드)를 먼저 붙여라. 그것 없는 리플렉션은 토큰 낭비이거나 후퇴다."** 신호가 없으면 루프를 넣지 말고 **사람에게 올려라.**

### 5.4 세 소스가 독립적으로 같은 결론에 도달한 지점 (가장 강한 주장들)

이 책에서 가장 자신 있게 쓸 수 있는 명제들이다 — **공식 문서·학술 논문·현장 경험이 각각 다른 경로로 같은 곳에 도착했다.**

| 명제 | 웹(1차 문서) | 논문 | 커뮤니티 |
|------|------------|------|---------|
| ⚠️ **추론은 확률적으로, 집행은 결정적으로** — **합성 명제(저자 주장)** | Anthropic *"Start with simple prompts"* / MS *"If you can write a function… do that instead"* (= **에이전트를 쓸지 말지**) | 원칙 1 (= **루프 설계**) | *"정책이 아니라 확률"* / 결정적 궤적 해시 (= **부작용 경계 집행**) |
| **인젝션 방어는 권한에서 시작한다** | 가드레일 4층 배치 / 최소권한·승인 게이트 / OS 샌드박싱 | AgentDojo 도구 필터 → ASR **7.5%** / 역스케일링 / AgentHarm | *"경계 혼동"* / MCP 두 위험 분리 / DB 삭제 사건 → 최소권한 공학 질문으로 수렴 |
| **멀티에이전트의 정당한 이유는 정확도가 아니라 컨텍스트 격리·병렬성** | 서브에이전트 = 별도 컨텍스트 윈도(Claude Code 문서) | MAST *"성능 향상이 종종 미미하다"* | *"신선한 컨텍스트 윈도를 만든다"* / *"현 세대 LLM의 인공물"* |
| **검색 품질은 DB 교체가 아니라 하이브리드+청킹+리랭킹에서 온다** | Anthropic 5.7%→1.9% / 벡터 검색은 1차 후보 축소기 | OP-RAG 역U자 / Lost in the Middle | *"벡터 DB에 붓고 끝"이 실패 / 전처리·라벨링이 더 큰 이득* |
| **컨텍스트 예산이 지배 변수다** | *"performance degrades as it fills"* / 우아한형제들 전처리 | Lost in the Middle / ReWOO 토큰 5배 | *"에이전트는 자기 역사를 환각한다"* / MCP 툴 정의 팽창 |

> **이 표가 이 책의 논지 골격이다.** 2~5행은 세 소스가 **substantively 같은 명제**를 주장하므로 강하게 써도 된다. §4의 미해소 논쟁은 양쪽을 병기해야 한다.
>
> ⚠️ **1행은 성격이 다르다.** 세 셀이 **서로 다른 층위의 주장**이다 — 웹은 "에이전트를 쓸지 말지", 논문은 "루프를 어떻게 설계할지", 커뮤니티는 "부작용 경계를 어떻게 집행할지". "추론은 확률적으로, 집행은 결정적으로"는 이 셋에서 끌어낸 **합리적 귀납이지만 어느 소스도 이 문장으로 말하지 않는다.** 따라서 **확립된 합의로 단정하지 말고, 본문에 쓸 때 세 근거를 병기해 저자의 종합임을 드러내라.**

### 5.5 용도별 추천 스택 (합성)

> **합성 근거:** 아래 각 셀은 §신선도 원장의 표 행에서 왔다. 이 절은 리서처 한 명의 산출물이 아니라 **web #1(프레임워크·런타임) + web #2(데이터·eval) 교차 합성**이다. 제품 우열이 아니라 **제약 조건**으로 갈랐다.

| 용도 | 프레임워크 | 데이터 계층 | eval·관측성 | 가드레일 | 런타임 | 핵심 제약 |
|------|-----------|-----------|------------|---------|--------|----------|
| **사내 문서 Q&A** | LangGraph 또는 Pydantic AI (도구 1~3회, harness 불필요) | 코퍼스 20만 토큰 미만 → **벡터 DB 없음**. 그 이상 → pgvector(≤1536차원) | Langfuse 셀프호스팅(무료) | 입력 분류기 + 출력 근거성 | 일반 서버 (샌드박스 불필요) | 차원 한계·출처 표기 요구 |
| **코딩 에이전트** | **harness 층 필수** — Claude Agent SDK / deepagents / Strands Harness | **인덱스보다 탐색 도구**(grep·파일 읽기) + 서브에이전트로 컨텍스트 분리 | Terminal-Bench류 + 자체 회귀 스위트 | **도구 승인 게이트 + OS 샌드박싱**(최우선) | **microVM 필수** — Vercel Sandbox(Firecracker 확인) / E2B / Modal | 신뢰불가 코드 실행 = 격리가 1순위 |
| **고객 지원** | CrewAI Flows 또는 LangGraph (결정적 분기 + HITL) | pgvector/Qdrant + **하이브리드 필수**(제품명·오타) + 리랭커 | τ-bench 계열 도메인 시뮬레이션 + LLM-as-judge(편향 주의) | 출력 콘텐츠 검사 + 승인 게이트 | 일반 서버 + 세션 상태 | 오답 비용이 높음 → 사람 개입 지점 설계 |
| **데이터 파이프라인** | Prefect/Dagster(데이터 계보) 또는 워크플로로 충분 — **에이전트 불필요할 수 있음** | 원본 DB·SQL. 벡터 불필요한 경우 다수 | 결정적 단위 테스트 우선 | 스키마 검증 | **Temporal/DBOS**(외부 부작용+재개) | 결정론이 요구사항 → 자율성 최소화 |
| **브라우저/컴퓨터 사용 자동화** | Cloudflare Agents(Browser 내장) / ADK | 대체로 불필요 | WebArena류(**정체 주의**) + 자체 시나리오 | **최소권한 자격증명 + 승인 게이트**(부작용이 실세계) | **강한 격리 + 영속 세션** — microVM/스냅샷 | 프롬프트 인젝션 노출면 최대 |
| **장기 실행·다단계 리서치** | deepagents / Microsoft Agent Framework Harness | 필요 시 하이브리드 | trace 필수(단계가 많아 디버깅 불가능해짐) | 단계별 예산·스텝 상한 | **Cloudflare Workflows**(sleep 365일·대기 인스턴스 무과금) 또는 Temporal | 비용 폭발·종료 조건 설계 |

**전 용도 공통 (확인된 사실 기반)**
1. **비용은 토큰이 98%다**(AWS 실측). 컴퓨팅 최적화는 두 번째.
2. **컨텍스트 예산이 지배 변수다** — *"Claude's context window fills up fast, and performance degrades as it fills."* ~~우아한형제들은 전처리로 96.5% 줄였다.~~ ⛔ **사용 금지 (§3.2·§7.1 참조).** 이 문서 내부 모순이었다 — 같은 문서의 §3.2·§7.1이 `96.5%`를 ❌로 판정한다(원문에 그런 단일 수치가 없고 실제로는 규모별 3행 표다: 41,944→1,763 / 29,386→668 / 9,749→539 bytes). **후자가 우선한다.** 이 절의 문장은 최초 합성 시 남은 잔재이며 2026-07-26 fact-checker가 발견해 오케스트레이터가 표시했다. 후속 개정에서 이 항을 그라운딩으로 쓰지 말 것.
3. **에이전트에게 스스로 돌릴 수 있는 검증을 줘라** — *"Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from."*
4. **실패 패턴을 미리 알라** — *"The infinite exploration"*(범위 없는 탐색이 컨텍스트를 태운다) / *"The trust-then-verify gap"*(그럴듯하지만 엣지 케이스를 놓친 구현).
5. **라이선스를 성능과 같은 급으로 검토하라** — Typesense GPL-3.0, Elasticsearch/Redis 비-OSI, 그리고 `NOASSERTION` 다수(§7.2).

### 7.3 커버하지 못한 영역

- **JS 렌더링 리더보드 3종**(MTEB·GAIA·SWE-bench) — 브라우저 렌더링이 필요. Phase 4에서 Critical 항목만 2차 확인 권장.
- **durable execution 가격 데이터가 전무하다** (Temporal·Restate·Inngest·DBOS). **비용이 선택을 가장 크게 좌우하는 카테고리인데 데이터 포인트가 0이다.** E2B 가격·한도 문서도 404(Mintlify 이전). 이 절을 본문에서 다룰 경우 "가격은 각 벤더 현재 페이지 확인 필요"로 처리하고 수치를 박지 말 것.
- **한국어 자료 비중** — web 1차 소스 15건 중 3건(우아한형제들·AWS Korea·LY). 국내 프로덕션 사례가 절대적으로 적다.
- **LY Corporation 세션** 본문 미확인.

**한국 사례가 절대적으로 부족하다 (가장 큰 공백)**
