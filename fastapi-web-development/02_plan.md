### 독자 여정

**진입 상태:** Spring Boot 또는 Express/NestJS로 프로덕션 웹 애플리케이션을 만들어 봤다. `@RestController`·`@Valid`·`@Autowired`·`@Transactional`·Spring Security 필터 체인이 무엇을 해주는지 몸으로 안다. Python 문법은 읽고 쓸 줄 알지만, **FastAPI 앱을 프로덕션에 올렸을 때 무엇이 자기를 물지 모른다.**

**출구 상태:** 자기가 알던 웹 프레임워크의 개념 하나하나에 대해 **FastAPI에서의 대응물이 무엇이고, 대응물이 아예 없는 곳이 어디인지** 지도를 갖는다. 구체적으로 이런 것들을 할 수 있게 된다.

- 이벤트 루프를 블로킹하지 않는 코드를 쓰고, `def`/`async def` 선택을 **근거를 대며** 한다 (기본 스레드풀 40이라는 숫자가 어디서 오는지 알기 때문에)
- 앱이 커질 때 라우터·서비스 레이어를 어떻게 나눌지 판단한다 — 정답이 정해져 있지 않은 영역이라는 것까지 포함해서
- 비동기 SQLAlchemy 세션의 생명주기와 트랜잭션 경계를 직접 설계한다 — `@Transactional`이 대신해주던 일을 자기 손으로 조립한다
- REST 말고도 실시간·백그라운드·서버 렌더링·GraphQL·BFF 스타일의 앱을 FastAPI 위에서 어떤 모양으로 짓는지 판단한다
- 인증·인가를 프레임워크가 정해주지 않는 상황에서, **무엇을 직접 조립하고 무엇을 위임할지** 결정한다
- uv 기반 프로젝트를 GitHub Actions에 태우고, 컨테이너로 굽고, K8s·서버리스·PaaS 중 자기 앱에 맞는 곳에 올린다 — 각 플랫폼이 동시성 모델에 대해 요구하는 것이 서로 다르다는 것을 알고서
- "FastAPI는 빠르다" 같은 문장을 만났을 때 **어떤 질문을 던져야 하는지** 안다

한 문장으로: **이미 아는 답을 새 도구로 다시 쓰는 법, 그리고 답이 아예 없는 자리를 알아보는 눈.**

## 전체를 관통하는 예제 애플리케이션

### 도메인: 사내 이슈 트래커 (`tracker`)

프로젝트·이슈·댓글·첨부·알림으로 이루어진 Jira-lite. 1장에서 빈 프로젝트로 시작해 14장까지 매 장 자란다.

**이 도메인을 고른 근거:**

1. **도메인 학습 비용이 0이다.** 대상 독자는 전원 이슈 트래커를 써봤고 대부분 비슷한 걸 만들어봤다. 독자의 주의력이 도메인이 아니라 **FastAPI라는 도구 자체**에 100% 쏠린다. 이 책은 개념 밀도가 높아서, 도메인이 조금이라도 낯설면 인지 예산이 샌다.
2. **요구된 7축을 억지 없이 전부 요구한다.** 이슈 CRUD(REST) → 첨부 파일(업로드) → 상태 변경 알림(WebSocket·SSE) → 주간 리포트 생성(스케줄링·백그라운드·태스크 큐) → 관리자 화면(Jinja2·HTMX) → 외부·모바일 클라이언트용 유연 조회(GraphQL) → 사내 검색 서비스 호출(BFF) → 로그인(JWT) → 배포. **어느 것도 "예제를 위한 예제"가 아니다.**
3. **ORM 관계가 자연스럽게 깊다.** 프로젝트 1:N 이슈, 이슈 1:N 댓글, 이슈 N:M 라벨. `MissingGreenlet`과 N+1을 **꾸며내지 않고** 만나게 할 수 있다.
4. **Spring 독자가 같은 앱을 Spring Boot로 어떻게 짤지 이미 머릿속에 갖고 있다.** 대조 축이 매 장 공짜로 생긴다.

**금지 사항 (저술가 준수):** 도메인 설명에 지면을 쓰지 않는다. 엔티티 소개는 1장에서 한 번, 표 하나로 끝낸다. 이후로는 "이슈에 댓글을 단다" 수준의 한 줄이면 충분하다 — 독자는 이미 안다.

**용도 중복 방지:** "대시보드"는 **9장 관리자 화면(Jinja2·HTMX)** 한 곳에만 쓴다. 7장 SSE의 수요자는 **이슈 상세 화면의 실시간 갱신**이고, 9장 GraphQL의 수요자는 **외부·모바일 클라이언트가 각자 필요한 모양으로 가져가는 것**이다 — 세 기능의 동기가 서로 다르게 유지되어야 억지가 없다.

## 내러티브 아크

이 책은 **"당신이 이미 아는 것 → FastAPI에서의 대응물 → 대응물이 없는 자리"**라는 하나의 문장을 14번 반복하는 구조다. 다만 반복이 지루해지지 않도록, 그 문장의 무게중심을 세 번 옮긴다.

**1~4장은 "번역이 잘 되는 구간"이다.** ASGI라는 땅을 밟고(1장), 라우팅·앱 구조·설정이라는 프로젝트의 골격을 세우고(2장), Pydantic이 Bean Validation의 자리를 어떻게 다르게 차지했는지 확인하고(3장), `Depends`가 DI 컨테이너가 아니라는 걸 안다(4장). 여기까지 독자는 "생각보다 비슷하네"라고 느낀다. 그리고 그 안도감이 바로 함정이다 — 2장의 서비스 레이어 논쟁, 3장의 422·RFC 9457, 4장의 자동 와이어링 부재에서 이미 균열이 보이기 시작한다.

**5~6장이 이 책의 등뼈이자 배신 지점이다.** 5장에서 `def` 하나를 잘못 쓰면 40개짜리 스레드풀이 말라붙는다는 걸 소스까지 따라가 확인하고, 6장에서 `@Transactional`이 없는 세계에서 세션과 트랜잭션 경계를 직접 그어야 한다는 걸 배운다. **여기가 실무 사고가 가장 많이 나는 곳이므로 가장 두껍게(각 8,500자) 배치했다.** 순서상 5장이 6장 앞에 오는 것이 결정적이다 — 비동기 모델을 모른 채 비동기 세션을 읽으면 `MissingGreenlet`이 그냥 마법으로 보인다.

**7~9장은 시야를 옆으로 넓힌다.** 지금까지 만든 건 REST API 하나뿐이지만, 실무의 웹 애플리케이션은 그것만이 아니다. 실시간(7장), 오래 걸리는 일(8장), API가 아닌 것들(9장). 이 세 장은 앞의 코어 지식을 **다른 모양으로 재사용하는 훈련**이다 — 7장의 WebSocket 팬아웃, 8장의 스케줄러 N중 실행, 9장의 Strawberry sync 리졸버 블로킹은 전부 5장의 "프로세스와 스레드가 경계다"라는 사실의 다른 얼굴이다. 그리고 9장 끝에서 독자는 스스로 묻는다. **"그런데 이걸 어떻게 프로덕션에 올리지?"**

**10~14장이 그 질문에 답한다.** 인증을 직접 조립하고(10장), 테스트를 세우고(11장), 그 테스트를 파이프라인에 태우고(12장), 컨테이너로 구워 어딘가에 올리고(13장), 올린 것을 관찰하고 판단한다(14장). 이 구간의 톤은 앞과 다르다 — 앞이 "어떻게 쓰는가"였다면 여기는 **"무엇을 감당할 것인가"**다. 마지막 14장은 관측성과 성능을 다루면서 이 책이 계속 미뤄온 질문 하나를 정면으로 꺼낸다: *0.x 버전대에 머무는, 마이너 릴리스가 생태계를 깨는 이 도구를 정말 써도 되는가?* 답을 정해주지 않고, 판단에 필요한 사실을 다 꺼내놓고 닫는다.

**챕터 독립성:** 이 독자는 입문자가 아니라 **아는 장을 건너뛰는 사람**이다. 그래서 각 장은 **자기 주제 안에서 완결**되도록 쓰되, 앞 장의 결론에 기대는 지점은 각 장의 「선행 장·후행 고리」 필드에 명시했다. 완전한 단독 성립을 주장하지는 않는다 — 4장의 `Depends`와 5장의 동시성 모델은 뒤 장들이 실제로 딛고 서는 토대다.

## 설계 근거

### 채택한 구조의 이유

1. **14장은 사용자가 명시 요구한 3축(앱 스타일·CI/CD·배포)을 전부 독립 지면으로 만드는 최소 수이자, 사용자가 허용한 상한이다.** 앱 스타일 3개 장(7·8·9, 21,500자), CI/CD 독립 장(12장, 6,500자), 배포 독립 장(13장, 8,500자).
2. **대조 축을 챕터 경계로 삼지 않고, 챕터마다 내장했다.** "Spring 편 / Node 편"이나 "대조표 부록" 같은 분리 구조를 쓰지 않는다. 독자가 원하는 건 비교표가 아니라 **자기가 아는 개념으로 진입해 새 개념으로 나오는 경험**이다. 그래서 모든 장에 "이미 아는 것" 연결고리를 배정하고, **그 회수를 「주요 내용」 본문 항목으로 승격**했다(연결고리 줄에만 적어두면 저술 때 사라진다).
3. **개념 난이도가 아니라 "사고가 나는 순서"로 배열했다.** 실무에서 FastAPI 프로젝트가 무너지는 순서는 대체로 이벤트 루프 블로킹(5장) → 비동기 세션(6장) → 인증 조립(10장) → 배포 시 워커/프로세스 모델(13장)이다. 이 순서가 곧 챕터 순서이자 분량 배분의 근거다.
4. **예제 앱 하나를 14장 내내 키운다.**

### 분량 경로 선택 (라운드 1 리뷰 C-1)

**경로 C를 택했다 — CI/CD만 분할하고(11·12장), 나머지는 장을 쪼개지 않은 채 장당 분량을 6,000~8,500자로 올린다.** 총량 **105,000자**(산문).

- **경로 A(6·11·13장 다중 분할)를 택하지 않은 이유:** 사용자 지침의 **챕터 수 상한이 14장**이다. CI/CD 분할에 한 장을 쓰면 남는 슬롯이 없다. 상한을 넘겨 구조를 최적화하는 것보다, 사용자가 그은 선 안에서 분량으로 푸는 편이 옳다고 판단했다.
- **경로 B(13장 유지 + 상한 오버라이드)를 택하지 않은 이유:** CI/CD가 독립 장을 받지 못한다. 리뷰 C-2의 지적이 정확하다 — 대안 1을 기각하며 "§5-C는 압축하면 사라지는 종류가 아니다"라고 써놓고 4,000자에 넣은 건 내 논리의 일관성 문제였다.
- **상한 오버라이드는 명문화했다**(위 「분량 정의」 2항). 이건 경로 C의 대가이며, 숨기지 않고 근거와 함께 적는다.

### 기각한 대안 1 — 12장 압축안 (테스트·CI/CD·관측성 통합)

11장을 "테스트·품질·관측성·CI/CD"로 묶어 12장을 맞추는 안.

**기각 사유:** §5-C 하나만으로도 **PEP 751 `pylock.toml` Final(2025-03-31) vs `uv.lock` 불일치 / `--locked`와 `--frozen`을 두 공식 문서가 다르게 쓰는 사실 / ruff의 minor=breaking 버저닝 / `ty`(0.0.63)와 `pyrefly`(1.1.1)의 성숙도 역전 / `actions/setup-python`의 `cache:`가 uv를 지원하지 않는 지뢰 / 파이프라인 조립**이 있다 — 8주제다. 압축하면 사라지는 종류의 정보가 아니라 **이 책만 할 수 있는 이야기**다. 12라는 숫자를 위해 요구사항을 깎는 건 순서가 뒤집힌 것이다.

### 기각한 대안 2 — 3부 구성 (기초 / 응용 / 운영)

1~6장을 「1부 기초」, 7~9장을 「2부 응용」, 10~14장을 「3부 운영」으로 묶는 안. 목차가 깔끔해지고 독자가 자기 위치를 파악하기 쉽다.

**기각 사유:** 이 책의 가장 중요한 통찰 몇 개가 **정확히 부 경계를 가로지른다.** "Lambda는 실행 환경당 1요청, Cloud Run은 인스턴스당 80×vCPU 동시성"이라는 사실(§5-D)은 배포 이야기(3부)처럼 보이지만 실제로는 **5장의 `async def` 선택을 뒤집는다.** 마찬가지로 7장의 WebSocket 팬아웃과 8장의 스케줄러 N중 실행은 13장의 프로세스 모델 없이는 이해되지 않는다. 부 경계는 이런 연결을 "다른 파트의 이야기"로 밀어내 끊는다. 대신 각 장에 **「선행 장·후행 고리」 필드**를 두어 연결을 명시했다.

### 기각한 대안 3 — 튜토리얼 1개 완주형

빈 프로젝트에서 배포까지 한 줄기 튜토리얼로 따라 만드는 안.

**기각 사유:** 이 독자는 입문자가 아니다. `APIRouter` 사용법은 30초면 읽고 넘어가고, 대신 "왜 `Depends`에 컨테이너가 없는가"에서 멈춰 선다. 튜토리얼 완주형은 **건너뛰기를 허용하지 않는 구조**여서 이 독자의 실제 독서 행동과 정면으로 어긋난다. 또한 "왜"를 담을 자리가 없어서 차별화 축(멘탈 모델 번역)이 통째로 증발한다. 예제 앱은 유지하되, 장 구분은 개념으로 하고 예제는 **각 장에서 자라는 지점만 짚는** 방식으로 절충했다.

## 저술 제약 (전 챕터 공통 — chapter-writer 필독)

1. **🚨 출신 귀속 금지 (가장 중요).** 모든 장이 "당신이 이미 아는 것"에서 출발하므로, 그 연결고리가 슬그머니 **인과 주장**으로 미끄러지기 쉽다. 실수 패턴 자체(`async def` 안 동기 호출 등)는 근거가 풍부한 **사실**이지만, **"서블릿 스레드 모델 출신이라서 그렇게 한다"고 밝힌 증언은 리서치 전체에서 0건이다**(§7-2). 원인 귀속은 반드시 **저자 가설**로 표시하라. "Java 개발자는 이렇게 실수한다"는 문장은 이 책에 없어야 한다.
2. **근거가 얇다 ≠ 쓸 것이 없다 (증량 방향 규정).** §7-2·§7-3이 "0건"이라 말하는 것은 **커뮤니티 토론·전환자 체감·경험담**이다. 반면 **API 계약·시그니처·소스 코드로 확인된 것**(`TemplateResponse` 인자 순서, `app.frontend()` 시그니처, Strawberry sync 리졸버 블로킹, httpx `retries` 의미론, `spool_max_size`/`max_part_size` 1MB, uvicorn WS 프로토콜 5종 등)은 마음껏 설명해도 된다. **검증된 계약을 풀어 쓴 산문과 「저자 설계」로 표시한 walkthrough는 fact-checker에 걸리지 않는다. 걸리는 건 없는 경험담을 만드는 경우다.** 분량이 필요하면 반드시 전자 방향으로 늘려라.
3. **버전 표기.** 모든 버전은 `"{버전}/{연월} 기준"` 형식. 계열 버전(`Pydantic v2`, `SQLAlchemy 2.0`)은 안전하고 패치 버전 단정은 위험하다. FastAPI는 월 3~5회 릴리스한다.
4. **뉘앙스 지뢰 6종은 배정된 장에서 정확히 서술한다** (아래 표). 뭉개면 사실 오류다.
5. **§7-1 금지선.** Reddit·Stack Overflow 인용은 리서치에 **한 건도 없다.** 새로 만들어 넣지 마라. OKKY·GeekNews는 제목만 확인됐으므로 내용을 지어내지 마라.
6. **§4 표집 편향.** 커뮤니티 근거 상당수가 HN 단일 스레드(44816755, Litestar 권유 글의 댓글)에서 나왔다. "커뮤니티는 async에 회의적이다", "실무자들은 서비스 레이어를 둔다" 같은 **다수설 일반화를 하지 마라.**
7. **없는 백래시를 만들지 마라.** FastAPI Cloud 상업화에 대한 비판적 반응은 확인되지 않았다(§4-6).
8. **#14603(이벤트 루프 블로킹 경고)은 이 책에 쓰지 않는다.** 목록만 확인된 제안 단계이고 원문 미확인이다(§4-7). **기본값은 미수록.**
9. **🚨 코드 프로바넌스 — 코드는 두 종류이고 규율이 다르다 (§7-5).**

   배경: 리서치 중 **존재하지 않는 코드를 만들어낸 사례 2건**이 적발됐다(oauth2-scopes의 가짜 주석, Auth0의 없는 import 경로 `fastapi_plugin.fast_api_client`). **그리고 이 하네스에는 코드를 실행·컴파일하는 단계가 없다 — 코드 정확성은 저술 규율로만 확보된다.**

   **(A) 인용 코드** — anyio 테스트 예제·SQLAlchemy Quickstart·Uvicorn Dockerfile·`Depends` 시그니처처럼 **남이 쓴 코드를 옮기는 경우.** **1차 소스 원문에서 재확인한 것만** 싣고 **출처와 조회 시점**을 남긴다. 재확인이 안 되면 코드를 빼고 산문으로 설명한다. 최우선 위험 구역: **oauth2-scopes·Auth0(10장) · testcontainers(11장) · Azure Bicep(13장)** — 전부 렌더링 페이지 요약을 경유해 들어온 것들이다.

   **(B) 저자 작성 코드** — `tracker`와 배선 walkthrough처럼 **저자가 직접 쓰는 코드. 이 책 코드의 대부분이 여기 속한다**(2장 서비스 골격, 3장 에러 스키마, 4장 요청 ID 미들웨어, 6장 엔티티 매핑·`get_session`·Alembic 리비전, 7장 Redis 팬아웃, 10장 토큰 발급, 11장 `conftest.py`, 12장 `ci.yml`, 13장 Dockerfile·K8s 매니페스트). 여기에 (A)를 적용하면 **예제 앱이 통째로 사라진다.** 대신 아래 4개를 **전부** 만족해야 싣는다.
   1. **API 표면 추적성 (가장 중요).** 등장하는 **모든 import 경로·클래스·함수·파라미터 이름**이 `01_reference.md` §1-2(0.140.0 AST 목록)·§1-6·§5-A·§5-D·버전 핀 테이블 중 하나로 추적돼야 한다. **목록에 없는 파라미터·데코레이터·import 경로를 쓰지 마라 — 적발된 2건이 정확히 이 유형이다.**
      **필수 예외:** 레퍼런스에 실제 구멍이 있는 영역(Alembic `env.py`의 비동기 표면, `fly.toml`·Railway·Azure 등)은 **1차 소스에서 확인하고 각주로 남긴다. 확인이 안 되면 산문으로 설명하고 그 사실을 해당 장의 「근거 두께」에 적는다.** 이 예외가 없으면 6장 Alembic·13장 매니페스트를 쓸 수 없게 되어 과잉 적용이 된다.
   2. **버전 정합 관용구.** `Annotated[str, Query()]`(≠`Query(None)`) / `model_dump()`(≠`.dict()`) / `DeclarativeBase`·`Mapped[]`(≠`declarative_base()`) / `lifespan`(≠`@app.on_event`) / `pwdlib`·`PyJWT`(≠`passlib`·`python-jose`) / `from httpx import ...`의 층위(지뢰표 해당 행).
   3. **「저자 설계」 표시.** 공식 권장으로 오독되게 두지 않는다.
   4. **주석 금지선. 코드 주석에 동작 설명을 지어 넣지 마라** — 적발 사례 1이 정확히 가짜 주석이다.

   **(C) 자기 신고.** 1차 소스로 추적하지 못한 API 표면이 남으면 그 줄에 `(사실 확인 필요)`를 달아 넘긴다. `fact-checker`가 API 시그니처를 판정 대상으로 갖는다.

   **(D) 코드 분량 규율.** 분량 게이트가 코드를 제외해 세므로 **코드는 자수 예산을 쓰지 않는다 — 구조적으로 길어지기 쉽다.** 논지에 필요한 최소 범위만 싣는다. 예외는 `ci.yml`·Dockerfile처럼 전문 자체가 산출물인 경우이며, 그때도 각 줄이 본문에서 설명돼야 한다.
10. **🚨 대조 축의 반대편에도 같은 잣대를 적용하라.** 이 계획이 쓰는 Spring 측 사실 중 레퍼런스에 실제로 근거가 있는 건 **2건뿐**이다 — §1-4의 `spring.servlet.multipart.max-file-size` 기본 1MB, §1-6의 HikariCP `minimumIdle`. Tomcat `maxThreads`, Actuator `/health/liveness`·`/health/readiness`, `server.shutdown=graceful`, `@Transactional`의 구체 동작 등은 **레퍼런스에 근거가 없다.** fact-checker는 수치·시그니처를 레퍼런스 대조로 판정하므로 이대로 두면 ⚠️ 판정이 다발한다. 따라서 **Spring·Node 측의 설정 키·기본값·엔드포인트 경로**를 쓸 때는 (a) 벤더 공식 문서를 확인하고 **각주를 달거나**, (b) **수치·키를 빼고 구조만 대조**한다. FastAPI 쪽에 적용한 신선도 규율을 반대편에만 면제할 이유가 없다.

### 입문서 흘러내림 방지 (저술가 경계선)

- **1장:** uv를 **Maven/npm의 자리**로 소개하고 명령 대응표 하나로 끝낸다. **설치법·가상환경 개념 설명으로 미끄러지지 마라.**

- **전 장:** Python 기본 문법·REST 개념·HTTP 메서드 설명 금지.

## 챕터 목록

### 1장. 익숙한 웹, 낯선 땅 — FastAPI는 무엇 위에 서 있는가

- **핵심 질문:** 내가 지난 몇 년간 쌓은 웹 프레임워크 지식 중, 무엇이 그대로 옮겨오고 무엇이 여기서는 아예 없는가?
- **선행 장·후행 고리:** 선행 없음(진입 장). → 전 장의 대조 지도를 여기서 깐다. ASGI 계약은 **4장(미들웨어)·5장(동시성)**이 직접 딛고 선다.
- **주요 내용:** (6절)
  - FastAPI는 프레임워크가 아니라 **조립체**다 — Starlette(ASGI·라우팅·미들웨어) + Pydantic(검증·직렬화) + anyio(스레드 오프로드) 위에 얹힌 층. "FastAPI를 배운다"는 실은 **네 프로젝트를 동시에 배운다**는 뜻이다
  - ASGI 3.0 계약: `coroutine application(scope, receive, send)`. 서블릿이 요청·응답을 **객체**로 주는 자리에 ASGI는 **딕셔너리 + 두 개의 async 콜러블**을 준다. `root_path` 축자 *"same as `SCRIPT_NAME` in WSGI"* ↔ `server.servlet.context-path`
  - **7년째 안 변한 계약과 6개월간 세 번 깨진 생태계** — ASGI 3.0(2019-03-20)은 고정돼 있는데, 그 위 FastAPI는 최근 6개월 사이에만 **Python 3.9 지원 중단(0.129.0 / 2026-02-12)·`strict_content_type` 기본 True 전환(0.132.0 / 2026-02-23)·라우터 내부 구조의 트리 변경(0.137.0 / 2026-06-14)**을 했다. 이 대비가 책 전체의 좌표계다. ⚠️ **날짜 규율:** `pydantic.v1` 완전 제거(0.128.0)는 **2025-12-27**이라 "지난 6개월" 창에 들어오지 않는다 — 이 창에 넣지 마라(§3-1의 절 제목은 "2026년 상반기"지만 **표 본문이 정본**이고 2025-12부터 시작한다)
  - 버전 지형과 그 의미 — FastAPI는 **0.140.0 / 2026-07 기준 아직 0.x**인데 Starlette은 **1.3.1 / 2026-06 기준 이미 1.x**다. 성숙도가 역전돼 있다(판단 재료만 제시, 결론은 14장)
  - 예제 앱 `tracker` 소개(엔티티 표 하나) + **uv로 프로젝트 시작** — 공식 문서가 0.140.0/2026-07 기준 uv 프로젝트를 기본으로 쓴다(PR #16032). **Maven/Gradle/npm 명령 대응표 하나로 끝낸다**
  - 이 책이 다루지 않는 것 — Python 문법·REST 개념·HTTP 기초, 그리고 **API 버저닝 전략·캐시 아키텍처**(이 둘은 레퍼런스에 근거가 거의 없어 다루지 않는다고 정직하게 밝힌다)
- **이미 아는 것 연결고리:** 서블릿 컨테이너·`HttpServletRequest`/`Response` / Node의 `(req, res)` 시그니처 / Maven·Gradle·npm → uv
- **독자가 얻는 것:** 이 책 전체의 대조 지도, 그리고 이 생태계의 **변화 속도에 대한 정확한 감각**
- **예제 앱이 자라는 지점:** 빈 uv 프로젝트 + 헬스 엔드포인트 하나
- **오프닝 기법:** 충격적 사실 — "ASGI 명세는 2019년 3월 20일 이후 7년째 한 글자도 바뀌지 않았다. 그 위에 선 FastAPI는 지난 6개월 동안 마이너 릴리스만으로 생태계를 세 번 깨뜨렸다." **그 세 번은 0.129.0(2026-02-12)·0.132.0(2026-02-23)·0.137.0(2026-06-14)이다** — 저술 시 이 셋으로 못 박아라. (§1-1 + §3-1·§3-2, **전부 1차 소스이자 2026년 사실**) 🚨 **이건 책의 첫 문장이다. 날짜 산술을 틀리면 신선도를 셀링 포인트로 내건 책이 첫 줄에서 무너진다**
- **근거:** §1-1, §1-2, §3-1, §3-2, §버전 핀 A·B·J, §5-C, R10·R11
- **근거 두께:** **두꺼움** (1차 소스·소스 코드 직접 확인). ⚠️ Starlette 저장소 이전(`encode`→`Kludex`) 경위는 미확인 — **사실만 쓰고 경위는 쓰지 않는다**
- **예상 분량:** **7,500자** (훅 챕터. `book-editing` 「분량 균형 점검」 3항이 *"1장(훅 챕터)이 중앙값 아래로 떨어지지 않게"*를 요구한다 — 14장 배분의 중앙값이 **7,500자**이므로 이 값이 가드를 만족하는 최소치다. 6,500으로 두면 중앙값 7,250 대비 미달이라 게이트에 걸린다)

### 2장. 라우팅과 앱 구조 — `@RestController`가 사라진 자리

- **핵심 질문:** 라우팅은 어느 프레임워크나 비슷해 보인다. 그런데 왜 FastAPI 앱은 커질수록 구조를 다시 짜게 되는가?
- **선행 장·후행 고리:** 1장의 조립체 구조를 전제한다. → 여기서 정한 프로젝트 골격과 설정을 **6장(DB URL)·13장(워커 수)·14장(OTel)**이 그대로 쓴다.
- **주요 내용:** (8절)
  - 경로 데코레이터의 실제 표면적 — `@app.get`·`@app.post` 등이 **파라미터가 완전히 동일**하다는 사실과 그 목록(`response_model`·`status_code`·`tags`·`dependencies`·`responses`·`operation_id`…)
  - `APIRouter`로 앱 쪼개기 (`prefix`·`tags`·라우터 레벨 `dependencies`) ↔ `@RequestMapping` 클래스 레벨 / Express `Router()`. ⚠️ **함정:** `FastAPI.include_router`와 `APIRouter.include_router`는 **파라미터 순서가 다르다** — 키워드 인자로만 쓰자
  - **핵심 질문에 답하는 절 — 서비스 레이어를 둘 것인가 (§4-4).** Spring식 3계층이 여기서는 관례가 아니다. 한쪽: rmonvfer는 공식 템플릿이 CRUD를 한 파일에 몰아넣는 걸 보고 *"started cringing"*, 결론은 *"not without requiring you to write a framework on top, like I've unfortunately done"*. 반대쪽: 얇은 라우터 + 직접 로직이 Python답다는 주장. 그리고 mattmanser의 경고 — DTO 남발 자체가 문제다(*"to add one property I had to edit 40 files"*). 🚨 **다수설로 일반화 금지** — rmonvfer는 §4 표집 편향의 진원지(HN 44816755)다. **의사결정 기준을 저자 기준으로 제시**하고 독자가 고르게 한다
  - 그래서 `tracker`는 어떤 골격을 갖는가 — 라우터·스키마·서비스·리포지터리 배치의 **한 가지 안**(저자 설계로 표시)과, 그 안을 언제 버려야 하는가
  - **설정 관리** — `pydantic-settings`(2.14.2 / 2026-06 기준)로 `application.yml` + `@ConfigurationProperties`의 자리 메우기. 환경별 분리. **프로젝트 골격의 일부이므로 여기서 정한다**(시크릿 취급은 10장). ⚠️ `application.yml` vs pydantic-settings의 **체감 비교 근거는 없다**(§7-2) — 기능 대응만
  - 자동 OpenAPI **3.1.0** — FastAPI의 최대 셀링 포인트. Springdoc·Swagger 설정 경험과 대조. `operation_id`·`tags`의 존재는 §1-2 AST 목록으로 확인된 **사실**이지만, **그것이 클라이언트 코드 생성에 미치는 영향은 레퍼런스에 근거가 없다 — 저자 서술로 표시하라**
  - **0.137.0(2026-06-14)이 `router.routes`를 트리로 바꿨다.** 축자: *"Any logic that depended on iterating on the `router.routes` directly would be affected."* 대체 API는 `iter_route_contexts()`
  - 그 변경이 실제로 깨뜨린 기록 — `prometheus-fastapi-instrumentator` #370(2026-06-14)·#379(2026-06-25)·#388(2026-07-08). **고쳤는데 3주 뒤 또 터졌다.** 양면을 함께 쓴다(§3-2)
- **이미 아는 것 연결고리:** `@RestController`+`@RequestMapping` / `@Service`·`@Repository` 3계층 / NestJS `@Controller`+모듈 / Express 라우터 마운트 / Springdoc / `application.yml`·`@ConfigurationProperties`
- **독자가 얻는 것:** 앱이 커질 때의 구조 결정 기준(정답이 없다는 사실 포함), 프로젝트 골격과 설정, 그리고 **Spring Boot의 "메이저 아니면 안 깬다" 계약이 여기서는 성립하지 않는다**는 첫 실물 증거
- **예제 앱이 자라는 지점:** `projects`·`issues` 라우터 분리, 서비스·리포지터리 골격, `Settings` 클래스, `/docs`의 첫 스펙
- **오프닝 기법:** 수사적 질문
- **근거:** §1-2(AST 추출 시그니처), §3-1, §3-2, §4-4, §버전 핀 B, R20
- **근거 두께:** **두꺼움** (소스 AST + 릴리스 노트 축자 + 이슈 3건). ⚠️ **얇은 지점:** 서비스 레이어 논쟁은 **HN 소수 발언**이고 §4 표집 편향의 진원지다 → **양측 인용 + 저자 기준**으로만, 다수설 서술 금지. 이슈 본문의 버전 번호는 **보고자 환경 정보**이므로 "무엇이 바뀌었는지"는 릴리스 노트로만
- **예상 분량:** **8,000자**

### 3장. Pydantic과 에러 계약 — 검증이 타입 시스템이 될 때

- **핵심 질문:** `@Valid`가 하던 일을 Pydantic이 한다는데, 왜 실제로는 "검증"보다 훨씬 넓은 무언가처럼 느껴지는가? 그리고 이 API의 에러 응답 계약은 누가 정하는가?
- **선행 장·후행 고리:** 2장의 라우터·스키마 배치를 전제한다. → **이 장이 에러 응답 계약을 끝까지 책임진다.** 4장은 전역 예외 처리 **메커니즘**만 다루고 계약 설계는 이 장을 참조한다.
- **주요 내용:** (8절)
  - `BaseModel`은 검증기가 아니라 **경계에서 타입을 만들어내는 장치**다. 요청 파싱·검증·직렬화·스키마 생성이 한 선언에 붙는다
  - `Annotated[str, Query(...)]` 현대 스타일과, 인터넷에 널린 `q: str = Query(None)` 구식 스타일의 차이. 파라미터 선언 함수 공통 인자(`gt`·`le`·`min_length`·`pattern`·`discriminator`…) ↔ Bean Validation 애너테이션 대응
  - **422라는 선택** — #643(2019-10-22)의 tiangolo 축자 논거(*"sending invalid contents, even though using the correct content format (JSON) through the correct channel (valid HTTP)"*)와 antonagestam의 정면 반박(*"the format here is not simply JSON, but a rich OpenAPI schema"*), Jaza의 절충(구문 400 / 의미 422)
  - **진짜 고통은 상태 코드가 아니라 문서다** — #1376이 5년짜리 우회법 전시장이 된 경위. *"auto-generated documentation doesn't reflect the updated status code"*, 소스 직접 수정까지 간 사례, 모듈 전역 변수 덮어쓰기, 3단 조합. **최대 셀링 포인트가 커스터마이징의 최대 장벽이라는 아이러니**
  - **RFC 9457 문제 상세** — Spring Boot 3 `ProblemDetail` 사용자에게 직결. 🚨 지뢰표 참조: **7807(2019) → 9457(2025) 7년 아크**, PR은 프로세스 사유 close, 현재 코어 지원 없음
  - **✅ 그래서 에러 계약을 이렇게 설계하자 (종합 절 — 이 장의 착지점)** — 검증 에러(422)·도메인 에러·인프라 에러의 3층을 하나의 응답 스키마로 묶는 **저자 설계**. RFC 9457을 직접 흉내 낼 것인가 말 것인가의 판단 기준(*"you can wire it up with a custom exception class and handler"* — 공식 대응이 없으니 직접 배선한다). **자동 문서와의 충돌을 감수할 지점을 명시**
  - 계층 분리 논쟁 — **통념이 뒤집히는 지점.** Java 진영: *"a single annotated record can function as a model for both data and API layers"*(microflash). Python 진영 다수설: *"Your API and your database schema are not the same thing"*(globular-toast). 통념과 정반대다. 그리고 rtpg의 정확한 한계 지적: *"Now it's up to you to actually build up a useful data structure from the straightforward one"*. 🕒 hiram112(2021-12-04)의 *"endless annotations ... pseudo-types ... unlike Java, these types aren't even really guaranteed by the language at compile time"*와 그에 달린 반박 쌍을 **인지 충돌의 기록으로만** 배치(생태계 서술 금지)
  - v1→v2 마이그레이션 어휘 (`.dict()`→`model_dump()`, `orm_mode`→`from_attributes`, `@validator`→`@field_validator`, `class Config`→`model_config`)
- **이미 아는 것 연결고리:** Bean Validation(JSR-380)·`@Valid`·`BindingResult` / class-validator + DTO / Spring `ProblemDetail`·`@ControllerAdvice`의 에러 포맷
- **독자가 얻는 것:** 요청·응답 스키마 설계 능력과 **완결된 에러 응답 계약 하나**, 그리고 그 계약을 자동 문서와 화해시키는 비용의 실측치
- **예제 앱이 자라는 지점:** `IssueCreate`/`IssueRead`/`IssuePatch` 분리, 통합 에러 응답 스키마 + `RequestValidationError` 핸들러
- **오프닝 기법:** 정의 뒤집기 — "검증은 흔히 '잘못된 입력을 막는 일'이라고 한다. Pydantic을 며칠 써보면 생각이 바뀐다. 이건 막는 장치가 아니라 **만들어내는 장치**에 가깝다."
- **근거:** §1-2, §3-4, §3-5, §3-6, §5(마이그레이션 함정), R13
- **근거 두께:** **두꺼움** (이슈 원문 축자 다수). ⚠️ **얇은 지점 2곳:** ① `ConstraintValidator` ↔ `field_validator` 커뮤니티 대조는 **4개 경로 전부 0건**(§7-2) — 구조 비교는 저자 서술로 하되 "두 진영이 이렇게 논쟁한다"고 쓰지 마라 ② `validation_error_response_definition`의 현행 소스 위치는 커뮤니티 진술이므로 **인용 전 현행 소스 대조 필수**. 종합 절의 에러 계약 설계는 **저자 설계로 명시**
- **예상 분량:** **8,000자**

### 4장. `Depends`와 미들웨어 — 컨테이너 없는 의존성 주입

- **핵심 질문:** `Depends`를 DI라고 부르는데 왜 `@Autowired`처럼 쓰면 곧바로 벽에 부딪히는가? 그리고 필터 체인을 쓰던 자리는 이제 무엇이 채우는가?
- **선행 장·후행 고리:** 1장의 ASGI 계약(`scope`/`receive`/`send`)을 딛는다. → `Depends`와 `dependency_overrides`는 **6장(세션·트랜잭션)·10장(인가)·11장(테스트)**이 전부 여기 기댄다. **이 책에서 가장 많이 회수되는 장이다.**
- **주요 내용:** (8절)
  - `Depends`의 실제 계약 — 함수 시그니처를 읽어 재귀적으로 해석하고, `use_cache=True`로 **한 요청 안에서만** 캐시한다
  - **"DI 컨테이너가 없다"의 정확한 의미는 자동 와이어링(auto-wiring)이 없다는 것이다.** dishka 축자: *"You have to declare each dependency with `Depends` on each level of application. So either your business logic contains details of IoC-container or you have to duplicate constructor signatures."* 비교표: 자동 와이어링 ❌, 컨텍스트 데이터 ❌, 동시성 안전성 ➖
  - 애플리케이션 스코프 싱글턴 문제 — #8054는 **2026년 현재까지 Unanswered**이고, 커뮤니티가 5년에 걸쳐 쌓은 우회법 계보(`lru_cache` → startup 인스턴스화 → `app.state` → `AsyncExitStack`+app state)
  - **⭐ 이 책의 핵심 역설:** Spring 개발자는 `Depends`가 **마법이 부족해서** 불만이고, Python 개발자는 `Depends`가 **마법이 과해서** 불만이다("Explicit is better than implicit"에 어긋난다는 비판). 그리고 2026-04-28에도 누군가 NestJS식 `@Module`·DI 컨테이너·Guards를 그리워하며 FastNest를 만들었다 — ⚠️ **단일 저자 프로젝트이지 커뮤니티 합의가 아니다**
  - `yield` 의존성과 생명주기 — `Depends(..., scope="function"|"request")`(0.140.0 / 2026-07 기준). 축자: `"function"`은 응답 전송 **전**, `"request"`는 **후** 종료. 🚨 지뢰: #11107 해결 여부 **미확정**
  - **미들웨어 — 필터 체인을 쓰던 자리 (최소 1,000자 보장)** ASGI 미들웨어의 구조를 1장의 `scope`/`receive`/`send` 계약으로 설명한다 — 서블릿 필터가 `(request, response, chain)`을 받는 자리에 ASGI는 세 요소를 받는다. `BaseHTTPMiddleware`와 순수 ASGI 미들웨어의 **실행 시점·적용 범위 차이**(⚠️ "예외 처리 차이"로 쓰지 마라 — 그건 §7-4가 미확인으로 분류한 한계 영역이고, 같은 절에서 "한계를 단정하지 마라"고 해놓고 예외 처리 동작을 단정하면 자기모순이다). **미들웨어 vs `Depends` 선택 기준**(전자는 모든 요청·라우팅 이전, 후자는 라우트 단위·타입 안전). ⚠️ **`BaseHTTPMiddleware`의 구체적 한계는 §7-4 미확인 — 한계를 단정하지 마라.** 안전하게 쓸 수 있는 건 구조 대조와 선택 기준까지다
  - 예외 처리 **메커니즘** — `HTTPException`·`add_exception_handler`·전역 핸들러의 등록과 우선순위 ↔ `@ControllerAdvice`. **응답 계약 설계는 3장이 책임진다**(여기서 반복하지 말고 명시 참조)
  - lifespan — 🚨 지뢰: `on_event` **3층 구조**를 정확히. 앱 수명 자원(HTTP 클라이언트·커넥션 풀)을 여기 두는 이유. `dependency_overrides` 씨앗(11장 회수) ↔ `@MockBean`/`overrideProvider()`
- **이미 아는 것 연결고리:** Spring DI 컨테이너·`@Autowired`·`@Bean`·스코프 / **서블릿 필터·`HandlerInterceptor`·Spring Security 필터 체인** / NestJS provider·module·Guards·Interceptors / **Express 미들웨어 체인(`next()`)** / `@ControllerAdvice`
- **독자가 얻는 것:** `Depends`를 **컨테이너가 아니라 함수 조합기**로 다시 보는 눈, 횡단 관심사를 미들웨어와 의존성 중 어디에 둘지 고르는 기준
- **예제 앱이 자라는 지점:** `get_session`·`get_current_user` 자리표시자, 요청 ID 미들웨어, lifespan의 `AsyncClient`
- **오프닝 기법:** 상황 가정 ① — "`UserService`를 하나 만들어 여러 라우터에서 쓰려 한다고 해보자. 스프링이라면 `@Service` 한 줄이면 끝나는 일이다."
- **근거:** §1-1(ASGI 계약), §1-2, §3-8, §5(on_event 3층), R6, R20
- **근거 두께:** **두꺼움** (소스 시그니처 + dishka·python-dependency-injector 문서 축자 + 이슈 원문). ⚠️ `BaseHTTPMiddleware` 한계 **미확인 — 단정 금지**. dishka·python-dependency-injector 문서는 **게시일 미확인**이므로 현재형 생태계 서술에 쓰지 말고 논지 근거로만. FastNest는 **단일 저자**임을 명시
- **예상 분량:** **8,000자**

### 5장. 이벤트 루프 — `def`와 `async def` 사이의 40

- **핵심 질문:** 함수 앞에 `async`를 붙이느냐 마느냐가 왜 이 프레임워크에서는 성능이 아니라 **장애**의 문제가 되는가?
- **선행 장·후행 고리:** 1장의 ASGI 계약을 딛는다. → **이 장이 7·8·9·13장의 토대다.** 7장 WebSocket 팬아웃, 8장 스케줄러 N중 실행, 9장 Strawberry sync 리졸버, 13장 워커 모델이 전부 여기서 나온다. **그리고 이 장의 결론은 13장에서 한 번 뒤집힌다** — 플랫폼(Lambda vs Cloud Run)이 답을 바꾼다. 그 예고를 이 장 끝에 명시적으로 남긴다.
- **주요 내용:** (8절)
  - **"40"을 소스로 끝까지 추적한다** — FastAPI `routing.py`의 `is_coroutine` 분기 → Starlette `run_in_threadpool` → anyio `to_thread.run_sync`(limiter 미전달) → **`CapacityLimiter(40)`**(anyio 4.14.2 / 2026-07 기준). 조정: `anyio.to_thread.current_default_thread_limiter().total_tokens = N`
  - **sync `Depends`도 같은 40을 공유한다.** 경로 함수 + 의존성이 하나의 풀을 함께 소진한다 — 이게 실무 함정의 정체
  - 프레임워크가 왜 이렇게 생겼는지 — sync `yield` 의존성의 정리 코드는 **일부러 제한 밖에서** 돈다(`exit_limiter = CapacityLimiter(1)`). 소스 주석 축자: *"can create race conditions/deadlocks if the context manager itself has its own internal pool"*
  - **동시성의 두 층: 프로세스와 스레드** — 지금까지 이야기는 전부 **한 프로세스 안**이다. uvicorn `--workers`(기본 `None`, `$WEB_CONCURRENCY`)는 **독립 프로세스를 N개** 띄운다. 즉 **워커는 메모리를 공유하지 않는다.** 40개 스레드풀도, 인메모리 캐시도, WebSocket 연결 목록도 **워커마다 따로**다. (여기서는 이 사실까지만 확정하고, 워커 수 결정·오케스트레이션은 13장으로 넘긴다)
  - 서블릿 스레드-per-request / Node 단일 이벤트 루프와의 구조 대조 — FastAPI는 **두 모델을 한 프로세스 안에 동시에 갖고 있다**. ⚠️ **`async`/`await` 문법·코루틴 개념은 설명하지 않는다**(독자는 Node 경험자)
  - backpressure — **`--limit-concurrency`가 정답이다**(초과 시 503). `--backlog`(기본 2048)와 혼동하지 말자. uvicorn 0.51.0 / 2026-07 기준 플래그와 기본값. Little's Law로 동시성·지연·처리량 관계 잡기
  - 원리의 뿌리 — Adya et al.(USENIX ATC 2002) *"Event-driven Programming is Not the Opposite of Threaded Programming"*의 **2축 공간**(작업 관리 × 스택 관리). 20년 뒤 async/await가 그 sweet spot을 실현했다는 서사. SEDA(SOSP 2001)·von Behren(HotOS 2003)은 🕒 **하드웨어 전제가 다름을 명시**하고 원리만
  - free-threading과 남은 불확실성 — PEP 703(Final, 3.13)·PEP 779(Final, 3.14), FastAPI 0.136.0의 3.14t 지원. ⚠️ **기본 빌드 전환 시점·벤치마크 미확인 → 단정 금지.** 그리고 **13장 예고**: 이 장에서 내린 `async def` 결론이 플랫폼에 따라 뒤집힌다
- **이미 아는 것 연결고리:** 서블릿 컨테이너 스레드풀(Tomcat `maxThreads`) / Node 이벤트 루프와 `libuv` 스레드풀 / Spring 스레드풀 큐 포화 ↔ `--limit-concurrency` / PM2 클러스터 모드 ↔ `--workers`
- **독자가 얻는 것:** `def`/`async def` 선택을 **근거를 대며** 하는 능력, "느려졌다"는 신고에 어디를 먼저 볼지 아는 순서, 그리고 **프로세스가 경계라는 감각**
- **예제 앱이 자라는 지점:** 첨부 썸네일 생성(CPU 바운드)을 `def`로 뒀을 때 벌어지는 일 재현 → 오프로드로 교정
- **오프닝 기법:** 충격적 수치 — "당신의 FastAPI 앱이 동시에 처리할 수 있는 동기 작업은 **40개**다. 어디에도 그렇게 적혀 있지 않은데 그렇다."
- **근거:** §1-3, §2-2, §5(2·3항), §6-4(동시성 고전), R12·R20·R21·R22·R23
- **근거 두께:** **두꺼움 (이 책에서 가장 단단한 장).** 4단계 체인 전부 1차 소스. ⚠️ **얇은 지점:** ① **Spring WebFlux/Reactor → asyncio 교차 경험담은 0건**(§7-2) — 서블릿 스레드 모델과의 **구조 대조**는 하되 "리액터 하다 asyncio로 넘어온 사람은 이렇게 느낀다"는 서사는 **쓰지 마라** ② asyncio 실증 연구 **0건** → Kotlin 코루틴 버그 연구(ECOOP 2024)는 **언어 불일치를 밝히고** 프록시로만 ③ #14603 **미수록**
- **예상 분량:** **8,500자**

### 6장. 데이터 계층 — JPA를 놓고 SQLAlchemy 2.0을 잡기

- **핵심 질문:** `@Transactional` 한 줄이 대신해주던 일을 이제 누가 하는가? 그리고 왜 비동기로 바꾸는 순간 멀쩡하던 코드가 `MissingGreenlet`으로 죽는가?
- **선행 장·후행 고리:** 4장의 `yield` 의존성·`Depends(scope=)`, 5장의 동시성 모델을 **둘 다** 딛는다(둘 없이는 이 장이 마법으로 읽힌다). → 커넥션 풀 산정은 **13장 워커 수**와, 세션 관리는 **11장 테스트**와 직결된다.
- **주요 내용:** (8절)
  - 2.0 스타일 매핑 — `DeclarativeBase`·`Mapped[...]`·`mapped_column()`. **nullable이 `@Column(nullable=false)`가 아니라 타입의 `Optional[]` 유무에서 파생된다.** ⚠️ 독자가 JPA를 아므로 **매핑 문법 소개는 짧게 지나간다**
  - 레거시로 강등된 것 — `Query`가 *"become long term legacy objects"*, 문자열 기반 `joinedload("addresses")`는 2.0에서 제거. `execute()` vs `scalars()` — 전자는 `Row` 튜플, 후자는 엔티티
  - **`MissingGreenlet`의 정체와 처방 4종** — 공식 정의 축자: *"When using the ORM this is nearly always due to the use of lazy loading, which is not directly supported under asyncio."* 처방과 **각각의 대가**를 하나씩: `selectinload`(*"The most useful eager loading strategy"*) / `AsyncAttrs`·`awaitable_attrs` / `expire_on_commit=False`(공식이 asyncio에선 정상이라고 명시) / `run_sync`(문서 스스로 *"can probably be considered 'controversial'"*). `lazy="raise"`로 아예 차단하는 선택지
  - 동시성 경고 축자: *"A single instance of `AsyncSession` is not safe for use in multiple, concurrent tasks."* → `asyncio.gather()`에는 태스크별 세션. greenlet 의존(⚠️ **일부 플랫폼 기본 미설치**), `await engine.dispose()` 누락 시 `RuntimeError`
  - **트랜잭션 경계를 직접 긋기 (테스트 롤백과 합쳐 최소 1,500자 보장)** — `yield` 의존성 + `Depends(scope=)`(4장 회수). Spring `@Transactional`/OSIV 논쟁과의 대응 관계. 커밋과 세션 종료의 순서 문제. 🚨 지뢰: #11107 해결 여부 **미확정**으로 서술. 테스트 롤백 레시피 `join_transaction_mode="create_savepoint"`(2.0 도입) — **`@Transactional` 테스트 롤백의 정확한 대응물**. ⚠️ `AsyncSession` 판 레시피는 **공식 두 페이지에 없다** — 그 표현 그대로
  - 커넥션 풀 (SQLAlchemy 2.0.51 / 2026-06 기준) — `pool_size` **5**, `max_overflow` **10**, `pool_timeout` 30, `pool_recycle` **-1**, `pool_pre_ping` **False**. *"none of them 'pre create' connections"* → **HikariCP `minimumIdle` 프리워밍이 없다.** **5+10=15가 워커 수와 곱해진다** → DB `max_connections` 산정. `pool_pre_ping` 한계 축자(*"does not accommodate for connections dropped in the middle of transactions"*). 비동기는 `AsyncAdaptedQueuePool`
  - 마이그레이션과 드라이버 — Alembic: 🔴 **autogenerate가 컬럼 rename을 add+drop으로 처리한다(데이터 손실).** 생성물은 반드시 읽는다 ↔ Flyway/Liquibase. 드라이버 URL(`postgresql+asyncpg`·`postgresql+psycopg`·`sqlite+aiosqlite`). ⚠️ asyncpg의 *"5x faster than psycopg3"*는 **자체 측정(2023-06)**이므로 조건 없이 인용 금지. **aiomysql vs asyncmy 우열 단정 금지**
  - **낡은 예제에 걸리지 않기** — 🔴 **Motor(3.7.1 / 2025-05-14)는 EOL을 지났다.** MongoDB를 쓴다면 PyMongo 4.17.0의 async API가 현재 경로다. **구조적으로 10장 passlib 함정과 같다** — 인터넷 예제가 낡은 도구를 쓰고 독자가 복붙한다. redis는 8.0.1에서 `aioredis`가 흡수됐다(⚠️ asyncio 풀 기본값 미확인). 그리고 🔴 **반전: FastAPI 공식 SQL 튜토리얼은 SQLModel을 쓰고 전부 동기다** — *"FastAPI doesn't force you to use anything. 😎"*. N+1은 프레임워크 문제가 아니라 ORM의 문제다(velog JUNYOUNG 2025-03-07: **Spring으로 옮겨갔는데도 N+1을 다시 겪었다**)
- **이미 아는 것 연결고리:** JPA/Hibernate·Fetch Join·N+1 / `@Transactional`·OSIV / HikariCP `minimumIdle` / TypeORM·Prisma / Flyway·Liquibase / Spring `@Transactional` 테스트 롤백
- **독자가 얻는 것:** 비동기 세션 생명주기를 스스로 설계하는 능력, 풀 크기를 **숫자로** 산정하는 법, 마이그레이션을 신뢰하지 않는 습관
- **예제 앱이 자라는 지점:** 이슈-댓글-라벨 매핑, `get_session` 완성, 첫 Alembic 리비전, 트랜잭션 경계 확정
- **오프닝 기법:** 실패 장면(in medias res) — 새벽 알림, 로그에 `MissingGreenlet`. 로컬에서도 스테이징에서도 멀쩡했던 코드다
- **근거:** §1-6, §4-1, §4-2, §4-5, §5-A(테스트 롤백), §3-10, §버전 핀 D
- **근거 두께:** **두꺼움** (공식 문서 축자·시그니처 직접 확인). ⚠️ SQLAlchemy 2.1 GA·`Query` 제거 여부 미확인 → **2.1을 프로덕션 권장으로 쓰지 마라**(2.1.0b3 / 2026-06 베타). `expire_on_commit` 함정·세션 누수의 **커뮤니티 실증 없음**(§7-3) — 구조적 설명으로만

### 7장. 실시간 — WebSocket, SSE, 그리고 스트리밍

- **핵심 질문:** 연결이 오래 살아 있는 앱에서는 무엇이 달라지는가? 그리고 왜 워커를 2개로 늘리는 순간 알림이 절반만 도착하는가?
- **선행 장·후행 고리:** **5장의 "워커는 메모리를 공유하지 않는다"를 직접 딛는다**(그 사실 없이는 팬아웃 문제가 설명되지 않는다). → 11장에서 httpx2 내장 도구로 **여기서 만든 것을 테스트**한다.
- **주요 내용:** (7절)
  - WebSocket 엔드포인트와 연결 수명 관리 — `uvicorn[standard]`가 `websockets`를 설치한다(기본 설치 `h11`+`click`만으로는 WS가 안 된다). 프로토콜 선택지 5종(`auto`/`none`/`websockets`/`websockets-sansio`/`wsproto`)
  - **STOMP 같은 상위 프로토콜이 여기엔 없다** — Spring WebSocket이 STOMP·SockJS로 주던 메시지 라우팅·구독 모델·폴백을 FastAPI는 주지 않는다. 프레임 위에서 **당신이 프로토콜을 정한다**. 그 대가와 이득
  - **Socket.IO의 Redis adapter가 해주던 팬아웃을 이제 당신이 짠다** — 다중 워커 팬아웃은 프레임워크가 풀어주지 않는다(5장의 프로세스 경계). Redis pub/sub 배선(**저자 설계**로 표시). 🔴 **`broadcaster`(0.3.1 / 2024-08-01)는 아카이브됐는데 공식 문서가 아직 링크한다.** ⚠️ 공식 대체재 안내는 **없다** — 사실만 쓰고 대체재를 지어내지 않는다
  - **SSE는 FastAPI 0.135.0(2026-03-01)에 내장됐다.** 인터넷 자료 대다수가 아직 `sse-starlette` 설치를 안내한다 — **이제 1차 선택지가 아니다**. 0.134.0의 `yield` 기반 JSON Lines·바이너리 스트리밍
  - **언제 SSE로 충분하고 언제 WebSocket이 필요한가** (비교 대조형) — 단방향/양방향, 재연결 의미론, 프록시 통과성, 인증 부착 방식의 4축 의사결정 ↔ `SseEmitter` vs `@MessageMapping`
  - 스트리밍 응답의 실무 — 백프레셔, 연결 수명과 타임아웃, ⚠️ 프록시 버퍼링 함정(13장 forwarded headers와는 **별개 문제**)
  - `tracker`의 알림 파이프라인 조립 — 이벤트 발행 → 팬아웃 → 클라이언트 전달의 한 가지 완결된 배선(**저자 설계**)
- **이미 아는 것 연결고리:** Spring WebSocket·**STOMP·SockJS** / `SseEmitter`·`ResponseBodyEmitter` / **Socket.IO Redis adapter** / Express + ws
- **독자가 얻는 것:** 실시간 기능을 **수평 확장 가능한 모양**으로 설계하는 감각, 그리고 "인터넷 예제가 낡았을 수 있다"는 의심
- **예제 앱이 자라는 지점:** 이슈 상태 변경 알림 — WS 채널 + 이슈 상세 화면 SSE 갱신, Redis pub/sub 팬아웃
- **오프닝 기법:** 수사적 질문 — "로컬에서 완벽하게 동작하던 알림이, 워커를 2개로 늘리자 절반만 도착한다. 무엇이 잘못됐을까?"
- **근거:** §1-5(WebSocket·SSE), §3-1, §버전 핀 C·G
- **근거 두께:** **중간~두꺼움.** 프레임워크 사실(내장 SSE·프로토콜 5종·broadcaster 아카이브·`uvicorn[standard]` 구성)은 1차 소스로 단단하다. ⚠️ **실시간 운영 경험담은 없다** → 팬아웃·알림 파이프라인 배선은 **저자 설계로 표시**한다(제약 2번에 따라 이 방향의 증량은 안전)
- **예상 분량:** **7,000자**

### 8장. 오래 걸리는 일 — 스케줄링, 백그라운드 작업, 태스크 큐, 대용량 업로드

- **핵심 질문:** 응답은 즉시 돌려주고 일은 나중에 하고 싶다. `BackgroundTasks` 한 줄이면 되는 것처럼 보이는데, 어디까지 믿어도 되는가?
- **선행 장·후행 고리:** 5장의 프로세스·스레드 두 층을 딛는다. → 8장의 grace period 요구가 **13장 종료 시퀀스**와 정확히 맞물린다.
- **주요 내용:** (7절)
  - `BackgroundTasks`의 정확한 계약 — **같은 프로세스에서 응답 후 실행**된다. **프로세스가 죽으면 사라진다.** uvicorn은 종료 시 백그라운드 태스크 완료를 기다리므로 **grace period 안에 끝나야 한다**(13장 직결)
  - 신뢰도 등급으로 고르기 — 재시도 필요·유실 불가·수 초 초과·CPU 바운드 중 하나라도 걸리면 큐로 넘어간다는 **저자 기준**
  - 태스크 큐 지형(2026-07 기준) — Celery 5.6.3 / arq 0.28.0 / Dramatiq 2.2.0 / RQ 2.10.0 / TaskIQ 0.12.4. ⚠️ **Celery의 asyncio 네이티브 지원에 대한 공식 진술은 확보하지 못했다** — 정황(concurrency 옵션이 prefork·eventlet·gevent·thread·solo로 **asyncio 풀이 없다**)만 제시하고 **단정하지 않는다**. ⚠️ Celery 문서와 PyPI 최신 버전의 지원 범위 불일치도 미확인. **큐 도구 간 우열 단정 금지**
  - **주기 실행 — Quartz·`@Scheduled`를 쓰던 자리** 선택지가 3층이다: 앱 내 스케줄러 / 큐 도구의 주기 기능 / **K8s CronJob**(13장 연결). 🔴 **핵심 함정: 앱 내 스케줄러는 워커가 N개면 N번 실행된다** — 5장의 프로세스 경계에서 **연역되는 구조적 사실**이므로 안전하게 단정할 수 있다(7장 팬아웃 문제와 정확히 대칭이다). 리더 선출·분산 락이 필요한 이유. ⚠️ **APScheduler 등 개별 도구는 버전 핀 표에 없다 — 도구를 단정하지 말고 선택 구조만 제시**
  - 파일 업로드의 실제 한계 (Starlette 1.3.1 소스 확인) — `spool_max_size = 1MB`, `max_part_size = 1MB`. **`UploadFile`은 1MB를 넘는 순간 메모리에서 디스크로 스풀된다.** "다 메모리에 올린다"도 "항상 디스크에 쓴다"도 틀렸다. 대용량은 `max_part_size`를 **명시적으로 올려야 한다**. 우연의 일치: **Spring `spring.servlet.multipart.max-file-size` 기본값도 1MB다**
  - 업로드 → 처리 → 저장 파이프라인을 이벤트 루프를 막지 않고 짜기(5장 회수) — 스트리밍 저장, 오프로드, 크기 제한의 3중 방어
  - `tracker`의 주간 리포트 — `BackgroundTasks`로 시작해 큐로 승격하는 과정을 **판단 근거와 함께** 보여준다
- **이미 아는 것 연결고리:** `@Async`·`TaskExecutor` / **`@Scheduled`·Quartz·Spring Batch** / Bull·BullMQ·Agenda·node-cron / `MultipartFile`
- **독자가 얻는 것:** "나중에 처리"의 신뢰도 등급을 구분하는 눈, 주기 실행을 다중 워커에서 안전하게 하는 구조, 업로드 경로에서 메모리가 터지지 않게 하는 설정값
- **예제 앱이 자라는 지점:** 첨부 업로드, 주간 리포트 스케줄링 + 큐 승격
- **오프닝 기법:** 상황 가정 ② — "리포트 생성 버튼을 누르면 12초가 걸린다고 해보자. 사용자를 12초 기다리게 할 수는 없다."
- **근거:** §1-4, §1-5(BackgroundTasks·태스크 큐), §1-3(워커), §버전 핀 G
- **근거 두께:** **중간~두꺼움.** 업로드 한계·`BackgroundTasks` 계약은 소스로 단단하고, 스케줄러 N중 실행은 **프로세스 모델에서 연역**되므로 안전하다. ⚠️ **얇은 지점:** 태스크 큐 선택 기준·업로드 메모리 실무 증언 **없음**(§7-3), Celery asyncio 공식 진술 **미확보** → 판단 기준은 **저자 기준으로 명시**하고 도구 우열·APScheduler 단정 금지
- **예상 분량:** **7,000자**

### 9장. API 너머 — 화면을 붙이고, 다른 서비스와 말하기

> **내부 2부 구성(명시 — 대조 축이 다르다):** **(가) 프론트엔드를 어떻게 붙일 것인가** 약 3,500자 (SSR·SPA — Thymeleaf/JSP/EJS 대조) / **(나) 다른 서비스와 어떻게 말할 것인가** 약 4,000자 (GraphQL·BFF·httpx — `WebClient`/Resilience4j 대조).
>
> **(가)→(나) 전환 문장을 반드시 두어라.** 두 반부의 대조 축이 다르므로 그냥 이어 붙이면 장이 둘로 쪼개져 읽힌다. 전환의 논리는 *"지금까지는 이 앱이 **사람**에게 무엇을 보여줄지의 문제였다. 이제 상대가 사람이 아니라 **다른 서비스**로 바뀌면, 같은 질문의 답이 달라진다"*는 방향이다. ⚠️ **"이제 2부로 넘어가겠다" 류의 메타 선언은 금지**(`voice.md` §5).

- **핵심 질문:** FastAPI로 JSON API 말고 다른 것도 지을 수 있을까? 지을 수 있다면, 어디까지가 합리적인가?
- **선행 장·후행 고리:** 4장(의존성·lifespan)·5장(블로킹)을 딛는다. → 여기서 만든 관리자 화면과 외부 호출이 **13장 배포**에서 정적 파일·타임아웃 설정으로 이어진다.
- **주요 내용:** (7절)
  - **(가)** 서버 렌더링 — `Jinja2Templates` + `StaticFiles`. ⚠️ **`TemplateResponse`의 인자 순서가 바뀌었다** — 구식 예제 복붙 주의. Thymeleaf·JSP·EJS에서 오는 독자를 위한 대조: 템플릿 해석 시점, 모델 전달 방식, 부분 렌더링
  - **(가)** HTMX와의 궁합 — 부분 갱신을 서버가 HTML 조각으로 돌려주는 패턴. 7장 SSE와 겹치는 지점과 갈리는 지점. ⚠️ **FastAPI 전용 공식 가이드는 확인되지 않았다** — 배선은 **저자 구성**으로 표시
  - **(가)** SPA 서빙 — **`app.frontend(path, directory, fallback="auto", check_dir=True)`**(0.138.0 신규 / 2026-06 기준, 시그니처 직접 확인). 히스토리 폴백이 왜 필요한지, `StaticFiles` 직접 마운트와의 차이 ↔ Spring `/static` 관례·`express.static`
  - **(나)** GraphQL — 공식 문서 권장은 **Strawberry**(0.323.2 / 2026-07 기준). 🔴 **함정: `sync def` 리졸버는 워커 전체를 블록한다** — 5장이 여기서 회수된다. REST와 병존시키는 배치, 스키마와 Pydantic 모델의 관계(3장 회수)
  - **(나)** 서비스 간 호출의 기본기 — `AsyncClient`를 요청마다 만들지 말고 lifespan에서 재사용(4장 회수), 타임아웃·커넥션 풀 설정 ↔ `RestTemplate`/`WebClient`의 커넥션 관리
  - **(나)** 🔴 **httpx의 `retries`는 연결 실패만 재시도한다. HTTP 5xx는 재시도하지 않는다.** Spring Retry·Resilience4j를 기대하고 오면 **반드시 틀린다.** 재시도·타임아웃·서킷 브레이킹을 직접 조립하는 구조(⚠️ pybreaker의 asyncio 지원은 **미확인** — 도구 추천 대신 **패턴만**)
  - **(나)** BFF로 쓸 때의 경계 — 무엇을 모아주고 무엇을 그대로 흘려보낼 것인가. ⚠️ BFF는 학술 근거도 약하다(Microusity, ICPC 2023이 사실상 유일) → **업계 관행으로 정직하게** 서술
- **이미 아는 것 연결고리:** Thymeleaf·JSP / `WebMvcConfigurer` 정적 리소스 / Express + EJS·Pug / NestJS GraphQL 모듈 / **`RestTemplate`·`WebClient`·Spring Retry·Resilience4j** / axios 인터셉터 재시도
- **독자가 얻는 것:** FastAPI의 적용 범위 지도, 각 스타일에서 **가장 먼저 밟는 지뢰**, 그리고 외부 호출의 복원력을 직접 조립하는 뼈대
- **예제 앱이 자라는 지점:** 관리자 대시보드(Jinja2+HTMX), 사내 검색 서비스 호출(BFF), 외부·모바일 클라이언트용 GraphQL 읽기 엔드포인트
- **오프닝 기법:** 앞 장 콜백 — "지금까지 우리는 JSON을 돌려주는 앱 하나를 키워왔다. 그런데 실무의 웹 애플리케이션이 전부 그렇게 생기지는 않았다."
- **근거:** §1-5(서버 렌더링·GraphQL·마이크로서비스), §1-2(`frontend()` 시그니처), §6-4(BFF), §버전 핀 G·H
- **근거 두께:** **API 계약은 확실하고 경험담은 없다.** 확인된 것: `TemplateResponse` 인자 순서 변경, `app.frontend()` 시그니처, Strawberry sync 리졸버 블로킹, httpx `retries` 의미론, `AsyncClient` 재사용. ⚠️ **없는 것:** fasthx·htmx 공식 가이드, pybreaker asyncio, **NestJS↔FastAPI 아키텍처 토론 0건**(§7-2). **대응(제약 2번 적용): 확인된 계약은 충분히 풀어 쓰고, 배선·판단은 「저자 설계」로 명시한다. 경험담·다수설은 만들지 않는다**
- **예상 분량:** **7,500자**

### 10장. 인증과 인가 — Spring Security를 직접 조립하기

- **핵심 질문:** 필터 체인도, `@PreAuthorize`도, 비밀번호 해시 자동 업그레이드도 없다. 그러면 그 일들은 이제 누가 하는가?
- **선행 장·후행 고리:** 4장(의존성 합성·미들웨어)을 딛고, 2장에서 정한 설정 골격 위에 시크릿을 얹는다. → 11장에서 인증 경로를 테스트하고, 13장에서 프록시 뒤 클라이언트 IP 신뢰 문제로 이어진다.
- **주요 내용:** (7절)
  - FastAPI가 주는 것과 주지 않는 것을 정확히 가르기 — `OAuth2PasswordBearer`·`SecurityScopes`는 **스펙 표현과 문서화 도구**에 가깝고, 정책 실행은 당신 몫이다. 🚨 **제약 9번(코드 프로바넌스) 최우선 적용 구역** — oauth2-scopes·Auth0 관련 코드는 리서치에서 **날조가 적발된 영역**이다. **1차 소스 재확인 없이 코드를 싣지 마라**
  - **공식 권장이 이동했다** — `python-jose` → **PyJWT**(2.13.0 / 2026-05 기준), `passlib[bcrypt]` → **pwdlib[argon2]**(0.3.0 / 2025-10 기준). 축자: *"The recommended algorithm is 'Argon2'."* 그리고 *"pwdlib also supports the bcrypt hashing algorithm but does not include legacy algorithms — for working with outdated hashes, it is recommended to use the passlib library"*
  - 🚨 지뢰: **passlib의 마지막 릴리스는 1.7.4 / 2020-10-08이다**(사실). "사실상 방치 상태"는 **해석**이며, 문장을 나눠 쓴다. 인터넷의 `python-jose`+`passlib` 예제가 **왜** 낡았는지 설명해야 독자가 다시 속지 않는다(6장 Motor와 같은 구조의 함정)
  - **조립의 비용은 시간으로 측정된다** — 신고에서 공식 문서 변경까지 **1년/15개월**이 걸린 기록. ⚠️ **§3-9의 antoinewdg 인용은 Django 비교이지 Spring Security 사용자 발언이 아니다** — *"I generally prefer the 'build it yourself' approach, but not for security"*는 **마이크로 프레임워크에서 보안을 직접 조립하는 것에 대한 실무자 불안**으로만 인용하고, **"Spring Security 경험자가 이렇게 말했다"로 묶지 마라**
  - 토큰 설계 실무 — 만료·갱신·회수, 쿠키 vs 헤더, `pyjwt[crypto]`가 필요한 경우(RSA·ECDSA), 키 회전
  - 인가를 의존성으로 조립하기 — 역할·스코프 검사를 `Depends`로 합성(4장 회수). `@PreAuthorize`의 선언적 표현력을 어디까지 흉내 낼 수 있고 어디서 포기해야 하는가. 리소스 단위 권한(프로젝트 멤버십)의 배치

- **이미 아는 것 연결고리:** Spring Security 필터 체인·`SecurityFilterChain`·`@PreAuthorize` / `PasswordEncoder`와 해시 업그레이드 / Passport.js·NestJS Guards / `@Value`·시크릿 관리
- **독자가 얻는 것:** 인증·인가를 **직접 조립하되 감당 가능한 범위로 설계**하는 판단, 그리고 자기가 무엇을 포기했는지에 대한 정직한 목록
- **예제 앱이 자라는 지점:** 로그인·토큰 발급, `get_current_user` 완성, 프로젝트 멤버 권한 검사, 시크릿 분리
- **오프닝 기법:** 충격적 사실 — "당신이 인터넷에서 찾은 FastAPI 인증 예제 열에 아홉은 `passlib`을 쓴다. 그 라이브러리의 마지막 릴리스는 **2020년 10월 8일**이다."
- **근거:** §2-3, §3-9, §7-5(프로바넌스), §버전 핀 F, R2

### 11장. 테스트 — 공식 문서가 `anyio`를 쓰는 이유

- **핵심 질문:** 비동기 앱을 어떻게 테스트하는가? 그리고 왜 내가 아는 방식(`pytest-asyncio`)과 공식 문서가 다른가?
- **선행 장·후행 고리:** 4장(`dependency_overrides`)·6장(트랜잭션 롤백 레시피)·7장(SSE·WS 엔드포인트)을 회수한다. → 여기서 세운 스위트를 12장이 파이프라인에 태운다.
- **주요 내용:** (6절)
  - 🔴 **공식 문서는 `pytest-asyncio`가 아니라 `anyio`를 쓴다.** 대부분의 독자가 반대로 알고 있다. 축자: *"AnyIO provides a neat plugin for this"* / *"By running our tests asynchronously, we can no longer use the `TestClient` inside our test functions."* `TestClient`(동기)와 `AsyncClient`+`ASGITransport`(비동기)를 언제 각각 쓰는가
  - ⚠️ **함정 2개:** ① `anyio_backend` fixture를 지정하지 않으면 **asyncio·trio 양쪽으로 실행된다**(공식 예제 디렉터리에 `conftest.py`가 없다) ② **lifespan 이벤트는 `AsyncClient`가 트리거하지 않는다** — 공식이 권하는 `asgi-lifespan`은 **2.1.0 / 2023-03-28로 3년 넘게 릴리스가 없다**(정체 상태를 병기). pytest-asyncio를 쓴다면 1.0.0(2025-05-26)에서 **`event_loop` fixture가 제거됐다** — 인터넷의 옛 예제가 대량으로 깨진 지점
  - 🚨 **지뢰: `httpx2`의 층위** (지뢰표 4행) — FastAPI `[standard]`는 **여전히 `httpx<1.0.0`을 핀하고**, httpx2로 간 건 **Starlette TestClient**다. `testclient.py`가 `try: import httpx2 / except: import httpx + 경고` 구조이므로 **권장이지 필수가 아니다.** 공식 테스트 예제의 `from httpx import ...`와 버전 핀 표의 httpx2 2.9.1은 **모순이 아니라 층위가 다른 것**이다. **"FastAPI가 httpx2로 갈아탔다"고 쓰면 사실 오류**
  - **그 층위가 주는 실익 — 7장에서 만든 것을 서드파티 없이 테스트한다.** httpx2(2.9.1 / 2026-07 기준)는 `EventSource`·`ServerSentEvent`와 `httpx2.websockets` 서브패키지를 **내장**한다. ⚠️ `alias_httpx`의 정확한 동작은 **미확인 — 단정 금지**
  - `dependency_overrides`로 경계 갈아 끼우기(4장 회수) ↔ `@MockBean`/`overrideProvider()`. `app.dependency_overrides = {}` 초기화 규율. 무엇을 갈아 끼우고 무엇을 진짜로 둘 것인가
  - DB 테스트 — 6장의 `join_transaction_mode="create_savepoint"` 롤백 레시피 적용, testcontainers 4.15.0(축자: *"Version 4.0.0 onwards we do not support the testcontainers-* packages"*) ↔ Testcontainers JVM 판. 🚨 **제약 9번 적용** — testcontainers 코드는 요약 경유 오염 위험 영역이므로 1차 소스 재확인
- **이미 아는 것 연결고리:** JUnit·`@SpringBootTest`·MockMvc·`@MockBean` / Testcontainers(JVM) / Jest·supertest
- **독자가 얻는 것:** 비동기 앱의 테스트 골격, 그리고 **공식 문서와 인터넷 통념이 갈리는 지점에서 공식 쪽을 알아보는 눈**
- **예제 앱이 자라는 지점:** `conftest.py`(anyio backend·오버라이드·DB 롤백), 단위+통합 스위트, SSE·WS 엔드포인트 테스트
- **오프닝 기법:** 인용·일화 — 공식 문서가 스스로 적어둔 문장에서 출발한다: *"By running our tests asynchronously, we can no longer use the `TestClient` inside our test functions."* 대부분의 독자가 그 반대로 알고 있다
- **근거:** §5-A, §5(6·9항), §버전 핀 B·E, R24
- **근거 두께:** **두꺼움** (공식 문서 축자 + httpx2 wheel 직접 확인). ⚠️ **얇은 지점:** JUnit/MockMvc ↔ pytest **전환 경험담 없음**(§7-2) — API 대응은 사실로 쓰되 체감 비교는 하지 않는다. `alias_httpx` **미확인**
- **예상 분량:** **6,000자**

### 12장. CI/CD — 락파일, 품질 게이트, 그리고 파이프라인

- **핵심 질문:** Maven·npm이 정해주던 것들(락파일 표준, 버저닝 관례, 캐시)이 여기서는 왜 하나씩 다 다른가?
- **선행 장·후행 고리:** 11장 스위트를 태운다. 2장의 uv 프로젝트 골격을 전제한다. → 여기서 구운 이미지를 13장이 배포한다.
- **주요 내용:** (6절)
  - **uv가 공식 기본이 됐다** — FastAPI 0.140.0에 PR #16032 *"Update docs to use uv projects by default"*가 포함됐고, 보안·프록시·설정 문서의 명령이 전부 `uv add`/`uv run`이다. Maven·npm에서 오는 독자를 위한 명령 대응과 워크스페이스 개념
  - 🔴 **이 책만 할 수 있는 이야기 — PEP 751.** Status **Final**, Resolution **2025-03-31**, 표준 파일명 **`pylock.toml`**, Author Brett Cannon. **락파일 표준이 확정됐는데 사실상 표준 도구 uv의 산출물(`uv.lock`)은 그 포맷이 아니다.** uv 축자: *"a universal or cross-platform lockfile"* / *"This file should be checked into version control"* / *"**The `uv.lock` format is specific to uv and not usable by other tools**"*. Maven `pom.xml`·Gradle 락파일처럼 단일 표준에 익숙한 독자에게 반드시 설명해야 한다. 그리고 Poetry 2.4.1도 PEP 621 `[project]`로 이동했고(2.0부터 `[tool.poetry]`의 메타 필드는 deprecated), pip-tools는 죽지 않았다 — uv가 `uv pip compile`로 **인터페이스를 흡수**한 것이다
  - `--locked` vs `--frozen` — 의미가 다르다. 축자: `--frozen`은 *"To use the lockfile without checking if it is up-to-date"*, `--locked`는 *"raise an error instead of updating the lockfile"*. ⚠️ **두 공식 문서가 서로 다른 쪽을 쓴다** — uv 자신의 Docker 가이드는 `--locked`, Uvicorn 공식 Dockerfile은 `--frozen`. uv 문서에 "프로덕션엔 `--frozen`" 같은 명시 권고는 **없다.** 사실 그대로 서술하고 선택 기준은 저자 기준으로
  - 🔴 **ruff의 버저닝은 SemVer가 아니다** — 축자: *"Ruff uses a custom versioning scheme that uses the **minor** version number for breaking changes and the **patch** version number for bug fixes."* → **`0.16.0` → `0.17.0`이 breaking change다.** CI 핀 전략에 직결하며 Spring·Node 독자가 반드시 오해한다. 포매터는 *"drop-in replacement for Black"*, *"> 99.9% of lines are formatted identically"*. ⚠️ **formatter의 "stable 선언" 여부는 확인 실패 — "현재 stable로 선언됨"이라고 쓰지 마라**
  - 🔴 **타입체커 성숙도가 통념과 반대다** — Astral `ty`는 **0.0.63**이고 스스로 *"ty is currently in beta."*, 버전 정책은 *"breaking changes ... may occur between any two versions"*. Meta `pyrefly`는 **1.1.1**이고 *"Pyrefly's current development status is stable."*, 실적은 *"the default type checker for Instagram's 20-million-line Python codebase at Meta"* + Pydantic 내장 지원. Astral 제품(uv·ruff)의 성공 때문에 `ty`도 성숙했으리라 짐작하기 쉽지만 **반대다. CI 게이트로 걸 수 있는 건 pyrefly 쪽이다.** 방증: FastAPI 소스 `applications.py`에 **`# ty: ignore[deprecated]`** 주석이 있다(FastAPI가 ty를 실제로 돌린다는 1차 증거). ⚠️ PyPI의 `pyright` 패키지는 **커뮤니티 래퍼**다. ⚠️ mypy 2.3.0·pytest 9.1.1의 breaking change 내역은 **미확인**
  - **파이프라인 조립 (GitHub Actions)** — `astral-sh/setup-uv` **v9**(v9.0.0 / 2026-07-21, "Change `prune-cache` default to `false`"), `actions/setup-python` **v7**(2026-07-20). 🔴 **가장 흔한 지뢰:** `actions/setup-python`의 `cache:`는 축자 *"Supported values: pip, pipenv, poetry."* — **uv를 지원하지 않는다.** `setup-uv`의 `enable-cache`나 `actions/cache`를 직접 써야 한다. ⚠️ uv 자신의 가이드는 아직 setup-uv **v8.1.0**을 핀한 예제를 싣는다(문서 지연). lint → 타입 → 테스트(매트릭스) → 컨테이너 빌드 → 푸시의 게이트 순서와 각 게이트가 막는 것
- **이미 아는 것 연결고리:** Maven·Gradle 빌드 수명주기와 락파일 / npm `package-lock.json`·`npm ci` / Checkstyle·SpotBugs·ESLint ↔ ruff / Jenkins·GitHub Actions 캐시 전략
- **독자가 얻는 것:** 복붙 가능한 파이프라인이 아니라 **각 게이트가 무엇을 막는지 알고 고를 수 있는 능력**, 그리고 Python 생태계의 버저닝 관례가 자기 직관과 다르다는 경계심
- **예제 앱이 자라는 지점:** `.github/workflows/ci.yml` 전문, 핀 전략, 컨테이너 빌드·푸시 잡
- **오프닝 기법:** 정의 뒤집기 — "락파일은 흔히 '버전을 고정해두는 것'이라고 한다. 그런데 2025년 3월 31일에 락파일 **표준**(PEP 751, `pylock.toml`)이 Final로 확정됐는데도, 사실상 표준 도구인 uv의 산출물은 그 포맷이 아니다." (⚠️ 검증된 사실만으로 구성한다 — "CI가 가장 많이 막는 것은 ~다" 같은 **빈도 주장은 근거가 없으므로 쓰지 않는다**)
- **근거:** §5-C, §버전 핀 E
- **근거 두께:** **두꺼움** (PEP 원문·uv/ruff/ty/pyrefly 공식 문서 축자·`action.yml` 축자). ⚠️ **얇은 지점:** Maven/Gradle/npm 대 uv의 **락파일·모노레포 대조 근거는 없다**(§7-2) — 구조 대조(PEP 751 vs `uv.lock`)는 1차 소스로 충분하니 거기에 싣고, 체감 비교는 하지 않는다. ruff formatter stable 선언·mypy 2.x·pytest 9.x breaking **미확인**

### 13장. 컨테이너와 클라우드 — 어디에, 몇 개의 프로세스로 올릴 것인가

- **핵심 질문:** JAR 하나 만들어 던지던 배포가 왜 여기서는 "워커를 몇 개 둘 것인가"라는 질문부터 시작하는가?
- **선행 장·후행 고리:** 5장(프로세스·스레드)·6장(풀 크기)·8장(grace period)·12장(이미지 빌드)을 전부 회수한다. → **여기서 5장의 `async def` 결론이 플랫폼에 따라 뒤집힌다.**
- **주요 내용:** (8절)
  - **Uvicorn 공식 Dockerfile(uv 기반)을 읽는다** — 축자: *"The key strategy is to install dependencies first, then copy the project files."* 캐시 마운트·바인드 마운트의 역할. ⚠️ **그대로 베끼면 안 되는 이유 2개:** ① 비루트 유저 **경고문만 있고 `USER` 지시어가 실제로 없다** ② 베이스가 `python:3.12-slim`으로 **하드코딩**돼 있는데 3.12는 현시점 최신이 아니다. 비루트 처방은 uv가 링크하는 예제 저장소에 있다(`groupadd --system --gid 999 nonroot` + `USER nonroot`)
  - 🔴 **Alpine vs slim — 통념이 절반만 맞다.** "musl이라 wheel을 못 쓴다"는 설명은 **출처가 어긋나 있다**: 공식 이미지 README의 alpine 문단은 *"it does use musl libc instead of glibc and friends, so software will often run into issues"*로 **런타임 호환성** 얘기고, "소스 빌드" 문장은 **slim** 문단에 있으며 원인은 musl이 아니라 **컴파일러 부재**다. PEP 656(musllinux)은 2021년 Final이고, **실측 결과 FastAPI 스택의 핵심 네이티브 확장은 전부 musllinux wheel을 배포한다**(pydantic-core 21·uvloop 16·httptools 14·orjson 20·cryptography 6, 조회 2026-07-25). 정확한 권고는 "Alpine 쓰지 마라"가 아니라 ① 기본은 `-slim` ② Alpine이면 의존성 전체의 musllinux wheel 보유를 **실제로 확인** ③ 남는 리스크는 musl 런타임 차이·롱테일·툴체인 부재
  - **프로세스 모델** — 🚨 지뢰: FastAPI 배포 문서는 *"when running on Kubernetes you will probably not want to use workers and instead run a single Uvicorn process per container"*를 권하고 **gunicorn을 언급하지 않는데**, Uvicorn 자체 문서는 여전히 gunicorn으로 시작한다. **두 공식 문서가 다르다는 사실 자체를 쓴다.** gunicorn을 꼭 써야 한다면 `uvicorn.workers`는 임포트 시 DeprecationWarning을 던지고(대체 `uvicorn-worker` 0.4.0 / 2025-09), 경유 시 축자 *"some options such as `--limit-concurrency` are not yet supported when running with Gunicorn"* — **5장의 backpressure가 여기서 사라진다**
  - **프록시 뒤 배치** — uvicorn이 지원하는 헤더는 `X-Forwarded-For`·`X-Forwarded-Proto` **둘뿐**. `--proxy-headers`는 기본 활성이나 `--forwarded-allow-ips` 기본값은 **`127.0.0.1`**이다. 🚨 **FastAPI 프록시 문서 예시가 `--forwarded-allow-ips="*"`를 쓴다 — 복붙 위험을 반드시 경고한다.** 축자: *"Only trust clients you can actually trust! Incorrectly trusting other clients can lead to malicious actors spoofing their apparent client address"*. `root_path`와 리버스 프록시 경로(1장 회수)
  - **Kubernetes 프로브** — liveness/readiness **분리**가 공식 권장이다. 축자: *"The liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available."* → `/healthz`(liveness)와 `/ready`(readiness)를 나누고 readiness에서만 DB·Redis 확인. 기본값 `periodSeconds` 10 / `timeoutSeconds` 1 / `failureThreshold` 3, `httpGet`은 200~399면 성공. **Spring Actuator에는 대응물이 없다 — 직접 만들어야 한다**

HPA: `desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]`, tolerance 0.1, downscale stabilization **5분**. ⚠️ "IO-bound async 앱에 CPU가 나쁜 신호"는 k8s 문서에 **없는 문장** — 저자 추론으로 표기

**그래서 압력이 걸릴 때 무엇을 쪼개고 무엇을 줄일지 미리 정한다.** 저술가는 즉흥 판단하지 말고 이 표를 따른다.

| 장 | 저술 시 **분할할 불릿** (2개 소절로) | 지면이 모자라면 **먼저 줄일 것** |
|---|---|---|
| 2 | 서비스 레이어 논쟁 → ①양측 입장 ②저자 기준·`tracker` 골격 | 경로 데코레이터 파라미터 **전체 나열**(대표 6개 + 나머지는 표로) |
| 3 | 422 논쟁 → ①상태 코드 논쟁 ②문서 커스터마이징 아이러니 | v1→v2 마이그레이션 어휘(표 하나로 압축) |
| 4 | 미들웨어 절 → ①ASGI 구조 대조 ②미들웨어 vs `Depends` 선택 기준 | 싱글턴 우회법 **계보 4단계**(현재 권장형 + "5년간 쌓였다"는 사실만) |
| 7 | 팬아웃 절 → ①왜 프레임워크가 안 풀어주는가 ②Redis pub/sub 배선 | 프로토콜 선택지 5종의 개별 설명(목록 + 기본값 근거만) |
| 8 | 주기 실행 절 → ①3층 선택지 ②워커 N중 실행과 리더 선출 | 태스크 큐 5종 개별 소개(선택 기준 표로 대체) |
| 10 | 토큰 설계 → ①발급·만료 ②갱신·회수·키 회전 | 알고리즘 선택(RSA·ECDSA) 상세 — `pyjwt[crypto]` 필요 조건만 |
| 11 | 함정 2개 → ①`anyio_backend` ②lifespan 미트리거 | testcontainers 상세(원칙 + 축자 한 줄) |
| 14 | 벤치마크 규율 → ①측정 편향·통계 ②SoK 22결함·꼬리 지연 | 대안 프레임워크 3종 개별 소개(존재와 버전만) |
| 13 | 종료 시퀀스 절 → ①통념 교정 ②grace period 매핑 | **🥇 축약 1순위: HPA 식·tolerance 0.1·downscale stabilization 5분** — 수치를 빼고 "오토스케일링이 축소에 보수적이라는 성질"만 남겨도 논지가 선다 |

**원칙:** 줄일 때 **사실을 흐리지 말고 범위를 좁혀라.** 수치를 뭉개는 축약(예: "약 5분쯤")은 금지다 — 정확히 쓰거나 빼거나 둘 중 하나다.
