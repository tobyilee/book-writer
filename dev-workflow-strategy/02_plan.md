## 제목 후보

1. **개발 워크플로 전략 — 브랜치에서 머지 큐까지, 자주 합치고 안전하게 머지하는 법** — 톤: 정공법·실무서. 포지셔닝: 사용자 요청의 주제어를 그대로 제목에 두어 검색·서가에서 무엇을 다루는 책인지 즉시 드러난다. 부제가 책 전체의 축(통합 빈도 + main의 안전)을 말한다.
2. **main이 늘 초록인 팀 — 브랜치 전략, 코드 리뷰, GitHub Actions, 머지 큐로 짜는 개발 흐름** — 톤: 결과 중심·약간 도발적. 포지셔닝: "초록 main"이라는 구체적 목표 상태를 약속한다. 1~5년차가 매일 겪는 "main이 깨졌다" 경험에 직접 닿는다.
3. **머지의 기술 — 작게 나누고, 자주 합치고, 검증한 그대로 머지하기** — 톤: 원리 중심·에세이 기운. 포지셔닝: 도구보다 원리를 앞세운다. 다만 GitHub Actions를 자세히 다루는 책이라는 점이 제목에서 보이지 않는다.

**추천:** 1번. 사용자가 요청한 주제명("개발 워크플로 전략")이 제목에 그대로 있어야 독자가 책을 찾을 수 있고, 부제가 책의 두 축인 통합 빈도("자주 합치고")와 머지 무결성("안전하게 머지하는")을 함께 담는다. 2번의 "초록 main"은 1장 오프닝과 14장 클로징의 반복 이미지로 본문 안에서 쓴다.

## 내러티브 아크

책은 하나의 장면에서 출발한다. PR 두 개가 각각 초록 체크를 받고 머지됐는데 main이 빨개진다. 이 "머지 레이스"는 책 전체의 두 질문을 품고 있다 — 우리는 얼마나 자주 합치는가(통합 빈도), 그리고 우리가 검증한 것이 정말 머지된 것인가(머지 무결성). 1장은 이 두 축과 DORA 지표를 세우고, 이후 모든 장은 이 축 위에서 한 칸씩 전진한다.

**1부 흐름의 뼈대(1~4장)**는 "어디에, 얼마나 오래 브랜치를 두는가"를 정한다. 2장에서 여섯 가지 브랜치 전략을 통합 빈도 축에 나란히 놓고, 3장에서 실제 팀이 왜 전략을 바꿨는지(우아한형제들의 GitHub Flow→Git Flow, 맘시터의 Git Flow→TBD, Microsoft Release Flow)를 분석하며 기능 플래그라는 대가를 짚는다. 4장은 정한 전략을 main 보호 규칙·룰셋·CODEOWNERS·머지 방식으로 "실행 가능한 약속"으로 바꾼다. 전략을 먼저 두는 이유는 독자가 이 책을 집는 가장 흔한 질문이 "어떤 브랜치 전략을 써야 하나"이기 때문이다. 다만 2장의 결론은 "통합 빈도를 받쳐 줄 리뷰·CI·머지 장치가 있어야 짧은 브랜치가 가능하다"로 열어 두고, 14장에서 전 도구를 갖춘 상태로 다시 고른다.

**2부 PR과 리뷰(5~6장)**는 통합의 단위를 다룬다. 5장은 PR을 작게, 이유가 보이게 만드는 법(크기 연구의 상충까지 정직하게), 6장은 리뷰가 실제로 무엇을 하는지(결함보다 지식 전달)와 병목인 "사람의 주의"를 SLA·리마인더·자동 머지로 푸는 법이다.

**3부 CI(7장)**는 "무엇을 필수 체크로 삼을 것인가"를 도구 이전의 설계 문제로 다룬다. 테스트 계층화와 flaky 테스트가 여기 모인다. CI를 도구보다 먼저 두어야 Actions 장들이 "YAML 문법"이 아니라 "설계를 구현하는 수단"으로 읽힌다.

**4부 GitHub Actions(8~11장)**는 사용자가 "자세히"를 요청한 부분이라 네 장을 쓴다. 기초 해부(8) → 속도와 비용(9) → 재사용과 배포(10) → 보안(11) 순서는 독자가 실제로 부딪히는 순서다 — 일단 돌리고, 느려서 고치고, 여러 저장소로 퍼뜨리고, 사고가 난 뒤에야 보안을 본다. 이 책은 그 순서를 따라가되 11장에서 "사고 전에" 볼 수 있게 한다.

**5부 머지 큐(12~13장)**에서 1장의 장면이 회수된다. 12장은 머지 큐가 무엇을 보장하고 무엇을 보장하지 않는지(원리·계보·사례·2026-04 squash 되돌림 사고), 13장은 도입 판단부터 `merge_group` 설정·two-step CI·처리량 계산·트러블슈팅까지 실전이다. 앞의 모든 장(보호 규칙, 필수 체크, flaky, Actions 트리거)이 여기서 한데 맞물린다.

**14장 종합**은 팀 유형별(웹 서비스 스타트업, 모바일 앱, 오픈소스 라이브러리, 대형 모노레포) 워크플로 설계도를 그리고 DORA로 측정하며, 1장 장면으로 돌아가 닫는다.

## 설계 근거

- **채택한 구조: "통합의 흐름" 순서(브랜치 → 규칙 → PR → 리뷰 → CI → Actions → 머지 큐 → 종합)**
  1. 코드 한 줄이 main에 들어가는 실제 경로와 순서가 같다. 독자는 자기 팀 흐름의 어느 지점이 막혔는지 목차에서 바로 찾는다.
  2. 모든 장이 두 축(통합 빈도, 머지 무결성)에 매달린다. 레퍼런스의 이론 축(Fowler, Bird & Zimmermann, Not Rocket Science Rule)이 이 두 축으로 정리되기 때문에, 주제 나열이 아니라 하나의 논증으로 읽힌다.
  3. 머지 큐를 마지막 도구로 두면 보호 규칙·필수 체크·flaky·`merge_group` 트리거가 모두 앞에서 준비된다. 머지 큐는 앞 장들을 전제로 해야만 제대로 설명되는 기능이다.
- **기각한 대안 1: GitHub 기능 카탈로그형(보호 규칙 / PR / Actions / 머지 큐를 기능 단위로 레퍼런스처럼 배열)** — 기각 사유: 레퍼런스의 한도·플랜 수치는 수개월 단위로 바뀐다(Actions 동시 잡, concurrency `queue`, stacked PR preview 등). 기능 목록 중심 책은 빨리 낡고 GitHub Docs와 경쟁하게 된다. 이 책의 가치는 "왜, 언제"이므로 기능은 설계 질문에 답하는 도구로만 등장시킨다.
- **기각한 대안 2: 브랜치 전략 비교를 마지막(종합 직전)에 배치** — 리뷰·CI·머지 큐를 다 알고 나서야 TBD와 Git Flow의 차이("main의 임의 커밋을 안전하게 배포할 수 있는가")가 제대로 보인다는 점에서 진지하게 고려했다. 기각 사유: 대상 독자가 책을 집는 첫 질문이 브랜치 전략이고, 앞에 두지 않으면 1~4장이 동기 없이 규칙 설명으로 흐른다. 대신 2장 결론을 열린 채로 두고 14장에서 다시 고르게 해 이 대안의 장점을 흡수했다.
- **기각한 대안 3: 팀 성장 단계 서사(1인 → 5인 → 50인 → 500인)로 책 전체를 짜기** — 단계마다 필요한 도구가 자연스럽게 등장한다는 장점이 있었다. 기각 사유: Actions 내용이 네 단계에 흩어져 "Actions를 자세히" 요청을 한곳에서 충족하지 못하고, 머지 큐도 마지막 단계에만 등장해 독립 장 요구와 맞지 않는다. 이 틀은 14장의 팀 유형별 설계도로 축소해 쓴다.
- **머지 큐를 두 장으로 나눈 이유:** 사용자는 독립 장을 요청했다. 레퍼런스 분량(원리·계보·5개 사례·사고·설정·처리량·트러블슈팅·대안)이 한 장 11,000자 상한을 넘고, "무엇을 보장하나"(판단)와 "어떻게 켜고 운영하나"(실전)는 독자가 다른 시점에 다시 찾는 내용이라 나눴다.

## 용어 표기

- **PR**: 첫 등장 "풀 리퀘스트(PR)", 이후 "PR". "풀리퀘" 금지.
- **머지**: "병합" 대신 "머지". 머지 방식은 "머지 커밋", "스쿼시 머지", "리베이스 머지"(GitHub UI 명칭은 첫 등장 시 괄호로 영문 병기).
- **머지 큐**: 일반 개념은 "머지 큐", GitHub 제품을 가리킬 때 "GitHub 머지 큐". 첫 등장 "머지 큐(merge queue)". 큐가 만드는 묶음은 "머지 그룹", 이벤트는 코드 표기 `merge_group`. GitLab 기능은 "머지 트레인(merge train)".
- **main**: 기본 브랜치는 코드 표기 `main`. `master`는 인용과 역사적 맥락(Git Flow 원문 등)에서만.
- **브랜치 전략 이름**: Git Flow, GitHub Flow, GitLab Flow, 트렁크 기반 개발(TBD — 첫 등장 풀어쓰기), OneFlow, Release Flow. "깃플로우" 한글 표기 금지.
- **필수 체크**: required status check. 첫 등장 "필수 상태 체크(required status check)", 이후 "필수 체크".
- **브랜치 보호 규칙 / 룰셋**: "브랜치 보호 규칙(branch protection rule)", "룰셋(ruleset)". CODEOWNERS는 영문 그대로.
- **GitHub Actions 구성 요소**: 워크플로(workflow, "워크플로우" 금지), 잡(job), 스텝(step), 러너(runner), 액션(action — 재사용 단위), 이벤트/트리거. "GitHub 호스트 러너", "셀프호스트 러너".
- **재사용**: "재사용 워크플로(reusable workflow)", "복합 액션(composite action)".
- **배포 환경**: "환경(environment)" — 일반 명사 "환경"과 헷갈리면 "배포 환경(environment)".
- **flaky 테스트**: 첫 등장 "flaky 테스트(실행마다 결과가 달라지는 불안정한 테스트)", 이후 "flaky 테스트". 
- **기능 플래그**: feature flag/toggle은 "기능 플래그"로 통일(Hodgson 인용 시 원어 병기).
- **스택 PR**: stacked PR/stacked diffs → "스택 PR".
- **CI**: 첫 등장 "지속적 통합(CI)", CD도 같은 방식.
- **머지 레이스**: 각 PR은 초록인데 합치면 main이 깨지는 현상. 1장에서 정의하고 12·13장이 같은 말을 쓴다.

## 챕터 목록

### 1부 흐름의 뼈대

### 1장. 두 PR이 모두 초록이었는데 main이 깨졌다 — 워크플로는 왜 전략인가
- **핵심 질문:** 개발 워크플로를 "습관"이 아니라 "전략"으로 다뤄야 하는 이유는 무엇이고, 무엇을 기준으로 좋고 나쁨을 판단하는가?
- **주요 내용:**
  - 머지 레이스 장면 해부 — 각자 초록, 합치면 빨강. 이 책의 두 축(통합 빈도, 검증된 것 = 머지된 것) 도입
  - 통합 빈도의 이론: Fowler("Frequent integration increases the frequency of merges but reduces their complexity and risk"), Bird & Zimmermann의 branchmania(브랜치 제거로 변경당 8.9일 지연 절감, 충돌 +0.04)
  - 브랜치 구조는 조직 구조를 닮는다(Shihab 2012) — 전략이 기술 문제만이 아닌 이유
  - 무엇으로 잴 것인가: DORA 2026-01 갱신판 5지표(구 "4 key metrics/MTTR"과 구분)
  - 책의 지도: 코드 한 줄이 main에 들어가는 경로(브랜치 → PR → 리뷰 → CI → Actions → 머지 큐) mermaid 그림
- **독자가 얻는 것:** 팀 워크플로를 평가할 두 기준과 측정 지표, 책 전체의 지도
- **오프닝 기법:** 실패 장면(in medias res) — 오후 머지 두 건 직후 main 빨강
- **클로징 기법:** 질문 남기기 — "당신 팀에서 브랜치가 main에 합쳐지기까지 며칠이 걸리는가?"
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 7,000자

### 2장. 여섯 가지 브랜치 전략을 한 줄에 세우다 — Git Flow부터 트렁크 기반 개발까지
- **핵심 질문:** 브랜치 전략들은 무엇이 다르고, 그 차이는 어떤 축으로 비교해야 하는가?
- **주요 내용:**
  - 각 전략의 원문 정의와 탄생 맥락: Git Flow(Driessen 2010), GitHub Flow(Docs), GitLab Flow(2014, 환경 브랜치), TBD(trunkbaseddevelopment.com·DORA 기준), OneFlow(Ruka), Release Flow(Microsoft)
  - 비교 축: 장기 브랜치 수, 통합 빈도, 릴리스 방식(연속 배포 vs 명시적 버전), 다중 버전 지원, 핫픽스 경로 — 비교표 1개 + 브랜치 모양 mermaid 그림
  - Driessen 2020 반성 노트: "continuous delivery라면 GitHub Flow처럼 단순한 것을", "explicitly versioned라면 여전히 유효" ("10 years"는 2020 기준임을 지킬 것)
  - Fowler의 환경 브랜치 비판("poor man's modular architecture") — GitLab Flow를 쓸 때의 주의
  - GitHub Flow에서 배포는 언제인가 — Microsoft 해석 vs Docs(귀속해서 서술)
  - 흔한 오해: "TBD는 브랜치를 안 쓴다" → 짧은 feature branch는 리뷰·CI용으로 쓴다
- **독자가 얻는 것:** 전략 이름이 아니라 축으로 비교하는 눈, 결정 가이드 초안
- **오프닝 기법:** 인용·일화 — Driessen의 2020년 노트 "panaceas don't exist… Decide for yourself"
- **클로징 기법:** 의사결정 표로 매듭 — "이런 조건이면 이 전략"을 한 장 표로 압축하고, "단 짧은 브랜치를 받쳐 줄 장치는 뒤에서 채운다"로 열어 둔다
- **스캐폴드 유형:** 비교 대조형
- **예상 분량:** 10,000자

### 3장. 팀은 왜 전략을 바꾸는가 — 전환 사례와 기능 플래그라는 대가
- **핵심 질문:** 실제 팀들은 어떤 압력 때문에 브랜치 전략을 바꿨고, 그 전환은 무엇을 요구했는가?
- **주요 내용:**
  - 우아한형제들 배민 안드로이드(2017): GitHub Flow로 시작 → 릴리스 병행이 생기며 Git Flow로. 모바일 = 명시적 버전 소프트웨어(Driessen 노트와 정합)
  - 맘시터(2022): Git Flow → TBD. 잦은 충돌·드문 배포가 동기, 작은 배포·기능 플래그·테스트 자동화로 보완(수치는 원문 대조 전 완화 서술)
  - Microsoft Release Flow: release 브랜치는 main에 머지하지 않고 cherry-pick, 핫픽스는 main 먼저 — 그 이유
  - 기능 플래그: Hodgson 4분류(Release/Experiment/Ops/Permissioning), "재고(inventory)로서의 플래그", Rahman 2016(Chrome) 기술 부채. 수명과 제거 계획
  - 일반화: 전략을 가르는 건 브랜치 모양이 아니라 "main의 임의 커밋을 안전하게 배포할 수 있는가"(CD 성숙도·릴리스 승인·다중 버전)
- **독자가 얻는 것:** 자기 팀의 전환 신호를 알아보는 기준, 기능 플래그를 도입·정리하는 원칙
- **오프닝 기법:** 상황 가정 — "세 명이 GitHub Flow로 잘 굴리던 앱 팀에 다음 버전 작업과 현재 버전 핫픽스가 겹쳤다고 해보자" (1/3 한도 중 1회)
- **클로징 기법:** 한 문장 여운 — 브랜치 구조는 결국 팀 구조와 배포 능력의 그림자라는 한 문장
- **스캐폴드 유형:** 사례 분석형
- **예상 분량:** 8,000자

### 4장. main을 지키는 약속을 코드로 적다 — 보호 규칙, 룰셋, CODEOWNERS, 머지 방식
- **핵심 질문:** 팀이 정한 전략을 사람의 기억이 아니라 저장소 설정으로 강제하려면 무엇을 어떻게 켜야 하는가?
- **주요 내용:**
  - 브랜치 보호 규칙 항목 전체 훑기와 핵심 선택: 리뷰 필수, 필수 체크(strict vs loose 모드 — strict의 비용이 머지 큐의 동기라는 복선), stale 승인 무효화, 대화 해결, 관리자 포함
  - 룰셋: 여러 개 겹칠 때 가장 엄격한 규칙, 삭제 없이 비활성화, 플랜 제약(evaluate 모드는 Enterprise Cloud), required reviewer rule(2026-02 GA, `!` 부정 패턴)과 CODEOWNERS의 역할 분담
  - CODEOWNERS: 파일 위치·마지막 매칭 우선·미지원 문법·"아무 오너 1명 승인이면 충족"
  - 머지 커밋 / 스쿼시 / 리베이스 머지 비교: `--no-ff`의 원래 동기, GitHub 리베이스 머지는 항상 새 SHA·서명 검증 없음, 커뮤니티 논쟁(커밋 이야기 vs PR 단위 이력) — 결정 기준
  - 설정 예시: 소규모 팀 / 규제 있는 팀 두 가지 구성
- **독자가 얻는 것:** 자기 저장소 보호 설정을 이유를 대며 구성하는 능력, 머지 방식 선택 기준
- **오프닝 기법:** 정의 뒤집기 — "브랜치 보호는 누군가를 막는 장치로 여겨진다. 사실은 팀이 합의한 흐름을 실행 가능한 형태로 적어 둔 문서에 가깝다."
- **클로징 기법:** 적용 과제 — 지금 자기 저장소 설정 화면을 열고 확인할 다섯 가지
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 9,000자

### 2부 PR과 리뷰

### 5장. 리뷰할 수 있는 크기로 — 좋은 PR의 조건
- **핵심 질문:** 어떤 PR이 리뷰되고 머지되기 좋은가, "작게"는 왜 그리고 어디까지 옳은가?
- **주요 내용:**
  - Google 기준점: small CLs 가이드("100줄은 대개 적당, 1000줄은 대개 너무 큼"), Sadowski 2018 실측(중앙값 24줄, 35% 이상 파일 1개) — Google 맥락(monorepo·도구·가독성 인증) 병기
  - 크기 연구의 상충을 정직하게: Bosu 2015(파일 많을수록 유용 코멘트 비율↓) vs Kudrjavets 2022(크기와 머지 시간 무관) vs di Biase 2018(쪼개도 결함 발견 수 동일) → "작게"의 이유는 빠른 머지가 아니라 리뷰 품질과 되돌리기 쉬움
  - 리뷰어가 가장 어려워하는 것은 "변경 이유 이해"(Bacchelli & Bird) → PR 설명·템플릿(요구사항·핵심 변경·리뷰 포인트)
  - 쪼개는 기술: 리팩터링과 동작 변경 분리, Draft PR(2025-05부터 Free private까지), 스택 PR(GitHub 네이티브 `gh-stack` public preview 2026-07-30 — "2026년 9월 기준 preview" 명기, 스쿼시와의 충돌·커뮤니티 회의론)
  - 거절을 부르는 것: Gousios 2014(기술 문제 13% vs 분산 협업·소통 53%) — 2014년 데이터임을 명기
- **독자가 얻는 것:** 큰 변경을 리뷰 가능한 단위로 나누고, 이유가 보이는 PR을 쓰는 기술
- **오프닝 기법:** 충격적 수치·사실 — Google에서 수정 줄 수 중앙값은 24줄, 10% 이상은 한 줄짜리 변경
- **클로징 기법:** 다음 장을 부르는 긴장 — "완벽하게 쪼갠 PR을 올렸다. 그런데 사흘째 아무도 열어 보지 않는다면?"
- **스캐폴드 유형:** 문제-해결형 (거대 PR → 잘못된 쪼개기 → 올바른 쪼개기)
- **예상 분량:** 8,000자

### 6장. 코드 리뷰는 무엇을 위한 것인가 — 지식 전달, 지연, 그리고 팀 합의
- **핵심 질문:** 리뷰가 실제로 만들어 내는 가치는 무엇이고, 병목인 "사람의 주의"를 어떻게 설계로 다룰 것인가?
- **주요 내용:**
  - 버그 그물이라는 기대와 실제: Bacchelli & Bird(결함 코멘트 약 1/8, 개선 코멘트 최다), 75:25 유지보수성 대 기능(Mäntylä·Beller), Google 도입 동기(가독성·유지보수성), Rigby & Bird(지식 확산 66~150%), McIntosh 2014(커버리지·참여도↓ → 결함↑) — "리뷰는 무용"으로 읽지 않게
  - 리뷰어는 몇 명: Rigby & Bird 2명 수렴 vs Google 중앙값 1명 — 맥락별 선택
  - 두 종류의 대기(Kudrjavets 2022b): 첫 응답까지, 승인 후 머지까지 → auto-merge(12장 복선)
  - 지연을 설계로 푼다: Microsoft Nudge(해결 시간 -60%), Meta의 p75 꼬리(24시간), 리뷰 SLA("업무일 1일"), 토스페이먼츠 랜덤 리뷰어 할당+평일 14시 리마인더(Actions cron — 8장 예고), SK DEVOCEAN Pn·D-n 룰
  - 논쟁: "리뷰는 연극인가"(HN) vs 대규모 협업에서의 필수성, 설계 리뷰는 코드 리뷰보다 앞에. AI 생성 PR이 늘며 생기는 부담은 방향만 언급(저신뢰 수치 인용 금지)
- **독자가 얻는 것:** 리뷰의 목적을 팀에 설명하는 언어, 리뷰 지연을 줄이는 구체 장치
- **오프닝 기법:** 수사적 질문 — "코드 리뷰를 하는 이유를 물으면 대부분 '버그를 잡으려고'라고 답한다. 정말 그럴까?"
- **클로징 기법:** 산출물형 — 팀이 바로 채택할 수 있는 리뷰 합의문 초안(응답 시한·리뷰어 수·nit 표기·자동 머지 사용)
- **스캐폴드 유형:** 사례 분석형 (연구·기업 사례에서 원리 추출)
- **예상 분량:** 9,000자

### 3부 CI

### 7장. 무엇을 필수 체크로 삼을 것인가 — CI 설계와 flaky 테스트
- **핵심 질문:** CI는 무엇을 얻기 위한 것이며, PR마다 무엇을 돌리고 무엇을 뒤로 미룰 것인가?
- **주요 내용:**
  - CI의 효과를 정확히: Vasilescu 2015, Hilton 2016(수락 1.6시간 단축·릴리스 2배, 사용 이유 1위 "빌드 깨짐 걱정 감소" 87.71%) vs Bernardo 2018/2023("빨라진다는 보장은 없다, 핵심 이득은 판단 개선") — Travis 시대 데이터임을 명기. 결론: CI는 안심과 판단의 도구
  - 테스트 계층화: Microsoft(1·2단계 6만 개 테스트 5분 이내), PR은 빠르게·머지 후는 넓게, Google TAP 규모의 한계와 Meta 예측 테스트 선택 → 일반 팀의 축소판(경로 기반 선택)
  - 필수 체크 선정 원칙: 빠르고 결정적인 것만 필수로, 느린 것은 머지 큐·머지 후·야간으로(Hilton 2017의 속도↔확실성 축)
  - flaky 테스트: "잡음이 되면 신호가 죽는다"(HN), 원인 상위(Async Wait 45%·동시성·순서 의존, Luo 2014), 수치 규율(Google 1.5%와 Luo 4.56%는 분모가 달라 한 문장에 비교 금지), 무관용 vs 재시도+격리+소유자 통지 — 선택 기준
  - 머지 큐에서 flaky가 증폭된다는 복선(13장)
- **독자가 얻는 것:** 필수 체크 목록을 설계하는 원칙, flaky 테스트 대응 정책
- **오프닝 기법:** 상황 가정 — "금요일 오후, CI가 또 빨갛다. 로그를 보지도 않고 Re-run 버튼을 누른다고 해보자." (1/3 한도 중 2회)
- **클로징 기법:** 오해 정정으로 닫기 — "CI는 빠르게 하는 도구"라는 통념을 뒤집는 한 문단으로 매듭
- **스캐폴드 유형:** 문제-해결형
- **예상 분량:** 9,000자

### 4부 GitHub Actions

### 8장. GitHub Actions 해부 — 워크플로, 잡, 스텝, 러너, 트리거
- **핵심 질문:** 7장에서 설계한 검사를 GitHub Actions로 옮기려면 무엇을 알아야 하는가?
- **주요 내용:**
  - 구성 요소 지도: 워크플로 파일 → 이벤트 → 잡(러너) → 스텝(액션/`run`) mermaid 그림, 최소 CI 워크플로 한 벌 해설
  - 트리거 깊게: `push`/`pull_request`(fork PR에는 시크릿 미전달·`GITHUB_TOKEN` 읽기 전용), `workflow_dispatch`, `schedule`(토스 리마인더 예), `workflow_run`, `merge_group`은 존재만 소개(13장 소유), `pull_request_target`은 위험 표시만(11장 소유). `branches`/`paths` 필터 glob
  - 표현식·컨텍스트·`needs`·`if`, 잡 간 데이터 전달(outputs), `matrix`(최대 256잡)
  - `permissions` 키 개관과 기본값(11장 복선), 러너 종류(GitHub 호스트 / 셀프호스트)
  - 한도(2026년 9월 GitHub Docs 기준 명기): 잡 6시간, 워크플로 런 35일, 동시 잡 플랜별, `GITHUB_TOKEN` 요청 한도 — "자주 바뀌므로 Docs 확인" 규율
  - YAML의 어려움(Saroar 2023: 60.87%)과 이를 다루는 습관(actionlint 등 검사 도구는 일반론으로)
- **독자가 얻는 것:** 복붙이 아니라 이해하고 쓰는 Actions 기초, 첫 CI 워크플로
- **오프닝 기법:** 앞 장 콜백 — "앞 장에서 무엇을 필수 체크로 삼을지 정했다. 이제 그 검사를 실제로 돌릴 차례다."
- **클로징 기법:** 실습 과제 — 이 장의 최소 워크플로를 자기 저장소에 넣고 일부러 실패시켜 필수 체크가 머지를 막는지 확인
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 11,000자

### 9장. 빠르고 싼 파이프라인 — 캐시, 아티팩트, 동시성, 모노레포
- **핵심 질문:** 느리고 비싼 CI를 어떻게 빠르고 싸게 만들고, 그 과정의 함정은 무엇인가?
- **주요 내용:**
  - 비용 감각: 뱅크샐러드("3분 × 20명 = 1시간"), Bouzenia 2024(자원 91.2%가 테스트·빌드, 캐시 쓰는 유료 저장소 32.9%, 비활성 스케줄 끄기로 1.1~31.6% 절감)
  - 캐시: 키·restore-keys 매칭 순서, 스코프(현재·기본·base 브랜치만, 형제 브랜치 불가 — 흔한 오해), 7일 미접근 삭제, 저장소당 기본 10GB
  - 아티팩트: 캐시와의 차이, v3 차단(2025-01-30) — 최신 메이저는 fact-checker 확인 전 단정 금지
  - concurrency: 낡은 PR 런 취소 패턴, 2026-05 `queue: max`(최대 100 대기)와 `cancel-in-progress` 병용 불가
  - 모노레포 함정: `paths` 필터 워크플로를 필수 체크로 지정하면 영원히 대기(Discussion #13690) → "변경 감지 잡 + 항상 도는 집계 잡 하나만 필수" 패턴 전체 YAML, skip된 잡은 success가 아니라는 함정, `fetch-depth`
  - 러너 선택: GitHub 호스트 vs 셀프호스트(비용·보안·하드웨어), 2025-12 셀프호스트 과금 발표·연기 사례(재도입 여부 확인 후 서술)
  - 피드백 루프: "push하고 기다리기"를 끊는 법 — YAML은 얇게, 빌드 로직은 로컬에서 도는 도구(make·just·mise 등)로
- **독자가 얻는 것:** CI 시간·비용을 줄이는 구체 기법과 모노레포 필수 체크 설계
- **오프닝 기법:** 충격적 수치·사실 — 유료로 Actions를 쓰는 저장소 중 캐시를 쓰는 곳은 셋 중 하나꼴(32.9%)
- **클로징 기법:** 계산식으로 매듭 — "CI 한 번의 비용 = 대기 시간 × 기다리는 사람 수 × 하루 실행 횟수" 한 줄 공식과 자기 팀 값 넣어 보기
- **스캐폴드 유형:** 문제-해결형
- **예상 분량:** 11,000자

### 10장. 한 번 쓰고 여러 곳에서 — 재사용 워크플로, 복합 액션, 배포 환경
- **핵심 질문:** 여러 저장소·여러 잡에 퍼진 YAML을 어떻게 재사용하고, 배포를 어떻게 안전한 절차로 만들 것인가?
- **주요 내용:**
  - 재사용 워크플로 vs 복합 액션 비교표: 호출 위치(잡 vs 스텝), 여러 잡 포함 여부, 로깅, 시크릿 전달(`inherit` vs inputs — 원문 대조), 중첩 한도(10단계). 언제 무엇을
  - 조직 공용 워크플로 설계: 버전 관리(태그 vs SHA — 11장과 연결), 입력 계약, 호출자 권한
  - 배포 환경(environment): required reviewers(최대 6), 자기 승인 금지, wait timer(1~43,200분), 승인 전 환경 시크릿 접근 불가, 배포 보호 규칙 — 플랜 제약(Free/Pro/Team은 public만)
  - OIDC로 클라우드 자격 증명: 장기 시크릿 대신 잡 단위 단기 토큰, subject를 환경/ref로 제한하는 이유 (`id-token: write` 요구는 확인 후 서술)
  - concurrency로 배포 직렬화(9장 연결), GitHub Flow 배포 시점 논쟁과 환경 게이트의 관계
- **독자가 얻는 것:** 중복 없는 조직 공용 파이프라인과 승인·자격 증명이 갖춰진 배포 워크플로
- **오프닝 기법:** 수사적 질문 — "똑같은 YAML 40줄을 스무 개 저장소에 복붙해 두었다면, 버그 하나를 고치려면 몇 번 PR을 올려야 할까?"
- **클로징 기법:** 설계 원칙 세 줄 압축 — 재사용·배포에 관한 원칙을 세 문장으로
- **스캐폴드 유형:** 비교 대조형
- **예상 분량:** 10,000자

### 11장. YAML 한 줄이 공격 표면이다 — GitHub Actions 보안
- **핵심 질문:** CI가 가진 권한과 시크릿을 노리는 공격은 어떻게 일어나며, 워크플로를 어떻게 굳힐 것인가?
- **주요 내용:**
  - 사건 재구성: tj-actions/changed-files(CVE-2025-30066) — 태그 재지정, 로그로 시크릿 유출, SHA 고정 사용자는 무사. 확정 사실(CISA·Advisory)과 보도 수치(확인 필요 항목)를 구분해 서술
  - 태그는 불변이 아니다: full commit SHA 고정("currently the only way… immutable release"), Dependabot/Renovate로 갱신, 조직 정책의 SHA 고정 강제(2025-08-15), immutable releases(2025-10-28)
  - `GITHUB_TOKEN` 최소 권한: 기본 contents read + 잡 단위 상향, 2023-02 이전 조직은 기본값 점검. Koishybayev 2022의 99.8%는 전환 이전 데이터임을 명기
  - pwn request: `pull_request_target` + PR head 체크아웃의 위험(Security Lab 2021), 안전 패턴(`pull_request` → artifact → `workflow_run`), 2025-12-08 동작 변경(항상 기본 브랜치 워크플로·커밋) — 이전 자료와 달라진 점
  - 스크립트 인젝션: `${{ github.event.pull_request.title }}`를 `run`에 직접 넣지 않기, 중간 환경 변수 패턴(ARGUS 2023)
  - 그 밖의 방어선: `.github/workflows`를 CODEOWNERS에(4장 회수), public 저장소에 셀프호스트 러너 금지, AI 에이전트 액션의 프롬프트 인젝션이라는 새 표면(보도 수준 — 방향만)
- **독자가 얻는 것:** 자기 워크플로를 공격자 시선으로 점검하고 굳히는 절차
- **오프닝 기법:** 실패 장면(in medias res) — 2025년 3월 14일, 수만 개 저장소가 쓰던 액션의 버전 태그가 한꺼번에 다른 커밋을 가리키기 시작한다
- **클로징 기법:** 사례 되감기 — 오프닝의 사건으로 돌아가 "SHA를 고정하고, 토큰이 읽기 전용이었다면" 무엇이 달라졌는지 되짚으며 닫기
- **스캐폴드 유형:** 사례 분석형
- **예상 분량:** 11,000자

### 12장. 검증한 것을 머지한다 — 머지 큐는 무엇을 보장하는가
- **핵심 질문:** 머지 레이스는 왜 생기며, 머지 큐는 이를 어떤 원리로 막고 무엇은 막지 못하는가?
- **주요 내용:**
  - 1장 장면 회수: 머지 레이스의 원리, strict 필수 체크(4장)의 비용 — 매번 base 따라잡기와 재검사
  - 뿌리와 계보: Not Rocket Science Rule(2차 인용임을 명기), bors → GitHub 머지 큐·GitLab 머지 트레인, Uber SubmitQueue(투기 실행·충돌 분석 — 개념 계보로만, 구현이 다름을 명기)
  - GitHub 머지 큐 작동: 임시 브랜치(`gh-readonly-queue/…`)에 앞선 PR을 누적해 테스트, 머지 그룹, 실패 시 제거 사유 — 작동 흐름 mermaid 그림
  - 승인 후 대기 제거(6장 Kudrjavets 29~63% 회수), auto-merge와의 차이
  - 사례: GitHub 사내 "train" 방식에서 머지 큐로(대기 33% 감소, "2,500건"의 기간은 원문 대조 전 단정 금지), Shopify(예측 브랜치, 배치 8), Block(머지 후 빌드 실패 사실상 제거)
  - 보장의 경계: 2026-04-23 스쿼시 머지 그룹 되돌림 사고 — 도구 자체가 틀릴 수 있다. 규모 수치는 출처 병기 또는 생략. 머지 방식(4장)이 노출면을 바꾼다는 교훈
- **독자가 얻는 것:** 머지 큐가 필요한 상황을 판별하는 원리와 그 한계에 대한 정확한 기대
- **오프닝 기법:** 인용·일화 — GitHub 사내의 "기차(train)" 이야기: 기차에 탄 뒤 8시간 넘게 기다렸다가 충돌로 내려야 했던 시절
- **클로징 기법:** 두 줄 대비로 매듭 — "머지 큐가 보장하는 것 / 보장하지 않는 것"
- **스캐폴드 유형:** 개념 도입형
- **예상 분량:** 9,000자

### 13장. 머지 큐 도입 실전 — 설정, merge_group, 처리량, 트러블슈팅
- **핵심 질문:** 우리 팀은 머지 큐를 도입해야 하는가, 한다면 어떻게 설정하고 운영하는가?
- **주요 내용:**
  - 도입 판단: 트래픽·빌드 시간·main 파손 빈도. "비용만 두 배" 반론(같은 검사 두 번)과 two-step CI(PR엔 lint·unit, `merge_group`에서 통합·E2E)라는 답
  - 가용 범위와 대안: 플랜 제약(2026년 9월 기준 확인된 범위만 서술, Team 플랜 private 지원 여부는 fact-checker 확인 결과에 따름), 불가하면 strict 체크 + auto-merge, 서드파티(Mergify·Graphite 등, 벤더 글 중립성 주의), GitLab 머지 트레인
  - 설정 한 벌: 보호 규칙/룰셋의 "Require merge queue", 필수 체크 워크플로에 `merge_group` 추가(빠뜨리면 AWAITING_CHECKS에서 멈춤), 서드파티 CI는 `gh-readonly-queue/{base}/**` 대응, build concurrency·merge limits(범위 1~100만 확인 — **기본값 서술 금지**), 상태 체크 타임아웃, "Only merge non-failing pull requests"
  - 처리량 계산: 빌드 시간 × 동시 빌드 한도(danlucraft 예: 8개 PR, 30분 빌드, 동시 2 → 2시간), 배치와 실패 격리(Mergify 분할 방식), 앞자리 점프의 전체 재빌드 비용
  - 운영: flaky가 그룹 전체를 떨어뜨리는 증폭(7장 회수), 모노레포 집계 체크(9장 회수)와의 결합, 스택 PR의 머지 큐 지원(rolling out — 시점 명기)
  - 트러블슈팅: 큐가 멈췄을 때 순서(필수 체크 존재 → `merge_group` 트리거 → 헤드 제거 → 큐 비우기 → 끄고 다시 켜기)
- **독자가 얻는 것:** 머지 큐 도입 여부 판단과, 첫날부터 멈추지 않는 설정·운영 절차
- **오프닝 기법:** 상황 가정 — "머지 큐를 켰다. 첫 PR을 큐에 넣었는데 한 시간째 '체크 대기 중'이다." (1/3 한도 중 3회)
- **클로징 기법:** 도구형 — 큐가 막혔을 때의 진단 흐름을 mermaid 결정 흐름도로 남기고 한 문장으로 닫기
- **스캐폴드 유형:** 문제-해결형
- **예상 분량:** 10,000자

## 집필 규율 (레퍼런스 경고의 장별 적용)

- **시점 명기:** Actions 한도·플랜 가용성·가격, 머지 큐 가용 범위, stacked PR, concurrency `queue`, `pull_request_target` 동작은 "2026년 9월 기준"을 붙인다(8~11·13장).
- **예제 규약:** YAML 예제의 서드파티 액션은 실제 SHA를 지어내지 않는다. 11장 이전 예제는 `actions/checkout@v{N}` 형태로 쓰되 메이저 버전 숫자는 fact-checker가 확인한 값만 쓰고, 11장 이후 예제는 `@<full-commit-sha> # v{N}` 자리표시 형식으로 SHA 고정을 보여 준다. 예제 YAML은 문법적으로 유효해야 한다.
- **머지 큐 기본값 서술 금지**(범위 1~100만 확인) — 12·13장.
- **수치를 섞지 말 것:** Google flaky 1.5%와 Luo 4.56%(분모 다름), Kinsman 0.7%(2020 무렵 채택률), Gousios 14%(2014), Koishybayev 99.8%(2023-02 전환 이전), 2026-04 사고 규모 두 수치(병기 또는 생략).
- **귀속 서술:** GitHub Flow 배포 시점(Microsoft 해석), Ghiotto의 10~20%(선행 연구 재인용), Uber iOS 52%("Uber 보고에 따르면"), Not Rocket Science Rule(2차 인용).
- **인용 금지:** rarkins 발언(부정어 흐림), "200~400 LOC" 업계 수치, agentconn AI PR 수치.
- **인용문 대조:** web·community 인용문은 요약 모델 경유라 fact-checker가 원문 대조한다. 국내 사례 수치(토스 90%, 맘시터 하루 5회·300줄)는 원문 확인 전 "~로 보고했다" 수준으로.

## 레퍼런스 한계와 계획에 미친 영향

- **국내 자료 편중:** 국내 사례가 코드 리뷰(5·6장)와 브랜치 전략(3장)에 몰려 있고, Actions 보안·머지 큐·룰셋의 국내 1차 사례가 없다. 8~13장은 해외 사례와 공식 문서 중심이 될 수밖에 없다. 국내 팀의 머지 큐 도입 경험담을 넣고 싶다면 리서치 보강이 필요하다(선택).
- **주니어 목소리 부족:** Reddit 차단으로 1~5년차의 일상 경험담이 약하다. 오프닝의 상황 가정(3·7·13장)은 레퍼런스의 공개 토론(Discussions·HN)에서 재구성한 장면으로 쓰고, 특정 개인의 경험처럼 꾸미지 않는다.
- **머지 큐 학술 근거 얇음:** 동료 심사 논문은 SubmitQueue뿐이고 원문 미확보. 12장의 이론부는 계보 수준으로 두고 사례·공식 문서 비중을 높였다.
